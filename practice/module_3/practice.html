Для честных замеров страниц, индексов и планов запросов таблиц на 10 строк мало — PostgreSQL просто прочитает 1 страницу целиком. Поэтому рядом с практикумом лежит готовый скрипт 📄 practice/module_3/init.sql. За пару секунд он создаёт 5 таблиц в learning_db: мини-таблицу m3_backpack (5 строк, 1 страница) для опытов с ctid, а также объёмные таблицы маркетплейса и телеметрии (m3_customers, m3_products, m3_orders на 100 000 строк и m3_sensor_logs на 200 000 строк).

Когда запускать init.sql:
  • Для всех уроков Модуля 3 (3.1–3.4): нужен только базовый контейнер course_pg_primary (профиль Docker по умолчанию — никаких дополнительных профилей включать не нужно).
  • Загрузи init.sql один раз перед стартом — все задания Уроков 3.1–3.4 опираются на таблицы с префиксом m3_.
  • Для чистого сброса: скрипт полностью идемпотентен — запускай его повторно в любой момент, чтобы удалить созданные вручную индексы и тестовые таблицы и вернуть чистые Seq Scan (например, перед Уроком 3.3 или после краш-теста в Уроке 3.4).

3.1 Физическая архитектура PostgreSQL: страницы (8 КБ), Heap и Shared Buffers

Разбираем, как таблицы хранятся на диске в 8-килобайтных блоках, куда «переезжает» строка при UPDATE (ctid), как работают мёртвые кортежи и VACUUM, и как увидеть реальный кэш оперативной памяти Shared Buffers.

Уровень 1 · Разминка (на 1–2 минуты)

3.1.1 Узнай размер одной страницы (блока)
Очень легко

Выведи текущее значение системного параметра block_size в PostgreSQL.

Подсказка: используй короткую команду SHOW.

Показать ответ
SQL
SHOW block_size;

Ожидаемый результат: 8192 байта (ровно 8 КБ) — минимальная порция чтения с диска.

3.1.2 Проверь размер Shared Buffers
Очень легко

Узнай, сколько оперативной памяти выделено под общий буферный кэш shared_buffers в нашем Docker-контейнере.

Показать ответ

В образе postgres:16 по умолчанию стоит 128MB — это 16 384 слота по 8 КБ.

3.1.3 Увидеть физический адрес строки ctid
Очень легко

Выведи скрытую системную колонку ctid, а также id, item и price для всех строк таблицы m3_backpack.

Подсказка: ctid не показывается в SELECT * — её нужно явно указать в списке колонок.

Все 5 предметов лежат на странице 0: слоты от (0,1) до (0,5).

Уровень 2 · Базовая работа со страницами и Heap

3.1.4 Найди файл таблицы m3_orders и посчитай страницы
Базовое

Одним SELECT выведи для таблицы m3_orders: путь к физическому файлу (AS file_path), размер в байтах (AS size_bytes), читаемый размер (AS size_pretty) и количество 8-килобайтных страниц (AS pages_count).

Подсказка: используй функции pg_relation_filepath(), pg_relation_size(), pg_size_pretty() и деление на 8192.

Показать ответ
SQL
SELECT
    pg_relation_filepath('m3_orders') AS file_path,
    pg_relation_size('m3_orders') AS size_bytes,
    pg_size_pretty(pg_relation_size('m3_orders')) AS size_pretty,
    pg_relation_size('m3_orders') / 8192 AS pages_count;

Для 100 000 заказов m3_orders занимает около 9–10 МБ (~1 150 страниц по 8 КБ).

3.1.5 Рейтинг всех 5 таблиц модуля по размеру Heap
Базовое

Выведи из системного каталога pg_class все наши таблицы с именем, начинающимся на 'm3_' (relkind = 'r'): имя таблицы (AS table_name), читаемый размер самой таблицы (AS heap_size), полный размер вместе с индексами (AS total_size) и число страниц Heap (AS heap_pages). Отсортируй от самой тяжёлой к самой лёгкой.

Подсказка: для размера вместе с индексами есть функция pg_total_relation_size(oid), а для одного Heap — pg_relation_size(oid).

Показать ответ
SQL
SELECT
    relname AS table_name,
    pg_size_pretty(pg_relation_size(oid)) AS heap_size,
    pg_size_pretty(pg_total_relation_size(oid)) AS total_size,
    pg_relation_size(oid) / 8192 AS heap_pages
FROM pg_class
WHERE relnamespace = 'public'::regnamespace
  AND relkind = 'r'
  AND relname LIKE 'm3\_%'
ORDER BY pg_relation_size(oid) DESC;

Символ _ в LIKE экранируется как \_, чтобы не совпадать с любым символом. Обрати внимание, что m3_backpack занимает ровно 1 страницу (8 192 байта).

3.1.6 Поймай «переезд» строки при UPDATE
Базовое

В таблице m3_backpack измени price у «Железного меча» (id = 1) на 650 и удали «Зелье здоровья» (id = 3). Затем выведи ctid, id, item, price без ORDER BY и посмотри, куда переместилась строка id = 1.

Показать ответ
SQL
UPDATE m3_backpack
SET price = 650
WHERE id = 1;

DELETE FROM m3_backpack
WHERE id = 3;

SELECT ctid, id, item, price
FROM m3_backpack;

«Железный меч» переехал с адреса (0,1) на новый слот (0,6) и оказался в конце вывода, а слоты (0,1) и (0,3) стали мёртвыми кортежами.

3.1.7 Безопасный UPDATE без лишних мёртвых строк
Базовое

Напиши запрос, который в таблице m3_backpack устанавливает note = 'Проверено' только для тех строк, у которых note сейчас отличается от 'Проверено' (включая строку id = 4, где note IS NULL!). Запусти запрос дважды подряд и убедись, что второй запуск обновил 0 строк и не изменил ctid.

Подсказка: обычное note <> 'Проверено' пропустит NULL! Используй оператор IS DISTINCT FROM.

Показать ответ
SQL
-- Первый запуск обновит все оставшиеся строки, включая NULL
UPDATE m3_backpack
SET note = 'Проверено'
WHERE note IS DISTINCT FROM 'Проверено';

-- Второй запуск вернёт UPDATE 0 — ни одного лишнего мёртвого кортежа!
UPDATE m3_backpack
SET note = 'Проверено'
WHERE note IS DISTINCT FROM 'Проверено';

SELECT ctid, id, item, note
FROM m3_backpack;

IS DISTINCT FROM корректно работает с NULL и защищает таблицы от раздувания при повторных пакетных обновлениях.

Уровень 3 · Эксперименты с VACUUM и Shared Buffers

3.1.8 Раздувание Heap (n_dead_tup) и уборка VACUUM
Эксперимент

В таблице m3_orders увеличь amount на 10 для первых 15 000 заказов (id <= 15000). Посмотри в pg_stat_user_tables колонки relname AS table_name, n_live_tup, n_dead_tup и число страниц pages_count. Затем выполни VACUUM m3_orders; и снова проверь те же показатели.

Показать ответ
SQL
-- 1. Создаём 15 000 новых версий строк
UPDATE m3_orders
SET amount = amount + 10
WHERE id <= 15000;

-- 2. Проверяем число мёртвых строк и рост страниц
SELECT
    relname AS table_name,
    n_live_tup,
    n_dead_tup,
    pg_size_pretty(pg_relation_size('m3_orders')) AS heap_size,
    pg_relation_size('m3_orders') / 8192 AS pages_count
FROM pg_stat_user_tables
WHERE relname = 'm3_orders';

-- 3. Запускаем уборщика VACUUM и перепроверяем
VACUUM m3_orders;

SELECT
    relname AS table_name,
    n_live_tup,
    n_dead_tup,
    pg_size_pretty(pg_relation_size('m3_orders')) AS heap_size,
    pg_relation_size('m3_orders') / 8192 AS pages_count
FROM pg_stat_user_tables
WHERE relname = 'm3_orders';

После VACUUM счётчик n_dead_tup станет 0, но pages_count останется прежним: обычный VACUUM помечает место внутри страниц как свободное для новых записей, не урезая файл ОС.

3.1.9 Холодное vs горячее чтение: ловим shared read и shared hit
Эксперимент

Очисти Shared Buffers перезапуском контейнера pg_primary (во втором окне терминала или перед входом в psql), а затем дважды подряд выполни EXPLAIN (ANALYZE, BUFFERS) для подсчёта заказов в m3_orders с amount > 25000. Сравни строчку Buffers: и Execution Time в первом и втором запуске.

Показать ответ
BASH · Окно 2 (сброс Shared Buffers)
# Окно 2 (терминал хоста): перезапускаем контейнер PostgreSQL
docker compose restart pg_primary
SQL · Окно 1 (подключись в psql и выполни 2 раза подряд)
-- Окно 1: 1-й запуск («холодный» Shared Buffers → увидим shared read=...)
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM m3_orders
WHERE amount > 25000;

-- Окно 1: 2-й запуск («горячий» кэш → увидим 100% shared hit=...)
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM m3_orders
WHERE amount > 25000;

Во втором запуске число страниц shared hit совпадёт с прошлым shared read, а время выполнения уменьшится в разы — все блоки уже лежат в RAM.

3.1.10 Рентген оперативной памяти через pg_buffercache
Среднее

Активируй расширение pg_buffercache в текущей базе learning_db. Затем напиши запрос к pg_buffercache и pg_class, который для таблиц схемы public (relkind = 'r') выведет: имя таблицы (AS table_name), число занятых 8 КБ слотов (AS buffers_count), объём в памяти (AS cached_size) и число «грязных» страниц (AS dirty_buffers). Отсортируй по buffers_count DESC.

Подсказка: соединяй по b.relfilenode = pg_relation_filenode(c.oid) и фильтруй по b.reldatabase текущей БД.

Показать ответ
SQL
CREATE EXTENSION IF NOT EXISTS pg_buffercache;

SELECT
    c.relname AS table_name,
    count(*) AS buffers_count,
    pg_size_pretty(count(*) * 8192) AS cached_size,
    count(*) FILTER (WHERE b.isdirty) AS dirty_buffers
FROM pg_buffercache AS b
JOIN pg_class AS c
  ON b.relfilenode = pg_relation_filenode(c.oid)
WHERE b.reldatabase = (
    SELECT oid FROM pg_database WHERE datname = current_database()
)
  AND c.relnamespace = 'public'::regnamespace
  AND c.relkind = 'r'
GROUP BY c.relname
ORDER BY buffers_count DESC;

Если перед этим запросом обновить пару строк в m3_backpack, в колонке dirty_buffers сразу появится ненулевое значение — страница изменена в RAM и ждёт сброса на диск.

3.1.11 Какие параметры памяти требуют рестарта сервера?
Среднее

Выведи из системного представления pg_settings колонки name, setting, unit и context для четырёх параметров памяти: 'block_size', 'shared_buffers', 'work_mem' и 'effective_cache_size'. Отсортируй по name и определи, какой из них можно менять командой SET прямо в текущей сессии.

Показать ответ
SQL
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN (
    'block_size',
    'shared_buffers',
    'work_mem',
    'effective_cache_size'
)
ORDER BY name;

block_size — internal (задаётся при сборке), shared_buffers — postmaster (нужен рестарт сервера), а work_mem и effective_cache_size — user (можно менять в сессии через SET).

3.2 Индексы: B-Tree, составные индексы, ловушки, GIN и BRIN

Тренируемся ускорять запросы в сотни раз: строим B-Tree, проверяем правило левого префикса и порядок колонок, ловим 5 ловушек, пробуем покрывающие (INCLUDE), функциональные, частичные, GIN и сверхкомпактные BRIN индексы.

Уровень 1 · Разминка (первые шаги с B-Tree)

3.2.1 Посмотри существующие индексы таблицы m3_orders
Очень легко

Выведи из системного представления pg_indexes колонки indexname и indexdef для таблицы 'm3_orders'. Убедись, что на старте на ней есть только первичный ключ.

Показать ответ
SQL
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'm3_orders';

Внешние ключи (customer_id, product_id) в PostgreSQL НЕ создают индексы автоматически — их нужно добавлять вручную.

3.2.2 Поиск одного заказа БЕЗ индекса
Очень легко

Выполни EXPLAIN ANALYZE для поиска колонок id, customer_id, amount из таблицы m3_orders по условию order_code = 'ORD-077777'. Запомни тип сканирования и Execution Time.

Показать ответ
SQL
EXPLAIN ANALYZE
SELECT id, customer_id, amount
FROM m3_orders
WHERE order_code = 'ORD-077777';

Без индекса PostgreSQL делает Seq Scan, проверяет и выбрасывает 99 999 строк ради одной нужной.

3.2.3 Создай первый B-Tree индекс и ускорь поиск в 100+ раз
Очень легко

Создай B-Tree индекс idx_m3_orders_code на колонке order_code таблицы m3_orders и повтори EXPLAIN ANALYZE из задания 3.2.2.

Показать ответ
SQL
DROP INDEX IF EXISTS idx_m3_orders_code;
CREATE INDEX idx_m3_orders_code ON m3_orders (order_code);

EXPLAIN ANALYZE
SELECT id, customer_id, amount
FROM m3_orders
WHERE order_code = 'ORD-077777';

Теперь в плане Index Scan using idx_m3_orders_code, а время падает с десятков миллисекунд до < 0.1 ms.

Уровень 2 · Составные, покрывающие и функциональные индексы

3.2.4 Правило левого префикса и порядок «равенство → диапазон»
Базовое

Создай составной индекс idx_m3_orders_cust_amount на таблице m3_orders по колонкам (customer_id, amount). Проверь через EXPLAIN ANALYZE два запроса: 1) WHERE customer_id = 42 AND amount > 30000 (оба поля); 2) WHERE amount > 44500 (только вторая колонка). Убедись, что во втором случае индекс не используется!

Показать ответ
SQL
DROP INDEX IF EXISTS idx_m3_orders_cust_amount;
CREATE INDEX idx_m3_orders_cust_amount
    ON m3_orders (customer_id, amount);

-- 1. Левая колонка есть → Index Scan / Bitmap Index Scan
EXPLAIN ANALYZE
SELECT id, amount
FROM m3_orders
WHERE customer_id = 42
  AND amount > 30000;

-- 2. Левой колонки нет → Seq Scan!
EXPLAIN ANALYZE
SELECT id, amount
FROM m3_orders
WHERE amount > 44500;

Составной индекс (a, b) отсортирован сначала по a, поэтому без a в WHERE дерево не позволяет быстро найти диапазон по b.

3.2.5 Покрывающий индекс с INCLUDE
Базовое

Создай покрывающий индекс idx_m3_orders_cust_inc_amount на m3_orders (customer_id) INCLUDE (amount), обнови карту видимости командой VACUUM ANALYZE m3_orders; и проверь через EXPLAIN (ANALYZE, BUFFERS) запрос подсчёта суммы sum(amount) AS total_spent для customer_id = 42.

Подсказка: ищи в плане строчки Index Only Scan и Heap Fetches: 0.

Показать ответ
SQL
DROP INDEX IF EXISTS idx_m3_orders_cust_inc_amount;
CREATE INDEX idx_m3_orders_cust_inc_amount
    ON m3_orders (customer_id) INCLUDE (amount);

VACUUM ANALYZE m3_orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT sum(amount) AS total_spent
FROM m3_orders
WHERE customer_id = 42;

Все нужные значения amount лежат прямо в листьях индекса, поэтому PostgreSQL читает всего 3–4 страницы и вообще не обращается к Heap.

3.2.6 Ловушка LOWER(email) и функциональный индекс
Базовое

В таблице m3_customers на колонке email уже есть индекс UNIQUE, но адреса записаны в смешанном регистре ('User42@Shop.KZ'). Проверь план поиска WHERE LOWER(email) = 'user42@shop.kz' (увидишь Seq Scan), затем создай функциональный индекс idx_m3_customers_lower_email на выражении (LOWER(email)) и убедись, что появился Index Scan.

Показать ответ
SQL
-- 1. Обычный UNIQUE-индекс на email не спасает при LOWER(email)
EXPLAIN ANALYZE
SELECT id, full_name, email
FROM m3_customers
WHERE LOWER(email) = 'user42@shop.kz';

-- 2. Создаём функциональный (Expression) индекс
DROP INDEX IF EXISTS idx_m3_customers_lower_email;
CREATE INDEX idx_m3_customers_lower_email
    ON m3_customers (LOWER(email));

ANALYZE m3_customers;

-- 3. Теперь планировщик выбирает Index Scan
EXPLAIN ANALYZE
SELECT id, full_name, email
FROM m3_customers
WHERE LOWER(email) = 'user42@shop.kz';

Выражение в WHERE должно точно совпадать с выражением внутри скобок CREATE INDEX.

3.2.7 Ловушка формулы вокруг колонки: очисти условие WHERE
Базовое

Создай индекс idx_m3_orders_amount на m3_orders (amount). Сравни через EXPLAIN (ANALYZE, BUFFERS) «плохой» запрос WHERE amount * 1.2 > 54000 и исправленный запрос, где математика перенесена в правую часть (54000 / 1.2 = 45000).

Показать ответ
SQL
DROP INDEX IF EXISTS idx_m3_orders_amount;
CREATE INDEX idx_m3_orders_amount ON m3_orders (amount);

-- Плохо: формула на колонке ломает индекс (Seq Scan)
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, order_code, amount
FROM m3_orders
WHERE amount * 1.2 > 54000;

-- Правильно: колонка «чистая» → срабатывает индекс!
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, order_code, amount
FROM m3_orders
WHERE amount > 45000;

Любая арифметика на самой колонке (amount * 1.2, amount + 100) делает обычный B-Tree невидимым для планировщика.

В m3_orders статус 'pending' имеют всего 5% строк (5 000 из 100 000). Создай два индекса: полный idx_m3_orders_status_full ON m3_orders (status) и частичный idx_m3_orders_pending_only ON m3_orders (created_at) WHERE status = 'pending'. Сравни их размер (AS full_size, AS partial_size) и проверь план выборки 10 заказов со статусом 'pending' начиная с '2026-05-01 00:00:00+05'.

3.2.9 GIN-индекс на массив тегов TEXT[]
Среднее

В таблице m3_sensor_logs (200 000 строк) найди через EXPLAIN ANALYZE все записи, у которых массив tags содержит тег 'wal' (оператор @>). Затем создай GIN-индекс idx_m3_logs_tags_gin на колонке tags и повтори замер.

Подсказка: для массива используется синтаксис WHERE tags @> ARRAY['wal'] и метод USING gin (tags).

Показать ответ
SQL
-- 1. Замер ДО создания GIN (Seq Scan по 200 000 строкам)
EXPLAIN ANALYZE
SELECT id, sensor_id, tags

-- 2. Создаём обратный индекс GIN
DROP INDEX IF EXISTS idx_m3_logs_tags_gin;
CREATE INDEX idx_m3_logs_tags_gin

-- 3. Замер ПОСЛЕ (Bitmap Index Scan по idx_m3_logs_tags_gin)

SELECT id, sensor_id, tags
FROM m3_sensor_logs

В таблице ровно 400 строк с тегом 'wal' — GIN находит их мгновенно, без перебора 199 600 лишних записей.

3.2.10 GIN-индекс на JSONB и пересечение BitmapAnd
Среднее

Создай второй GIN-индекс idx_m3_logs_payload_gin на колонке payload (JSONB) таблицы m3_sensor_logs. Затем проверь через EXPLAIN ANALYZE поиск записей, где одновременно tags @> ARRAY['wal'] и payload @> '{"zone": "dc-1"}'::jsonb.

SQL

3.2.11 Битва размеров: BRIN против B-Tree на 200 000 логах
Эксперимент

В таблице m3_sensor_logs строки вставлены строго по возрастанию logged_at. Создай два индекса на logged_at: idx_m3_logs_time_btree (USING btree) и idx_m3_logs_time_brin (USING brin). Выведи размеры таблицы и обоих индексов (AS table_size, AS btree_size, AS brin_size). Затем удали B-Tree и проверь работу BRIN через EXPLAIN ANALYZE на часовом окне '2026-01-10 12:00:00+05' .. '2026-01-10 13:00:00+05' (выведи COUNT(*) и ROUND(AVG(temp_c), 2) AS avg_temp).

Показать ответ
SQL
DROP INDEX IF EXISTS idx_m3_logs_time_btree;
DROP INDEX IF EXISTS idx_m3_logs_time_brin;

CREATE INDEX idx_m3_logs_time_btree ON m3_sensor_logs USING btree (logged_at);
CREATE INDEX idx_m3_logs_time_brin  ON m3_sensor_logs USING brin  (logged_at);

-- Сравниваем вес таблицы и двух индексов
SELECT
    pg_size_pretty(pg_relation_size('m3_sensor_logs'))         AS table_size,
    pg_size_pretty(pg_relation_size('idx_m3_logs_time_btree')) AS btree_size,
    pg_size_pretty(pg_relation_size('idx_m3_logs_time_brin'))  AS brin_size;

-- Удаляем B-Tree, чтобы увидеть работу именно BRIN
DROP INDEX idx_m3_logs_time_btree;

EXPLAIN ANALYZE
SELECT
    COUNT(*) AS events_cnt,
    ROUND(AVG(temp_c), 2) AS avg_temp
FROM m3_sensor_logs
WHERE logged_at >= '2026-01-10 12:00:00+05'
  AND logged_at <  '2026-01-10 13:00:00+05';

B-Tree весит ~4.4 МБ, а BRIN — всего ~24–48 КБ (в ~100–180 раз меньше!), при этом отбрасывает ~95% лишних блоков Heap.

3.3.4 Поймай связку Bitmap Index Scan + Bitmap Heap Scan
Базовое

Создай обычный B-Tree индекс idx_m3_orders_customer_id на m3_orders (customer_id) (если он ещё не создан) и выполни EXPLAIN (ANALYZE, BUFFERS) для получения колонок id, order_code, status, amount, created_at по customer_id = 42. Найди в плане строчку Heap Blocks: exact=....

Показать ответ
SQL
DROP INDEX IF EXISTS idx_m3_orders_customer_id;
CREATE INDEX idx_m3_orders_customer_id
    ON m3_orders (customer_id);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, order_code, status, amount, created_at
FROM m3_orders
WHERE customer_id = 42;

100 заказов клиента №42 разбросаны по разным страницам Heap, поэтому PostgreSQL сначала собирает их битовую карту в индексе (Bitmap Index Scan), а затем упорядоченно читает блоки таблицы (Bitmap Heap Scan).

3.3.5 Добейся Index Only Scan с Heap Fetches: 0
Базовое

Для отчёта по товару часто выполняется запрос: SELECT count(*) AS orders_cnt, round(avg(amount), 2) AS avg_amount FROM m3_orders WHERE product_id = 15;. Создай покрывающий индекс idx_m3_orders_prod_inc_amt, обнови карту видимости и докажи через EXPLAIN (ANALYZE, BUFFERS), что запрос работает через Index Only Scan с Heap Fetches: 0.

Показать ответ
SQL
DROP INDEX IF EXISTS idx_m3_orders_prod_inc_amt;
CREATE INDEX idx_m3_orders_prod_inc_amt
    ON m3_orders (product_id) INCLUDE (amount);

-- Обновляем Visibility Map, чтобы Heap Fetches стал равен 0
VACUUM ANALYZE m3_orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    count(*) AS orders_cnt,
    round(avg(amount), 2) AS avg_amount
FROM m3_orders
WHERE product_id = 15;

Без VACUUM планировщик всё равно заглянет в Heap, чтобы проверить видимость строк (MVCC), и Heap Fetches будет больше нуля.

3.3.6 Сравни в плане date_trunc() и честный диапазон дат
Базовое

Создай индекс idx_m3_orders_created_at на m3_orders (created_at) и сделай VACUUM ANALYZE m3_orders;. Сравни через EXPLAIN (ANALYZE, BUFFERS) подсчёт заказов за январь 2026 двумя способами: 1) через date_trunc('month', created_at AT TIME ZONE '+05') = TIMESTAMP '2026-01-01'; 2) через диапазон created_at >= TIMESTAMPTZ '2026-01-01 00:00:00+05' AND created_at < TIMESTAMPTZ '2026-02-01 00:00:00+05'.

Показать ответ
SQL
DROP INDEX IF EXISTS idx_m3_orders_created_at;
CREATE INDEX idx_m3_orders_created_at ON m3_orders (created_at);
VACUUM ANALYZE m3_orders;

-- Вариант 1 (ловушка): функция на колонке → Seq Scan + ошибка прогноза rows!
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM m3_orders
WHERE date_trunc('month', created_at AT TIME ZONE '+05') = TIMESTAMP '2026-01-01';

-- Вариант 2 (правильно): Index Only Scan + точный прогноз rows!
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM m3_orders
WHERE created_at >= TIMESTAMPTZ '2026-01-01 00:00:00+05'
  AND created_at <  TIMESTAMPTZ '2026-02-01 00:00:00+05';

Во втором варианте срабатывает Index Only Scan, читается в разы меньше страниц Buffers, а прогноз rows почти идеально совпадает с реальным числом (~22 319 заказов).

3.3.7 Безопасный EXPLAIN ANALYZE для UPDATE (без изменения данных)
Базовое

Проверь реальный план повышения цены на 10% (price = round(price * 1.10, 2)) для всех товаров категории 'electronics' в m3_products с помощью EXPLAIN (ANALYZE, BUFFERS), но так, чтобы реальные цены в базе не изменились. Докажи это, сравнив sum(price) до и после.

Подсказка: оберни EXPLAIN (ANALYZE, BUFFERS) UPDATE ... в транзакцию BEGIN; ... ROLLBACK;.

Показать ответ
SQL
-- 1. Фиксируем сумму цен ДО
SELECT sum(price) AS price_before
FROM m3_products
WHERE category = 'electronics';

-- 2. Профилируем UPDATE безопасно с откатом
BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
UPDATE m3_products
SET price = round(price * 1.10, 2)
WHERE category = 'electronics';

ROLLBACK;

-- 3. Убеждаемся, что сумма цен не изменилась
SELECT sum(price) AS price_after
FROM m3_products
WHERE category = 'electronics';

EXPLAIN ANALYZE реально исполняет INSERT/UPDATE/DELETE — никогда не запускай его на боевых данных без BEGIN ... ROLLBACK!

Уровень 3 · Дерево плана, JOIN-ы и расследование тормозов

3.3.8 Прочитай 3-табличный план: Hash Join + top-N heapsort
Среднее

Временно удали индекс idx_m3_orders_amount (если создавал его в Уроке 3.2). Выполни EXPLAIN (ANALYZE, BUFFERS) для запроса: соедини m3_orders o, m3_customers c и m3_products p, найди 5 самых дорогих заказов (o.id AS order_id, c.full_name, p.title, o.amount) категории 'electronics' от клиентов из города 'Костанай' с суммой o.amount > 40000 (ORDER BY o.amount DESC LIMIT 5). Определи снизу вверх, какой узел съел больше всего Buffers.

Показать ответ
SQL
DROP INDEX IF EXISTS idx_m3_orders_amount;

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    o.id AS order_id,
    c.full_name,
    p.title,
    o.amount
FROM m3_orders AS o
JOIN m3_customers AS c ON c.id = o.customer_id
JOIN m3_products  AS p ON p.id = o.product_id
WHERE c.city = 'Костанай'
  AND p.category = 'electronics'
  AND o.amount > 40000
ORDER BY o.amount DESC
LIMIT 5;

Главный пожиратель времени и страниц — Seq Scan on m3_orders (~1 150 страниц). На самом верху ты увидишь оптимизацию Sort Method: top-N heapsort — база держит в памяти только пятёрку лидеров.

3.3.9 Ускорь 3-табличный запрос: Index Scan Backward + Nested Loop
Эксперимент

Добавь индекс idx_m3_orders_amount ON m3_orders (amount) и повтори точно такой же запрос из задания 3.3.8. Посмотри, как планировщик полностью сменил стратегию: узел Sort исчез, а вместо Hash Join появился Nested Loop поверх Index Scan Backward!

Показать ответ
SQL

    c.full_name,
    p.title,
    o.amount

LIMIT 5;

Index Scan Backward идёт с конца дерева от самых больших сумм, а LIMIT 5 обрывает весь конвейер, как только нашлись 5 подходящих строк — вместо 1 150 страниц читается ~100–150!

3.3.10 Поймай красный флаг Sort Method: external merge Disk
Эксперимент

Внутри транзакции сожми память сортировки командой SET LOCAL work_mem = '64kB'; и запусти EXPLAIN (ANALYZE, BUFFERS) для сортировки всех 100 000 заказов m3_orders по order_code DESC (выводя id, order_code, amount). Увидишь external merge Disk и temp read/written! Затем сделай то же с SET LOCAL work_mem = '32MB'; и сравни план.

Подсказка: используй ORDER BY order_code DESC (и удали idx_m3_orders_code, если он есть, чтобы заставить базу реально сортировать).

SQL

FROM m3_orders

Во втором запуске external merge Disk сменится на quicksort Memory, а временные файлы temp read/written полностью исчезнут.

3.4 Журнал предзаписи (WAL) и восстановление после сбоев (Crash Recovery)

Изучаем «чёрный ящик» PostgreSQL: измеряем позицию LSN и вес записей в pg_wal, проверяем CHECKPOINT и Full Page Images, сравниваем обычные и UNLOGGED-таблицы, проводим краш-тест с SIGKILL и решаем финальную задачу модуля.

Уровень 1 · Разминка (LSN, pg_stat_wal и настройки надёжности)

3.4.1 Текущий LSN и имя активного файла в pg_wal/
Очень легко

Одним SELECT выведи текущую позицию в журнале предзаписи (AS current_lsn) и имя активного 16-мегабайтного WAL-сегмента (AS active_wal_file).

Подсказка: функции pg_current_wal_lsn() и pg_walfile_name(...).

Показать ответ
SQL
SELECT
    pg_current_wal_lsn() AS current_lsn,
    pg_walfile_name(pg_current_wal_lsn()) AS active_wal_file;

Имя файла всегда состоит из 24 шестнадцатеричных символов (например, 000000010000000000000004) — это реальный файл на диске в папке pg_wal/.

3.4.2 Бортовой компьютер WAL: статистика pg_stat_wal
Очень легко

Выведи из системного представления pg_stat_wal: число записей wal_records, число полных снимков страниц wal_fpi AS full_page_images, общий объём записанного WAL в читаемом виде (AS total_wal_written) и счётчик wal_buffers_full.

Показать ответ
SQL
SELECT
    wal_records,
    wal_fpi AS full_page_images,
    pg_size_pretty(wal_bytes) AS total_wal_written,
    wal_buffers_full
FROM pg_stat_wal;

Если в боевой системе быстро растёт wal_buffers_full, значит, буфер WAL в памяти слишком тесный и его стоит увеличить.

3.4.3 Аудит настроек надёжности и контрольных точек
Очень легко

Выведи из pg_settings колонки name, setting, unit и context для параметров: 'wal_level', 'fsync', 'full_page_writes', 'synchronous_commit', 'checkpoint_timeout', 'max_wal_size' и 'checkpoint_completion_target'. Отсортируй по name.

Показать ответ
SQL
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN (
    'wal_level',
    'fsync',
    'full_page_writes',
    'synchronous_commit',
    'checkpoint_timeout',
    'max_wal_size',
    'checkpoint_completion_target'
)
ORDER BY name;

В нашем контейнере стоит wal_level = logical (из docker-compose.yaml для будущего Модуля 5), а fsync и full_page_writes включены (on).

3.4.4 Ручной CHECKPOINT и чтение pg_control
Базовое

Посмотри checkpoint_lsn, redo_lsn, redo_wal_file и checkpoint_time с помощью функции pg_control_checkpoint(). Затем выполни команду CHECKPOINT; и снова прочитай pg_control_checkpoint() — убедись, что redo_lsn и время обновились!

Показать ответ
SQL
-- До чекпоинта
SELECT checkpoint_lsn, redo_lsn, redo_wal_file, checkpoint_time
FROM pg_control_checkpoint();

-- Принудительно сбрасываем грязные страницы на диск
CHECKPOINT;

-- После чекпоинта: новый redo_lsn и свежее checkpoint_time
SELECT checkpoint_lsn, redo_lsn, redo_wal_file, checkpoint_time
FROM pg_control_checkpoint();

Именно с отметки redo_lsn PostgreSQL начинает чтение журнала, если произойдёт внезапный сбой питания.

3.4.5 Измерь «след» в WAL от вставки 10 000 строк
Базовое

Создай таблицу m3_wal_lab (id SERIAL PRIMARY KEY, order_code TEXT NOT NULL, amount NUMERIC(10, 2) NOT NULL). Одним запросом с CTE вставь 10 000 строк и выведи: число вставленных строк (AS rows_inserted), LSN до вставки (AS lsn_start), LSN после (AS lsn_end) и объём сгенерированного WAL в читаемом виде (AS wal_generated).

Подсказка: разницу двух позиций LSN в байтах считает функция pg_wal_lsn_diff(lsn_end, lsn_start).

Показать ответ
SQL
DROP TABLE IF EXISTS m3_wal_lab;

CREATE TABLE m3_wal_lab (
    id         SERIAL PRIMARY KEY,
    order_code TEXT NOT NULL,
    amount     NUMERIC(10, 2) NOT NULL
);

WITH lsn_before AS (
    SELECT pg_current_wal_lsn() AS pos
),
ins AS (
    INSERT INTO m3_wal_lab (order_code, amount)
    SELECT 'WAL-' || g, (500 + (g * 13 % 9000))::NUMERIC(10, 2)
    FROM generate_series(1, 10000) AS g
    RETURNING id
)
SELECT
    count(*) AS rows_inserted,
    (SELECT pos FROM lsn_before) AS lsn_start,
    pg_current_wal_lsn() AS lsn_end,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM lsn_before))
    ) AS wal_generated
FROM ins;

Вставка 10 000 строк вместе с обновлением индекса PRIMARY KEY генерирует примерно 1.2–1.4 МБ записей WAL.

3.4.6 Битва таблиц: Обычная vs UNLOGGED
Базовое

Создай две одинаковые таблицы m3_logged_bench (id INT, payload TEXT) (обычную) и m3_unlogged_bench (id INT, payload TEXT) (UNLOGGED). Вставь в каждую по 25 000 строк (g, repeat('x', 80)) и замерь объём WAL (AS table_type, AS wal_bytes, AS wal_pretty) для обеих таблиц.

Показать ответ
SQL
DROP TABLE IF EXISTS m3_logged_bench, m3_unlogged_bench;

CREATE TABLE m3_logged_bench (id INT, payload TEXT);
CREATE UNLOGGED TABLE m3_unlogged_bench (id INT, payload TEXT);

-- 1. Обычная таблица (~3 МБ в WAL)
WITH s AS (SELECT pg_current_wal_lsn() AS pos),
ins AS (
    INSERT INTO m3_logged_bench
    SELECT g, repeat('x', 80) FROM generate_series(1, 25000) AS g
)
SELECT
    'Обычная таблица' AS table_type,
    pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s)) AS wal_bytes,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s))) AS wal_pretty;

-- 2. UNLOGGED-таблица (0 байт в WAL!)
WITH s AS (SELECT pg_current_wal_lsn() AS pos),
ins AS (
    INSERT INTO m3_unlogged_bench
    SELECT g, repeat('x', 80) FROM generate_series(1, 25000) AS g
)
SELECT
    'UNLOGGED-таблица' AS table_type,
    pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s)) AS wal_bytes,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s))) AS wal_pretty;

Не удаляй m3_unlogged_bench — в задании 3.4.9 мы увидим, что с ней произойдёт после внезапного SIGKILL!

Уровень 3 · FPI, Краш-тест SIGKILL и Финал модуля

3.4.7 Поймай Full Page Image (FPI) после CHECKPOINT
Эксперимент

Создай таблицу m3_fpi_lab (id INT PRIMARY KEY, val TEXT) и вставь одну строку (1, 'v1'). Выполни CHECKPOINT;, затем сделай первый UPDATE (val = 'v2') и замерь wal_bytes через pg_wal_lsn_diff(). Сразу после этого (без чекпоинта) сделай второй UPDATE (val = 'v3') и снова замерь wal_bytes. Сравни два числа!

Показать ответ
SQL
DROP TABLE IF EXISTS m3_fpi_lab;
CREATE TABLE m3_fpi_lab (id INT PRIMARY KEY, val TEXT);
INSERT INTO m3_fpi_lab VALUES (1, 'v1');

-- Контрольная точка: следующая правка страницы заставит PG записать полный снимок!
CHECKPOINT;

-- 1-й UPDATE сразу после CHECKPOINT (попадёт FPI ~ несколько КБ)
WITH s AS (SELECT pg_current_wal_lsn() AS pos),
u AS (UPDATE m3_fpi_lab SET val = 'v2' WHERE id = 1)
SELECT
    '1-й UPDATE после CHECKPOINT (с FPI)' AS step,
    pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s)) AS wal_bytes;

-- 2-й UPDATE той же страницы (только маленькая дельта ~100–200 байт)
WITH s AS (SELECT pg_current_wal_lsn() AS pos),
u AS (UPDATE m3_fpi_lab SET val = 'v3' WHERE id = 1)
SELECT
    '2-й UPDATE без CHECKPOINT (без FPI)' AS step,
    pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s)) AS wal_bytes;

Из-за full_page_writes = on первое изменение страницы после CHECKPOINT кладёт в WAL её полный снимок (защита от разорванной страницы при сбое питания), а повторная правка — лишь компактную дельту.

3.4.8 Безопасный тюнинг SET LOCAL synchronous_commit = off
Среднее

Открой транзакцию BEGIN;, включи в ней локально SET LOCAL synchronous_commit = off;, проверь значение через SHOW synchronous_commit;, вставь одну запись в m3_wal_lab ('ASYNC-CLICK-1', 100.00) и сделай COMMIT;. После COMMIT; снова проверь SHOW synchronous_commit; — убедись, что глобальная настройка осталась on!

Показать ответ
SQL
BEGIN;
SET LOCAL synchronous_commit = off;
SHOW synchronous_commit; -- вернёт off только внутри этой транзакции

INSERT INTO m3_wal_lab (order_code, amount)
VALUES ('ASYNC-CLICK-1', 100.00);
COMMIT;

-- После COMMIT настройка автоматически вернулась в безопасное состояние 'on'
SHOW synchronous_commit;

В отличие от смертельно опасного fsync = off, асинхронный коммит никогда не повреждает базу — он лишь не ждёт подтверждения диска для конкретной некритичной транзакции.

3.4.9 Живой краш-тест SIGKILL в двух окнах терминала!
Эксперимент · 2 окна

Проверим Crash Recovery на практике! Убедись, что таблицы m3_wal_lab и m3_unlogged_bench существуют (из заданий 3.4.5 и 3.4.6). В Окне 1 (psql) вставь подтверждённую строку 'CRASH-OK-101', затем начни BEGIN; и вставь 'CRASH-LOST-999' без COMMIT. В Окне 2 (терминал) жёстко убей контейнер командой docker compose kill -s SIGKILL pg_primary, запусти его снова и прочитай логи automatic recovery in progress. Наконец, переподключись в Окне 1 и проверь: 1) какая из двух строк выжила в m3_wal_lab; 2) сколько строк осталось в m3_unlogged_bench!

Показать ответ
SQL · Окно 1 (Шаг 1: подготовка до аварии)
-- Окно 1: удаляем старые маркеры, если повторяешь опыт
DELETE FROM m3_wal_lab
WHERE order_code IN ('CRASH-OK-101', 'CRASH-LOST-999');

-- 1. Подтверждённый заказ (COMMIT сразу уходит в pg_wal!)
INSERT INTO m3_wal_lab (order_code, amount)
VALUES ('CRASH-OK-101', 99999.00);

-- 2. Незавершённая транзакция (НЕ делаем COMMIT!)
BEGIN;
INSERT INTO m3_wal_lab (order_code, amount)
VALUES ('CRASH-LOST-999', 77777.00);
-- Оставь Окно 1 открытым и перейди в Окно 2!
BASH · Окно 2 (Шаг 2: выдёргиваем вилку SIGKILL и смотрим логи)
# Окно 2: жёсткое отключение без штатного завершения
docker compose kill -s SIGKILL pg_primary

# Включаем сервер обратно
docker compose up -d pg_primary

# Смотрим отчёт Crash Recovery в логах контейнера
sleep 2
docker logs --tail=20 course_pg_primary
SQL · Окно 1 (Шаг 3: переподключись в psql и проверь итоги)
-- Окно 1: проверяем выжившие строки (будет ТОЛЬКО CRASH-OK-101!)
SELECT order_code, amount
FROM m3_wal_lab
WHERE order_code LIKE 'CRASH-%';

-- А UNLOGGED-таблица после аварии автоматически очистилась до 0!
SELECT count(*) AS unlogged_rows_after_crash
FROM m3_unlogged_bench;

Подтверждённый CRASH-OK-101 пережил аварию благодаря WAL, незавершённый CRASH-LOST-999 исчез, а m3_unlogged_bench обнулилась (0 строк).

3.4.10 Финал модуля: полная диагностика отчёта (Buffers + Partial Index + WAL)
Финал модуля

Собери все знания Модуля 3 в одной боевой задаче! Менеджменту нужен отчёт: топ-10 самых дорогих заказов в статусе 'pending' от VIP-клиентов (c.tier = 'vip') с колонками o.id AS order_id, o.order_code, c.full_name, p.title, o.amount, отсортированный по o.amount DESC LIMIT 10.

  1. Сбрось лишние индексы на m3_orders (или перезапусти init.sql) и сделай замер EXPLAIN (ANALYZE, BUFFERS) ДО оптимизации.
  2. Зафиксируй текущий LSN, создай идеальный частичный индекс idx_m3_boss_pending_amount на m3_orders (amount DESC) WHERE status = 'pending' и посчитай через pg_wal_lsn_diff(), сколько WAL ушло на построение этого индекса.
  3. Выполни VACUUM ANALYZE m3_orders;, повтори EXPLAIN (ANALYZE, BUFFERS) ПОСЛЕ оптимизации и сравни число прочитанных страниц Buffers и время выполнения!

Подсказка: в psql удобно запомнить LSN до создания индекса в переменную (или сравнить два SELECT pg_current_wal_lsn();), а сам частичный индекс позволит Index Scan пойти прямо по дорогим pending-заказам без сортировки!

Показать ответ
SQL · Эталонное решение финала модуля
-- 1. Замер ДО оптимизации (если нужно — предварительно удали старые доп. индексы на m3_orders)
DROP INDEX IF EXISTS idx_m3_orders_amount, idx_m3_boss_pending_amount;

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    o.id AS order_id,
    o.order_code,
    c.full_name,
    p.title,
    o.amount
FROM m3_orders AS o
JOIN m3_customers AS c ON c.id = o.customer_id
JOIN m3_products  AS p ON p.id = o.product_id
WHERE o.status = 'pending'
  AND c.tier = 'vip'
ORDER BY o.amount DESC
LIMIT 10;

-- 2. Запоминаем LSN, создаём частичный индекс под сортировку и замеряем WAL
CREATE TEMP TABLE _wal_mark (lsn pg_lsn);
INSERT INTO _wal_mark VALUES (pg_current_wal_lsn());

CREATE INDEX idx_m3_boss_pending_amount
    ON m3_orders (amount DESC)
    WHERE status = 'pending';

SELECT
    pg_size_pretty(pg_relation_size('idx_m3_boss_pending_amount')) AS index_size,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT lsn FROM _wal_mark))
    ) AS wal_for_index;

DROP TABLE _wal_mark;

-- 3. Обновляем статистику и делаем финальный замер ПОСЛЕ
VACUUM ANALYZE m3_orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT
    o.id AS order_id,
    o.order_code,
    c.full_name,
    p.title,
    o.amount
FROM m3_orders AS o
JOIN m3_customers AS c ON c.id = o.customer_id
JOIN m3_products  AS p ON p.id = o.product_id
WHERE o.status = 'pending'
  AND c.tier = 'vip'
ORDER BY o.amount DESC
LIMIT 10;

Крошечный частичный индекс (~128 КБ, ~150 КБ WAL на создание) убирает Seq Scan и Sort: PostgreSQL идёт по idx_m3_boss_pending_amount в порядке убывания суммы, проверяет tier = 'vip' через Nested Loop по m3_customers_pkey и останавливается, как только набирает 10 заказов!
