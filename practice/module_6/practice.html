6.1.1 Три базовых отчёта по «Звезде»: Q1, выходные vs будни и клиенты без продаж
PostgreSQL 16 DWH · SQL

Напиши 3 аналитических запроса по схеме m6_star: 1) Отчёт директора за Q1 2026: выручка (revenue) и штуки (items_sold) по city_name и category_name (сортировка по revenue DESC). 2) Выходные против будней (2026): подпись 'Выходные' / 'Будни', штуки, выручка и средний чек позиции avg_line_amount (до 2 знаков). 3) Покупатели без оплаченных продаж: найди в dim_customer всех клиентов без строк в fact_sales (LEFT JOIN).

Ожидаемые контрольные цифры
  • Q1: 7 строк, лидер — Москва / Электроника (70000.00); апрельский заказ №1007 не попадает.
  • Выходные приносят 178000.00 (9 шт.), будни — 53500.00 (4 шт.).
  • Без оплаченных продаж 2 клиента: Данияр Алимов (заказ 1004 был отменён) и Алина Нурланова.
Показать решение (3 запроса)
PostgreSQL Отчёты по m6_star
-- 1. Отчёт Q1 2026: города × категории
SELECT dc.city_name, dp.category_name,
       SUM(f.qty) AS items_sold, SUM(f.total_amount) AS revenue
FROM m6_star.fact_sales f
JOIN m6_star.dim_date     dd ON dd.date_sk     = f.date_sk
JOIN m6_star.dim_product  dp ON dp.product_sk  = f.product_sk
JOIN m6_star.dim_customer dc ON dc.customer_sk = f.customer_sk
WHERE dd.year_num = 2026 AND dd.quarter_num = 1
GROUP BY dc.city_name, dp.category_name
ORDER BY revenue DESC;

-- 2. Выходные vs будни
SELECT CASE WHEN dd.is_weekend THEN 'Выходные' ELSE 'Будни' END AS day_type,
       SUM(f.qty) AS total_qty, SUM(f.total_amount) AS revenue,
       ROUND(AVG(f.total_amount), 2) AS avg_line_amount
FROM m6_star.fact_sales f
JOIN m6_star.dim_date dd ON dd.date_sk = f.date_sk
WHERE dd.year_num = 2026
GROUP BY dd.is_weekend
ORDER BY revenue DESC;

-- 3. Клиенты без оплаченных покупок
SELECT dc.customer_bk, dc.full_name, dc.city_name, dc.segment
FROM m6_star.dim_customer dc
LEFT JOIN m6_star.fact_sales f ON f.customer_sk = dc.customer_sk
WHERE f.sale_sk IS NULL
ORDER BY dc.customer_bk;
6.1.2 Баг-фикс DWH: ловушка перезаписи цены и Fan-out на доставке (14 500 vs 9 000)
PostgreSQL 16 Баг-фикс

Финансовый директор заметил, что аналитик завысил январскую выручку на 3000.00, а общую стоимость доставки оплаченных заказов посчитал как 14 500.00 вместо реальных 9 000.00. Вот его проблемный запрос по m6_oltp:

❌ ПРОБЛЕМНЫЙ ОТЧЁТ (Fan-out при смешивании зёрен + текущая цена каталога)
SELECT
    COUNT(DISTINCT o.id)                       AS paid_orders_cnt,
    SUM(o.delivery_fee)                        AS wrong_delivery_fee,  -- 14 500 вместо 9 000!
    SUM(oi.qty * p.current_price - oi.discount) AS wrong_revenue       -- считает по новой цене каталога!
FROM m6_oltp.orders o
JOIN m6_oltp.order_items oi ON oi.order_id = o.id
JOIN m6_oltp.products    p  ON p.id = oi.product_id
WHERE o.status = 'paid';

Задача: 1) найди конкретные строки, где fact_sales.unit_price <> m6_oltp.products.current_price, и посчитай величину искажения (revenue_distortion); 2) перепиши запрос по m6_oltp через CTE (сначала сверни order_items до зерна order_id по price_at_purchase), чтобы получить честные: 6 заказов, доставка 9000.00, товары 231500.00.

Проверь себя
  • Почему SUM(o.delivery_fee) в исходном запросе вырос с 9000.00 до 14500.00?
Показать расследование цены и исправленный запрос без Fan-out
PostgreSQL 1) Поиск искажения цены · 2) Исправленный CTE без Fan-out
-- 1. Какие позиции исказились бы при расчёте по current_price (заказ 1001: +3000.00!)
SELECT f.order_bk, dp.product_title, f.unit_price, p.current_price,
       (p.current_price - f.unit_price) * f.qty AS revenue_distortion
FROM m6_star.fact_sales f
JOIN m6_star.dim_product dp ON dp.product_sk = f.product_sk
JOIN m6_oltp.products    p  ON p.id = dp.product_bk
WHERE f.unit_price <> p.current_price;

-- 2. Честный отчёт без Fan-out: сначала сворачиваем order_items до уровня order_id!
WITH items_by_order AS (
    SELECT order_id,
           SUM(qty * price_at_purchase - discount) AS order_items_sum
    FROM m6_oltp.order_items
    GROUP BY order_id
)
SELECT COUNT(*)               AS paid_orders_cnt,
       SUM(o.delivery_fee)    AS total_delivery_fee,   -- ровно 9000.00!
       SUM(i.order_items_sum) AS total_items_revenue   -- ровно 231500.00!
FROM m6_oltp.orders o
JOIN items_by_order i ON i.order_id = o.id
WHERE o.status = 'paid';

Причина Fan-out: orders имеет зерно «1 заказ», а order_items — «1 товар в заказе». При прямом JOIN заказы с 2 позициями размножили строку delivery_fee вдвое.

Показать эталонную реализацию DDL + DML

Создай представление m6_star.v_sales_flat, денормализующее fact_sales, dim_date, dim_product и dim_customer в одну широкую таблицу, и построй к ней отчёт без единого JOIN: выручка и штуки по country_name и segment за 2026 год.

Показать решение

-- 3. Без UNIQUE INDEX CONCURRENTLY упадёт! Создаём уникальный индекс без WHERE:
CREATE UNIQUE INDEX IF NOT EXISTS idx_m6_mv_city_monthly_uniq
    ON m6_part.mv_city_monthly (month_start, city_name, category);

REFRESH MATERIALIZED VIEW CONCURRENTLY m6_part.mv_city_monthly;

SELECT month_start, city_name, category, total_qty, total_revenue
FROM m6_part.mv_city_monthly WHERE month_start = DATE '2026-04-01' ORDER BY total_revenue DESC;

Разница: обычный REFRESH вешает ACCESS EXCLUSIVE LOCK (дашборд встаёт до конца пересчёта). CONCURRENTLY строит дифф по UNIQUE INDEX и позволяет читать старую версию витрины во время обновления.

COMMIT): Шаг 1 закрывает устаревшие активные версии (valid_to = '2026-02-28', is_current = false), Шаг 2 вставляет новые активные версии через LEFT JOIN. Прогони транзакцию дважды подряд!

    SET valid_to = DATE '2026-03-01' - INTERVAL '1 day', is_current = false

      AND d.is_current = true
      AND (d.full_name IS DISTINCT FROM s.full_name
        OR d.city      IS DISTINCT FROM s.city
        OR d.segment   IS DISTINCT FROM s.segment);

           DATE '2026-03-01', DATE '9999-12-31', true

    LEFT JOIN m6_elt.dim_customer_scd2 d
           ON d.customer_bk = s.customer_bk AND d.is_current = true
    WHERE d.customer_bk IS NULL
    ORDER BY s.customer_bk;

-- Помесячный DQ-аудит (все 3 партиции: 202601, 202602, 202603 -> OK ✓!)
WITH
    pg_m AS (
        SELECT toYYYYMM(order_date) AS part_month, count() AS pg_rows, sum(total_amount) AS pg_rev
        FROM postgresql('pg_primary:5432', 'learning_db', 'export_sales_mart',
                        'student', 'student_pass', 'm6_elt')
        GROUP BY part_month
    ),
    ch_m AS (
        SELECT toYYYYMM(order_date) AS part_month, count() AS ch_rows, sum(total_amount) AS ch_rev
        FROM m6_mart_sales GROUP BY part_month
    )
SELECT coalesce(pg_m.part_month, ch_m.part_month) AS part_month,
       pg_m.pg_rows, ch_m.ch_rows, pg_m.pg_rev, ch_m.ch_rev,
       pg_m.pg_rev - ch_m.ch_rev AS diff_rev,
       if(pg_m.pg_rows = ch_m.ch_rows AND pg_m.pg_rev = ch_m.ch_rev, 'OK ✓', 'MISMATCH ✗') AS dq_status
FROM pg_m FULL OUTER JOIN ch_m ON pg_m.part_month = ch_m.part_month
ORDER BY part_month;
