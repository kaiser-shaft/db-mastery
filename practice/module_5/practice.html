5.1 Физическая потоковая репликация: Primary, Standby и слоты (3 сценария)

Проверяем внутреннее устройство связки Primary → Hot Standby, чиним несовместимый аналитический отчёт и обезвреживаем «бомбу» утечки диска через заброшенный слот репликации.

5.1.1 Рентген физической репликации: конфиг Standby, heartbeat и сверка LSN с обеих сторон
Лаба · Runbook
Узлы: Host Bash Primary :5432 Standby :5433

Пройди полный чек-лист приёмки физической реплики: 1) найди внутри course_pg_standby файл-маркер standby.signal и строку primary_conninfo в postgresql.auto.conf; 2) запиши пульс в replication_heartbeat на Primary и убедись, что он доехал на Standby; 3) попробуй выполнить INSERT на Standby и зафиксируй ошибку Read-Only; 4) проверь статус стриминга с обеих сторон — pg_stat_replication (Primary) и pg_stat_wal_receiver + pg_last_wal_receive/replay_lsn() (Standby).

Критерии приёмки
  • На Primary: state = 'streaming', sync_state = 'async', lag_bytes = 0.
  • На Standby: status = 'streaming', pending_replay_bytes = 0, запись падает с cannot execute INSERT in a read-only transaction.

SET beat_count = beat_count + 1, note = 'Живой тест 5.1', updated_at = now()
WHERE id = 1;

SELECT pid, application_name, state, sync_state,

FROM pg_stat_replication;

VALUES ('Тест', 'Книги', 1000.00, 'new');

FROM pg_stat_wal_receiver;

SELECT pg_last_wal_receive_lsn() AS received_lsn,

Разбор: колонка slot_name сейчас пустая — реплика подключена напрямую и опирается на wal_keep_size = 128MB. Физическая реплика применяет сырые страницы 8 КБ байт-в-байт, поэтому локальная запись на ней запрещена.

5.1.2 Read/Write Splitting: чиним отчёт аналитика, падающий на Hot Standby
Баг-фикс
Узлы: Standby :5433

Чтобы разгрузить Primary, отчётность перевели на Standby (:5433), но утренний скрипт аналитика сразу упал с ERROR: cannot execute CREATE TABLE in a read-only transaction:

❌ ПРОБЛЕМНЫЙ СКРИПТ АНАЛИТИКА НА STANDBY
CREATE TEMP TABLE tmp_paid AS
SELECT category, COUNT(*) AS orders_cnt, SUM(amount) AS total_revenue
FROM ops_orders WHERE status = 'paid' GROUP BY category;

SELECT * FROM tmp_paid WHERE total_revenue > 15000 ORDER BY total_revenue DESC;

Задача: перепиши отчёт так, чтобы он работал на Read-Only Standby (через WITH / CTE), и проверь результат — должны вернуться «Одежда» (30200.00, 3 заказа) и «Гаджеты» (18900.00, 1 заказ).

Проверь себя
  • Почему даже временная таблица (CREATE TEMP TABLE) не работает на Hot Standby?
Показать исправление и разбор
Standby :5433 Безопасный Read-Only отчёт через CTE
WITH paid_by_category AS (
    SELECT
        category,
        COUNT(*)    AS orders_cnt,
        SUM(amount) AS total_revenue
    FROM ops_orders
    WHERE status = 'paid'
    GROUP BY category
)
SELECT category, orders_cnt, total_revenue
FROM paid_by_category
WHERE total_revenue > 15000
ORDER BY total_revenue DESC;

Причина: создание TEMP TABLE требует записи метаданных в системные каталоги (pg_class, pg_attribute), что невозможно в read-only режиме. CTE выполняется целиком в памяти/временных файлах сортировки без модификации каталогов.

5.1.3 Инцидент: заброшенный Replication Slot съедает диск Primary
Инцидент
Узлы: Primary :5432
🚨 СИМПТОМ: Тестовую реплику погасили неделю назад, а её слот репликации забыли удалить — каталог pg_wal на Primary безостановочно растёт и угрожает остановить базу ошибкой No space left on device.

Смоделируй и обезвредь утечку WAL на Primary (:5432): 1) создай неактивный физический слот practice_slot_5_1 с немедленным резервированием WAL (true); 2) сгенерируй WAL, обновив payload у всех 5 000 строк telemetry_stream; 3) найди объём удержанного WAL (retained_wal) через pg_replication_slots; 4) поставь серверный предохранитель max_slot_wal_keep_size = '1GB' без перезапуска (ALTER SYSTEM + pg_reload_conf()) и удали забытый слот.

Проверь себя
  • Чему по умолчанию равен max_slot_wal_keep_size в PostgreSQL?
  • В какой статус (wal_status) перейдёт слот, если его отставание превысит лимит max_slot_wal_keep_size?
Показать пошаговый Runbook спасения
Шаг 1 · Primary :5432 Воспроизводим утечку WAL
SELECT pg_drop_replication_slot(slot_name)
FROM pg_replication_slots WHERE slot_name = 'practice_slot_5_1';

SELECT * FROM pg_create_physical_replication_slot('practice_slot_5_1', true);

UPDATE telemetry_stream SET payload = repeat('slot_wal_', 12);
Шаг 2 · Primary :5432 Диагностика удержанного WAL
SELECT
    slot_name, slot_type, active, restart_lsn, wal_status,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots
WHERE slot_name = 'practice_slot_5_1';
Шаг 3 · Primary :5432 Ставим предохранитель 1 ГБ и удаляем слот (↺ Cleanup)
SHOW max_slot_wal_keep_size; -- по умолчанию -1 (без лимита!)

ALTER SYSTEM SET max_slot_wal_keep_size = '1GB';
SELECT pg_reload_conf();
SELECT current_setting('max_slot_wal_keep_size') AS slot_wal_limit;

-- Обязательно удаляем неактивный слот!
SELECT pg_drop_replication_slot('practice_slot_5_1');

Постмортем: при превышении лимита слот переходит в статус lost и PostgreSQL удаляет старые WAL. Лучше потерять одну отставшую реплику (её можно переналить), чем уронить боевой Primary из-за переполнения диска.

5.2 Синхронная vs асинхронная репликация и Replication Lag (4 сценария)

Учимся управлять RPO = 0 на уровне отдельных транзакций, честно измерять лаг и конфликты, отличать сетевое отставание от тормозов startup process и спасать Primary, зависший при падении синхронного Standby.

5.2.1 Гибридный кластер на лету: async → sync, remote_apply для биллинга и off для телеметрии
Лаба · Runbook
Узлы: Primary :5432 Standby :5433

Покажи, как один кластер одновременно даёт RPO = 0 для денег и максимальную скорость для логов: 1) на Primary включи синхронный режим для нашей реплики (synchronous_standby_names = 'walreceiver' + pg_reload_conf()) и убедись, что в pg_stat_replication появилось sync_state = 'sync'; 2) переведи 1000.00 в billing_accounts от Алины (id=1) к Тимуру (id=2) с SET LOCAL synchronous_commit = remote_apply и сразу проверь балансы на Standby; 3) в следующей транзакции с SET LOCAL synchronous_commit = off залей 1 000 строк в telemetry_stream; 4) верни кластер в async (ALTER SYSTEM RESET synchronous_standby_names).

Проверь себя
  • Чем synchronous_commit = remote_apply отличается от значения по умолчанию on?
  • Почему при synchronous_commit = on и пустом synchronous_standby_names реплика всё равно работает в async?
Показать пошаговый Runbook (4 шага)
Шаг 1 · Primary :5432 Включаем синхронный Standby без рестарта
ALTER SYSTEM SET synchronous_standby_names = 'walreceiver';
SELECT pg_reload_conf();

SELECT application_name, state, sync_priority, sync_state
FROM pg_stat_replication; -- sync_priority=1, sync_state='sync'
Шаг 2 · Primary :5432 Критичный перевод с remote_apply
BEGIN;
SET LOCAL synchronous_commit = remote_apply;
UPDATE billing_accounts SET balance = balance - 1000.00, updated_at = now() WHERE id = 1;
UPDATE billing_accounts SET balance = balance + 1000.00, updated_at = now() WHERE id = 2;
COMMIT;
Шаг 3 · Standby :5433 Балансы (49000 и 33000) видны сразу после COMMIT

Шаг 4 · Primary :5432 Быстрая телеметрия (off) + возврат в async (↺ Cleanup)

SELECT 'metrics', 'fast_click_' || g FROM generate_series(1, 1000) AS g;

Разбор: при on Primary ждёт лишь flush_lsn (запись WAL на диск Standby, но данные ещё не обязательно применены к страницам). При remote_apply Primary ждёт replay_lsn, гарантируя read-your-writes при чтении со Standby сразу после COMMIT.

5.2.2 Алертинг лага и конфликтов: «тихая база», heartbeat и светофор здоровья
Мониторинг · SQL
Узлы: Primary :5432 Standby :5433

Собери три продакшен-метрики мониторинга репликации: 1) На Standby (:5433): напиши запрос, защищённый от ловушки «тихой базы» — возвращай real_lag_seconds = 0, если pg_last_wal_receive_lsn() = pg_last_wal_replay_lsn(), иначе секунды от pg_last_xact_replay_timestamp(). Заодно проверь счётчики конфликтов pg_stat_database_conflicts и настройки max_standby_streaming_delay / hot_standby_feedback. 2) Heartbeat (Primary → Standby): обнови строку node_role = 'lag_monitor' в replication_heartbeat на Primary и замерь сквозной лаг now() - updated_at на Standby. 3) На Primary (:5432): напиши светофор здоровья с CTE по pg_stat_replication: 'CRITICAL' (если state <> 'streaming' или лаг > 16 МБ), 'WARNING' (от 1 до 16 МБ), иначе 'OK'.

Проверь себя
  • Какой счётчик в pg_stat_database_conflicts растёт, когда VACUUM на Primary отменяет долгий аналитический отчёт на Standby?
  • Какая побочная цена у включения hot_standby_feedback = on на Primary?
Показать 3 готовых запроса мониторинга
Standby :5433 Честный лаг + конфликты Hot Standby
SELECT
    pg_last_wal_receive_lsn() AS received_lsn,
    pg_last_wal_replay_lsn()  AS replayed_lsn,
    CASE
        WHEN pg_last_wal_receive_lsn() = pg_last_wal_replay_lsn() THEN 0
        ELSE EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()))::INT
    END AS real_lag_seconds;

SELECT datname, confl_lock, confl_snapshot, confl_bufferpin, confl_deadlock,
       current_setting('max_standby_streaming_delay') AS streaming_delay,
       current_setting('hot_standby_feedback') AS feedback_on
FROM pg_stat_database_conflicts
WHERE datname = 'learning_db';
Primary :5432 Пульс heartbeat + светофор здоровья для алертов
-- Обновляем heartbeat (затем проверь ROUND(EXTRACT(EPOCH FROM (now() - updated_at))::NUMERIC, 3) на Standby)
UPDATE replication_heartbeat
SET beat_count = beat_count + 1, updated_at = now()
WHERE node_role = 'lag_monitor';

-- Светофор здоровья реплики
WITH lag_metrics AS (
    SELECT application_name, state, sync_state,
           pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
    FROM pg_stat_replication
)
SELECT
    application_name, sync_state,
    pg_size_pretty(lag_bytes) AS lag_pretty,
    CASE
        WHEN state <> 'streaming' OR lag_bytes > 16777216 THEN 'CRITICAL'
        WHEN lag_bytes >= 1048576 THEN 'WARNING'
        ELSE 'OK'
    END AS health_status
FROM lag_metrics;

Разбор: рост confl_snapshot означает конфликты с VACUUM. Включение hot_standby_feedback = on спасает отчёты на Standby от отмены, но удерживает oldest_xmin на Primary — при долгих отчётах на реплике начнёт раздуваться (Bloat) сам Primary!

5.2.3 Инцидент: диагностируем тип Replication Lag (сеть/диск vs replay)
Инцидент
Узлы: Standby :5433 Primary :5432
🚨 СИМПТОМ: Пришёл алерт «Реплика отстала на несколько мегабайт». Нужно за 30 секунд определить виновника: не тянет сеть/диск реплики или не успевает однопоточный startup process (применение WAL).

1) На Standby (:5433) поставь применение WAL на паузу (pg_wal_replay_pause()). 2) На Primary (:5432) сгенерируй 15 000 строк в telemetry_stream и раздели лаг в pg_stat_replication на два слагаемых: network_lag_bytes (sent_lsn → flush_lsn) и replay_lag_bytes (flush_lsn → replay_lsn). 3) Обязательно сними паузу (pg_wal_replay_resume()) и сверь COUNT(*)!

Что наблюдать
  • Какая из двух метрик (network_lag_bytes или replay_lag_bytes) выросла на мегабайты, а какая осталась ~0?
Показать пошаговый Runbook диагностики
Шаг 1 · Standby :5433 Имитируем тормоз применения WAL
SELECT pg_wal_replay_pause();
SELECT pg_is_wal_replay_paused() AS is_paused;
Шаг 2 · Primary :5432 Нагоняем WAL и локализуем узкое место
INSERT INTO telemetry_stream (service_name, payload)
SELECT 'lag_bench', repeat('lag_payload_', 12)
FROM generate_series(1, 15000) AS g;

SELECT
    application_name, state,
    pg_wal_lsn_diff(sent_lsn, flush_lsn)   AS network_lag_bytes,
    pg_wal_lsn_diff(flush_lsn, replay_lsn) AS replay_lag_bytes,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS total_lag
FROM pg_stat_replication;
Шаг 3 · Standby :5433 Снимаем паузу и проверяем догонку (↺ Cleanup)
SELECT pg_wal_replay_resume();
SELECT COUNT(*) AS total_rows_on_standby FROM telemetry_stream;

Диагностическая матрица: network_lag >> 0 — тормозит сеть или диск Standby; network_lag ≈ 0, но replay_lag >> 0 — WAL уже на диске реплики, но не успевает применение (конфликт с долгим SELECT или слабый CPU/IOPS).

5.2.4 Ночной инцидент: падение единственного синхронного Standby вешает Primary
Инцидент

5.3.2 Ловушка №1: таблица без Primary Key ломает UPDATE при публикации (REPLICA IDENTITY)
Инцидент
Узлы: Primary :5432
🚨 СИМПТОМ: Добавили старую таблицу аудита raw_audit_events в логическую публикацию — сразу после этого на самом Primary перестали работать UPDATE и DELETE с ошибкой does not have a replica identity!

Воспроизведи ошибку на raw_audit_events (специально создана без PK), почини таблицу правильным способом (добавь id BIGSERIAL PRIMARY KEY), убедись, что UPDATE заработал, и удали тестовую публикацию audit_pub.

Проверь себя
  • Почему добавлять Primary Key намного лучше, чем ставить ALTER TABLE ... REPLICA IDENTITY FULL?
Показать пошаговый Runbook лечения
Primary :5432 Воспроизводим → Чиним через PK → Убираем публикацию

DROP PUBLICATION IF EXISTS audit_pub;
CREATE PUBLICATION audit_pub FOR TABLE raw_audit_events;

UPDATE raw_audit_events SET message = 'Проверено дважды' WHERE actor = 'Алина';
-- ERROR: cannot update table "raw_audit_events" because it does not have a replica identity

-- 2. Правильное лечение: добавляем суррогатный Primary Key
ALTER TABLE raw_audit_events ADD COLUMN id BIGSERIAL PRIMARY KEY;

-- 3. Теперь UPDATE проходит без ошибок!
UPDATE raw_audit_events SET message = 'Проверено дважды' WHERE actor = 'Алина';
SELECT id, actor, message FROM raw_audit_events ORDER BY id;

-- 4. Очистка
DROP PUBLICATION audit_pub;

Почему не REPLICA IDENTITY FULL: при FULL в WAL записывается вся старая строка целиком (раздувает WAL и сеть), а подписчику приходится делать полный Seq Scan таблицы при каждом UPDATE/DELETE.

5.4.2 Аудит соединений и починка «протекающего» скрипта под PgBouncer (transaction mode)
Баг-фикс
Узлы: Primary :5432 PgBouncer :6432

После включения PgBouncer в режиме transaction pooling разработчики заметили странные OOM-скачки памяти и ошибки relation "tmp_vip" does not exist на следующем запросе. Вот их код:

❌ ПРОБЛЕМНЫЙ СКРИПТ ЧЕРЕЗ PGBOUNCER (transaction mode)
-- Сессионный SET утечёт на ЧУЖИЕ запросы, а TEMP TABLE пропадёт на другом бэкенде!
SET work_mem = '32MB';
CREATE TEMP TABLE tmp_vip AS SELECT owner, balance FROM billing_accounts WHERE tier = 'vip';
SELECT SUM(balance) FROM tmp_vip;

Задача: 1) на Primary напиши аудит-запрос к pg_stat_activity (только client backend), показывающий число сессий по state и процент от max_connections; 2) перепиши скрипт разработчика так, чтобы он безопасно выполнялся через PgBouncer (одна транзакция с SET LOCAL и ON COMMIT DROP), и убедись через SHOW work_mem; после COMMIT, что настройка вернулась к 4MB.

Показать аудит соединений и исправленный скрипт
Шаг 1 · Primary :5432 Аудит клиентских соединений vs max_connections
WITH limits AS (
    SELECT current_setting('max_connections')::INT AS max_conn
)
SELECT
    COALESCE(a.state, 'unknown') AS conn_state,
    COUNT(*)                     AS connections_cnt,
    l.max_conn,
    ROUND(100.0 * COUNT(*) / l.max_conn, 1) AS pct_of_limit
FROM pg_stat_activity AS a
CROSS JOIN limits AS l
WHERE a.backend_type = 'client backend'
GROUP BY a.state, l.max_conn
ORDER BY connections_cnt DESC;
Шаг 2 · PgBouncer :6432 Исправленный скрипт (SET LOCAL + ON COMMIT DROP)
docker exec -e PGPASSWORD=student_pass course_pg_primary \
  psql -h pgbouncer -p 5432 -U student -d learning_db -c "
  BEGIN;
    SET LOCAL work_mem = '32MB';
    CREATE TEMP TABLE tmp_vip ON COMMIT DROP AS
    SELECT owner, balance FROM billing_accounts WHERE tier = 'vip';

    SELECT SUM(balance) AS vip_total, current_setting('work_mem') AS tx_work_mem
    FROM tmp_vip;
  COMMIT;

  SHOW work_mem; -- снова 4MB: чужим клиентам ничего не утекло!
"

Правило transaction pooling: всё, что привязано к сессии (SET без LOCAL, PREPARE, LISTEN/NOTIFY, pg_advisory_lock, обычные TEMP TABLE), опасно в режиме transaction — либо ограничивай их транзакцией, либо выноси в отдельный пул session mode.

5.4.5 Дашборд дежурного DBA: единый HA & Ops Healthcheck в одном SQL-запросе
Мониторинг · SQL Финал модуля
Узлы: Primary :5432

Собери итоговый диагностический отчёт на Primary (:5432) через UNION ALL с тремя колонками (check_name, metric_value, status), который одним запросом проверяет 6 критичных узлов эксплуатации: 1) роль узла (pg_is_in_recovery() — должно быть false); 2) число активных реплик (state = 'streaming' >= 1 → OK, иначе CRITICAL); 3) максимальный лаг репликации (> 16 МБ → WARNING); 4) заброшенные слоты (WHERE NOT active = 0 → OK, иначе CRITICAL); 5) ошибки архивации WAL (pg_stat_archiver.failed_count = 0 → OK); 6) заполненность max_connections клиентскими сессиями (> 80% → WARNING).

Критерий приёмки
  • На здоровом кластере после всех Cleanup-шагов все 6 строк возвращают статус OK.
Показать итоговый HA & Ops Healthcheck
Primary :5432 Единый HA & Ops Healthcheck (6 проверок)
SELECT
    '1. Роль узла (is_standby)' AS check_name,
    pg_is_in_recovery()::TEXT   AS metric_value,
    CASE WHEN NOT pg_is_in_recovery() THEN 'OK' ELSE 'WARNING' END AS status
UNION ALL
SELECT
    '2. Активные реплики (streaming)',
    COUNT(*)::TEXT,
    CASE WHEN COUNT(*) >= 1 THEN 'OK' ELSE 'CRITICAL' END
FROM pg_stat_replication
WHERE state = 'streaming'
UNION ALL
SELECT
    '3. Максимальный lag (replay)',
    pg_size_pretty(COALESCE(MAX(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)), 0)),
    CASE
        WHEN COALESCE(MAX(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)), 0) > 16777216 THEN 'WARNING'
        ELSE 'OK'
    END
FROM pg_stat_replication
UNION ALL
SELECT
    '4. Неактивные слоты (active=false)',
    COUNT(*)::TEXT,
    CASE WHEN COUNT(*) = 0 THEN 'OK' ELSE 'CRITICAL' END
FROM pg_replication_slots
WHERE NOT active
UNION ALL
SELECT
    '5. Ошибки архивации WAL (failed_count)',
    failed_count::TEXT,
    CASE WHEN failed_count = 0 THEN 'OK' ELSE 'CRITICAL' END
FROM pg_stat_archiver
UNION ALL
SELECT
    '6. Занято соединений от max_connections',
    ROUND(100.0 * COUNT(*) / current_setting('max_connections')::INT, 1)::TEXT || '%',
    CASE
        WHEN 100.0 * COUNT(*) / current_setting('max_connections')::INT > 80 THEN 'WARNING'
        ELSE 'OK'
    END
FROM pg_stat_activity
WHERE backend_type = 'client backend';
