01 Урок 4.1 · Транзакции, ACID и аномалии параллельного доступа (6 заданий)

Отрабатываем атомарность переводов, выход из режима aborted, точки сохранения SAVEPOINT, а затем переходим к двум окнам терминала: ловим классические аномалии чтения и чиним баг Lost Update.

4.1.1 Жизненный цикл транзакции: откат, подтверждение и инвариант балансов
1 окно · PG Практика

Выполни две короткие транзакции подряд: 1) Попробуй списать 100.00 с 'Алиса', убедись внутри блока, что баланс стал 900.00, и полностью отмени операцию через ROLLBACK;. 2) В новой единой транзакции переведи 200.00 от 'Алиса' (id = 1) к 'Боб' (id = 2), запиши операцию в transfer_log (note = 'Перевод за меч') и зафиксируй COMMIT;.

Критерий приёмки
  • У Алисы 800.00, у Боба 700.00, в transfer_log появилась 5-я строка.
  • Общая сумма всех кошельков (SUM(balance)) не изменилась и осталась 2450.00.
Показать решение и разбор
SQL · PostgreSQL 16
-- Часть 1: тренировочный откат
BEGIN;
UPDATE wallets SET balance = balance - 100.00 WHERE owner = 'Алиса';
SELECT owner, balance FROM wallets WHERE owner = 'Алиса'; -- 900.00 внутри блока
ROLLBACK;

-- Часть 2: атомарный перевод + запись в журнал
BEGIN;
UPDATE wallets SET balance = balance - 200.00 WHERE id = 1;
UPDATE wallets SET balance = balance + 200.00 WHERE id = 2;
INSERT INTO transfer_log (from_wallet_id, to_wallet_id, amount, note)
VALUES (1, 2, 200.00, 'Перевод за меч');
COMMIT;

-- Проверка инварианта Consistency
SELECT id, owner, balance FROM wallets WHERE id IN (1, 2) ORDER BY id;
SELECT SUM(balance) AS total_gold FROM wallets;

Почему это важно: в psql во время открытой транзакции приглашение меняется с =# на =*#. Если сервер упадёт между двумя UPDATE до COMMIT, WAL откатит незавершённую транзакцию и деньги не пропадут (Atomicity).

4.1.2 Режим aborted и щиты Consistency (wallets, transfer_log, shop_items)
1 окно · PG Практика

В PostgreSQL любая ошибка внутри BEGIN переводит транзакцию в состояние aborted (приглашение =!#), и все следующие команды игнорируются до ROLLBACK. Проверь на практике 3 защитных ограничения: 1) Внутри транзакции спиши 600.00 с Алисы (успешно!), затем попробуй списать 2 штуки 'Щит новичка' (в shop_items осталась 1 шт. → ошибка CHECK). Не закрывая транзакцию, выполни SELECT * FROM wallets;, поймай ошибку current transaction is aborted и выйди через ROLLBACK;. 2) Отдельно проверь запрет перевода самому себе в transfer_log (from_wallet_id = 1, to_wallet_id = 1).

Проверь себя
  • Если вместо ROLLBACK; в состоянии aborted написать COMMIT; — что на самом деле сделает PostgreSQL?
  • Списались ли 600.00 с Алисы после ошибки на втором шаге?
Показать решение и разбор
SQL · PostgreSQL 16
-- 1. Сбой на втором шаге покупки + состояние aborted
BEGIN;
UPDATE wallets SET balance = balance - 600.00 WHERE owner = 'Алиса';
UPDATE shop_items SET stock = stock - 2 WHERE title = 'Щит новичка';
-- ERROR: violates check constraint "shop_items_stock_check"

SELECT * FROM wallets;
-- ERROR: current transaction is aborted, commands ignored until end of transaction block

ROLLBACK;

-- 2. Запрет перевода самому себе (CHECK from_wallet_id <> to_wallet_id)
BEGIN;
INSERT INTO transfer_log (from_wallet_id, to_wallet_id, amount, note)
VALUES (1, 1, 100.00, 'Сам себе');
ROLLBACK;

Ответ на проверку: команда COMMIT; в состоянии aborted всё равно выполнит ROLLBACK (в psql так и напечатается — ROLLBACK). Списание 600.00 с Алисы полностью отменено.

4.1.3 Частичный откат покупки через SAVEPOINT и RELEASE SAVEPOINT
1 окно · PG Практика

Игрок 'Алиса' в одной транзакции покупает корзину из двух товаров: 1) 'Зелье маны' за 150.00 (есть на складе); 2) 'Плащ невидимки' за 450.00 (stock = 0 — упадёт с ошибкой!). Настрой SAVEPOINT так, чтобы при ошибке на плаще покупка зелья не пропала, сними статус aborted откатом к чекпоинту, освободи точку сохранения через RELEASE SAVEPOINT и подтверди транзакцию.

Проверь себя
  • Откатывает ли команда RELEASE SAVEPOINT изменения, сделанные после чекпоинта?
  • Почему нельзя создавать тысячи SAVEPOINT в цикле внутри одной транзакции?
Показать решение и разбор
SQL · PostgreSQL 16
BEGIN;

-- 1. Успешная покупка зелья
UPDATE wallets SET balance = balance - 150.00 WHERE owner = 'Алиса';
UPDATE shop_items SET stock = stock - 1 WHERE title = 'Зелье маны';

-- 2. Ставим точку сохранения
SAVEPOINT after_potion;

-- 3. Неудачная попытка купить плащ (stock = 0 -> CHECK error)
UPDATE wallets SET balance = balance - 450.00 WHERE owner = 'Алиса';
UPDATE shop_items SET stock = stock - 1 WHERE title = 'Плащ невидимки';

-- 4. Откатываем только неудачный шаг (снимает aborted!) и освобождаем чекпоинт
ROLLBACK TO SAVEPOINT after_potion;
RELEASE SAVEPOINT after_potion;
COMMIT;

SELECT owner, balance FROM wallets WHERE owner = 'Алиса';
SELECT title, stock FROM shop_items WHERE title IN ('Зелье маны', 'Плащ невидимки') ORDER BY id;

Разбор: RELEASE SAVEPOINT ничего не откатывает — он лишь удаляет метку и освобождает память. Каждый SAVEPOINT создаёт субтранзакцию (SubXID); больше 64 активных субтранзакций на бэкенд приводят к деградации (SubtransSLRU) под нагрузкой.

4.1.4 Доказываем, что Dirty Read невозможен
2 окна · PG Эксперимент

Проверь гарантию Isolation в двух параллельных сессиях: в Окне 1 измени цену 'Алмазный меч' на 9999.00 без COMMIT, а в Окне 2 попробуй прочитать этот «черновик» — даже с явным запросом уровня READ UNCOMMITTED!

Что наблюдать
  • Какую цену вернёт Окно 2: 600.00 или 9999.00?
  • Заблокируется ли SELECT в Окне 2 из-за незавершённого UPDATE в Окне 1?
Показать пошаговый протокол (Окно 1 | Окно 2)
Окно 1 · Писатель
Окно 2 · Читатель
Шаг 1 Меняем без COMMIT
BEGIN;
UPDATE shop_items
SET price = 9999.00
WHERE title = 'Алмазный меч';
Ждём завершения Шага 1
⏸ Транзакция открыта (без COMMIT)
Шаг 2 Пытаемся поймать Dirty Read

FROM shop_items
WHERE title = 'Алмазный меч';

Шаг 3 Отменяем черновик

Вывод: в PostgreSQL уровень READ UNCOMMITTED внутри работает идентично READ COMMITTED — грязное чтение архитектурно невозможно благодаря MVCC.

4.1.5 Ловим Non-Repeatable Read и Phantom Read в READ COMMITTED
2 окна · PG Эксперимент
↺ Стартовые числа (после init.sql): Компас героя = 120.00, товаров дешевле 200.00 ровно 2.

Покажи, что внутри одной транзакции на уровне по умолчанию (READ COMMITTED) два одинаковых SELECT могут вернуть разные данные: в Окне 1 прочитай цену 'Компас героя' и число товаров дешевле 200.00, затем в Окне 2 подними цену компаса до 180.00 и добавь новый товар ('Факел', 90.00, 10, 0) с COMMIT, после чего повтори оба запроса в Окне 1.

Что наблюдать
  • Какая из двух цифр иллюстрирует Non-Repeatable Read, а какая — Phantom Read?
  • В какой момент PostgreSQL берёт новый снимок данных (Snapshot) в режиме READ COMMITTED?
Показать пошаговый протокол (Окно 1 | Окно 2)
Окно 1 · Долгий отчёт (READ COMMITTED)
Окно 2 · Обновление прайса
Шаг 1 Первое чтение (120.00 и 2)
BEGIN;
SELECT title, price FROM shop_items
WHERE title = 'Компас героя';

SELECT COUNT(*) AS cheap_cnt
FROM shop_items WHERE price < 200.00;
Ждём Шаг 1
⏸ Транзакция всё ещё открыта
Шаг 2 Меняем строку + вставляем фантом
BEGIN;
UPDATE shop_items SET price = 180.00
WHERE title = 'Компас героя';
INSERT INTO shop_items (title, price, stock, views)
VALUES ('Факел', 90.00, 10, 0);
COMMIT;
Шаг 3 Повтор тех же SELECT
SELECT title, price FROM shop_items
WHERE title = 'Компас героя'; -- 180.00!

SELECT COUNT(*) AS cheap_cnt
FROM shop_items WHERE price < 200.00; -- 3!
COMMIT;
✓ Изменения уже видны Окне 1

Разбор: в READ COMMITTED новый снимок берётся на каждый отдельный оператор внутри транзакции. Изменившаяся цена 120 → 180 — Non-Repeatable Read, появление новой строки «Факел» (2 → 3) — Phantom Read.

4.1.6 Код-ревью: потерянное пополнение кошелька (Lost Update)
2 окна · PG Баг-фикс
↺ Сброс для Дины: UPDATE wallets SET balance = 750.00 WHERE owner = 'Дина';

Два платёжных воркера одновременно пополняют баланс 'Дина' (исходно 750.00): первый начисляет +100.00, второй — +250.00. Клиент жалуется, что вместо 1100.00 на счёте оказывается 1000.00. Вот фрагмент кода из бэкенда:

❌ ПРОБЛЕМНЫЙ КОД (read-modify-write в приложении)
-- Воркер 1 и Воркер 2 одновременно читают 750.00:
SELECT balance FROM wallets WHERE owner = 'Дина';
-- Код приложения считает 750 + 100 = 850 (Воркер 1) и 750 + 250 = 1000 (Воркер 2)
-- Затем каждый отправляет готовое абсолютное число:
UPDATE wallets SET balance = 850.00  WHERE owner = 'Дина'; -- Воркер 1
UPDATE wallets SET balance = 1000.00 WHERE owner = 'Дина'; -- Воркер 2 перезатёр +100!

Задача: исправь SQL-логику на атомарное обновление (без чтения числа в код приложения) и докажи в 2 окнах, что при перекрывающихся транзакциях Окно 2 честно дождётся Окна 1 и итоговый баланс Дины станет ровно 1100.00.

Проверь себя
  • Что происходит со строкой Дины в Окне 2 на Шаге 2 до того, как Окно 1 сделало COMMIT?
  • Откуда Окно 2 берёт новое значение 850.00 после отпускания замка, если его транзакция началась раньше?
Показать исправление и 2-оконную проверку
Окно 1 · Пополнение +100.00
Окно 2 · Пополнение +250.00
Шаг 1 Сброс + атомарный UPDATE
UPDATE wallets SET balance = 750.00
WHERE owner = 'Дина';

BEGIN;
UPDATE wallets
SET balance = balance + 100.00
WHERE owner = 'Дина';
Ждём Шаг 1
🔒 Держит замок на строке Дины
Шаг 2 Запустится и ЗАМРЁТ
BEGIN;
UPDATE wallets
SET balance = balance + 250.00
WHERE owner = 'Дина';
Шаг 3 Фиксируем +100 (850.00)
COMMIT;
⏳ Ждёт COMMIT в Окне 1…
✓ Завершено
Шаг 4 Проснулось → COMMIT + проверка
COMMIT;
SELECT owner, balance FROM wallets
WHERE owner = 'Дина'; -- ровно 1100.00!

Почему это работает: в READ COMMITTED ожидающий UPDATE после освобождения строчного замка перечитывает свежую закоммиченную версию строки (механизм EvalPlanQual) и вычисляет 850 + 250 = 1100. Альтернатива при сложной бизнес-логике в коде — SELECT ... FOR UPDATE или оптимистичная блокировка с колонкой version.

02 Урок 4.2 · MVCC (многоверсионность) и VACUUM в PostgreSQL (5 заданий)

Смотрим на реальную физику строк (ctid, xmin, xmax), проводим 3-шаговую лабораторную по Table Bloat и VACUUM, ловим паралич уборщика из-за забытой транзакции и чиним багованный скрипт обслуживания.

4.2.1 Рентген MVCC: доказываем «переезд» строки при UPDATE
1 окно · PG Практика

Выведи скрытые системные столбцы ctid, xmin, xmax вместе с title и stock для товара 'Зелье маны' в shop_items. Затем увеличь его stock на 1 (внутри BEGIN ... COMMIT, заодно посмотрев pg_current_xact_id()) и снова выведи те же системные столбцы.

Проверь себя
  • Что означают два числа в ctid вида (0,7) и почему номер слота вырос?
  • Совпал ли новый xmin с тем значением, которое вернула pg_current_xact_id()?
Показать решение и разбор
SQL · PostgreSQL 16
-- 1. До обновления
SELECT ctid, xmin, xmax, title, stock
FROM shop_items WHERE title = 'Зелье маны';

-- 2. Обновление внутри транзакции с фиксацией её XID
BEGIN;
SELECT pg_current_xact_id() AS my_xid;
UPDATE shop_items SET stock = stock + 1 WHERE title = 'Зелье маны';
COMMIT;

-- 3. После обновления: новый слот ctid и xmin = my_xid!
SELECT ctid, xmin, xmax, title, stock
FROM shop_items WHERE title = 'Зелье маны';

Физика MVCC: в PostgreSQL UPDATE не переписывает строку на месте — он помечает старую версию (xmax) и вставляет новую версию в новый слот страницы (новый ctid и новый xmin).

Показать пошаговый протокол (Окно 1 → Окно 2 → Окно 3)

    pid AS waiting_pid,
    pg_blocking_pids(pid) AS blocked_by_pids,
    wait_event_type,
    wait_event,
    state,
    left(query, 60) AS waiting_query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

ROLLBACK;

4.4.4 Суперсилы PostgreSQL: O(1) ROLLBACK и Index-Only Scan (Heap Fetches: 0)
1 окно · PG Практика
↺ Для контраста Heap Fetches нужен свежий init.sql (до ручного VACUUM на mvcc_lab).

Проверь две ключевые архитектурные особенности PostgreSQL на таблице mvcc_lab (10 000 строк): 1) Включи таймер \timing on в psql, обнови все 10 000 строк в транзакции и сделай ROLLBACK; — сравни время UPDATE и ROLLBACK. 2) Выполни EXPLAIN (ANALYZE, BUFFERS) SELECT id FROM mvcc_lab WHERE id BETWEEN 100 AND 200;, посмотри Heap Fetches, затем прогони VACUUM ANALYZE mvcc_lab; и повтори EXPLAIN — убедись, что Heap Fetches упал до 0.

Проверь себя

  • Какая внутренняя структура данных обновляется при VACUUM, позволяя не ходить в Heap при Index Only Scan?
Показать решение и разбор
SQL · PostgreSQL 16 (psql)
-- Часть 1: мгновенный O(1) ROLLBACK
\timing on
BEGIN;
UPDATE mvcc_lab SET counter = counter + 100;
ROLLBACK;
\timing off

-- Часть 2: Visibility Map и Heap Fetches: 0
-- До VACUUM: карта видимости пуста -> Heap Fetches > 0

VACUUM ANALYZE mvcc_lab;

SELECT id FROM mvcc_lab WHERE id BETWEEN 100 AND 200;

Разбор: в PostgreSQL ROLLBACK лишь меняет 2 бита статуса транзакции в CLOG (O(1)), а в InnoDB приходится физически откатывать каждую строку из Undo Log. Index Only Scan избавляется от походов в Heap благодаря Visibility Map (карте all-visible страниц), которую поддерживает VACUUM.

4.4.6 Финал Модуля 4: боевая транзакция покупки билета с защитой от всех аномалий
1 окно · PG Финал модуля
↺ Перед финалом прогони init.sql, чтобы проверить точные итоговые балансы.

Собери в PostgreSQL 16 продакшен-транзакцию покупки билета (300.00) для 'Алиса' (id = 1) с перечислением оплаты организатору 'Дина' (id = 4), объединив все лучшие практики Модуля 4:

  1. Поставь локальный предохранитель lock_timeout = '3s' только на текущую транзакцию.
  2. Захвати оба кошелька (id IN (1, 4)) в строгом порядке ORDER BY id FOR UPDATE (исключаем Deadlock).
  3. Поставь чекпоинт SAVEPOINT before_ticket;.
  4. Одним CTE-запросом забери первое свободное место в ticket_queue через FOR UPDATE SKIP LOCKED, переведи его в status = 'paid' (wallet_id = 1) и верни результат через RETURNING.
  5. Атомарно переведи 300.00 от id = 1 к id = 4 (без Lost Update), запиши в transfer_log (note = 'Покупка билета') и выполни COMMIT;.
Критерий приёмки
  • У Алисы 700.00, у Дины 1050.00 (сумма 2450.00 сохранилась).
  • Билет id = 1 в статусе paid на wallet_id = 1, в transfer_log есть свежая запись на 300.00.
  • После COMMIT SHOW lock_timeout; снова показывает 0 (благодаря SET LOCAL).
Показать эталонную транзакцию Модуля 4
SQL · PostgreSQL 16 (итоговый паттерн)
BEGIN;

-- 1. Локальный предохранитель от вечного ожидания блокировок
SET LOCAL lock_timeout = '3s';

-- 2. Единый порядок блокировок кошельков (гарантия отсутствия Deadlock)
SELECT id, owner, balance
FROM wallets
WHERE id IN (1, 4)
ORDER BY id
FOR UPDATE;

-- 3. Чекпоинт перед списанием и бронью
SAVEPOINT before_ticket;

-- 4. Атомарно забираем первое свободное место без простоев (SKIP LOCKED + RETURNING)
WITH next_seat AS (
    SELECT id
    FROM ticket_queue
    WHERE status = 'free'
    ORDER BY id
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
UPDATE ticket_queue t
SET status = 'paid', wallet_id = 1
FROM next_seat ns
WHERE t.id = ns.id
RETURNING t.id, t.seat, t.status, t.wallet_id;

-- 5. Атомарный перевод (без Lost Update) + запись в журнал
UPDATE wallets SET balance = balance - 300.00 WHERE id = 1;
UPDATE wallets SET balance = balance + 300.00 WHERE id = 4;

INSERT INTO transfer_log (from_wallet_id, to_wallet_id, amount, note)
VALUES (1, 4, 300.00, 'Покупка билета');

COMMIT;

-- 6. Проверка согласованности
SELECT id, owner, balance FROM wallets WHERE id IN (1, 4) ORDER BY id;
SELECT id, seat, status, wallet_id FROM ticket_queue WHERE id = 1;
SELECT id, from_wallet_id, to_wallet_id, amount, note
FROM transfer_log ORDER BY id DESC LIMIT 1;
SHOW lock_timeout;

Итог: в одной короткой транзакции сошлись все столпы Модуля 4 — ACID, SET LOCAL lock_timeout, ORDER BY id FOR UPDATE, SAVEPOINT, FOR UPDATE SKIP LOCKED и RETURNING.
