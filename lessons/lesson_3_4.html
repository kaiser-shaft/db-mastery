Урок 3.4: Журнал предзаписи (WAL) и восстановление после сбоев (Crash Recovery)

Главное в этом уроке
  • Как устроен Журнал предзаписи (WAL — Write-Ahead Log) и почему PostgreSQL сначала пишет маленькую строку в журнал, а не обновляет сразу файлы таблиц на диске.
  • Что такое LSN, 16-мегабайтные сегменты pg_wal, контрольные точки (CHECKPOINT) и статистика pg_stat_wal.
  • Как работает автоматическое восстановление после аварии (Crash Recovery) — проверим на живом краш-тесте с «выдёргиванием вилки» в Docker Compose!
  • Когда уместны UNLOGGED-таблицы, чем опасно отключение fsync и какие параметры WAL нельзя поменять без перезапуска сервера.

01 Зачем базе «чёрный ящик»: проблема грязных страниц и принцип WAL

Представь кассира в огромном гипермаркете. К нему стоит очередь из 100 покупателей. По правилам бухгалтерии каждый чек нужно подшить в нужную папку в архивной комнате в другом конце здания (папка «Молоко» на 2-м этаже, папка «Хлеб» в подвале, папка «Скидки» на 3-м этаже).

Если кассир будет бегать в архив после каждого покупателя, очередь растянется на три часа. А если он просто запомнит покупки в голове и пойдёт разносить папки в конце смены — при внезапной потере памяти (отключении электричества!) магазин потеряет данные обо всех продажах за день.

У PostgreSQL ровно та же дилемма! В Уроке 3.1 ты узнал, что при INSERT или UPDATE база меняет 8-килобайтные страницы в быстрой оперативной памяти (Shared Buffers), помечая их как «грязные» (dirty pages). Сбрасывать эти страницы по всему диску на каждый COMMIT чудовищно медленно (случайная запись в десятки разных файлов). А оставлять только в RAM — смертельно опасно: выдернули шнур питания — и все подтверждённые заказы испарились!

Инженеры придумали гениальное решение — Журнал предзаписи (WAL — Write-Ahead Log). Кассир кладёт рядом с собой одну простую тетрадку в линейку (кассовую ленту) и на каждого покупателя за доли секунды дописывает в конец короткую строчку: «12:01, клиент #42, оплатил 5 000». Писать подряд в конец одного файла на диске — в десятки раз быстрее, чем прыгать по разным файлам! А в архивные папки (файлы таблиц Heap и индексов) помощник разнесёт изменения спокойно позже, в фоне.

Простая аналогия: WAL — это «чёрный ящик» самолёта. Даже если оперативная память (Shared Buffers) мгновенно обнулилась при сбое питания, на диске осталась точная поминутная хроника всех подтверждённых операций. По ней PostgreSQL за секунды восстановит всё до последнего байта!

02 Трогаем WAL руками: LSN, сегменты по 16 МБ и pg_stat_wal

Журнал предзаписи — не какая-то невидимая магия, а реальные файлы в папке pg_wal/ на диске сервера. По умолчанию каждый файл-сегмент имеет строгий размер 16 МБ. Когда один файл заполняется, PostgreSQL открывает следующий — как чистый лист в тетради.

Чтобы точно указывать место в этой бесконечной ленте, в PostgreSQL используется «километровый столбик» — LSN (Log Sequence Number, номер позиции в логе). Выглядит он как два шестнадцатеричных числа через слэш, например 0/1A4F8C0. По сути, это просто смещение в байтах от самого момента создания базы данных!

Давай откроем learning_db, создадим учебную таблицу и вживую замерим, сколько байт WAL генерирует вставка 10 000 строк.

SQL · Пример 1: замеряем LSN и объём WAL при вставке 10 000 строк 
-- Безопасный перезапуск: пересоздаём учебную таблицу
DROP TABLE IF EXISTS wal_orders;

CREATE TABLE wal_orders (
    id         SERIAL PRIMARY KEY,
    order_code TEXT NOT NULL,
    amount     NUMERIC(10, 2) NOT NULL,
    status     TEXT NOT NULL DEFAULT 'paid'
);

-- Смотрим текущую позицию в журнале (LSN) и имя активного файла в pg_wal/
SELECT
    pg_current_wal_lsn() AS current_lsn,
    pg_walfile_name(pg_current_wal_lsn()) AS wal_file;

-- Фиксируем LSN ДО вставки, вставляем 10 000 строк и считаем разницу в байтах
WITH lsn_before AS (
    SELECT pg_current_wal_lsn() AS pos
),
inserted AS (
    INSERT INTO wal_orders (order_code, amount)
    SELECT 'ORD-' || g, round((500 + (g * 13 % 9000))::numeric, 2)
    FROM generate_series(1, 10000) AS g
    RETURNING id
)
SELECT
    count(*) AS rows_inserted,
    (SELECT pos FROM lsn_before) AS lsn_start,
    pg_current_wal_lsn() AS lsn_end,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM lsn_before))
    ) AS wal_generated
FROM inserted;
Ответ PostgreSQL
 current_lsn |         wal_file
-------------+--------------------------
 0/4B210A8   | 000000010000000000000004
(1 row)

 rows_inserted | lsn_start |  lsn_end  | wal_generated
---------------+-----------+-----------+---------------
         10000 | 0/4B210A8 | 0/4C5E420 | 1269 kB
(1 row)

Смотри, как наглядно! Вставка 10 000 строк (вместе с записями для первичного ключа PRIMARY KEY) продвинула наш «километровый столбик» с 0/4B210A8 до 0/4C5E420 — это ровно 1269 КБ записей в файле 000000010000000000000004.

В PostgreSQL 16 есть встроенное системное представление pg_stat_wal — своего рода бортовой компьютер, который считает все записи WAL с момента старта сервера. Давай посмотрим на него и заодно проверим, сколько WAL создаёт массовый UPDATE!

SQL · Пример 2: смотрим счётчики pg_stat_wal и вес операции UPDATE 
-- Смотрим общую статистику работы WAL на сервере
SELECT
    wal_records,
    wal_fpi AS full_page_images,
    pg_size_pretty(wal_bytes) AS total_wal_written,
    wal_buffers_full
FROM pg_stat_wal;

-- А теперь обновляем половину таблицы и замеряем объём WAL
WITH lsn_before AS (
    SELECT pg_current_wal_lsn() AS pos
),
updated AS (
    UPDATE wal_orders
    SET amount = amount + 100
    WHERE id <= 5000
    RETURNING id
)
SELECT
    count(*) AS rows_updated,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM lsn_before))
    ) AS wal_for_update
FROM updated;
Ответ PostgreSQL
 wal_records | full_page_images | total_wal_written | wal_buffers_full
-------------+------------------+-------------------+------------------
      142810 |              612 | 48 MB             |                0
(1 row)

 rows_updated | wal_for_update
--------------+----------------
         5000 | 742 kB
(1 row)

Обрати внимание на колонку full_page_images (wal_fpi) в pg_stat_wal! Что это за «полные снимки страниц»? Когда PostgreSQL меняет какую-то 8 КБ страницу в первый раз после контрольной точки, он на всякий случай кладёт в WAL целиком всю эту страницу (8 КБ), а не только маленькую правку. Зачем? Чтобы защититься от разорванной страницы (torn page): если свет погаснет в тот момент, когда операционная система успела записать на диск только 4 КБ из 8 КБ, PostgreSQL просто возьмёт целый снимок из WAL и восстановит страницу без единой царапины!

03 Контрольные точки (Checkpoint) и живой краш-тест базы!

Если WAL-файлы будут копиться вечно, то через месяц их станет 500 гигабайт. И если сервер внезапно перезагрузится, базе придётся перечитывать и проигрывать миллионы записей за целый месяц — восстановление займёт часы!

Чтобы этого не случилось, в PostgreSQL (как и в любой видеоигре) есть сохранения — контрольные точки (Checkpoint). Каждые несколько минут (по умолчанию checkpoint_timeout = 5min или когда WAL вырастает до max_wal_size = 1GB) просыпается фоновый процесс Checkpointer и делает три вещи:

  1. Аккуратно и плавно записывает все грязные страницы из Shared Buffers в реальные файлы таблиц (Heap) и индексов на диске.
  2. Записывает в специальный служебный файл global/pg_control отметку Redo LSN: «Всё, что было до этого LSN, уже надёжно лежит в таблицах на диске».
  3. Освобождает старые 16-мегабайтные WAL-сегменты (переиспользует или удаляет их), чтобы диск не переполнился.

Смотрим текущую контрольную точку в SQL

Ты можешь прямо сейчас заглянуть в настройки контрольных точек и прочитать тот самый файл pg_control через встроенную функцию pg_control_checkpoint()!

SQL · Пример 3: проверяем настройки и вызываем CHECKPOINT вручную 
-- Смотрим главные параметры контрольных точек
SELECT name, setting, unit
FROM pg_settings
WHERE name IN (
    'checkpoint_timeout',
    'max_wal_size',
    'checkpoint_completion_target'
);

-- Принудительно делаем контрольную точку (в учебной базе!)
CHECKPOINT;

-- Читаем данные последней контрольной точки из файла pg_control
SELECT
    checkpoint_lsn,
    redo_lsn,
    redo_wal_file,
    checkpoint_time
FROM pg_control_checkpoint();
Ответ PostgreSQL

------------------------------+---------+------
 checkpoint_completion_target | 0.9     |
 checkpoint_timeout           | 300     | s
 max_wal_size                 | 1024    | MB
(3 rows)

Настоящий краш-тест в Docker Compose: «выдёргиваем вилку»!

Хватит теории — давай проверим, действительно ли WAL спасёт наши деньги при внезапной аварии! Прежде чем запускать краш-тест, посмотри в таблице, что должно случиться с двумя разными заказами, если мгновенно убить процесс PostgreSQL сигналом SIGKILL:

Тестовый заказ Состояние в момент сбоя Что должно быть после Crash Recovery
CRASH-COMMITTED-101 Выполнен COMMIT (запись уже в pg_wal, но могла ещё не попасть в файл Heap!) Выживет на 100%! PostgreSQL восстановит её из WAL.
CRASH-UNCOMMITTED-999 Открыт BEGIN, сделан INSERT, но COMMIT не успели нажать Исчезнет без следа! Незавершённые изменения никогда не видны после сбоя.

Повторяй шаги аккуратно в двух окнах терминала (или последовательно, как показано ниже):

SQL · Пример 4 (Шаг 1): создаём один подтверждённый и один незавершённый заказ 
-- Подготовка: удаляем прошлые тестовые строки, если уже запускали краш-тест
DELETE FROM wal_orders
WHERE order_code IN ('CRASH-COMMITTED-101', 'CRASH-UNCOMMITTED-999');

-- 1. Подтверждённый заказ (COMMIT ушёл в WAL на диск!)
INSERT INTO wal_orders (order_code, amount, status)
VALUES ('CRASH-COMMITTED-101', 99999.00, 'paid');

-- 2. Начинаем вторую транзакцию, вставляем строку, НО НЕ ДЕЛАЕМ COMMIT!
BEGIN;
INSERT INTO wal_orders (order_code, amount, status)
VALUES ('CRASH-UNCOMMITTED-999', 77777.00, 'draft');

-- ОСТАВЬ это окно psql открытым и перейди во второе окно терминала!
BASH · Пример 4 (Шаг 2): жёстко убиваем контейнер (SIGKILL) и смотрим логи восстановления 
# 1. Имитируем внезапное отключение питания (SIGKILL не даёт базе спокойно закрыться!)
docker compose kill -s SIGKILL pg_primary

# 2. Включаем сервер обратно
docker compose up -d pg_primary

# 3. Ждём пару секунд и читаем отчёт о Crash Recovery в логах контейнера
sleep 2
docker logs --tail=20 course_pg_primary

Посмотри на эти легендарные строчки в логах: automatic recovery in progress → redo starts at 0/4D12028 → redo done at 0/4D13480 за 0.01 секунды! Подключаемся обратно к learning_db и проверяем, что выжило:

SQL · Пример 4 (Шаг 3): проверяем сохранность данных после «отключения света» 
-- Проверяем оба наших тестовых заказа
SELECT order_code, amount, status
FROM wal_orders
WHERE order_code LIKE 'CRASH-%';
Ответ PostgreSQL
     order_code      |  amount  | status

Проблема из Раздела 01 решена блестяще! Заказ CRASH-COMMITTED-101 пережил жёсткое убийство процесса без единой потери, а незавершённый CRASH-UNCOMMITTED-999 аккуратно исчез, не оставив «мусора» в таблице. Именно так обеспечивается буква D (Durability — долговечность) из знаменитых свойств транзакций ACID.

04 UNLOGGED-таблицы, опасные настройки и реальные ошибки

Иногда в проекте есть временные данные, которые не жалко потерять при аварии: например, кеш поисковых подсказок, корзина анонимного гостя или промежуточная витрина, которую можно пересчитать за 10 секунд. Можно ли попросить PostgreSQL не тратить время на запись в WAL для такой таблицы?

Да! Для этого существуют нежурналируемые таблицы (UNLOGGED TABLE). Они работают в разы быстрее на запись, потому что вообще не пишут в pg_wal. Цена проста: если сервер упадёт (как в нашем краш-тесте с SIGKILL), при перезапуске PostgreSQL автоматически очистит такую таблицу до нуля (сделает ей TRUNCATE).

SQL · Пример 5: сравниваем объём WAL у обычной и UNLOGGED-таблицы (50 000 строк) 
-- Безопасная подготовка двух одинаковых таблиц
DROP TABLE IF EXISTS wal_regular_log, wal_fast_cache;

CREATE TABLE wal_regular_log (
    id      INT,
    payload TEXT
);

CREATE UNLOGGED TABLE wal_fast_cache (
    id      INT,
    payload TEXT
);

-- 1. Замеряем WAL для 50 000 строк в ОБЫЧНОЙ таблице
WITH p AS (SELECT pg_current_wal_lsn() AS start_lsn),
ins AS (
    INSERT INTO wal_regular_log
    SELECT g, repeat('x', 80) FROM generate_series(1, 50000) AS g
)
SELECT
    'Обычная таблица' AS table_type,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT start_lsn FROM p))) AS wal_used;

-- 2. Замеряем WAL для 50 000 строк в UNLOGGED-таблице
WITH p AS (SELECT pg_current_wal_lsn() AS start_lsn),
ins AS (
    INSERT INTO wal_fast_cache
    SELECT g, repeat('x', 80) FROM generate_series(1, 50000) AS g
)
SELECT
    'UNLOGGED-таблица' AS table_type,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT start_lsn FROM p))) AS wal_used;
Ответ PostgreSQL
   table_type    | wal_used
-----------------+----------
 Обычная таблица | 6148 kB
(1 row)

    table_type    | wal_used
------------------+----------
 UNLOGGED-таблица | 0 bytes
(1 row)

Разница колоссальная: 6148 КБ против 0 байт! Главное — никогда не путать, какие данные можно доверять UNLOGGED-таблице, а какие — нет.

✗ Как НЕ надо
CREATE UNLOGGED TABLE payments (
    id SERIAL PRIMARY KEY,
    user_id INT NOT NULL,
    amount NUMERIC(10, 2)
);

После первого же сбоя питания таблица payments станет абсолютно пустой. Плюс UNLOGGED-таблицы не попадают на реплики!

✓ Как правильно
CREATE UNLOGGED TABLE page_cache (
    cache_key TEXT PRIMARY KEY,
    html_body TEXT,
    expires_at TIMESTAMPTZ
);

Идеально для временного кеша, сессий или этапа загрузки (staging) сырых файлов, которые легко пересоздать.

Ошибки при работе с параметрами WAL и функциями LSN

У WAL есть важные параметры конфигурации — например, wal_level (сколько подробностей писать в журнал) и fsync (требовать ли от диска честного физического сохранения). Некоторые из них защищены от случайной смены «на лету». Посмотрим две реальные ошибки PostgreSQL, с которыми сталкиваются на практике:

SQL · Пример 6: две типичные ошибки при работе с WAL 
-- Ошибка А: пытаемся поменять wal_level прямо в сессии
SET wal_level = 'minimal';

-- Ошибка Б: передаём обычное число вместо формата LSN в функцию pg_walfile_name
SELECT pg_walfile_name('12345');
Ошибка PostgreSQL (запрос А)
ERROR:  parameter "wal_level" cannot be changed without restarting the server
Ошибка PostgreSQL (запрос Б)
ERROR:  invalid input syntax for type pg_lsn: "12345"
LINE 1: SELECT pg_walfile_name('12345');
                               ^

Первая ошибка напоминает: wal_level (бывает minimal, replica по умолчанию и logical для логической репликации) задаёт формат всего журнала целиком, поэтому меняется только в postgresql.conf (или через ALTER SYSTEM) с обязательным перезапуском сервера. А вторая ошибка показывает, что тип pg_lsn всегда требует строгий формат X/Y (два шестнадцатеричных числа через косую черту, например '0/4D12028').

Смертельная ловушка тюнинга: fsync = off vs synchronous_commit = off

На форумах иногда советуют: «Хочешь ускорить запись в 5 раз — выключи fsync = off!» Никогда не слушай этот вредный совет в боевом проекте. Вот в чём критическая разница:

✗ Как НЕ надо
-- В postgresql.conf:
fsync = off

При сбое питания ломается вся база целиком — повреждаются системные таблицы, индексы и Heap. Сервер может просто не запуститься!

✓ Как правильно
-- Внутри некритичной транзакции:
BEGIN;
SET LOCAL synchronous_commit = off;
INSERT INTO click_logs VALUES (1);
COMMIT;

База остаётся на 100% целой! В худшем случае при аварии пропадут последние ~0.5 сек кликов, но сама БД никогда не повредится.

Железное правило продакшена: Параметр fsync = on и full_page_writes = on — это ремень безопасности и подушка безопасности базы данных. Отключать их допустимо только на одноразовых тестовых стендах, которые ты готов удалить и пересоздать с нуля в любой момент.
Совет на будущее: По умолчанию в PostgreSQL 16 стоит wal_level = replica. Это значит, что твой журнал предзаписи уже готов не только к восстановлению после сбоя, но и к двум суперсилам промышленных баз — потоковой репликации (отправка WAL в реальном времени на резервный сервер) и PITR (восстановлению базы на любую конкретную секунду до случайного DROP TABLE!).

05 Шпаргалка по WAL и мини-практикум

Перед практикой пробеги глазами короткий словарик урока — эти 5 терминов спрашивают на каждом втором собеседовании по PostgreSQL:

Шпаргалка перед практикой: 5 главных понятий WAL
  • WAL (Write-Ahead Log) — последовательный журнал изменений на диске (pg_wal/, сегменты по 16 МБ), куда запись попадает строго до подтверждения COMMIT.
  • LSN (Log Sequence Number) — «километровый столбик» в журнале (вида 0/4D12028), позволяющий точно измерить объём сгенерированного WAL через pg_wal_lsn_diff().
  • CHECKPOINT — контрольная точка, когда все грязные страницы из Shared Buffers сбрасываются в файлы таблиц, а в pg_control фиксируется новый redo_lsn.
  • Crash Recovery — автоматическое проигрывание WAL от последнего redo_lsn после внезапного сбоя питания.
  • UNLOGGED TABLE vs fsync — UNLOGGED безопасно ускоряет временный кеш (очищается при сбое), а fsync = off ломает всю базу и запрещён в продакшене.

Выполни 4 автономных задания в базе learning_db. Каждое задание само готовит нужные данные и не зависит от предыдущих.

Задание 1 (Базовый уровень). Измерь «след» в WAL от вставки 5 000 строк

Создай таблицу task1_wal_events(id SERIAL PRIMARY KEY, message TEXT) (с безопасным DROP TABLE IF EXISTS). Вставь в неё 5 000 строк и одним запросом выведи: LSN до вставки, LSN после вставки, имя текущего WAL-файла и размер сгенерированного WAL в человекочитаемом виде (pg_size_pretty).

Показать решение
SQL 
DROP TABLE IF EXISTS task1_wal_events;

CREATE TABLE task1_wal_events (
    id      SERIAL PRIMARY KEY,
    message TEXT NOT NULL
);

WITH lsn_before AS (
    SELECT pg_current_wal_lsn() AS pos
),
ins AS (
    INSERT INTO task1_wal_events (message)
    SELECT 'Событие #' || g
    FROM generate_series(1, 5000) AS g
    RETURNING id
)
SELECT
    count(*) AS inserted_rows,
    (SELECT pos FROM lsn_before) AS lsn_start,
    pg_current_wal_lsn() AS lsn_end,
    pg_walfile_name(pg_current_wal_lsn()) AS active_wal_file,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM lsn_before))
    ) AS wal_size
FROM ins;
Задание 2 (Средний уровень). Аудит настроек надёжности сервера

Напиши два SQL-запроса для быстрого аудита твоего PostgreSQL 16: первый должен вывести значения и контекст (context — нужен ли рестарт для изменения) параметров wal_level, fsync, full_page_writes, synchronous_commit и max_wal_size из pg_settings; второй — показать redo_lsn и время последней контрольной точки из pg_control_checkpoint().

Показать решение
SQL 
-- 1. Проверяем ключевые параметры WAL и способ их изменения (context)
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN (
    'wal_level',
    'fsync',
    'full_page_writes',
    'synchronous_commit',
    'max_wal_size'
)
ORDER BY name;

-- 2. Смотрим отметку последней контрольной точки
SELECT
    checkpoint_lsn,
    redo_lsn,
    redo_wal_file,
    checkpoint_time
FROM pg_control_checkpoint();
Задание 3 (Продвинутый уровень). Битва таблиц: Обычная vs UNLOGGED

Создай две одинаковые таблицы task3_logged (обычную) и task3_unlogged (UNLOGGED) с колонками (id INT, body TEXT). Вставь в каждую по 20 000 строк текста длиной 100 символов (repeat('a', 100)) и проверь через pg_wal_lsn_diff(), во сколько раз (или на сколько килобайт) меньше WAL записалось при вставке в UNLOGGED-таблицу.

Показать решение
SQL 
DROP TABLE IF EXISTS task3_logged, task3_unlogged;

CREATE TABLE task3_logged (id INT, body TEXT);
CREATE UNLOGGED TABLE task3_unlogged (id INT, body TEXT);

-- Замер №1: обычная таблица
WITH s AS (SELECT pg_current_wal_lsn() AS pos),
ins AS (
    INSERT INTO task3_logged
    SELECT g, repeat('a', 100) FROM generate_series(1, 20000) AS g
)
SELECT
    'task3_logged' AS tbl,
    pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s)) AS wal_bytes,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s))) AS wal_pretty;

-- Замер №2: UNLOGGED-таблица
WITH s AS (SELECT pg_current_wal_lsn() AS pos),
ins AS (
    INSERT INTO task3_unlogged
    SELECT g, repeat('a', 100) FROM generate_series(1, 20000) AS g
)
SELECT
    'task3_unlogged' AS tbl,
    pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s)) AS wal_bytes,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s))) AS wal_pretty;
Задание 4 (Боевой сценарий). Поймай Full Page Image (FPI) после CHECKPOINT

Докажи на практике работу защиты от «разорванных страниц» (full_page_writes): создай таблицу task4_fpi(id INT, val TEXT) и вставь 1 строку (1, 'v1'). Сделай CHECKPOINT;, затем выполни первый UPDATE этой строки и замерь объём WAL (он будет около 8 КБ из-за снимка всей страницы!). Сразу после этого (без нового чекпоинта) выполни второй UPDATE той же строки и снова замерь WAL — он окажется в десятки раз меньше (всего пара сотен байт!).

Показать решение
SQL 
DROP TABLE IF EXISTS task4_fpi;
CREATE TABLE task4_fpi (id INT PRIMARY KEY, val TEXT);
INSERT INTO task4_fpi VALUES (1, 'v1');

-- Делаем контрольную точку, чтобы следующая правка страницы вызвала Full Page Image
CHECKPOINT;

-- 1-й UPDATE сразу после CHECKPOINT (попадёт полный снимок страницы ~8 КБ!)
WITH s AS (SELECT pg_current_wal_lsn() AS pos),
u AS (UPDATE task4_fpi SET val = 'v2' WHERE id = 1)
SELECT
    '1-й UPDATE после CHECKPOINT (с FPI)' AS step,
    pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s)) AS wal_bytes;

-- 2-й UPDATE той же страницы (страница уже в WAL, пишется только маленькая дельта!)
WITH s AS (SELECT pg_current_wal_lsn() AS pos),
u AS (UPDATE task4_fpi SET val = 'v3' WHERE id = 1)
SELECT
    '2-й UPDATE без CHECKPOINT (без FPI)' AS step,
    pg_wal_lsn_diff(pg_current_wal_lsn(), (SELECT pos FROM s)) AS wal_bytes;
