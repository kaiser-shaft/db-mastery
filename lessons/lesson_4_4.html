Архитектурная дуэль: PostgreSQL vs MySQL (движок InnoDB)

Главное в этом уроке
  • Поймёшь фундаментальную разницу в хранении данных на диске: куча (Heap) в PostgreSQL против кластерного индекса (Clustered Index) в MySQL/InnoDB.
  • Сравнишь два подхода к многоверсионности: мёртвые строки, VACUUM и HOT-обновления в PostgreSQL против перезаписи на месте и Undo Log в InnoDB.
  • Разберёшь, почему в MySQL по умолчанию REPEATABLE READ и откуда берутся Gap Locks, а в PostgreSQL их нет — зато есть транзакционный DDL!
  • Проверишь уникальные механики PostgreSQL на практике в learning_db и получишь понятную шпаргалку: какую СУБД выбирать под разные проекты и как не споткнуться на собеседовании.

01 Раунд 1: Куча (Heap) против Кластерного индекса

Если спросить двух разработчиков «PostgreSQL или MySQL?», спор может длиться до утра. Но на самом деле обе базы великолепны — просто они устроены по-разному внутри. И главное отличие начинается прямо с того, как строки лежат на диске.

Представь две большие библиотеки:

  • Библиотека PostgreSQL — «Свободные полки» (Heap / Куча). Когда привозят новую книгу, библиотекарь ставит её на любую свободную полку, не тратя время на перестановку шкафов. А в каждом бумажном каталоге (и по ID, и по автору) записан точный адрес полки — тот самый ctid из урока 4.2! Ищешь по автору — сразу получаешь адрес полки и идёшь прямо туда за один шаг.
  • Библиотека MySQL/InnoDB — «Строгий порядок по номеру» (Clustered Index / Кластерный индекс). Все книги на стеллажах физически расставлены строго по возрастанию номера PRIMARY KEY — сама таблица и есть огромное дерево B-Tree по первичному ключу! Поиск по id здесь молниеносный: нашёл узел — и вся строка уже в руках. Но зато во вторичном каталоге (например, по email) записан не адрес полки, а номер id! Поэтому поиск по email делает двойной прыжок: сначала ищет id во вторичном индексе, а потом идёт за самой строкой в главный индекс по id.
Почему это важно на практике? В InnoDB случайный PRIMARY KEY (например, обычный UUID v4) заставляет базу постоянно расталкивать книги в середине плотно набитых полок — страницы расщепляются (Page Split), и вставка замедляется. В PostgreSQL вставка в Heap всегда дописывается в свободное место без перетряхивания всей таблицы — зато поиск по id требует одного шага из индекса в Heap.

Проверяем Heap-хранение на практике в learning_db

Давай убедимся, что PostgreSQL действительно кладёт строки в порядке вставки (в кучу), а не пересортировывает их физически по PRIMARY KEY, как сделал бы InnoDB.

SQL · Пример 1: Вставка id вразнобой и осмотр физического адреса ctid 
DROP TABLE IF EXISTS duel_users;

CREATE TABLE duel_users (
    id    INT PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,
    name  TEXT NOT NULL
);

-- Вставляем пользователей с id НЕ по порядку!
INSERT INTO duel_users (id, email, name) VALUES
    (500, 'alice@example.com', 'Алиса'),
    (10,  'bob@example.com',   'Боб'),
    (250, 'charlie@example.com', 'Чарли');

-- Смотрим, как строки РЕАЛЬНО лежат на странице диска (без ORDER BY)
SELECT ctid, id, email, name
FROM duel_users;
Ответ PostgreSQL
 ctid  | id  |        email        | name
-------+-----+---------------------+-------
 (0,1) | 500 | alice@example.com   | Алиса
 (0,2) |  10 | bob@example.com     | Боб
 (0,3) | 250 | charlie@example.com | Чарли
(3 rows)

Смотри на ctid: строка id = 500 лежит первой на слоте (0,1), id = 10 — второй на (0,2), а id = 250 — третьей на (0,3). В MySQL/InnoDB они бы физически выстроились в порядке 10 → 250 → 500 прямо внутри дерева первичного ключа!

02 Раунд 2: MVCC — VACUUM и HOT против Undo Log

Обе базы поддерживают MVCC (читатели не блокируют писателей), но делают это с точностью до наоборот! Представь снова тетрадь и ручку:

  • PostgreSQL (Append-Only + VACUUM): как ты уже знаешь из урока 4.2, при UPDATE Postgres оставляет старую версию прямо на странице таблицы, а рядом пишет новую. Плюс: ROLLBACK происходит мгновенно (достаточно поставить галочку «транзакция отменена», ничего переписывать не надо!). Минус: нужен VACUUM, а если у строки сменился адрес ctid, придётся обновить ссылки во всех индексах (если не сработал секретный приём HOT!).
  • MySQL / InnoDB (In-Place + Undo Log): при UPDATE InnoDB перезаписывает строку прямо на старом месте! А чтобы старые транзакции всё ещё могли видеть прежнее значение (MVCC), InnoDB выносит инструкцию «как вернуть прошлое значение» в отдельный блокнот — журнал отката (Undo Log). Плюс: в самой таблице нет мёртвых строк и не нужен VACUUM, а индексы не надо обновлять, если не менялось индексированное поле. Минус: если транзакция обновила миллион строк, а потом сделала ROLLBACK, InnoDB придётся долго и упорно переписывать все миллион строк обратно по Undo Log!

Секретное оружие PostgreSQL: HOT-обновления (Heap-Only Tuples)

Погоди: неужели в PostgreSQL при каждом UPDATE счётчика просмотров приходится переписывать все 5 индексов таблицы только потому, что строка переехала на новый ctid? Раньше так и было, и это считалось слабостью Postgres перед InnoDB. Но инженеры PostgreSQL придумали гениальную оптимизацию — HOT (Heap-Only Tuple)!

Если ты обновляешь столбец, по которому нет индекса, и на той же 8-килобайтной странице таблицы есть чуть-чуть свободного места, PostgreSQL кладёт новую версию на ту же страницу и ставит короткую стрелочку от старой версии к новой. Индексы вообще не трогаются! Давай увидим работу HOT вживую в learning_db.

SQL · Пример 2: Наблюдаем HOT-обновления в pg_stat_user_tables 
DROP TABLE IF EXISTS duel_products;

CREATE TABLE duel_products (
    id    SERIAL PRIMARY KEY,
    sku   TEXT NOT NULL,
    views INT NOT NULL DEFAULT 0
);

-- Индексируем ТОЛЬКО sku. Поле views НЕ индексировано!
CREATE INDEX idx_duel_products_sku ON duel_products (sku);

INSERT INTO duel_products (sku, views) VALUES ('SWORD-01', 0);

-- 1. Трижды обновляем НЕиндексированное поле views -> сработает HOT!
UPDATE duel_products SET views = views + 1 WHERE id = 1;
UPDATE duel_products SET views = views + 1 WHERE id = 1;
UPDATE duel_products SET views = views + 1 WHERE id = 1;

-- 2. Один раз обновляем ИНДЕКСИРОВАННОЕ поле sku -> HOT невозможен!
UPDATE duel_products SET sku = 'SWORD-02' WHERE id = 1;

-- Сбрасываем буфер статистики, чтобы увидеть свежие цифры немедленно
SELECT pg_stat_force_next_flush();

SELECT
    relname,
    n_tup_upd     AS total_updates,
    n_tup_hot_upd AS hot_updates
FROM pg_stat_user_tables
WHERE relname = 'duel_products';
Ответ PostgreSQL
    relname    | total_updates | hot_updates
---------------+---------------+-------------
 duel_products |             4 |           3
(1 row)

Точно в цель! Из 4 обновлений ровно 3 прошли как HOT (индексы даже не шелохнулись!), и только 4-е обновление столбца sku потребовало залезть в индекс. Вот почему в PostgreSQL так вредно создавать лишние индексы на часто меняемые колонки вроде updated_at или views!

✗ Как НЕ надо
-- Индекс «на всякий случай»
-- на часто меняемый счётчик:
CREATE INDEX idx_views
ON duel_products (views);

Полностью отключает HOT-обновления при каждом +1 к просмотрам! Нагрузка на диск и раздувание индексов резко растут.

✓ Как правильно
-- Индексируем только поля
-- поиска; для горячих таблиц
-- оставляем запас места:
ALTER TABLE duel_products
SET (fillfactor = 80);

fillfactor = 80 оставляет 20% пустого места на каждой странице специально под молниеносные HOT-обновления.

Проверяем молниеносный ROLLBACK в PostgreSQL

Давай проверим ещё одно преимущество архитектуры PostgreSQL: обновим сразу 20 000 строк внутри транзакции, а потом передумаем и сделаем ROLLBACK. Засеки время командой \timing on в psql!

SQL · Пример 3: Мгновенный откат массового UPDATE в PostgreSQL 
DROP TABLE IF EXISTS duel_rollback_test;

CREATE TABLE duel_rollback_test (
    id  INT PRIMARY KEY,
    val INT NOT NULL
);

INSERT INTO duel_rollback_test (id, val)
SELECT g, 0 FROM generate_series(1, 20000) AS g;

-- Включаем таймер в psql (работает в интерактивной консоли psql)
\timing on

BEGIN;
UPDATE duel_rollback_test SET val = 999;
-- Ой, передумали! Откатываем все 20 000 строк:
ROLLBACK;

\timing off
Ответ PostgreSQL
BEGIN
Time: 0.214 ms
UPDATE 20000
Time: 34.812 ms
ROLLBACK
Time: 0.195 ms

Посмотри на последнюю строчку: UPDATE 20000 занял ~35 мс, а ROLLBACK — всего 0.195 миллисекунды! PostgreSQL вообще не трогал эти 20 000 строк на диске — он просто пометил транзакцию как отменённую (а мусор потом тихо уберёт Autovacuum). В MySQL/InnoDB откат огромного UPDATE может длиться дольше, чем сам UPDATE!

03 Раунд 3: Gap Locks и суперсила транзакционного DDL

Теперь переходим к двум самым неожиданным отличиям, на которых регулярно «горят» разработчики, переезжающие с MySQL на PostgreSQL (или обратно).

Отличие А: Уровень по умолчанию и Gap Locks (Замки на пустоту)

В PostgreSQL уровень изоляции по умолчанию — READ COMMITTED. В MySQL/InnoDB по умолчанию стоит REPEATABLE READ.

Чтобы на уровне REPEATABLE READ защищаться от фантомов при блокирующих запросах, InnoDB использует блокировки промежутков (Gap Locks). Представь парковку, где стоят машины на местах 10 и 30, а между ними — 19 пустых мест. Если в InnoDB выполнить SELECT ... WHERE id BETWEEN 10 AND 30 FOR UPDATE, база натянет красную ленту на все пустые места между 10 и 30: никто не сможет припарковать туда новую машину id = 20!

А вот в PostgreSQL Gap Locks не существует вообще! Он блокирует только те реальные строки, которые уже есть в таблице. Давай проверим это в двух терминалах psql!

SQL · Пример 4: Убеждаемся, что в PostgreSQL нет Gap Locks 
-- Подготовка (в любом терминале): создаём «дырку» между id = 10 и id = 30
DROP TABLE IF EXISTS duel_parking;
CREATE TABLE duel_parking (
    id   INT PRIMARY KEY,
    car  TEXT NOT NULL
);
INSERT INTO duel_parking VALUES (10, 'Седан'), (30, 'Джип');

-- [ШАГ 1 — ТЕРМИНАЛ 1] Блокируем весь диапазон от 10 до 30
BEGIN;
SELECT * FROM duel_parking
WHERE id BETWEEN 10 AND 30
FOR UPDATE;
-- Строки 10 и 30 заблокированы. НЕ закрываем транзакцию!

-- [ШАГ 2 — ТЕРМИНАЛ 2] Вставляем новую машину прямо в «дырку» (id = 20)!
BEGIN;
INSERT INTO duel_parking VALUES (20, 'Спорткар');
COMMIT;
-- В PostgreSQL вставится МГНОВЕННО! (В MySQL/InnoDB здесь было бы зависание на Gap Lock!)

-- [ШАГ 3 — ТЕРМИНАЛ 1] Закрываем транзакцию и смотрим таблицу
COMMIT;
SELECT * FROM duel_parking ORDER BY id;
Ответ PostgreSQL
 id |   car
----+----------
 10 | Седан
 20 | Спорткар
 30 | Джип
(3 rows)

Мгновенная вставка без единого тормоза и без неожиданных Deadlock на пустых промежутках!

Отличие Б: Транзакционный DDL — машина времени для миграций

Представь, что ты обновляешь базу работающего сайта: нужно добавить колонку, переименовать таблицу и поменять тип поля. Что случится, если 3-й шаг упадёт с ошибкой?

  • В MySQL: любая команда изменения структуры (CREATE TABLE, ALTER TABLE, DROP TABLE — это называется DDL) автоматически делает неявный COMMIT! Если миграция сломалась посередине, база застрянет в полуразрушенном состоянии — чинить придётся вручную!
  • В PostgreSQL: почти весь DDL — полностью транзакционный! Ты можешь внутри BEGIN удалить таблицу, перекроить колонки, передумать, нажать ROLLBACK — и таблица вернётся целой и невредимой, будто ничего и не было!
SQL · Пример 5: Машина времени — откатываем DROP TABLE через ROLLBACK 
-- Подготовка: проверяем, что таблица duel_parking на месте
SELECT count(*) AS before_count FROM duel_parking;

-- Запускаем «опасную» миграцию внутри транзакции
BEGIN;

ALTER TABLE duel_parking ADD COLUMN color TEXT DEFAULT 'синий';
DROP TABLE duel_parking;

-- ОЙ! Удалили таблицу целиком! Но транзакция ещё открыта -> жмём ROLLBACK!
ROLLBACK;

-- Проверяем: таблица и все 3 машины чудесным образом спасены!
SELECT * FROM duel_parking ORDER BY id;
Ответ PostgreSQL
 before_count
--------------
            3
(1 row)

BEGIN
ALTER TABLE
DROP TABLE
ROLLBACK

 id |   car
----+----------
 10 | Седан
 20 | Спорткар
 30 | Джип
(3 rows)

Ловушка при переезде из MySQL: ошибка синтаксиса

Если разработчик по привычке из MySQL напишет в PostgreSQL обратные кавычки ` или AUTO_INCREMENT, PostgreSQL сразу вежливо напомнит о стандарте SQL:

SQL · Попытка запустить MySQL-диалект в PostgreSQL 
CREATE TABLE bad_mysql_style (
    id INT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(100)
);
Ошибка PostgreSQL
ERROR:  syntax error at or near "AUTO_INCREMENT"
LINE 2:     id INT AUTO_INCREMENT PRIMARY KEY,
                   ^
✗ Как НЕ надо: тащить привычки MySQL в PostgreSQL
-- В PostgreSQL нет AUTO_INCREMENT, обратных кавычек `table` и ON DUPLICATE KEY:
INSERT INTO `duel_users` (`id`, `email`, `name`)
VALUES (10, 'bob@example.com', 'Боб 2.0')
ON DUPLICATE KEY UPDATE `name` = 'Боб 2.0';

Этот запрос завершится синтаксической ошибкой. Кроме того, в PostgreSQL для строк подходят TEXT (не нужно выдумывать VARCHAR(255) без причины).

✓ Как правильно: идиоматичный PostgreSQL (IDENTITY + ON CONFLICT + RETURNING)
-- Стандарт SQL: GENERATED ALWAYS AS IDENTITY, ON CONFLICT и мощнейший RETURNING:
INSERT INTO duel_users (id, email, name)
VALUES (10, 'bob@example.com', 'Боб 2.0')
ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name
RETURNING id, name;

RETURNING сразу возвращает изменённую строку за один сетевой запрос — ещё одна фишка PostgreSQL, которую обожают бэкенд-разработчики!

Бонус-эксперимент: как PostgreSQL ускоряет чтение без захода в Heap

Помнишь, в Раунде 1 мы говорили, что PostgreSQL приходится прыгать из индекса в таблицу Heap? Но Postgres умеет делать трюк Index-Only Scan: если все нужные столбцы есть в индексе, и VACUUM ранее отметил страницу в карте видимости (Visibility Map) как полностью видимую для всех транзакций, PostgreSQL вообще не заходит в таблицу Heap (Heap Fetches: 0)! Проверим на EXPLAIN (ANALYZE, BUFFERS):

SQL · Пример 6: Index-Only Scan с нулём обращений к таблице Heap 
DROP TABLE IF EXISTS duel_fast_read;

CREATE TABLE duel_fast_read (
    id    INT PRIMARY KEY,
    email TEXT NOT NULL
);

INSERT INTO duel_fast_read (id, email)
SELECT g, 'user' || g || '@example.com'
FROM generate_series(1, 50000) AS g;

-- VACUUM заполняет Visibility Map, разрешая Index-Only Scan без походов в Heap!
VACUUM ANALYZE duel_fast_read;

-- Выбираем ТОЛЬКО id (он уже есть в индексе Primary Key!)
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM duel_fast_read WHERE id BETWEEN 1000 AND 1050;
Ответ PostgreSQL (EXPLAIN ANALYZE)
                                                               QUERY PLAN
----------------------------------------------------------------------------------------------------------------------------------------
 Index Only Scan using duel_fast_read_pkey on duel_fast_read  (cost=0.29..5.19 rows=51 width=4) (actual time=0.028..0.041 rows=51 loops=1)
   Index Cond: ((id >= 1000) AND (id <= 1050))
   Heap Fetches: 0
   Buffers: shared hit=3
 Planning Time: 0.142 ms
 Execution Time: 0.068 ms
(6 rows)

Посмотри на строчку Heap Fetches: 0 и время 0.068 миллисекунды! Связка «индекс + VACUUM + Visibility Map» позволила PostgreSQL ответить на запрос, даже не открывая саму таблицу.

04 Финальный счёт: сводная таблица и как выбрать СУБД

В архитектурной дуэли нет «плохого» и «хорошего» бойца — есть разные инструменты под разные задачи. Сведём всё, что мы разобрали за весь Модуль 4, в одну чёткую таблицу для памяти и собеседований:

Критерий PostgreSQL 16 MySQL 8 (движок InnoDB)
Хранение таблицы Heap (Куча): строки лежат в свободном месте, индексы хранят ctid. Clustered Index: таблица физически отсортирована в B-Tree по PRIMARY KEY.
Поиск по PK vs вторичному индексу Вторичный индекс идёт сразу в Heap (1 шаг). Поиск по PK идеален (0 лишних шагов); вторичный индекс делает 2 шага (через PK).
Механика MVCC Старые версии лежат в таблице (xmin/xmax) + Autovacuum + HOT. Перезапись на месте + старые версии в отдельном Undo Log + Purge Thread.
Скорость ROLLBACK Мгновенная (O(1) — пометка статуса транзакции). Зависит от объёма: нужно физически откатывать изменения по Undo Log.
Изоляция по умолчанию READ COMMITTED REPEATABLE READ
Gap Locks (замки на дырки) Нет (меньше неожиданных Deadlocks на вставках). Есть на REPEATABLE READ (частый источник Deadlocks).
Транзакционный DDL Да (можно откатить ALTER и DROP TABLE!). Нет (DDL вызывает неявный COMMIT).
Модель подключений Процесс ОС на каждое подключение (в проде нужен пулер вроде PgBouncer). Лёгкий поток (Thread) на подключение — проще терпит тысячи прямых коннектов.
Сильные фишки JSONB + GIN, геоданные (PostGIS), векторы (pgvector), сложные аналитические запросы, расширения. Высокая скорость простых чтений по PK, нет проблемы Table Bloat / XID Wraparound, простая репликация.
Как выбирать в реальных проектах?
• Выбирай PostgreSQL как стандарт по умолчанию для новых проектов: финтех, аналитика, сложные связи, JSONB, поиск, геоданные, AI-векторы и безопасные миграции.
• Выбирай MySQL (InnoDB), если у команды уже есть сильная экспертиза в MySQL, нагрузка — это гигантский поток простых чтений/обновлений по PRIMARY KEY (например, профиль пользователя по user_id), и не хочется настраивать тонкий тюнинг Autovacuum.
Главное ограничение PostgreSQL, о котором спросят на собеседовании: Не открывай 5 000 прямых соединений от микросервисов к PostgreSQL! Поскольку в Postgres каждое подключение — это отдельный процесс ОС (а не лёгкий поток, как в MySQL), тысячи соединений быстро съедят всю оперативную память и загрузят процессор. Решение стандартное: поставь перед PostgreSQL пулер соединений (PgBouncer или Odyssey).

05 Шпаргалка урока перед практикой

Пять главных отличий дуэли, которые стоит держать в голове перед практикумом:

  • Heap vs Clustered Index: PostgreSQL складывает строки в кучу (поиск по любому индексу идёт через ctid), а MySQL/InnoDB физически сортирует таблицу в дереве по PRIMARY KEY.
  • MVCC + HOT vs Undo Log: PostgreSQL держит старые версии в таблице (мгновенный ROLLBACK, уборка VACUUM, ускорение HOT для неиндексированных полей), а InnoDB правит на месте и ведёт Undo Log.
  • Нет Gap Locks: в отличие от MySQL на REPEATABLE READ, PostgreSQL не блокирует пустые промежутки между строками при FOR UPDATE.
  • Транзакционный DDL: в PostgreSQL можно обернуть ALTER TABLE и даже DROP TABLE в BEGIN ... ROLLBACK; в MySQL любой DDL делает неявный COMMIT.
  • Index-Only Scan: после VACUUM (заполнения Visibility Map) PostgreSQL может отвечать прямо из индекса с Heap Fetches: 0.

Показать решение

);

Задание 4 (Две сессии). Тест на отсутствие Gap Locks + Index-Only Scan

Создай таблицу task4_slots (slot_no INT PRIMARY KEY, info TEXT) и вставь (100, 'занято') и (200, 'занято'). В Терминале 1 открой транзакцию и заблокируй диапазон WHERE slot_no BETWEEN 100 AND 200 FOR UPDATE. Не закрывая Терминал 1, в Терминале 2 вставь строку (150, 'успешно без Gap Lock') и закоммить её — убедись, что она не зависла! Затем закрой Терминал 1, выполни VACUUM ANALYZE task4_slots; и с помощью EXPLAIN ANALYZE SELECT slot_no FROM task4_slots WHERE slot_no = 150; проверь план запроса.

Показать решение
SQL · Решение задания 4 (Терминал 1 и Терминал 2) 
-- Подготовка (в любом терминале)
DROP TABLE IF EXISTS task4_slots;
CREATE TABLE task4_slots (
    slot_no INT PRIMARY KEY,
    info    TEXT NOT NULL
);
INSERT INTO task4_slots VALUES (100, 'занято'), (200, 'занято');

-- [ШАГ 1 — ТЕРМИНАЛ 1] Блокируем диапазон 100..200
BEGIN;
SELECT * FROM task4_slots
WHERE slot_no BETWEEN 100 AND 200
FOR UPDATE;

-- [ШАГ 2 — ТЕРМИНАЛ 2] Вставляем в пустой промежуток (slot_no = 150)
BEGIN;
INSERT INTO task4_slots VALUES (150, 'успешно без Gap Lock');
COMMIT;
-- Вставка прошла мгновенно — Gap Locks в PostgreSQL нет!

-- [ШАГ 3 — ТЕРМИНАЛ 1] Закрываем транзакцию и проверяем Index-Only Scan
COMMIT;
VACUUM ANALYZE task4_slots;

-- На маленькой таблице из 3 строк планировщик может выбрать Seq Scan,
-- поэтому для демонстрации Index-Only Scan на 3 строках временно подскажем:
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS)
SELECT slot_no FROM task4_slots WHERE slot_no = 150;
RESET enable_seqscan;
