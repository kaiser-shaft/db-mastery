Индексы: устройство B-Tree, составные индексы, ловушки, GIN и BRIN

Главное в этом уроке

  • Освоишь составные индексы, правило левого префикса и порядок колонок «равенство — сначала, диапазон — потом».
  • Научишься замечать 5 типичных ловушек, из-за которых PostgreSQL игнорирует индекс, и исправлять их с помощью функциональных и частичных индексов.
  • Разберёшься, когда обычный B-Tree не подходит и пора доставать спецтехнику: GIN (для массивов и JSONB) и сверхкомпактный BRIN (для гигантских таблиц логов).

01 Зачем нужны индексы и как устроен B-Tree

В прошлом уроке (3.1) ты узнал, что таблица в PostgreSQL — это не аккуратный алфавитный список, а куча страниц по 8 КБ (Heap), куда строки складываются вперемешку. Представь себе огромную энциклопедию на 1000 страниц, в которой статьи про животных, космос и компьютеры напечатаны в случайном порядке — просто как их приносили авторы.

Если тебе нужно найти статью про «Снежного барса», а оглавления и указателя нет, остаётся только одно: листать книгу с 1-й страницы до 1000-й. В мире баз данных такое чтение «от корки до корки» называется последовательным сканированием (Sequential Scan или Seq Scan). Для таблицы на 50 строк это мгновенно. А для таблицы на 10 миллионов заказов — катастрофа.

Теперь представь, что в конце энциклопедии есть алфавитный указатель, а ещё лучше — многоуровневый каталог в библиотеке: сначала выбираешь шкаф «А–М» или «Н–Я», затем ящик «С–Т», а в ящике находишь карточку: Снежный барс → страница 412, абзац 3. Тебе хватило трёх шагов вместо тысячи!

Именно так работает индекс по умолчанию в PostgreSQL — B-Tree (Balanced Tree, сбалансированное дерево). Это отдельный файл рядом с таблицей, который тоже состоит из страниц по 8 КБ, но внутри ключи строго отсортированы:

  • Корневая страница (Root) — самый верхний «указатель на шкафы». С него всегда начинается поиск.
  • Промежуточные страницы (Branch / Internal) — «ящики каталога», направляют поиск влево или вправо по диапазонам значений.
  • Листовые страницы (Leaf) — самый нижний уровень, где лежат сами отсортированные значения и точный адрес строки в куче Heap — ctid (номер страницы и номер слота). Листья связаны между собой в обе стороны, поэтому диапазоны вроде BETWEEN 100 AND 200 и сортировка ORDER BY читаются одним плавным проходом!
Магия высоты дерева: В одну страницу B-Tree (8 КБ) помещаются сотни ключей. Поэтому даже для таблицы на 10 миллионов строк высота дерева обычно равна всего 3–4 уровням! Всего 4 чтения страниц вместо десятков тысяч.

Практика 1: проверяем B-Tree вживую на 100 000 заказах

Хватит теории — давай почувствуем разницу руками в нашей базе learning_db. Создадим таблицу интернет-магазина shop_orders на 100 000 строк и найдём один конкретный заказ по его номеру order_code.

Этап эксперимента Что делает PostgreSQL Ожидаемый эффект
Было (без индекса) Seq Scan — читает все ~1 200 страниц таблицы подряд Десятки миллисекунд, нагрузка на CPU и диск
Стало (с B-Tree) Index Scan — спускается по 3 страницам дерева + 1 страница Heap Менее 0.1 мс — ускорение в сотни раз!
SQL · Подготовка данных (learning_db) 
-- Безопасный перезапуск: удаляем старую таблицу, если она уже есть
DROP TABLE IF EXISTS shop_orders;

CREATE TABLE shop_orders (
    id           BIGSERIAL PRIMARY KEY,
    order_code   TEXT NOT NULL,
    customer_id  INT NOT NULL,
    email        TEXT NOT NULL,
    status       TEXT NOT NULL,
    total_price  NUMERIC(10, 2) NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL
);

-- Генерируем 100 000 реалистичных заказов за пару секунд
INSERT INTO shop_orders (order_code, customer_id, email, status, total_price, created_at)
SELECT
    'ORD-' || LPAD(g::TEXT, 6, '0'),
    (g % 5000) + 1,
    'User' || ((g % 5000) + 1) || '@Example.com',
    CASE
        WHEN g % 20 = 0 THEN 'pending'    -- 5% ожидают оплаты
        WHEN g % 10 = 1 THEN 'cancelled'  -- 10% отменены
        ELSE 'paid'                       -- 85% оплачены
    END,
    ROUND((500 + (RANDOM() * 45000))::NUMERIC, 2),
    TIMESTAMPTZ '2026-01-01 00:00:00+05' + (g * INTERVAL '2 minutes')
FROM generate_series(1, 100000) AS g;

-- Обязательно обновляем статистику таблицы для планировщика запросов
ANALYZE shop_orders;

Теперь выполним поиск заказа ORD-077777 сначала без индекса, а потом создадим B-Tree и повторим. Команду EXPLAIN ANALYZE мы подробно разберём в следующем уроке (3.3), а сейчас смотри только на две строки: название способа чтения и Execution Time.

SQL · Поиск БЕЗ индекса vs С индексом B-Tree 
-- 1. Ищем заказ без индекса на колонке order_code
EXPLAIN ANALYZE
SELECT id, customer_id, total_price
FROM shop_orders
WHERE order_code = 'ORD-077777';

-- 2. Создаём B-Tree индекс (B-Tree используется по умолчанию)
CREATE INDEX idx_orders_code ON shop_orders (order_code);

-- 3. Повторяем точно такой же запрос
EXPLAIN ANALYZE
SELECT id, customer_id, total_price
FROM shop_orders
WHERE order_code = 'ORD-077777';
Ответ PostgreSQL (сравнение до и после)
-- ДО индекса:
Seq Scan on shop_orders  (cost=0.00..2684.00 rows=1 width=20)
                         (actual time=8.412..14.835 rows=1 loops=1)
  Filter: (order_code = 'ORD-077777'::text)
  Rows Removed by Filter: 99999
Execution Time: 14.872 ms

-- ПОСЛЕ создания idx_orders_code:
Index Scan using idx_orders_code on shop_orders  (cost=0.42..8.44 rows=1 width=20)
                                                 (actual time=0.041..0.043 rows=1 loops=1)
  Index Cond: (order_code = 'ORD-077777'::text)
Execution Time: 0.068 ms

Посмотри на результат: проблема из начала раздела решена радикально! Раньше PostgreSQL пришлось прочитать и выбросить в корзину 99 999 лишних строк за 14.87 мс. После создания B-Tree он провалился по дереву за 0.068 мс — больше чем в 200 раз быстрее.

Бесплатных индексов не бывает! Нельзя навешивать индекс «на всякий случай на каждую колонку». Каждый индекс занимает место на диске (и в Shared Buffers), а главное — замедляет запись (INSERT, UPDATE, DELETE). Ведь каждый раз, добавляя новую статью в энциклопедию, редактор обязан вручную вписать её во все алфавитные указатели.

02 Составные индексы и правило левого префикса

А что, если пользователь в магазине почти всегда фильтрует заказы сразу по двум полям — например, по клиенту и по цене? Можно создать один общий индекс сразу на две колонки — составной индекс (Composite Index). Но тут скрывается самая частая ошибка новичков: порядок колонок в скобках критически важен!

Представь школьный справочник, отсортированный строго по правилу: сначала Класс, потом Фамилия (7А Иванов, 7А Смирнов, 7Б Алексеев, 7Б Иванов, 8А Иванов...).

  • Ищешь «7Б, Иванов»? Мгновенно находишь раздел 7Б и внутри него Иванова.
  • Ищешь «всех учеников из 7Б»? Легко! Они все стоят плотной группой рядом.
  • А если ты ищешь «всех Ивановых во всей школе», не зная их класса? Ивановы разбросаны по 7А, 7Б, 8А, 11В — справочник не поможет, придётся листать его целиком!

В базах данных это называется правилом левого префикса (Leftmost Prefix Rule): составной индекс (col_a, col_b, col_c) отлично работает для поиска по col_a, по (col_a, col_b) и по всем трём (col_a, col_b, col_c). Но если в условии WHERE нет самой левой колонки col_a, обычный поиск по дереву не сработает.

Условие в запросе WHERE Индекс (customer_id, total_price) Почему так происходит
customer_id = 42 AND total_price > 30000 Отлично работает Сначала точно заходим в «класс 42», затем берём диапазон цен
customer_id = 42 Отлично работает Используется левая часть (префикс) индекса
total_price > 30000 Не сработает (Seq Scan) Нет левой колонки customer_id — дорогие заказы разбросаны по всем клиентам

Практика 2: проверяем порядок колонок в деле

Давай создадим составной индекс (customer_id, total_price) на нашей таблице shop_orders и проверим все три сценария из таблицы выше.

SQL · Проверка правила левого префикса 
-- Создаём составной индекс: сначала клиент (равенство), потом цена (диапазон)
DROP INDEX IF EXISTS idx_orders_cust_price;
CREATE INDEX idx_orders_cust_price
    ON shop_orders (customer_id, total_price);

-- Сценарий А: ищем по обеим колонкам — индекс сработает идеально
EXPLAIN ANALYZE
SELECT id, total_price
FROM shop_orders
WHERE customer_id = 42
  AND total_price > 30000;

-- Сценарий Б: ищем ТОЛЬКО по второй колонке — левый префикс нарушен!
EXPLAIN ANALYZE
SELECT id, total_price
FROM shop_orders
WHERE total_price > 44500;
Ответ PostgreSQL
-- Сценарий А (обе колонки):
Index Scan using idx_orders_cust_price on shop_orders
  Index Cond: ((customer_id = 42) AND (total_price > 30000))
Execution Time: 0.052 ms

-- Сценарий Б (только вторая колонка total_price):
Seq Scan on shop_orders
  Filter: (total_price > 44500)
  Rows Removed by Filter: 98891
Execution Time: 13.410 ms

Ещё одно золотое правило при проектировании составного индекса: равенство ставь слева, диапазон — справа (Equality first, Range second). Если поставить диапазон total_price > 30000 на первое место, внутри этого огромного отрезка все customer_id снова окажутся вперемешку!

✗ Как НЕ надо
-- Сначала диапазон, потом =
CREATE INDEX idx_bad
ON shop_orders (
  total_price,
  customer_id
);

Для customer_id = 42 AND total_price > 30000 базе придётся перебрать в индексе все дорогие заказы всех клиентов и отсеивать лишних.

✓ Как правильно
-- Сначала =, потом диапазон
CREATE INDEX idx_good
ON shop_orders (
  customer_id,
  total_price
);

PostgreSQL мгновенно прыгает к customer_id = 42 и читает ровно те 5–7 строк, где цена выше 30 000.

Суперспособность INCLUDE (Покрывающий индекс): Представь, что на карточке в библиотечном каталоге сразу написано имя автора и год издания — тебе даже не нужно идти в зал за самой книгой! Если написать CREATE INDEX idx_cover ON shop_orders (customer_id) INCLUDE (total_price);, то запрос SELECT total_price FROM shop_orders WHERE customer_id = 42; выполнится через Index Only Scan — вообще без чтения страниц Heap!

03 Когда индексы НЕ работают: 5 главных ловушек

Бывает обидная ситуация: ты честно создал индекс, запускаешь запрос, а он всё равно ползёт как черепаха через Seq Scan. Почему PostgreSQL «не видит» твой индекс? Давай разберём 5 главных причин.

  1. Функция или вычисление вокруг колонки. В индексе хранятся значения в исходном виде, например 'User42@Example.com'. Если ты пишешь WHERE LOWER(email) = 'user42@example.com' или WHERE total_price * 2 > 80000, то просишь библиотекаря найти книги «по названию, прочитанному задом наперёд». Обычный алфавитный каталог здесь бесполезен!
  2. Поиск по шаблону с % в начале. Для LIKE 'ORD-077%' дерево B-Tree сработает (при нужной локали или text_pattern_ops), потому что известно начало слова. А для LIKE '%777%' слово может начинаться с любой буквы — индекс бессилен.
  3. Низкая селективность (подходит слишком много строк). Представь, что тебе нужно выписать цитаты из 85% страниц толстой книги. Будешь ли ты 850 раз открывать предметный указатель и скакать туда-сюда? Нет! Проще один раз прочитать книгу подряд. Если условию WHERE status = 'paid' соответствует 85% таблицы, планировщик PostgreSQL намеренно выберет Seq Scan — так быстрее!
  4. Несовпадение типов данных. Например, колонка order_code имеет тип TEXT, а ты передаёшь число без кавычек или приводишь саму колонку order_code::INT. Приведение типа на колонке ломает индекс точно так же, как функция.
  5. Таблица слишком маленькая. Если вся таблица помещается в 1–2 страницы (меньше 16 КБ), читать индекс и потом прыгать в таблицу — лишняя трата времени.
✗ Как НЕ надо: прячем колонку внутри функции или формулы
-- Колонка изменена функцией/формулой — обычный B-Tree по ней НЕ сработает
SELECT * FROM shop_orders WHERE LOWER(email) = 'user42@example.com';
SELECT * FROM shop_orders WHERE total_price * 1.2 > 48000;
SELECT * FROM shop_orders WHERE EXTRACT(YEAR FROM created_at) = 2026;

PostgreSQL вынужден вычислять выражение для каждой из 100 000 строк в таблице.

✓ Как правильно: оставляем колонку «чистой» или индексируем выражение
-- 1) Для LOWER(email) — создаём функциональный индекс (Expression Index)
CREATE INDEX idx_orders_lower_email ON shop_orders (LOWER(email));
-- 2) Математику переносим в правую часть (48000 / 1.2 = 40000)
SELECT * FROM shop_orders WHERE total_price > 40000;
-- 3) Вместо EXTRACT — задаём честный диапазон дат
SELECT * FROM shop_orders
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

Теперь колонка (или точно совпадающее с индексом выражение) сравнивается напрямую по дереву B-Tree.

Практика 3: ломаем индекс через LOWER() и чиним функциональным индексом

Давай убедимся в ловушке №1 на реальной таблице shop_orders. У нас адреса записаны с заглавными буквами (User42@Example.com), а на сайте клиент вводит почту строчными.

SQL · Обычный индекс vs функциональный индекс 
-- Создаём обычный индекс на email
DROP INDEX IF EXISTS idx_orders_email;
DROP INDEX IF EXISTS idx_orders_lower_email;
CREATE INDEX idx_orders_email ON shop_orders (email);

-- Проверяем поиск без учёта регистра: обычный индекс ИГНОРИРУЕТСЯ!
EXPLAIN ANALYZE
SELECT id, email FROM shop_orders
WHERE LOWER(email) = 'user42@example.com';

-- Создаём функциональный индекс (Expression Index) точно под выражение LOWER(email)
CREATE INDEX idx_orders_lower_email ON shop_orders (LOWER(email));

-- Повторяем запрос: теперь индекс срабатывает!
EXPLAIN ANALYZE
SELECT id, email FROM shop_orders
WHERE LOWER(email) = 'user42@example.com';
Ответ PostgreSQL
-- С обычным индексом idx_orders_email:
Seq Scan on shop_orders
  Filter: (lower(email) = 'user42@example.com'::text)
  Rows Removed by Filter: 99980
Execution Time: 24.615 ms

-- С функциональным индексом idx_orders_lower_email:
Bitmap Heap Scan on shop_orders
  Recheck Cond: (lower(email) = 'user42@example.com'::text)
  ->  Bitmap Index Scan on idx_orders_lower_email
        Index Cond: (lower(email) = 'user42@example.com'::text)
Execution Time: 0.148 ms

Проблема исчезла: вместо 24.6 мс запрос выполнился за 0.148 мс — ускорение более чем в 160 раз! Старый ненужный idx_orders_email после этого лучше удалить командой DROP INDEX, чтобы не тратить память впустую.

Практика 4: частичный индекс (Partial Index) для редких статусов

Помнишь ловушку №3 про низкую селективность? В нашей таблице 85% заказов имеют статус 'paid', и только 5% — 'pending' (ожидают оплаты). Операторам магазина нужно постоянно мониторить именно неоплаченные заказы. Зачем индексировать все 100 000 строк, если 95 000 нам вообще не интересны?

В PostgreSQL можно создать частичный индекс (Partial Index) с условием WHERE — он сохранит в дереве только нужные 5% строк и будет занимать в 20 раз меньше места!

SQL · Частичный индекс и сравнение его размера 
DROP INDEX IF EXISTS idx_orders_status_full;
DROP INDEX IF EXISTS idx_orders_pending_only;

-- Полный индекс на все 100 000 строк
CREATE INDEX idx_orders_status_full ON shop_orders (status);

-- Частичный индекс: хранит ТОЛЬКО заказы в статусе 'pending' (5 000 строк)
CREATE INDEX idx_orders_pending_only
    ON shop_orders (created_at)
    WHERE status = 'pending';

-- Сравниваем размер двух индексов на диске
SELECT
    pg_size_pretty(pg_relation_size('idx_orders_status_full'))  AS full_index_size,
    pg_size_pretty(pg_relation_size('idx_orders_pending_only')) AS partial_index_size;

-- Проверяем, что запрос по неоплаченным заказам подхватывает крошечный частичный индекс
EXPLAIN ANALYZE
SELECT id, order_code, created_at
FROM shop_orders
WHERE status = 'pending'
  AND created_at >= '2026-05-01 00:00:00+05'
LIMIT 10;
Ответ PostgreSQL
 full_index_size | partial_index_size
-----------------+--------------------
 688 kB          | 128 kB
(1 row)

Limit  (actual time=0.039..0.046 rows=10 loops=1)
  ->  Index Scan using idx_orders_pending_only on shop_orders
        Index Cond: (created_at >= '2026-05-01 00:00:00+05'::timestamptz)
Execution Time: 0.064 ms

04 Не только B-Tree: обзор индексов GIN и BRIN

Дерево B-Tree — отличный универсальный инструмент, как швейцарский нож. Но оно работает только с «обычными» значениями, которые можно выстроить в шеренгу от меньшего к большему (числа, даты, строки). Что делать, если задачи нестандартные? В PostgreSQL есть специализированные типы индексов, и два самых полезных из них — GIN и BRIN.

GIN (Generalized Inverted Index): поиск внутри массивов, JSONB и текста

Представь, что ты ищешь в учебнике биологии все страницы, где упоминается слово «хлорофилл». Обычное оглавление по главам тебе не поможет — слово может прятаться в любом абзаце. Зато в самом конце учебника есть предметный указатель: хлорофилл → стр. 14, 52, 108.

GIN (обобщённый обратный индекс) устроен точно так же! Вместо того чтобы запоминать «у строки №14 есть теги postgresql, sql, docker», он переворачивает связь наоборот: «тег docker встречается в строках 14, 52, 108». Поэтому GIN незаменим для:

  • массивов (TEXT[], INT[]) — оператор «содержит» @>;
  • документов JSONB — поиск по вложенным ключам и значениям (@>, ?);
  • полнотекстового поиска (tsvector) — оператор @@.

Но будь осторожен: GIN нельзя просто так повесить на обычную текстовую или числовую колонку — PostgreSQL не знает, на какие «кусочки» её дробить. Если попытаться сделать это без специального расширения (например, pg_trgm), база сразу остановит тебя понятной ошибкой:

SQL · Попытка создать GIN на обычной колонке TEXT 
-- Пытаемся повесить GIN на обычный TEXT без специального класса операторов
CREATE INDEX idx_wrong_gin ON shop_orders USING gin (order_code);
Ошибка PostgreSQL
ERROR:  data type text has no default operator class for access method "gin"
HINT:  You must specify an operator class for the index or define a default operator class for the data type.

Причина ошибки: тип TEXT не умеет по умолчанию раскладываться на составные элементы для GIN. А вот типы TEXT[] (массив) и JSONB умеют делать это «из коробки»!

Практика 5: ускоряем поиск по тегам и JSONB с помощью GIN

Создадим каталог курсов и статей learning_articles на 50 000 записей с массивом тегов tags и JSON-характеристиками meta. Попробуем найти все статьи уровня advanced с тегом wal.

SQL · Подготовка таблицы и тест GIN-индекса 
DROP TABLE IF EXISTS learning_articles;

CREATE TABLE learning_articles (
    id    BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    tags  TEXT[] NOT NULL,
    meta  JSONB NOT NULL
);

-- Заполняем 50 000 статей; редкий тег 'wal' попадёт только в каждую 500-ю статью
INSERT INTO learning_articles (title, tags, meta)
SELECT
    'Статья #' || g,
    CASE
        WHEN g % 500 = 0 THEN ARRAY['postgresql', 'internals', 'wal']
        WHEN g % 3 = 0   THEN ARRAY['sql', 'basics', 'queries']
        ELSE ARRAY['backend', 'docker', 'linux']
    END,
    jsonb_build_object(
        'level', CASE WHEN g % 500 = 0 THEN 'advanced' ELSE 'beginner' END,
        'minutes', (g % 25) + 5
    )
FROM generate_series(1, 50000) AS g;

ANALYZE learning_articles;

-- 1. Ищем статьи с тегом 'wal' БЕЗ индекса
EXPLAIN ANALYZE
SELECT id, title FROM learning_articles
WHERE tags @> ARRAY['wal'];

-- 2. Создаём GIN-индексы на массив и на JSONB
CREATE INDEX idx_articles_tags_gin ON learning_articles USING gin (tags);
CREATE INDEX idx_articles_meta_gin ON learning_articles USING gin (meta);

-- 3. Повторяем поиск по тегу и добавляем фильтр по JSONB
EXPLAIN ANALYZE
SELECT id, title FROM learning_articles
WHERE tags @> ARRAY['wal']
  AND meta @> '{"level": "advanced"}'::JSONB;
Ответ PostgreSQL
-- ДО создания GIN:
Seq Scan on learning_articles  (actual time=0.221..11.940 rows=100 loops=1)
  Filter: (tags @> '{wal}'::text[])
  Rows Removed by Filter: 49900
Execution Time: 11.985 ms

-- ПОСЛЕ создания GIN:
Bitmap Heap Scan on learning_articles  (actual time=0.095..0.281 rows=100 loops=1)
  Recheck Cond: ((tags @> '{wal}'::text[]) AND (meta @> '{"level": "advanced"}'::jsonb))
  ->  BitmapAnd
        ->  Bitmap Index Scan on idx_articles_tags_gin
        ->  Bitmap Index Scan on idx_articles_meta_gin
Execution Time: 0.312 ms

Посмотри, как красиво сработал PostgreSQL: он взял результаты сразу из двух GIN-индексов, пересек их в памяти через BitmapAnd и нашёл ровно 100 нужных статей за 0.31 мс вместо 12 мс!

BRIN (Block Range Index): микроскопический индекс для гигантских логов

А теперь представь архив школьного музея, где на стеллажах стоят 10 000 коробок с квитанциями, сложенными строго по дате — с 2000 по 2026 год. Если заводить карточку B-Tree на каждую бумажку, каталог займёт полкомнаты!

Инженеры придумали гениальный трюк — BRIN (индекс диапазонов блоков). Вместо того чтобы записывать каждую строку, он вешает одну маленькую наклейку на каждые 128 страниц Heap (1 МБ данных): «Блоки 0–127: даты от 1 января до 3 января», «Блоки 128–255: даты от 4 января до 6 января».

Когда тебе нужны логи за 5 января, BRIN мгновенно отбрасывает 99% коробок и открывает только нужный диапазон страниц. При этом сам индекс весит в сотни раз меньше, чем B-Tree!

Практика 6: сравниваем размер и скорость B-Tree vs BRIN на 200 000 логов

Создадим таблицу показаний датчиков sensor_logs (200 000 строк, идущих строго по времени logged_at) и сравним на диске обычный B-Tree и BRIN.

SQL · Эксперимент: B-Tree vs BRIN на таблице логов 
DROP TABLE IF EXISTS sensor_logs;

CREATE TABLE sensor_logs (
    id        BIGSERIAL PRIMARY KEY,
    sensor_id INT NOT NULL,
    temp_c    NUMERIC(5, 2) NOT NULL,
    logged_at TIMESTAMPTZ NOT NULL
);

-- Вставляем 200 000 записей строго в хронологическом порядке (append-only)
INSERT INTO sensor_logs (sensor_id, temp_c, logged_at)
SELECT
    (g % 50) + 1,
    ROUND((18 + (RANDOM() * 12))::NUMERIC, 2),
    TIMESTAMPTZ '2026-01-01 00:00:00+05' + (g * INTERVAL '10 seconds')
FROM generate_series(1, 200000) AS g;

ANALYZE sensor_logs;

-- Создаём оба индекса, чтобы сравнить их вес
CREATE INDEX idx_logs_time_btree ON sensor_logs USING btree (logged_at);
CREATE INDEX idx_logs_time_brin  ON sensor_logs USING brin  (logged_at);

-- Сравниваем размер таблицы и двух индексов
SELECT
    pg_size_pretty(pg_relation_size('sensor_logs'))         AS table_size,
    pg_size_pretty(pg_relation_size('idx_logs_time_btree')) AS btree_size,
    pg_size_pretty(pg_relation_size('idx_logs_time_brin'))  AS brin_size;

-- Удаляем B-Tree, чтобы увидеть работу именно BRIN
DROP INDEX idx_logs_time_btree;

EXPLAIN ANALYZE
SELECT COUNT(*), ROUND(AVG(temp_c), 2)
FROM sensor_logs
WHERE logged_at >= '2026-01-15 12:00:00+05'
  AND logged_at <  '2026-01-15 13:00:00+05';
Ответ PostgreSQL
 table_size | btree_size | brin_size
------------+------------+-----------
 11 MB      | 4408 kB    | 24 kB
(1 row)

Aggregate  (actual time=1.184..1.185 rows=1 loops=1)
  ->  Bitmap Heap Scan on sensor_logs
        Recheck Cond: ((logged_at >= '2026-01-15 12:00:00+05') AND (logged_at < '2026-01-15 13:00:00+05'))
        Rows Removed by Index Recheck: 17140
        Heap Blocks: lossy=128
        ->  Bitmap Index Scan on idx_logs_time_brin
Execution Time: 1.218 ms

Посмотри на цифры в таблице: B-Tree занял 4.4 МБ (почти половину самой таблицы!), а BRIN — всего 24 КБ, то есть в 180 раз меньше! На реальных базах объёмом 500 ГБ эта разница экономит десятки гигабайт оперативной памяти и диска.

Главное ограничение BRIN: если данные в таблице лежат вперемешку (например, на коробке написано «от 2001 до 2026 года», потому что в неё скидали случайные квитанции), BRIN не сможет отбросить ни одну коробку и станет бесполезным. Используй его только для данных с естественным физическим порядком — created_at в логах, событиях, телеметрии.
Тип индекса Главная задача Операторы Размер Цена записи
B-Tree Точный поиск, диапазоны, ORDER BY, уникальность =, <, <=, >, >=, BETWEEN, IN Средний Умеренная
GIN Составные значения: массивы, JSONB, полнотекст @>, <@, ?, ?&, @@ Большой Высокая (обновляется тяжелее)
BRIN Сверхбольшие отсортированные таблицы (логи, события) =, <, >, BETWEEN Крошечный Минимальная

05 Шпаргалка перед практикой

Пробегись глазами по этим 5 правилам и мини-словарику перед тем, как решать задачи практикума:

  • Не оборачивай колонку в функцию: вместо WHERE col + 10 > 100 пиши WHERE col > 90, а для LOWER(email) создавай функциональный индекс.
  • Помни порядок в составном индексе: сначала колонка с точным равенством (=), затем колонка с диапазоном (>, BETWEEN). Левая колонка обязательна в WHERE!
  • Не индексируй «почти всю таблицу»: если нужна только редкая часть строк (например, status = 'pending'), используй частичный индекс с WHERE.
  • Подбирай инструмент под тип данных: для обычных чисел/дат/строк — B-Tree; для массивов и JSONB — GIN; для гигантских хронологических логов — BRIN.
  • Не забывай ANALYZE: после массовой загрузки данных обнови статистику, иначе планировщик может не знать реальный размер таблицы.
Термин урока Короткий перевод на «человеческий»
B-Tree Сбалансированное дерево-каталог; находит любую строку за 3–4 прыжка по страницам
ctid Физический адрес строки в таблице Heap: пара (номер страницы, номер слота)
Leftmost Prefix Правило левого префикса: составной индекс (a, b) работает только если в запросе есть a
Partial Index Индекс с условием WHERE, который хранит только нужную часть таблицы
GIN / BRIN GIN — предметный указатель для массивов/JSONB; BRIN — мини-наклейки min..max на группы страниц

Задание 1 (Базовый уровень). Ускоряем поиск и сортировку игроков

Создай автономную таблицу practice_players (50 000 строк) с колонками id, nickname и rating. Затем:

  1. Замерь через EXPLAIN ANALYZE поиск игрока с nickname = 'player_42000'.

DROP TABLE IF EXISTS practice_players;

Задание 2 (Средний уровень). Почини «сломанный» составной индекс и запрос

Разработчик создал таблицу тикетов поддержки practice_tickets (60 000 строк) и повесил индекс (created_at, department), а ещё в запросе написал UPPER(department) = 'BILLING'. Запрос тормозит! Подготовь таблицу, исправь и порядок колонок в составном индексе, и сам запрос (убери лишнюю функцию), чтобы поиск тикетов отдела 'billing' за последнюю неделю стал мгновенным.

Показать решение
SQL · Эталонное решение 2 
-- 1. Подготовка автономной таблицы
DROP TABLE IF EXISTS practice_tickets;
CREATE TABLE practice_tickets (
    id         BIGSERIAL PRIMARY KEY,
    department TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
);

INSERT INTO practice_tickets (department, created_at)
SELECT
    CASE (g % 4)
        WHEN 0 THEN 'billing'
        WHEN 1 THEN 'tech'
        WHEN 2 THEN 'sales'
        ELSE 'delivery'
    END,
    TIMESTAMPTZ '2026-01-01 00:00:00+05' + (g * INTERVAL '5 minutes')
FROM generate_series(1, 60000) AS g;

ANALYZE practice_tickets;

-- 2. Правильный составной индекс: сначала равенство (department), потом диапазон (created_at)
CREATE INDEX idx_tickets_dept_created
    ON practice_tickets (department, created_at);

-- 3. Убираем UPPER() с колонки (данные уже в нижнем регистре) и проверяем план
EXPLAIN ANALYZE
SELECT id, department, created_at
FROM practice_tickets
WHERE department = 'billing'
  AND created_at >= '2026-07-20 00:00:00+05';

Создай таблицу practice_gadgets на 40 000 товаров с колонкой specs JSONB (ключи brand, ram_gb, nfc). Создай правильный индекс типа GIN и проверь через EXPLAIN ANALYZE, что поиск всех гаджетов бренда "Pixel" с поддержкой nfc: true (оператор @>) использует индекс.

Показать решение
SQL · Эталонное решение 3

DROP TABLE IF EXISTS practice_gadgets;

);

Задание 4 (Инженерный челлендж). Экономим гигабайты с BRIN и Partial Index

Создай таблицу событий сервера practice_events на 150 000 строк, идущих строго по времени event_time, где у 98% строк severity = 'info', а у 2% — severity = 'critical'. Реши сразу две инженерные задачи:

  1. Создай BRIN-индекс на event_time и сравни его размер с обычным B-Tree через pg_size_pretty.
  2. Создай частичный индекс только для событий с severity = 'critical' и проверь его в EXPLAIN ANALYZE.
Показать решение
SQL · Эталонное решение 4 
-- 1. Автономная таблица событий (строго по возрастанию времени)
DROP TABLE IF EXISTS practice_events;
CREATE TABLE practice_events (
    id         BIGSERIAL PRIMARY KEY,
    severity   TEXT NOT NULL,
    event_time TIMESTAMPTZ NOT NULL
);

INSERT INTO practice_events (severity, event_time)
SELECT
    CASE WHEN g % 50 = 0 THEN 'critical' ELSE 'info' END,
    TIMESTAMPTZ '2026-01-01 00:00:00+05' + (g * INTERVAL '15 seconds')
FROM generate_series(1, 150000) AS g;

ANALYZE practice_events;

-- 2. Создаём B-Tree и BRIN на event_time + частичный индекс для critical
CREATE INDEX idx_events_time_btree ON practice_events USING btree (event_time);
CREATE INDEX idx_events_time_brin  ON practice_events USING brin  (event_time);
CREATE INDEX idx_events_critical   ON practice_events (event_time)
    WHERE severity = 'critical';

-- 3. Сравниваем размеры всех трёх индексов
SELECT
    pg_size_pretty(pg_relation_size('idx_events_time_btree')) AS btree_size,
    pg_size_pretty(pg_relation_size('idx_events_time_brin'))  AS brin_size,
    pg_size_pretty(pg_relation_size('idx_events_critical'))   AS partial_size;

-- 4. Проверяем, что поиск критических ошибок берёт крошечный частичный индекс
EXPLAIN ANALYZE
SELECT id, event_time
FROM practice_events
WHERE severity = 'critical'
  AND event_time >= '2026-01-20 00:00:00+05'
LIMIT 15;
