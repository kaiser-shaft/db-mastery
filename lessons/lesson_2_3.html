Урок 2.3: Подзапросы, CTE, работа с датами, строками и JSONB

Главное в этом уроке

  • Освоишь работу со временем (TIMESTAMPTZ, DATE_TRUNC, INTERVAL) и «причёсывание» грязных строк (TRIM, LOWER, SPLIT_PART, ILIKE).

01 Готовим стенд в learning_db

В прошлых уроках ты научился связывать таблицы через JOIN и считать итоги через GROUP BY. Но в реальных задачах одного шага часто мало. Например, директор магазина просит: «Покажи клиентов, которые потратили больше, чем средний покупатель, разбей выручку по месяцам, почисти кривые имена и найди все товары с тегом hit».

Чтобы все примеры этого урока запускались с первой попытки и давали точно такой же результат, как в конспекте, обновим учебные таблицы интернет-магазина в базе learning_db. Скрипт ниже безопасно пересоздаёт четыре таблицы (клиенты, товары с JSONB-характеристиками, заказы с датами и доставкой, позиции заказов) — его можно перезапускать сколько угодно раз.

SQL · Подготовка данных в learning_db 
-- Безопасный перезапуск: удаляем старые версии таблиц урока, если они есть
DROP TABLE IF EXISTS order_items, orders, products, customers CASCADE;

-- 1. Клиенты (специально добавили «грязные» пробелы, разный регистр и один NULL)

  id SERIAL PRIMARY KEY,
  full_name TEXT NOT NULL,
  email TEXT NOT NULL UNIQUE,
  city TEXT,
  registered_at TIMESTAMPTZ NOT NULL
);

-- 2. Товары со строгими полями + гибким JSONB-рюкзаком specs
CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  title TEXT NOT NULL,
  category TEXT NOT NULL,
  price NUMERIC(10, 2) NOT NULL CHECK (price >= 0),
  specs JSONB NOT NULL DEFAULT '{}'::jsonb
);

-- 3. Заказы с датой (TIMESTAMPTZ) и вложенным JSONB-описанием доставки
CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  customer_id INT NOT NULL REFERENCES customers(id),
  status TEXT NOT NULL CHECK (status IN ('paid', 'cancelled', 'pending')),

-- 4. Позиции внутри каждого заказа
CREATE TABLE order_items (
  id SERIAL PRIMARY KEY,
  order_id INT NOT NULL REFERENCES orders(id),
  product_id INT NOT NULL REFERENCES products(id),
  quantity INT NOT NULL CHECK (quantity > 0),
  unit_price NUMERIC(10, 2) NOT NULL
);

02 Подзапросы (Subqueries) — запрос внутри запроса

Представь, что на контрольной по математике учитель говорит: «Выпиши всех учеников, чей рост выше среднего по классу». Ты не можешь сразу открыть список и тыкать пальцем — сначала нужно на черновике сложить рост всех ребят и поделить на их количество. И только потом сравнить каждого ученика с этим числом.

В SQL таким «черновиком в скобках» служит подзапрос (Subquery) — это обычный SELECT, спрятанный внутри другого запроса. База сначала вычисляет внутренний запрос, а потом подставляет его результат во внешний.

Вид подзапроса Что возвращает Где чаще всего стоит
Скалярный Ровно 1 строку и 1 колонку (одно число или текст) После =, >, < в WHERE или в SELECT
Списочный Один столбец, но много строк Внутри IN (...) или ANY (...)
Проверка факта Есть ли хоть одна подходящая строка (да / нет) Внутри EXISTS (...) / NOT EXISTS (...)
Табличный Целую временную таблицу (много строк и колонок) В блоке FROM (...) AS alias

Пример 1: Скалярный подзапрос в WHERE

Решим нашу задачу «выше среднего»: найдём товары, которые стоят дороже средней цены по магазину. В нашей таблице 6 товаров на общую сумму 78 000, значит, средняя цена — ровно 13000.00. Запрос вычислит её сам, без калькулятора.

SQL · Пример 1 — Товары дороже средней цены 
-- Внешний запрос выбирает товары,
-- а внутренний (в скобках) заранее вычисляет среднюю цену
SELECT id, title, price
FROM products
WHERE price > (
  SELECT AVG(price) FROM products
)
ORDER BY price DESC;
Ответ PostgreSQL
 id |          title          |  price
----+-------------------------+----------
  3 | Механическая клавиатура | 39100.00
  1 | Худи «SQL Master»       | 14500.00
(2 rows)

А что случится, если после знака > или = по ошибке написать подзапрос, который вернёт не одно число, а сразу несколько строк? Например, попытаться сравнить цену товара сразу со списком цен из категории 'Мерч':

SQL · Ошибочный запрос 
-- ОШИБКА: в категории 'Мерч' два товара (14500 и 7800)
SELECT title, price
FROM products
WHERE price > (
  SELECT price FROM products WHERE category = 'Мерч'
);
Ошибка PostgreSQL
ERROR:  more than one row returned by a subquery used as an expression

PostgreSQL честно предупреждает: «Я ждал одно число после знака >, а получил целую стопку строк — не знаю, с какой именно сравнивать». Чтобы починить это, нужно либо свернуть подзапрос до одного числа (MAX(price)), либо использовать оператор > ALL (...) / IN (...).

Пример 2: Поиск «пропавших» записей через NOT EXISTS

Теперь представим другую задачу магазина: маркетолог хочет отправить купон на скидку тем клиентам, которые зарегистрировались, но не оформили ни одного оплаченного заказа. Для таких проверок в SQL создан оператор EXISTS — он как охранник на входе: ему не важен весь список покупок, достаточно увидеть первую же подходящую строку, чтобы сказать «да, есть!».

SQL · Пример 2 — Клиенты без оплаченных заказов 
-- Ищем клиентов, для которых в таблице orders НЕТ ни одной оплаченной строки
SELECT c.id, c.full_name, c.email
FROM customers c
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.id
    AND o.status = 'paid'
);
Ответ PostgreSQL
 id |    full_name    |      email
----+-----------------+-----------------
  5 | Данияр Нурланов | daniyar@tech.kz
(1 row)

Обрати внимание на SELECT 1 внутри EXISTS. Мы не читаем никакие колонки из orders — нам важен сам факт существования строки. Зато NOT EXISTS спасает от одной из самых коварных ловушек SQL: поведения NOT IN при встрече с NULL.

✗ Как НЕ надо
SELECT title FROM products
WHERE category NOT IN (
  SELECT city FROM customers
);

Если подзапрос вернёт хотя бы один NULL (как город у Данияра), условие превратится в «неизвестно» и запрос тихо вернёт 0 строк!

✓ Как правильно
SELECT c.full_name
FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id
);

NOT EXISTS никогда не ломается из-за NULL и работает быстрее на больших таблицах, останавливаясь на первом совпадении.

Частая ошибка: Не вставляй коррелированный подзапрос (который ссылается на внешнюю таблицу) прямо в список колонок SELECT для больших таблиц. На миллионе строк такой подзапрос может запуститься миллион раз подряд. Лучше переписать его через LEFT JOIN или CTE.

03 CTE (WITH) — раскладываем сложный запрос по полочкам

Представь кулинарный рецепт, записанный в одно длинное предложение со скобками внутри скобок: «Подай суп, сваренный из бульона (из мяса (купленного на рынке (утром)))...». Читать такое невозможно! Гораздо проще разбить рецепт на пронумерованные шаги: «Шаг 1: свари бульон. Шаг 2: нарежь овощи. Шаг 3: соедини и подавай».

В SQL именно так работают обобщённые табличные выражения — CTE (Common Table Expressions), которые начинаются со слова WITH. Ты придумываешь временным промежуточным таблицам понятные имена и выстраиваешь из них линейный конвейер сверху вниз.

Решим реальную бизнес-задачу на трёх таблицах сразу (customers, orders, order_items): найдём VIP-клиентов, которые потратили в магазине больше среднего чека всех покупателей. Сначала посмотрим на схему шагов:

Пример 3: Многошаговый CTE на трёх таблицах

Обрати внимание, как легко читается запрос: сначала мы собираем траты каждого клиента в блок customer_totals, затем на его основе считаем среднее в store_avg, и только в самом конце сравниваем их.

SQL · Пример 3 — VIP-клиенты через многошаговый CTE 
-- Шаг 1: считаем общую сумму оплаченных покупок для каждого клиента
WITH customer_totals AS (
  SELECT
    c.id AS customer_id,
    INITCAP(TRIM(c.full_name)) AS customer_name,
    COUNT(DISTINCT o.id) AS paid_orders,
    SUM(oi.quantity * oi.unit_price) AS total_spent
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status = 'paid'
  GROUP BY c.id, c.full_name
),
-- Шаг 2: вычисляем средние траты среди всех платящих клиентов
store_avg AS (
  SELECT ROUND(AVG(total_spent), 2) AS avg_spent
  FROM customer_totals
)
-- Финал: выводим только VIP-клиентов и их отрыв от среднего
SELECT
  ct.customer_name,
  ct.paid_orders,
  ct.total_spent,
  sa.avg_spent,
  ct.total_spent - sa.avg_spent AS above_avg
FROM customer_totals ct
CROSS JOIN store_avg sa
WHERE ct.total_spent > sa.avg_spent
ORDER BY ct.total_spent DESC;
Ответ PostgreSQL
 customer_name  | paid_orders | total_spent | avg_spent | above_avg
----------------+-------------+-------------+-----------+-----------
 Мария Смирнова |           2 |    60500.00 |  31850.00 |  28650.00
 Алексей Иванов |           2 |    39200.00 |  31850.00 |   7350.00
(2 rows)

Посмотри, как элегантно решилась наша задача из начала раздела: вместо того чтобы дважды переписывать один и тот же JOIN трёх таблиц с GROUP BY, мы описали расчёт customer_totals один раз, а затем переиспользовали его и в store_avg, и в финальном SELECT. Сравни читаемость двух подходов:

✗ Как НЕ надо — «матрёшка» из дублирующихся подзапросов
SELECT t.customer_name, t.total_spent
FROM (
  SELECT c.full_name AS customer_name, SUM(oi.quantity * oi.unit_price) AS total_spent
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status = 'paid'
  GROUP BY c.id, c.full_name
) t
WHERE t.total_spent > (
  SELECT AVG(sub.s) FROM (
    SELECT SUM(oi.quantity * oi.unit_price) AS s
    FROM orders o JOIN order_items oi ON oi.order_id = o.id
    WHERE o.status = 'paid' GROUP BY o.customer_id
  ) sub
);

Логика дублируется дважды: если завтра поменяется условие оплаты, придётся править запрос в двух местах, и велик шанс ошибиться.

✓ Как правильно — один источник правды в CTE
WITH customer_totals AS (
  SELECT c.full_name AS customer_name, SUM(oi.quantity * oi.unit_price) AS total_spent
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status = 'paid'
  GROUP BY c.id, c.full_name
)
SELECT customer_name, total_spent
FROM customer_totals
WHERE total_spent > (SELECT AVG(total_spent) FROM customer_totals);

Синтаксис читается как книга сверху вниз, расчёт суммы написан ровно один раз, а каждый шаг легко проверить отдельно простым SELECT * FROM customer_totals;.

Совет на будущее (PostgreSQL 12+): Раньше CTE всегда сохраняли свой результат в память как временную таблицу и могли мешать индексам. В современном PostgreSQL 16 планировщик сам решает, «встроить» ли CTE в основной запрос. Но если CTE используется дважды или ты хочешь явно зафиксировать вычисление, можно написать WITH step AS MATERIALIZED (...) или наоборот AS NOT MATERIALIZED (...).

04 Работа с датами и временем

В жизни время кажется простым, пока не начнёшь считать календарь: в феврале то 28, то 29 дней, в месяце то 30, то 31, а у покупателя в Алматы и сервера во Франкфурте на часах разное время. В PostgreSQL не нужно выдумывать математику с секундами вручную — у базы есть встроенные «умные часы» (TIMESTAMPTZ) и «мерная линейка» для отрезков времени (INTERVAL).

Функция / тип Что делает простыми словами Пример
TIMESTAMPTZ Хранит точный момент времени с учётом часового пояса '2026-03-15 13:15:00+05'
INTERVAL Отрезок времени, который можно прибавлять и вычитать NOW() - INTERVAL '7 days'
DATE_TRUNC(unit, ts) «Срезает» дату до начала месяца, недели, дня или часа DATE_TRUNC('month', created_at)
EXTRACT(field FROM ts) Достаёт одно число: год, месяц, день недели или час EXTRACT(DOW FROM created_at)
AGE(ts1, ts2) Считает красивую разницу в годах, месяцах и днях AGE(NOW(), registered_at)

Пример 4: Выручка по месяцам через DATE_TRUNC и INTERVAL

Вернёмся к просьбе директора: «Разбей выручку магазина по месяцам за первый квартал 2026 года». Функция DATE_TRUNC('month', o.created_at) превратит любую дату января (хоть 12-е, хоть 25-е число) в единую метку 2026-01-01, благодаря чему GROUP BY легко соберёт все заказы месяца в одну строку.

SQL · Пример 4 — Помесячный отчёт за 1-й квартал 
-- Срезаем дату каждого заказа до первого числа месяца и суммируем выручку
SELECT
  DATE_TRUNC('month', o.created_at)::date AS order_month,
  COUNT(DISTINCT o.id) AS orders_count,
  SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = 'paid'
  -- Полуоткрытый интервал: с 1 января включительно по 1 апреля не включительно
  AND o.created_at >= TIMESTAMPTZ '2026-01-01 00:00:00+05'
  AND o.created_at <  TIMESTAMPTZ '2026-01-01 00:00:00+05' + INTERVAL '3 months'
GROUP BY order_month
ORDER BY order_month;
Ответ PostgreSQL
 order_month | orders_count | revenue
-------------+--------------+----------
 2026-01-01  |            2 | 56000.00
 2026-02-01  |            2 | 37900.00
 2026-03-01  |            2 | 33500.00
(3 rows)

Обрати внимание на фильтр дат в WHERE: мы не написали BETWEEN '2026-01-01' AND '2026-03-31' (иначе потеряли бы все заказы 31 марта после полуночи!) и не завернули колонку в функцию EXTRACT. Вот почему это критически важно:

✗ Как НЕ надо
SELECT * FROM orders
WHERE EXTRACT(
  YEAR FROM created_at
) = 2026;

Функция вокруг колонки отключает обычный индекс: PostgreSQL вынужден прочитать всю таблицу целиком.

✓ Как правильно
SELECT * FROM orders
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01';

Полуоткрытый диапазон (>= и <) не теряет последние секунды года и позволяет базе мгновенно использовать индекс.

Золотое правило времени: Для событий (время заказа, оплаты, регистрации) всегда используй TIMESTAMPTZ, а не просто TIMESTAMP. Тогда при переезде сервера из Алматы в Европу или при заходе клиента из другого города даты никогда не «съедут» на несколько часов.

05 Работа со строками — наводим порядок в текстах

Пользователи заполняют формы на сайте как придётся: кто-то случайно нажал пробел перед именем (' алексей иванов '), кто-то забыл выключить Caps Lock ('ELENA.VOLKOVA@company.org'), а кто-то вообще оставил поле города пустым. Работа со строками в SQL похожа на работу корректора в издательстве: перед тем как отдавать отчёт руководству, текст нужно аккуратно «причесать».

Посмотри в таблице «Было → Стало», как базовые строковые функции приводят данные из нашей таблицы customers в идеальный вид:

Было (сырые данные) Функция SQL Стало (чистый результат)
' алексей иванов ' INITCAP(TRIM(full_name)) 'Алексей Иванов'
'Alex.Ivanov@Example.COM' LOWER(email) 'alex.ivanov@example.com'
'alex.ivanov@example.com' SPLIT_PART(LOWER(email), '@', 2) 'example.com'
NULL (пустой город) COALESCE(city, 'Не указан') 'Не указан'

Пример 5: Очистка клиентской базы и извлечение почтовых доменов

Соберём аккуратную адресную книгу для рассылки: уберём лишние пробелы, сделаем заглавные буквы в именах, приведём email к нижнему регистру, вырежем домен после символа @ и заменим NULL в городе на понятную подпись.

SQL · Пример 5 — Очистка строк и разбор email 
-- Причёсываем грязные тексты и достаём домен почты
SELECT
  id,
  INITCAP(TRIM(full_name)) AS clean_name,
  LOWER(email) AS clean_email,
  SPLIT_PART(LOWER(email), '@', 2) AS email_domain,
  COALESCE(city, 'Не указан') AS city_label
FROM customers
ORDER BY id;

  2 | Мария Смирнова  | maria.s@mail.kz           | mail.kz      | Астана
  3 | Тимур Касымов   | timur_k@gmail.com         | gmail.com    | Костанай
  4 | Елена Волкова   | elena.volkova@company.org | company.org  | Алматы

Полезные фишки PostgreSQL для текста: Для поиска без учёта регистра используй ILIKE вместо LIKE (например, WHERE title ILIKE '%sql%' найдёт и SQL, и sql). А для склейки строк вместо оператора || (который превращает всю строку в NULL, если хоть одна часть пустая) бери функцию CONCAT(a, ' — ', b) — она безопасно пропускает NULL.

06 JSONB — гибкий «рюкзак» внутри строгой таблицы

Представь, что ты проектируешь каталог интернет-магазина. У худи есть размер и материал, у клавиатуры — тип переключателей и вес в граммах, у термокружки — объём в миллилитрах, а у коврика — ширина. Если под каждую характеристику заводить отдельную колонку в таблице products, таблица быстро разрастётся до 200 колонок, на 95% заполненных пустотой (NULL).

Решение в PostgreSQL гениально простое: важные общие поля (id, title, price) остаются обычными строгими колонками, а для переменных характеристик каждому товару выдаётся «рюкзак с кармашками» формата ключ → значение — тип данных JSONB (Binary JSON).

Почему именно JSONB, а не JSON? Обычный JSON хранит сырой текст как есть (с пробелами) и каждый раз заново разбирает его при чтении. JSONB сохраняет данные в уже разобранном двоичном виде: он быстрее читается, поддерживает оператор поиска @> и умеет ускоряться через GIN-индексы. В реальных проектах почти всегда выбирают JSONB.

Главное, что путает новичков в JSONB — стрелочки операторов. Запомни простое правило по схеме ниже: одна стрелка -> оставляет значение в формате JSONB (чтобы идти глубже), а двойная стрелка ->> вытаскивает готовый текст (TEXT).

Пример 6: Поиск хитов продаж и чтение свойств из JSONB

Найдём все товары, у которых в массиве tags есть метка "hit", и достанем их цвет и вес (если вес указан). Для проверки вхождения используем быстрый оператор @> («левый JSONB содержит правый»).

SQL · Пример 6 — Фильтрация через @> и чтение полей ->> 
-- Находим товары с тегом "hit" и извлекаем свойства из JSONB
SELECT
  title,
  price,
  specs ->> 'color' AS color,
  (specs ->> 'weight_g')::int AS weight_g
FROM products
WHERE specs @> '{"tags": ["hit"]}'::jsonb
ORDER BY price DESC;
Ответ PostgreSQL
          title          |  price   | color | weight_g
-------------------------+----------+-------+----------
 Механическая клавиатура | 39100.00 | white |      820
 Худи «SQL Master»       | 14500.00 | black |
 Термокружка кодера      |  6900.00 | black |
(3 rows)

А вот классическая ошибка, на которой спотыкается почти каждый в первый день работы с JSONB: попытка сравнить число после одинарной стрелки -> без перевода в текст и число:

SQL · Частая ошибка с одинарной стрелкой -> 
-- ОШИБКА: оператор -> возвращает JSONB, а его нельзя напрямую сравнить с integer
SELECT title FROM products
WHERE specs -> 'volume_ml' > 300;
Ошибка PostgreSQL
ERROR:  operator does not exist: jsonb > integer
HINT:  No operator matches the given name and argument types. You might need to add explicit type casts.

Исправляется за секунду: берём двойную стрелку ->> (получаем текст '450') и приводим к числу через ::int — WHERE (specs ->> 'volume_ml')::int > 300!

Пример 7: Вложенные пути (#>>) и распаковка JSON-массивов

Что если в JSONB лежит объект внутри объекта (как address.city в таблице orders.delivery_info) или нужно посчитать, сколько раз встречается каждый тег из массива tags? Для вложенного пути берём оператор #>> '{address, city}', а для превращения массива в обычные строки — функцию jsonb_array_elements_text().

SQL · Пример 7А — Вложенный адрес доставки (#>>) 
-- Группируем оплаченные заказы по городу и службе доставки из вложенного JSONB
SELECT
  delivery_info #>> '{address, city}' AS delivery_city,
  delivery_info ->> 'courier' AS courier,
  COUNT(*) AS orders_count
FROM orders
WHERE status = 'paid'
GROUP BY 1, 2
ORDER BY orders_count DESC, delivery_city;
Ответ PostgreSQL
 delivery_city | courier | orders_count
---------------+---------+--------------
 Алматы        | FastBox |            3
 Астана        | FastBox |            1
 Астана        | PostKZ  |            1
 Костанай      | PostKZ  |            1
(4 rows)
SQL · Пример 7Б — Подсчёт популярности тегов из JSON-массива 
-- Распаковываем массив tags в отдельные строки и считаем популярность каждого тега
SELECT
  tag,
  COUNT(*) AS products_count
FROM products,
  jsonb_array_elements_text(specs -> 'tags') AS tag
GROUP BY tag
ORDER BY products_count DESC, tag ASC;
Ответ PostgreSQL
  tag   | products_count
--------+----------------
 hit    |              3
 gift   |              2
 pro    |              2
 summer |              1
 winter |              1
(5 rows)
Индекс для JSONB и чувство меры: Чтобы оператор @> летал на миллионах товаров, добавь CREATE INDEX idx_products_specs_gin ON products USING GIN (specs);. Но не превращай всю базу в один гигантский JSON: поля, по которым ты постоянно связываешь таблицы (customer_id) или считаешь деньги (price), всегда держи в обычных колонках.

07 Шпаргалка урока перед практикой

Пробегись глазами по пяти правилам ниже — они пригодятся тебе в задачах практикума и на реальных собеседованиях:

  • Скалярный подзапрос после =, >, < обязан возвращать не больше 1 строки, иначе PostgreSQL выдаст ошибку.
  • Вместо NOT IN (подзапрос) всегда пиши NOT EXISTS — так ты гарантированно защищён от «пустого результата» из-за случайного NULL.
  • Используй WITH (CTE), как только в запросе появляется 2+ шага логики или повтор одного и того же подзапроса — код сразу станет читаемым и простым в отладке.
  • Фильтруй даты полуоткрытым диапазоном (>= начало AND < конец) и не оборачивай колонку даты в функции в WHERE, чтобы не «сломать» индекс.
  • В JSONB помни разницу стрелок: -> оставляет JSONB, ->> и #>> возвращают TEXT (для чисел добавляй ::int или ::numeric), а @> быстро проверяет вхождение.

08 Мини-практикум для закрепления

Выполни задания в своей базе learning_db (на таблицах из Раздела 01). Все 4 задачи полностью автономны — их можно решать в любом порядке. Постарайся написать запрос самостоятельно, прежде чем открывать решение.

Задание 1 (Базовый). Бюджетные товары заглавными буквами

Выведи названия (в ВЕРХНЕМ РЕГИСТРЕ) и цены всех товаров из таблицы products, которые стоят строго дешевле средней цены по магазину. Отсортируй результат от самых дешёвых к более дорогим.

Показать решение
SQL · Решение задания 1 
SELECT
  UPPER(title) AS upper_title,
  price
FROM products
WHERE price < (
  SELECT AVG(price) FROM products
)
ORDER BY price ASC;
Задание 2 (Средний). Февральские заказы через CTE и даты

Напиши запрос с WITH (CTE): сначала посчитай итоговую сумму каждого оплаченного заказа (order_id, order_total), а в основном запросе выведи заказы, оформленные в феврале 2026 года (используя безопасный полуоткрытый диапазон дат), вместе с очищенным именем клиента (INITCAP(TRIM(...))) и датой заказа.

Показать решение
SQL · Решение задания 2 
WITH paid_order_totals AS (
  SELECT
    o.id AS order_id,
    o.customer_id,
    o.created_at,
    SUM(oi.quantity * oi.unit_price) AS order_total
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status = 'paid'
  GROUP BY o.id, o.customer_id, o.created_at
)
SELECT
  pot.order_id,
  INITCAP(TRIM(c.full_name)) AS customer_name,
  pot.created_at::date AS order_date,
  pot.order_total
FROM paid_order_totals pot
JOIN customers c ON c.id = pot.customer_id
WHERE pot.created_at >= TIMESTAMPTZ '2026-02-01 00:00:00+05'
  AND pot.created_at <  TIMESTAMPTZ '2026-03-01 00:00:00+05'
ORDER BY pot.created_at;
Задание 3 (Средний). Экспресс-доставки из JSONB

Найди все оплаченные заказы, у которых в поле delivery_info указано "express": true (используй оператор @>). Выведи номер заказа, службу доставки (courier), город доставки (из вложенного объекта address) и общую сумму заказа.

Показать решение
SQL · Решение задания 3 
SELECT
  o.id AS order_id,
  o.delivery_info ->> 'courier' AS courier,
  o.delivery_info #>> '{address, city}' AS delivery_city,
  SUM(oi.quantity * oi.unit_price) AS order_total
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = 'paid'
  AND o.delivery_info @> '{"express": true}'::jsonb
GROUP BY o.id, o.delivery_info
ORDER BY o.id;
Задание 4 (Продвинутый). Лидеры цен внутри каждой категории

С помощью CTE вычисли среднюю цену товаров для каждой категории в products. Затем выведи только те товары, чья цена строго выше средней цены своей категории. Добавь колонки: категория, название товара, цена, средняя цена по категории и цвет из specs (если цвета нет — вывести 'не указан').

Показать решение
SQL · Решение задания 4 
WITH category_avg AS (
  SELECT
    category,
    ROUND(AVG(price), 2) AS avg_category_price
  FROM products
  GROUP BY category
)
SELECT
  p.category,
  p.title,
  p.price,
  ca.avg_category_price,
  COALESCE(p.specs ->> 'color', 'не указан') AS color
FROM products p
JOIN category_avg ca ON ca.category = p.category
WHERE p.price > ca.avg_category_price
ORDER BY p.category, p.price DESC;
