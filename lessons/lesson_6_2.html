Партиционирование таблиц и материализованные представления в PostgreSQL

Главное в этом уроке
  • Научишься разрезать гигантские таблицы фактов на быстрые «ломтики» с помощью декларативного партиционирования (RANGE, LIST, HASH).
  • Увидишь вживую через EXPLAIN ANALYZE, как работает отсечение партиций (Partition Pruning) и как мгновенно убирать старые архивы командой DETACH PARTITION.
  • Разберёшься, чем обычное представление (VIEW) отличается от материализованного представления (MATERIALIZED VIEW), и ускоришь тяжёлый отчёт в сотни раз.
  • Узнаешь, как обновлять витрины командой REFRESH MATERIALIZED VIEW CONCURRENTLY без зависания дашбордов у пользователей.

01 Зачем резать таблицу на папки: что такое партиционирование

Представь школьную библиотеку, в которой все читательские карточки за последние 5 лет просто свалили в одну гигантскую картонную коробку. Когда библиотекарь просит найти все выданные книги за февраль 2026 года, тебе приходится перерыть всю гору бумаги до самого дна. А если директор скажет «выброси карточки за 2021 год», ты потратишь три дня, выискивая их по одной штучке!

Теперь представь, что библиотекарь поставил шкаф с аккуратными папками, подписанными по месяцам: «Январь 2026», «Февраль 2026», «Март 2026». Вся полка целиком по-прежнему называется «Архив выдач», но:

  • Чтобы посмотреть февраль, ты достаёшь ровно одну папку и даже не прикасаешься к остальным.
  • Чтобы удалить старый месяц, ты просто вынимаешь папку со шкафа целиком за 1 секунду.

В PostgreSQL этот приём называется декларативным партиционированием (Declarative Partitioning). Для твоих SQL-запросов существует одна привычная родительская таблица (Parent Table), но внутри база сама раскладывает строки по отдельным маленьким таблицам-файлам — партициям (Partitions). Когда ты пишешь WHERE sale_date ..., планировщик автоматически отбрасывает ненужные папки — эта магия называется отсечением партиций (Partition Pruning).

В PostgreSQL есть три способа нарезать таблицу на папки — выбор зависит от того, по какому признаку твои запросы чаще всего фильтруют данные:

Тип партиционирования Как раскладывает строки Типичный пример в DWH
RANGE (по диапазону) По интервалам «ОТ и ДО» (даты, числа) Продажи по месяцам (sale_date), логи событий по дням
LIST (по списку) По конкретным значениям из списка Регионы ('KZ', 'RU'), статусы, филиалы
HASH (по хэшу) Равномерно раскидывает по остатку от деления хэша Миллионы пользователей по customer_id, когда нет даты
Важная деталь границ в RANGE: Фраза FROM ('2026-01-01') TO ('2026-02-01') работает как полуинтервал [начало, конец) — то есть 1 января входит в январскую папку, а 1 февраля уже нет (оно пойдёт в февраль). Благодаря этому между месяцами никогда не бывает дыр и нахлёстов!

02 Создаём партиционированную таблицу фактов на 300 000 строк

Давай проверим партиционирование на деле, а не на 10 строчках! Подключись к нашему контейнеру с PostgreSQL 16 и базе learning_db:

Bash · Подключение к PostgreSQL 
docker compose up -d
docker exec -it course_pg_primary psql -U student -d learning_db

Пример 1. Создаём таблицу с PARTITION BY RANGE и наполняем её

В PostgreSQL есть одно железное правило: если ты хочешь создать PRIMARY KEY или UNIQUE на партиционированной таблице, ключ партиционирования (sale_date) обязан входить в этот первичный ключ. Иначе база не сможет быстро гарантировать уникальность без проверки всех остальных папок.

SQL · Создание партиционированной таблицы и 300 000 продаж 
DROP SCHEMA IF EXISTS dwh_part CASCADE;
CREATE SCHEMA dwh_part;

-- 1. Родительская таблица (сама строки не хранит — только маршрутизирует!)
CREATE TABLE dwh_part.fact_sales_part (
    sale_id      BIGINT GENERATED ALWAYS AS IDENTITY,
    sale_date    DATE NOT NULL,
    city_name    TEXT NOT NULL,
    category     TEXT NOT NULL,
    qty          INT NOT NULL,
    total_amount NUMERIC(10, 2) NOT NULL,
    PRIMARY KEY (sale_id, sale_date)
) PARTITION BY RANGE (sale_date);

-- 2. Создаём 3 папки-партиции на 1-й квартал 2026 года
CREATE TABLE dwh_part.fact_sales_2026_01
    PARTITION OF dwh_part.fact_sales_part
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE dwh_part.fact_sales_2026_02
    PARTITION OF dwh_part.fact_sales_part
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

CREATE TABLE dwh_part.fact_sales_2026_03
    PARTITION OF dwh_part.fact_sales_part
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');

-- 3. Генерируем 300 000 покупок равномерно за 90 дней (январь–март 2026)
INSERT INTO dwh_part.fact_sales_part (sale_date, city_name, category, qty, total_amount)
SELECT
    DATE '2026-01-01' + (g % 90),
    (ARRAY['Алматы', 'Астана', 'Костанай', 'Москва'])[1 + (g % 4)],
    (ARRAY['Электроника', 'Мерч', 'Аксессуары'])[1 + (g % 3)],
    1 + (g % 3),
    (1 + (g % 3)) * (5000 + (g % 5) * 3000)::NUMERIC(10, 2)
FROM generate_series(1, 300000) AS g;

-- Собираем свежую статистику для планировщика запросов
ANALYZE dwh_part.fact_sales_part;

-- 4. Смотрим через системную колонку tableoid, в какие папки легли строки
SELECT tableoid::regclass AS partition_name, COUNT(*) AS rows_count
FROM dwh_part.fact_sales_part
GROUP BY tableoid
ORDER BY partition_name;
Ответ PostgreSQL
       partition_name       | rows_count 
----------------------------+------------
 dwh_part.fact_sales_2026_01 |     103353
 dwh_part.fact_sales_2026_02 |      93324
 dwh_part.fact_sales_2026_03 |     103323
(3 rows)

Обрати внимание: мы сделали один обычный INSERT INTO dwh_part.fact_sales_part, но PostgreSQL сам аккуратно разложил 300 000 строк по трём разным файлам-партициям!

Пример 2. Что случится 1 апреля, если забыть создать новую папку?

Это классический ночной кошмар инженеров данных: наступает новый месяц, прилетает первая покупка за апрель, а подходящей партиции в базе нет. Давай воспроизведём эту ошибку прямо сейчас:

SQL · Попытка вставить дату без партиции 
INSERT INTO dwh_part.fact_sales_part (sale_date, city_name, category, qty, total_amount)
VALUES ('2026-04-05', 'Алматы', 'Мерч', 2, 44000.00);
Ошибка PostgreSQL
ERROR:  no partition of relation "fact_sales_part" found for row
DETAIL:  Partition key of the failing row contains (sale_date) = (2026-04-05).

PostgreSQL честно говорит: «Я не знаю, в какую папку положить 5 апреля!». Как защититься? Во-первых, создавать партиции на следующие месяцы заранее (автоматическим скриптом или расширением pg_partman). Во-вторых, можно добавить страховочную папку DEFAULT — туда временно попадут все строки, для которых не нашлось своего интервала, чтобы ночная загрузка не упала.

SQL · Создаём партицию на апрель и страховочную DEFAULT-партицию 
-- Создаём партицию на апрель 2026
CREATE TABLE dwh_part.fact_sales_2026_04
    PARTITION OF dwh_part.fact_sales_part
    FOR VALUES FROM ('2026-04-01') TO ('2026-05-01');

-- Добавляем страховочную папку для любых других дат
CREATE TABLE dwh_part.fact_sales_default
    PARTITION OF dwh_part.fact_sales_part
    DEFAULT;

-- Повторяем вставку — теперь всё проходит без ошибок!
INSERT INTO dwh_part.fact_sales_part (sale_date, city_name, category, qty, total_amount)
VALUES ('2026-04-05', 'Алматы', 'Мерч', 2, 44000.00);
Ответ PostgreSQL
INSERT 0 1

03 Магия Partition Pruning и мгновенная очистка архивов

Давай посмотрим, какую реальную выгоду мы получили от нарезки таблицы. Сравним две главные операции любого хранилища данных:

Операция Было (одна огромная таблица) Стало (партиции по месяцам)
Отчёт за 1 месяц Сканирует все 300 000 строк (или огромный B-Tree индекс) Читает только 1 папку (93 324 строки), остальные отбрасывает
Удаление старого месяца Медленный DELETE, блокировки, раздувание таблицы и долгий VACUUM Мгновенный DETACH PARTITION + DROP TABLE за пару миллисекунд

Пример 3. Проверяем отсечение партиций через EXPLAIN ANALYZE

Запустим подсчёт выручки за февраль 2026 года и заглянем внутрь плана выполнения:

SQL · Проверка Partition Pruning 
EXPLAIN (ANALYZE, COSTS OFF)
SELECT city_name, SUM(total_amount) AS feb_revenue
FROM dwh_part.fact_sales_part
WHERE sale_date >= DATE '2026-02-01'
  AND sale_date <  DATE '2026-03-01'
GROUP BY city_name
ORDER BY feb_revenue DESC;
План выполнения PostgreSQL (EXPLAIN ANALYZE)
 Sort (actual time=24.112..24.114 rows=4 loops=1)
   Sort Key: (sum(total_amount)) DESC
   Sort Method: quicksort  Memory: 25kB
   ->  HashAggregate (actual time=24.085..24.088 rows=4 loops=1)
         Group Key: city_name
         ->  Seq Scan on fact_sales_2026_02 fact_sales_part (actual time=0.014..11.640 rows=93324 loops=1)
               Filter: ((sale_date >= '2026-02-01'::date) AND (sale_date < '2026-03-01'::date))
 Planning Time: 0.245 ms
 Execution Time: 24.180 ms

Посмотри на строчку Seq Scan on fact_sales_2026_02! Январь, март, апрель и default даже не упоминаются в плане — PostgreSQL мгновенно отсёк лишние 200 000 строк ещё на этапе планирования. Именно так мы решили проблему медленного перебора всей «коробки с карточками» из начала урока!

✗ Как НЕ надо
SELECT SUM(total_amount)
FROM dwh_part.fact_sales_part
WHERE EXTRACT(MONTH FROM sale_date)
      = 2;

Функция вокруг sale_date ослепляет планировщик: Partition Pruning не сработает, и база просканирует все 5 партиций целиком!

✓ Как правильно
SELECT SUM(total_amount)
FROM dwh_part.fact_sales_part
WHERE sale_date >= '2026-02-01'
  AND sale_date <  '2026-03-01';

Сравнивай саму колонку sale_date напрямую с границами дат — тогда отсечение сработает идеально.

Пример 4. Мгновенная архивация старого месяца через DETACH PARTITION

Представь, что январь 2026 года устарел и больше не нужен в оперативной витрине, но удалять его навсегда пока страшно — вдруг бухгалтерия попросит сверку? Вместо тяжёлого DELETE FROM ... WHERE sale_date < '2026-02-01' мы просто отцепляем январскую папку от шкафа!

SQL · Мгновенное отцепление партиции без DELETE 
-- Отцепляем январскую папку (в продакшене добавляют слово CONCURRENTLY!)
ALTER TABLE dwh_part.fact_sales_part
    DETACH PARTITION dwh_part.fact_sales_2026_01;

-- В родительской таблице января больше нет
SELECT tableoid::regclass AS partition_name, COUNT(*) AS rows_count
FROM dwh_part.fact_sales_part
GROUP BY tableoid
ORDER BY partition_name;

-- Зато данные января спокойно лежат в отдельной архивной таблице!
SELECT COUNT(*) AS archived_jan_rows
FROM dwh_part.fact_sales_2026_01;

-- Если архив больше не нужен, его можно удалить мгновенно:
-- DROP TABLE dwh_part.fact_sales_2026_01;
Ответ PostgreSQL
       partition_name       | rows_count 
----------------------------+------------
 dwh_part.fact_sales_2026_02 |      93324
 dwh_part.fact_sales_2026_03 |     103323
 dwh_part.fact_sales_2026_04 |          1
(3 rows)

 archived_jan_rows 
-------------------
            103353
(1 row)
Совет для продакшена: На живой базе с активными пользователями всегда пиши ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY (доступно начиная с PostgreSQL 14). Обычный DETACH на долю секунды вешает жёсткую блокировку на всю родительскую таблицу, а вариант с CONCURRENTLY аккуратно ждёт завершения текущих запросов и никому не мешает.

04 Обычное VIEW против Материализованного (MATERIALIZED VIEW)

Партиционирование отлично помогло сократить объём чтения с 300 000 строк до 93 000. Но представь, что каждый понедельник в 9:00 утра 500 менеджеров одновременно открывают один и тот же дашборд: «Выручка по городам и категориям за каждый месяц». Даже если запрос бегает за 50 миллисекунд, 500 одинаковых тяжёлых подсчётов подряд перегрузят процессор!

Подумай о разнице между рецептом борща и готовой кастрюлей борща в холодильнике:

  • Обычное представление (VIEW) — это просто сохранённый рецепт. Оно не хранит никаких данных на диске. Каждый раз, когда менеджер делает SELECT * FROM v_revenue, PostgreSQL заново «режет овощи и варит суп» — бежит в fact_sales_part и заново суммирует сотни тысяч строк.
  • Материализованное представление (MATERIALIZED VIEW) — это готовая кастрюля. PostgreSQL один раз выполняет тяжёлый GROUP BY и физически сохраняет маленькую готовую табличку на диск. Когда 500 менеджеров открывают дашборд, база не считает ничего заново — она за доли миллисекунды отдаёт 25 готовых строчек!

Пример 5. Создаём материализованную витрину и замеряем ускорение

Давай создадим MATERIALIZED VIEW поверх нашей партиционированной таблицы и сравним скорость отчёта за февраль с тем, что мы видели в Примере 3 (там было 24.18 ms):

SQL · Создание материализованной витрины и замер скорости 
DROP MATERIALIZED VIEW IF EXISTS dwh_part.mv_monthly_city_revenue;

-- Создаём витрину и сразу наполняем её данными (WITH DATA)
CREATE MATERIALIZED VIEW dwh_part.mv_monthly_city_revenue AS
SELECT
    DATE_TRUNC('month', sale_date)::DATE AS month_start,
    city_name,
    category,
    SUM(qty)          AS total_qty,
    SUM(total_amount) AS total_revenue
FROM dwh_part.fact_sales_part
GROUP BY DATE_TRUNC('month', sale_date)::DATE, city_name, category
WITH DATA;

-- На материализованном представлении можно строить обычные индексы!
CREATE INDEX idx_mv_month ON dwh_part.mv_monthly_city_revenue (month_start);

-- Замеряем скорость того же февральского отчёта по готовой витрине
EXPLAIN (ANALYZE, COSTS OFF)
SELECT city_name, SUM(total_revenue) AS feb_revenue
FROM dwh_part.mv_monthly_city_revenue
WHERE month_start = DATE '2026-02-01'
GROUP BY city_name
ORDER BY feb_revenue DESC;
План выполнения PostgreSQL (EXPLAIN ANALYZE)
 Sort (actual time=0.058..0.060 rows=4 loops=1)
   Sort Key: (sum(total_revenue)) DESC
   Sort Method: quicksort  Memory: 25kB
   ->  HashAggregate (actual time=0.044..0.046 rows=4 loops=1)
         Group Key: city_name
         ->  Seq Scan on mv_monthly_city_revenue (actual time=0.012..0.021 rows=12 loops=1)
               Filter: (month_start = '2026-02-01'::date)
               Rows Removed by Filter: 13
 Planning Time: 0.140 ms
 Execution Time: 0.088 ms

Сравни результат: было 24.18 ms и 93 324 прочитанных строки — стало 0.088 ms и всего 25 строк! Ускорение почти в 275 раз, а на реальной таблице с 50 миллионами покупок разница будет в тысячи раз. Проблема перегрузки процессора от 500 менеджеров решена!

05 Обновление витрины без простоя (REFRESH ... CONCURRENTLY)

У готовой кастрюли в холодильнике есть один очевидный минус: если в магазин завезли свежие покупки, сама собой кастрюля не обновится! Материализованное представление в PostgreSQL не обновляется автоматически при вставке новых строк в fact_sales_part. Его нужно пересчитывать командой REFRESH MATERIALIZED VIEW (обычно по расписанию — раз в 15 минут, раз в час или ночью).

Но здесь прячется коварная ловушка: обычный REFRESH MATERIALIZED VIEW на всё время пересчёта вешает замок ACCESS EXCLUSIVE. Если витрина пересчитывается 2 минуты, то все 2 минуты дашборд директора просто висит и не открывается! Чтобы читатели продолжали видеть старые данные, пока в фоне готовятся свежие, добавляют ключевое слово CONCURRENTLY.

Пример 6. Ошибка CONCURRENTLY без уникального индекса и её решение

Добавим в апрель новую продажу из Астаны и попробуем обновить витрину в режиме CONCURRENTLY прямо сейчас:

SQL · Вставляем новую продажу и пробуем CONCURRENTLY 
-- Пришла новая продажа за апрель 2026
INSERT INTO dwh_part.fact_sales_part (sale_date, city_name, category, qty, total_amount)
VALUES ('2026-04-10', 'Астана', 'Электроника', 1, 35000.00);

-- Пробуем обновить витрину без блокировки читателей
REFRESH MATERIALIZED VIEW CONCURRENTLY dwh_part.mv_monthly_city_revenue;
Ошибка PostgreSQL
ERROR:  cannot refresh materialized view "dwh_part.mv_monthly_city_revenue" concurrently
HINT:  Create a unique index with no WHERE clause on one or more columns of the materialized view.

Зачем PostgreSQL требует UNIQUE INDEX? Чтобы обновлять витрину незаметно для пользователей, база должна сравнить старую версию витрины с новой строчка к строчке и точечно заменить только изменившиеся строки (сделать внутренний diff). Без уникального ключа она просто не знает, какая новая строка соответствует какой старой! Исправляем в две команды:

SQL · Создаём UNIQUE INDEX и обновляем витрину без блокировок 
-- 1. Создаём уникальный индекс по колонкам группировки (без WHERE!)
CREATE UNIQUE INDEX idx_mv_monthly_city_rev_uniq
    ON dwh_part.mv_monthly_city_revenue (month_start, city_name, category);

-- 2. Теперь обновление проходит мягко и не мешает дашбордам!
REFRESH MATERIALIZED VIEW CONCURRENTLY dwh_part.mv_monthly_city_revenue;

-- 3. Проверяем свежие данные за апрель
SELECT month_start, city_name, category, total_qty, total_revenue
FROM dwh_part.mv_monthly_city_revenue
WHERE month_start = DATE '2026-04-01'
ORDER BY total_revenue DESC;
Ответ PostgreSQL
 month_start | city_name |  category   | total_qty | total_revenue 
-------------+-----------+-------------+-----------+---------------
 2026-04-01  | Алматы    | Мерч        |         2 |      44000.00
 2026-04-01  | Астана    | Электроника |         1 |      35000.00
(2 rows)
✗ Как НЕ надо
-- Вешает ACCESS EXCLUSIVE!
REFRESH MATERIALIZED VIEW
  dwh_part.mv_monthly_city_revenue;

Пока идёт пересчёт, любые SELECT от BI-систем и аналитиков встают в очередь и ждут.

✓ Как правильно
-- Нужен UNIQUE INDEX (один раз)
REFRESH MATERIALIZED VIEW
  CONCURRENTLY
  dwh_part.mv_monthly_city_revenue;

Читатели мгновенно получают старый снимок данных, а после расчёта база незаметно подменяет отличия.

Помни о цене свежести: MATERIALIZED VIEW всегда показывает данные с задержкой на момент последнего REFRESH. Если бизнесу нужны цифры «секунда в секунду» (например, баланс банковской карты), материализованное представление не подойдёт. Зато для аналитических отчётов, которые достаточно обновлять раз в час или ночью, это идеальный инструмент!

06 Шпаргалка урока перед практикой

Короткий чек-лист главных правил этого урока — держи его под рукой, пока решаешь задачи:

Инструмент / Правило Как работает и на что смотреть
PARTITION BY RANGE / LIST / HASH Режет одну гигантскую таблицу на маленькие файлы-партиции. Ключ партиционирования обязан входить в PRIMARY KEY.
Partition Pruning Отсечение ненужных папок на этапе планирования. Не оборачивай колонку партиционирования в функции вроде EXTRACT() в WHERE!
DEFAULT и DETACH Папка DEFAULT спасёт от падения вставки вне диапазона. DETACH PARTITION [CONCURRENTLY] отцепляет старый месяц за миллисекунды без DELETE.
MATERIALIZED VIEW Сохраняет результат тяжёлого GROUP BY на диск. Можно вешать индексы. Не обновляется само — нужен REFRESH.
REFRESH ... CONCURRENTLY Обновляет витрину без блокировки читателей. Обязательное условие — наличие UNIQUE INDEX без WHERE.

07 Мини-практикум для закрепления

Выполни 4 автономных задания в learning_db. Каждая задача полностью независима — она сама создаёт нужную схему/таблицы, поэтому ты можешь решать их в любом порядке.

Задание 1 (Базовый). Партиционирование по странам (LIST)

Создай схему dwh_part (если её ещё нет) и таблицу dwh_part.lab_list_orders (order_id INT, country_code TEXT, amount NUMERIC(10, 2)) с партиционированием PARTITION BY LIST (country_code) и первичным ключом (order_id, country_code). Создай 3 партиции: для 'KZ', для 'RU' и папку DEFAULT для остальных стран. Вставь 4 заказа (из 'KZ', 'RU', 'UZ', 'KZ') и проверь через EXPLAIN (COSTS OFF), что запрос WHERE country_code = 'KZ' обращается только к одной партиции.

Показать решение
SQL · Эталонное решение задания 1 
CREATE SCHEMA IF NOT EXISTS dwh_part;
DROP TABLE IF EXISTS dwh_part.lab_list_orders CASCADE;

CREATE TABLE dwh_part.lab_list_orders (
    order_id     INT NOT NULL,
    country_code TEXT NOT NULL,
    amount       NUMERIC(10, 2) NOT NULL,
    PRIMARY KEY (order_id, country_code)
) PARTITION BY LIST (country_code);

CREATE TABLE dwh_part.lab_list_orders_kz
    PARTITION OF dwh_part.lab_list_orders FOR VALUES IN ('KZ');

CREATE TABLE dwh_part.lab_list_orders_ru
    PARTITION OF dwh_part.lab_list_orders FOR VALUES IN ('RU');

CREATE TABLE dwh_part.lab_list_orders_other
    PARTITION OF dwh_part.lab_list_orders DEFAULT;

INSERT INTO dwh_part.lab_list_orders VALUES
    (1, 'KZ', 15000.00),
    (2, 'RU', 22000.00),
    (3, 'UZ',  9000.00),
    (4, 'KZ', 31000.00);

-- В плане должна остаться только одна партиция: lab_list_orders_kz
EXPLAIN (COSTS OFF)
SELECT * FROM dwh_part.lab_list_orders WHERE country_code = 'KZ';
Задание 2 (Средний). Поймай «потерянные» строки в DEFAULT-партиции

Создай таблицу dwh_part.lab_logs (log_id SERIAL, log_date DATE, msg TEXT) с PARTITION BY RANGE (log_date). Добавь партиции на май 2026 (2026-05-01 — 2026-06-01), июнь 2026 (2026-06-01 — 2026-07-01) и папку lab_logs_default. Вставь 4 события: по одному на май и июнь, и два события с ошибочной датой из июля ('2026-07-03' и '2026-07-15'). Выведи количество строк в каждой партиции через tableoid::regclass, чтобы увидеть, сколько строк осело в DEFAULT.

Показать решение
SQL · Эталонное решение задания 2 
CREATE SCHEMA IF NOT EXISTS dwh_part;
DROP TABLE IF EXISTS dwh_part.lab_logs CASCADE;

CREATE TABLE dwh_part.lab_logs (
    log_id   SERIAL,
    log_date DATE NOT NULL,
    msg      TEXT NOT NULL,
    PRIMARY KEY (log_id, log_date)
) PARTITION BY RANGE (log_date);

CREATE TABLE dwh_part.lab_logs_2026_05
    PARTITION OF dwh_part.lab_logs
    FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');

CREATE TABLE dwh_part.lab_logs_2026_06
    PARTITION OF dwh_part.lab_logs
    FOR VALUES FROM ('2026-06-01') TO ('2026-07-01');

CREATE TABLE dwh_part.lab_logs_default
    PARTITION OF dwh_part.lab_logs DEFAULT;

INSERT INTO dwh_part.lab_logs (log_date, msg) VALUES
    ('2026-05-10', 'Оплата прошла'),
    ('2026-06-14', 'Новый клиент'),
    ('2026-07-03', 'Июльский заказ #1'),
    ('2026-07-15', 'Июльский заказ #2');

SELECT tableoid::regclass AS partition_name, COUNT(*) AS rows_count
FROM dwh_part.lab_logs
GROUP BY tableoid
ORDER BY partition_name;
-- В lab_logs_default окажется 2 строки!
Задание 3 (Продвинутый). Быстрая витрина с обновлением CONCURRENTLY

Создай автономную таблицу dwh_part.lab_sales (id SERIAL PRIMARY KEY, category TEXT, amount NUMERIC(10, 2)) и вставь в неё 4 продажи по категориям 'Игры' и 'Книги'. Затем создай материализованное представление dwh_part.mv_lab_category_stats с количеством продаж и суммой выручки по каждой категории, добавь на него правильный UNIQUE INDEX, вставь ещё 1 продажу в категорию 'Игры' на 15000.00, обнови витрину через REFRESH MATERIALIZED VIEW CONCURRENTLY и проверь свежие итоги.

Показать решение
SQL · Эталонное решение задания 3 
CREATE SCHEMA IF NOT EXISTS dwh_part;
DROP MATERIALIZED VIEW IF EXISTS dwh_part.mv_lab_category_stats;
DROP TABLE IF EXISTS dwh_part.lab_sales;

CREATE TABLE dwh_part.lab_sales (
    id       SERIAL PRIMARY KEY,
    category TEXT NOT NULL,
    amount   NUMERIC(10, 2) NOT NULL
);

INSERT INTO dwh_part.lab_sales (category, amount) VALUES
    ('Игры',  12000.00),
    ('Игры',   8000.00),
    ('Книги',  4500.00),
    ('Книги',  5500.00);

CREATE MATERIALIZED VIEW dwh_part.mv_lab_category_stats AS
SELECT
    category,
    COUNT(*)    AS sales_count,
    SUM(amount) AS total_revenue
FROM dwh_part.lab_sales
GROUP BY category
WITH DATA;

-- Уникальный индекс обязателен для CONCURRENTLY
CREATE UNIQUE INDEX idx_mv_lab_cat_uniq
    ON dwh_part.mv_lab_category_stats (category);

-- Новая продажа
INSERT INTO dwh_part.lab_sales (category, amount) VALUES ('Игры', 15000.00);

-- Обновляем витрину без блокировок
REFRESH MATERIALIZED VIEW CONCURRENTLY dwh_part.mv_lab_category_stats;

SELECT * FROM dwh_part.mv_lab_category_stats ORDER BY total_revenue DESC;
-- Ожидаемый результат: Игры (3 шт, 35000.00), Книги (2 шт, 10000.00)
Задание 4 (Проектирование). Безопасная архивация прошлого года через DETACH

Создай партиционированную таблицу dwh_part.lab_events (event_id SERIAL, event_date DATE, title TEXT) с двумя годовыми партициями: lab_events_2025 (весь 2025 год) и lab_events_2026 (весь 2026 год). Добавь по 2 события в каждый год. Затем отцепи партицию за 2025 год командой DETACH PARTITION и двумя запросами SELECT докажи, что: 1) в основной таблице lab_events остались только 2 события за 2026 год; 2) события за 2025 год не пропали и доступны в самостоятельной таблице lab_events_2025.

Показать решение
SQL · Эталонное решение задания 4 
CREATE SCHEMA IF NOT EXISTS dwh_part;
DROP TABLE IF EXISTS dwh_part.lab_events CASCADE;
DROP TABLE IF EXISTS dwh_part.lab_events_2025;

CREATE TABLE dwh_part.lab_events (
    event_id   SERIAL,
    event_date DATE NOT NULL,
    title      TEXT NOT NULL,
    PRIMARY KEY (event_id, event_date)
) PARTITION BY RANGE (event_date);

CREATE TABLE dwh_part.lab_events_2025
    PARTITION OF dwh_part.lab_events
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

CREATE TABLE dwh_part.lab_events_2026
    PARTITION OF dwh_part.lab_events
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

INSERT INTO dwh_part.lab_events (event_date, title) VALUES
    ('2025-03-10', 'Весенняя акция 2025'),
    ('2025-11-28', 'Чёрная пятница 2025'),
    ('2026-01-15', 'Зимняя распродажа 2026'),
    ('2026-02-20', 'Старт нового каталога 2026');

-- Отцепляем 2025 год в архив
ALTER TABLE dwh_part.lab_events
    DETACH PARTITION dwh_part.lab_events_2025;

-- 1. В основной таблице только 2026 год (2 строки)
SELECT event_date, title FROM dwh_part.lab_events ORDER BY event_date;

-- 2. В архивной таблице полностью сохранён 2025 год (2 строки)
SELECT event_date, title FROM dwh_part.lab_events_2025 ORDER BY event_date;
