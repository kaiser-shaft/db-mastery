OLTP vs OLAP и размерное моделирование («Звезда» и «Снежинка»)

Главное в этом уроке
  • Поймёшь разницу между «кассовой» базой (OLTP) и базой для отчётов и графиков (OLAP / DWH).
  • Научишься проектировать таблицы фактов (fact_*), таблицы измерений (dim_*), выбирать правильное зерно (Grain) и суррогатные ключи.
  • Соберёшь в learning_db реальную схему «Звезда» (Star Schema) и схему «Снежинка» (Snowflake Schema) из сырого интернет-магазина.
  • Узнаешь две главные ловушки аналитиков: перезапись истории цен и задвоение выручки из-за смешивания гранулярностей (Fan-out).

01 Зачем делить базы на «кассу» и «кабинет директора» (OLTP vs OLAP)

Представь большой супермаркет вечером в пятницу. У десяти касс стоят очереди, и каждая касса делает одно и то же: быстро сканирует штрих-код, списывает деньги и выдаёт чек. Главная цель кассира — обслужить одного покупателя за 2 секунды и ничего не потерять.

А теперь представь, что в этот же момент в зал заходит директор сети и говорит кассиру: «Подожди пробивать покупки! Перебери-ка все бумажные чеки за последние три года и скажи, в какой день недели в магазинах Алматы чаще всего покупали шоколад с орехами вместе с кофе». Что произойдёт? Очередь встанет намертво, покупатели уйдут к конкурентам, а директор всё равно будет ждать ответ до ночи.

В мире баз данных происходит ровно то же самое. Поэтому инженеры разделили нагрузку на два разных мира:

  • OLTP (Online Transaction Processing) — это «касса». Боевая база сайта, игры или банковского приложения. В ней каждую секунду прилетают тысячи крошечных операций: «создать заказ», «списать 500 тенге», «обновить адрес доставки». Здесь важна скорость одной короткой транзакции и строгий порядок без дубликатов (нормализация, 3НФ).
  • OLAP (Online Analytical Processing) — это «кабинет директора и аналитиков». Сюда периодически копируют данные из кассы, приводят их в удобный для расчётов вид и складывают в специальное хранилище данных (DWH — Data Warehouse). Здесь почти ничего не меняют по одной строчке, зато часто запускают тяжёлые запросы с SUM, AVG и GROUP BY по миллионам строк за годы работы.
Критерий OLTP (Касса) OLAP / DWH (Аналитика)
Кто пользуется Пользователи сайта, приложения, игроки Аналитики, директора, BI-графики, ML-модели
Типичные запросы Много коротких INSERT, UPDATE, точечных SELECT по id Мало запросов, но огромные SELECT с GROUP BY и SUM
Сколько строк читает запрос От 1 до 50 строк От сотен тысяч до миллиардов строк
Устройство таблиц Нормализовано (3НФ) — минимум дублирования Денормализовано («Звезда» / «Снежинка») — минимум JOIN
Глубина истории Обычно актуальные данные (месяцы) Архив за 3–10 лет для сравнения год к году
Школьная аналогия: OLTP — это твой текущий бумажный дневник, куда учитель каждый день быстро ставит новые оценки и может исправить опечатку. OLAP — это сводная таблица завуча в конце учебного года, где собраны оценки всех классов за пять лет, чтобы сравнить, как изменилась успеваемость по математике.

02 Боль аналитики в OLTP: собираем «боевой» магазин

Чтобы не верить на слово, давай сами почувствуем, почему строить отчёты прямо по нормализованной OLTP-базе неудобно. Запусти контейнер с PostgreSQL 16 и подключись к нашей учебной базе learning_db.

Bash · Подключение к PostgreSQL 
docker compose up -d
docker exec -it course_pg_primary psql -U student -d learning_db

Представь, что у нас есть интернет-магазин гик-товаров «ПиксельМаркет». Программисты бэкенда спроектировали базу по всем правилам третьей нормальной формы (3НФ): страны лежат отдельно от городов, города отдельно от клиентов, категории отдельно от товаров, а шапка заказа отдельно от списка позиций в чеке. Получилось 7 связанных таблиц.

Таблица в oltp_shop Что хранит С кем связана
countries и cities Справочники стран и городов cities.country_id → countries.id
categories и products Категории и текущий каталог товаров products.category_id → categories.id
customers Покупатели и их город customers.city_id → cities.id
orders и order_items Заказы и купленные позиции в чеке order_items → orders, products

Пример 1. Подготовка учебной OLTP-схемы

Этот скрипт можно безопасно перезапускать сколько угодно раз благодаря DROP SCHEMA IF EXISTS ... CASCADE. Обрати внимание на заказ №1004 (он отменён) и заказ №1007 (он прошёл уже во 2-м квартале) — они пригодятся для проверки точности отчётов.

SQL · Подготовка данных OLTP 
DROP SCHEMA IF EXISTS oltp_shop CASCADE;
CREATE SCHEMA oltp_shop;

-- 1. География (нормализована на 2 уровня)
CREATE TABLE oltp_shop.countries (
    id   INT PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE oltp_shop.cities (
    id         INT PRIMARY KEY,
    name       TEXT NOT NULL,
    country_id INT NOT NULL REFERENCES oltp_shop.countries(id)
);

-- 2. Каталог товаров (нормализован на 2 уровня)
CREATE TABLE oltp_shop.categories (
    id   INT PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE oltp_shop.products (
    id            INT PRIMARY KEY,
    title         TEXT NOT NULL,
    category_id   INT NOT NULL REFERENCES oltp_shop.categories(id),
    current_price NUMERIC(10, 2) NOT NULL
);

-- 3. Покупатели и заказы
CREATE TABLE oltp_shop.customers (
    id        INT PRIMARY KEY,
    full_name TEXT NOT NULL,
    city_id   INT NOT NULL REFERENCES oltp_shop.cities(id),
    segment   TEXT NOT NULL
);

CREATE TABLE oltp_shop.orders (
    id          INT PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES oltp_shop.customers(id),
    order_date  DATE NOT NULL,
    status      TEXT NOT NULL
);

CREATE TABLE oltp_shop.order_items (
    id                INT PRIMARY KEY,
    order_id          INT NOT NULL REFERENCES oltp_shop.orders(id),
    product_id        INT NOT NULL REFERENCES oltp_shop.products(id),
    qty               INT NOT NULL,
    price_at_purchase NUMERIC(10, 2) NOT NULL,
    discount          NUMERIC(10, 2) NOT NULL DEFAULT 0
);

Пример 2. Отчёт директора напрямую по OLTP-таблицам

Теперь директор просит простой отчёт: «Покажи выручку и количество проданных штук по городам и категориям за 1-й квартал 2026 года, только по оплаченным заказам». Посмотри, сколько цепочек JOIN приходится сплести в нормализованной базе ради одного базового вопроса:

SQL · Тяжёлый отчёт в OLTP (5 JOIN) 
SELECT
    ci.name AS city_name,
    cat.name AS category_name,
    SUM(oi.qty) AS items_sold,
    SUM(oi.qty * oi.price_at_purchase - oi.discount) AS revenue
FROM oltp_shop.order_items oi
JOIN oltp_shop.orders     o   ON o.id   = oi.order_id
JOIN oltp_shop.customers  cu  ON cu.id  = o.customer_id
JOIN oltp_shop.cities     ci  ON ci.id  = cu.city_id
JOIN oltp_shop.products   p   ON p.id   = oi.product_id
JOIN oltp_shop.categories cat ON cat.id = p.category_id
WHERE o.status = 'paid'
  AND o.order_date >= DATE '2026-01-01'
  AND o.order_date <  DATE '2026-04-01'
GROUP BY ci.name, cat.name
ORDER BY revenue DESC;

Пока строк всего одиннадцать, запрос кажется безобидным. Но вернёмся к нашей проблеме из начала раздела: в реальном магазине таких таблиц не 7, а 80, и в order_items лежат десятки миллионов строк. Каждому аналитику приходится помнить кучу хрупких правил: не забыть status = 'paid', не забыть вычесть discount, соединить 6 таблиц и при этом не положить боевую кассу. Чтобы решить эту боль раз и навсегда, придумали размерное моделирование.

03 Размерное моделирование: Факты, Измерения и Зерно

Представь экран статистики в компьютерной игре после матча. В центре на табло горят числа — сколько голов ты забил, сколько урона нанёс, сколько монет заработал. Их можно складывать и считать среднее. А по бокам написан контекст — за какого героя ты играл, на какой карте, в какой день и против какой команды. По контексту удобно фильтровать («покажи мои матчи только на карте Dust2 за прошлую неделю»).

Ровно так же Ральф Кимбалл предложил делить все таблицы в аналитическом хранилище (Dimensional Modeling):

  • Таблица фактов (Fact Table, префикс fact_) — хранит события бизнеса и измеримые числа-метрики (выручка, количество, скидка, вес). В ней миллионы строк, но сами строки узкие: в основном числа и ссылки на справочники.
  • Таблица измерений (Dimension Table, префикс dim_) — отвечает на вопросы «Кто? Что? Где? Когда?» (dim_customer, dim_product, dim_date). Строк в ней немного, зато колонок с понятными текстовыми описаниями много.
  • Зерно / Гранулярность (Grain) — самый важный термин в проектировании DWH! Зерно чётко отвечает на вопрос: «Что именно описывает ОДНА строка таблицы фактов?» Например: одна позиция одного товара в одном оплаченном чеке.
  • Суррогатный ключ (Surrogate Key, суффикс _sk) — искусственный числовой ID внутри хранилища (например, product_sk), не привязанный к бизнес-ключам из OLTP (product_bk). Если завтра магазин переедет на новую кассовую программу с другими артикулами, хранилище не сломается!
✗ Как НЕ надо
-- Цена берётся из каталога!
SELECT SUM(f.qty * p.price)
FROM fact_sales f
JOIN dim_product p
  ON p.id = f.product_id;

Как только клавиатура подорожает с 32 000 до 35 000, выручка за прошлый январь волшебным образом вырастет. История испорчена!

✓ Как правильно
-- Сумма зафиксирована в факте
SELECT SUM(f.total_amount)
FROM fact_sales f;

Цена продажи, скидка и итоговая сумма сохраняются прямо в строке fact_sales на момент покупки и никогда не плывут.

Золотое правило зерна: Никогда не пиши CREATE TABLE fact_..., пока не сформулируешь вслух одно предложение о зерне таблицы. Нельзя в одну таблицу фактов одновременно класть и строки товаров из чека, и итоговую сумму доставки на весь заказ — при подсчёте SUM() ты получишь ложные цифры.

04 Схема «Звезда» (Star Schema) — золотой стандарт аналитики

Представь школьный двор в день ярмарки. В самом центре стоит главный стенд с кассой, куда стекаются все билеты о покупках. А прямо вокруг него на расстоянии одного шага стоят четыре аккуратных столика: «Календарь», «Товары», «Покупатели» и «Магазины». Тебе не нужно бежать через три коридора, чтобы узнать, из какого города покупатель — вся информация о нём лежит на одном столике!

Если нарисовать такую структуру таблиц, получится схема «Звезда» (Star Schema): в центре лежит таблица фактов fact_sales, а от неё во все стороны расходятся лучи к плоским (денормализованным) таблицам измерений.

Что было в oltp_shop (7 таблиц) Что стало в dwh_star (4 таблицы)
products + categories Одна плоская dim_product (категория уже внутри!)
customers + cities + countries Одна плоская dim_customer (город и страна уже внутри!)
Только колонка order_date Готовый справочник dim_date с кварталами, днями недели и флагом выходного
orders + order_items (включая отменённые) Чистая fact_sales с зерном «1 позиция в оплаченном заказе» и готовой total_amount

Пример 3. Создаём схему «Звезда» в PostgreSQL

Обрати внимание на хитрый инженерный трюк с ключом date_sk: вместо случайных номеров 1, 2, 3 в DWH используют целое число формата ГГГГММДД (например, 20260110). Его легко читать глазами, удобно сортировать и быстро фильтровать по диапазонам!

SQL · Создание таблиц схемы «Звезда» 
DROP SCHEMA IF EXISTS dwh_star CASCADE;
CREATE SCHEMA dwh_star;

-- Измерение 1: Календарь (Date Dimension)
CREATE TABLE dwh_star.dim_date (
    date_sk     INT PRIMARY KEY,      -- формат YYYYMMDD, например 20260110
    full_date   DATE NOT NULL UNIQUE,
    year_num    INT NOT NULL,
    quarter_num INT NOT NULL,
    month_num   INT NOT NULL,
    day_of_week INT NOT NULL,         -- 1 = Пн ... 7 = Вс
    is_weekend  BOOLEAN NOT NULL
);

-- Измерение 2: Товары (денормализовано вместе с категорией)
CREATE TABLE dwh_star.dim_product (
    product_sk    SERIAL PRIMARY KEY, -- суррогатный ключ DWH
    product_bk    INT NOT NULL UNIQUE,-- бизнес-ключ из OLTP
    product_title TEXT NOT NULL,
    category_name TEXT NOT NULL
);

-- Измерение 3: Покупатели (денормализовано вместе с городом и страной)
CREATE TABLE dwh_star.dim_customer (
    customer_sk   SERIAL PRIMARY KEY,
    customer_bk   INT NOT NULL UNIQUE,
    full_name     TEXT NOT NULL,
    segment       TEXT NOT NULL,
    city_name     TEXT NOT NULL,
    country_name  TEXT NOT NULL
);

-- Таблица фактов: Зерно = 1 позиция товара в оплаченном заказе
CREATE TABLE dwh_star.fact_sales (
    sale_sk         BIGSERIAL PRIMARY KEY,
    order_bk        INT NOT NULL,     -- вырожденное измерение (номер чека)
    date_sk         INT NOT NULL REFERENCES dwh_star.dim_date(date_sk),
    product_sk      INT NOT NULL REFERENCES dwh_star.dim_product(product_sk),
    customer_sk     INT NOT NULL REFERENCES dwh_star.dim_customer(customer_sk),
    qty             INT NOT NULL CHECK (qty > 0),
    unit_price      NUMERIC(10, 2) NOT NULL,
    discount_amount NUMERIC(10, 2) NOT NULL DEFAULT 0,
    total_amount    NUMERIC(10, 2) NOT NULL
);

Пример 4. Ловушка порядка загрузки и наполнение «Звезды»

Новички часто пытаются сначала загрузить данные в таблицу фактов, а справочники заполнить «потом». Давай посмотрим, как PostgreSQL мгновенно пресечёт такую попытку:

SQL · Попытка загрузить факт раньше измерений 
-- Пытаемся вставить продажу, пока dim_date и dim_product пустые
INSERT INTO dwh_star.fact_sales
    (order_bk, date_sk, product_sk, customer_sk, qty, unit_price, discount_amount, total_amount)
VALUES
    (1001, 20260110, 1, 1, 1, 32000.00, 2000.00, 30000.00);
Ошибка PostgreSQL
ERROR:  insert or update on table "fact_sales" violates foreign key constraint "fact_sales_date_sk_fkey"
DETAIL:  Key (date_sk)=(20260110) is not present in table "dim_date".

Причина проста: внешний ключ (FOREIGN KEY) защищает хранилище от «сиротских» фактов, у которых нет описания в справочниках. Отсюда железное правило любого пайплайна загрузки данных: сначала всегда наполняем измерения (dim_*), и только потом — таблицу фактов (fact_*).

SQL · Правильная загрузка «Звезды» из OLTP 
-- Шаг 1. Генерируем календарь на весь 2026 год одной командой
INSERT INTO dwh_star.dim_date
    (date_sk, full_date, year_num, quarter_num, month_num, day_of_week, is_weekend)
SELECT
    TO_CHAR(d, 'YYYYMMDD')::INT,
    d::DATE,
    EXTRACT(YEAR FROM d)::INT,
    EXTRACT(QUARTER FROM d)::INT,
    EXTRACT(MONTH FROM d)::INT,
    EXTRACT(ISODOW FROM d)::INT,
    EXTRACT(ISODOW FROM d) IN (6, 7)
FROM generate_series(DATE '2026-01-01', DATE '2026-12-31', INTERVAL '1 day') AS d
ON CONFLICT (date_sk) DO NOTHING;

-- Шаг 2. Загружаем плоский справочник товаров (соединяем products + categories)
INSERT INTO dwh_star.dim_product (product_bk, product_title, category_name)
SELECT p.id, p.title, c.name
FROM oltp_shop.products p
JOIN oltp_shop.categories c ON c.id = p.category_id
ON CONFLICT (product_bk) DO NOTHING;

-- Шаг 3. Загружаем плоский справочник покупателей (customers + cities + countries)
INSERT INTO dwh_star.dim_customer (customer_bk, full_name, segment, city_name, country_name)
SELECT cu.id, cu.full_name, cu.segment, ci.name, co.name
FROM oltp_shop.customers cu
JOIN oltp_shop.cities    ci ON ci.id = cu.city_id
JOIN oltp_shop.countries co ON co.id = ci.country_id
ON CONFLICT (customer_bk) DO NOTHING;

Пример 5. Тот самый отчёт директора — теперь по схеме «Звезда»

✗ Как НЕ надо · Ловушка гранулярности (Fan-out / задвоение сумм)
-- Заказ 1001 содержит 2 позиции, а доставка (1500) указана на весь заказ!
-- Наивный JOIN размножит строку доставки на каждую позицию в чеке:
SELECT o.id, SUM(o.delivery_fee) AS broken_delivery, SUM(oi.qty * oi.price_at_purchase) AS items_sum
FROM orders_with_delivery o
JOIN oltp_shop.order_items oi ON oi.order_id = o.id
GROUP BY o.id; -- Для заказа 1001 выдаст 3000 вместо 1500!

Когда соединяют две таблицы с разным зерном («1 строка = 1 заказ» и «1 строка = 1 товар в заказе»), метрики верхнего уровня (доставка, бонус на чек) незаметно умножаются на число товаров. Это самая дорогая ошибка в отчётности!

✓ Как правильно · Разделять зерно или агрегировать до JOIN
-- Сначала свёртываем позиции до зерна "1 заказ", и только потом соединяем с доставкой:
WITH items_by_order AS (
    SELECT order_id, SUM(qty * price_at_purchase - discount) AS items_sum
    FROM oltp_shop.order_items
    GROUP BY order_id
)
SELECT o.id, o.delivery_fee, i.items_sum
FROM orders_with_delivery o
JOIN items_by_order i ON i.order_id = o.id;

В DWH для метрик разного зерна создают две отдельные таблицы фактов (fact_sales по товарам и fact_orders по заказам), либо честно распределяют доставку пропорционально по каждой строке товара.

05 Схема «Снежинка» (Snowflake Schema) — когда лучи ветвятся

Посмотри ещё раз на таблицу dwh_star.dim_customer из нашей «Звезды». Если в магазине миллион покупателей из Алматы, то слово 'Алматы' и слово 'Казахстан' будут повторены в таблице миллион раз. А если нам ещё нужно хранить население города, часовой пояс и код валюты страны?

Если начать выносить повторяющиеся атрибуты из таблиц измерений в отдельные под-таблицы (dim_customer → dim_city → dim_country), то лучи нашей звезды начнут ветвиться, как кристаллы настоящей снежинки. Так появляется схема «Снежинка» (Snowflake Schema) — это та же «Звезда», но с нормализованными измерениями.

Пример 6. Собираем «Снежинку» и сравниваем со «Звездой»

Давай соберём схему dwh_snow из тех же данных oltp_shop и выполним точно такой же отчёт директора. Обрати внимание, что таблица fact_sales в центре вообще не изменилась — изменились только «лучи» вокруг неё!

SQL · Схема «Снежинка» и аналитический запрос

    country_name TEXT NOT NULL
);

CREATE TABLE dwh_snow.dim_city (
    city_sk    SERIAL PRIMARY KEY,

    city_name  TEXT NOT NULL,
    country_sk INT NOT NULL REFERENCES dwh_snow.dim_country(country_sk)
);

CREATE TABLE dwh_snow.dim_customer (
    customer_sk SERIAL PRIMARY KEY,
    customer_bk INT NOT NULL UNIQUE,
    full_name   TEXT NOT NULL,
    segment     TEXT NOT NULL,
    city_sk     INT NOT NULL REFERENCES dwh_snow.dim_city(city_sk)
);

-- Ветка товаров: category <- product
CREATE TABLE dwh_snow.dim_category (
    category_sk   SERIAL PRIMARY KEY,
    category_bk   INT NOT NULL UNIQUE,
    category_name TEXT NOT NULL
);

CREATE TABLE dwh_snow.dim_product (
    product_sk    SERIAL PRIMARY KEY,
    product_bk    INT NOT NULL UNIQUE,
    product_title TEXT NOT NULL,
    category_sk   INT NOT NULL REFERENCES dwh_snow.dim_category(category_sk)
);

-- Календарь и таблица фактов (такие же, как в «Звезде»)
CREATE TABLE dwh_snow.dim_date AS TABLE dwh_star.dim_date;
ALTER TABLE dwh_snow.dim_date ADD PRIMARY KEY (date_sk);

CREATE TABLE dwh_snow.fact_sales (
    sale_sk      BIGSERIAL PRIMARY KEY,
    order_bk     INT NOT NULL,

    customer_sk  INT NOT NULL REFERENCES dwh_snow.dim_customer(customer_sk),

    total_amount NUMERIC(10, 2) NOT NULL
);

SELECT
    o.id,
    TO_CHAR(o.order_date, 'YYYYMMDD')::INT,
    dp.product_sk,
    dc.customer_sk,
    oi.qty,
    (oi.qty * oi.price_at_purchase - oi.discount)
FROM oltp_shop.order_items oi
JOIN oltp_shop.orders o ON o.id = oi.order_id
JOIN dwh_snow.dim_product  dp ON dp.product_bk  = oi.product_id
JOIN dwh_snow.dim_customer dc ON dc.customer_bk = o.customer_id
WHERE o.status = 'paid';

Сравни два подхода бок о бок, чтобы безошибочно выбирать архитектуру под конкретную задачу:

Параметр Схема «Звезда» (Star) Схема «Снежинка» (Snowflake)
Количество JOIN Минимальное (1 шаг до атрибута) Больше (цепочки по 2–4 шага)
Скорость чтения отчётов Выше — планировщику проще строить план Ниже из-за дополнительных соединений
Место на диске Чуть больше (дублируются названия городов/категорий) Экономнее за счёт нормализации справочников
Обновление справочника При переименовании города нужно обновить все строки клиентов в нём Меняешь 1 строку в dim_city — и всё обновилось
Удобство для BI-аналитиков Максимальное — всё понятно с первого взгляда Сложнее — нужно знать иерархию таблиц
Совет для реальных проектов: В 90% аналитических задач выбирай «Звезду». Дисковое пространство сегодня стоит копейки (тем более таблицы измерений крошечные по сравнению с таблицами фактов), а простота SQL и скорость дашбордов экономят команде сотни часов. Используй «Снежинку» точечно — только если у тебя гигантская и часто меняющаяся многоуровневая иерархия (например, сложная оргструктура корпорации или справочник адресов с 30 полями).

06 Шпаргалка урока перед практикой

Перед тем как перейти к заданиям, пробегись глазами по пяти главным опорам этого урока:

Термин / Правило Короткий смысл
OLTP vs OLAP OLTP — быстрая «касса» (3НФ, много мелких записей). OLAP / DWH — «штаб аналитики» (мало записей, огромные чтения с GROUP BY).
Fact & Dimension fact_* хранит числа-метрики (суммы, штуки) и ключи. dim_* хранит текстовый контекст («кто, что, где, когда»).
Зерно (Grain) Строгий ответ на вопрос «что означает 1 строка в таблице фактов». Не смешивай разные зёрна в одном JOIN без предварительной группировки!
Порядок загрузки Всегда сначала загружай справочники (dim_*), и только потом — таблицу фактов (fact_*).
Звезда vs Снежинка «Звезда» — плоские измерения и быстрый SQL (выбор по умолчанию). «Снежинка» — нормализованные ветвистые измерения ради экономии и единой точки правки.

Задание 4 (Проектирование). Сплющиваем «Снежинку» в витрину без JOIN

BI-аналитики пожаловались, что в схеме dwh_snow приходится писать по 6 JOIN, чтобы получить страну покупателя и категорию товара. Создай поверх dwh_snow плоское представление dwh_snow.v_sales_mart (витрину), объединяющее факты со всеми ветками снежинки, и напиши к этой витрине запрос без единого JOIN, который выведет выручку по странам и категориям за 2026 год.

CREATE OR REPLACE VIEW dwh_snow.v_sales_mart AS
SELECT
    f.sale_sk,
    f.order_bk,
    dd.full_date,
    dd.year_num,
    dd.quarter_num,
    dco.country_name,
    dci.city_name,
    dcu.segment,
    dcat.category_name,
    dp.product_title,
    f.qty,
    f.total_amount
FROM dwh_snow.fact_sales f
JOIN dwh_snow.dim_date     dd   ON dd.date_sk       = f.date_sk
JOIN dwh_snow.dim_product  dp   ON dp.product_sk    = f.product_sk
JOIN dwh_snow.dim_category dcat ON dcat.category_sk = dp.category_sk
JOIN dwh_snow.dim_customer dcu  ON dcu.customer_sk  = f.customer_sk
JOIN dwh_snow.dim_city     dci  ON dci.city_sk      = dcu.city_sk
JOIN dwh_snow.dim_country  dco  ON dco.country_sk   = dci.country_sk;

SELECT
    country_name,
    category_name,
    SUM(qty)          AS total_qty,
    SUM(total_amount) AS revenue
FROM dwh_snow.v_sales_mart
WHERE year_num = 2026
GROUP BY country_name, category_name
ORDER BY revenue DESC;
