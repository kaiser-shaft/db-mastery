Резервное копирование и PITR (почему репликация — не бэкап) + пулинг соединений (PgBouncer)

Главное в этом уроке
  • Поймёшь, почему репликация никогда не заменяет бэкап, и в чём разница между логическим (pg_dump / pg_restore) и физическим (pg_basebackup) копированием.
  • Освоишь «машину времени» PostgreSQL — PITR (Point-in-Time Recovery): включишь архивирование WAL (archive_mode), создашь точку восстановления и откатишь базу ровно на секунду до катастрофы.
  • Узнаешь, почему 500 открытых соединений от приложений способны положить мощный сервер PostgreSQL, и как PgBouncer решает эту проблему через пулинг соединений.
  • Протестируешь course_pgbouncer (порт 6432) в режиме transaction pooling, посмотришь его админ-консоль SHOW POOLS и разберёшь главные ловушки SET / PREPARE.

01 Почему репликация — это НЕ бэкап (и два вида бэкапов)

Представь двух друзей на контрольной, где второй мгновенно списывает всё из тетради первого. Если у первого порвалась тетрадь (сгорел диск сервера) — копия у друга спасёт! Это репликация. Но представь другую ситуацию: первый ученик случайно зачеркнул всю решённую задачу жирной чёрной ручкой (разработчик выполнил DELETE FROM orders; без WHERE или DROP TABLE users;). Что сделает верный друг-реплика? Через 2 миллисекунды он точно так же зачеркнёт задачу у себя!

Отсюда главное правило эксплуатации баз данных:

  • Репликация защищает от поломки железа (доступность, High Availability).
  • Резервное копирование (Backup) защищает от ошибок людей, багов кода и вирусов-шифровальщиков — это «сфотографированная» тетрадь, запертая в отдельном сейфе, куда случайная команда DROP TABLE не дотянется.

В PostgreSQL есть два основных способа сделать резервную копию:

Критерий Логический бэкап (pg_dump / pg_restore) Физический бэкап (pg_basebackup + WAL)
Жизненная аналогия Рецепт блюда текстом (SQL-команды CREATE + COPY) Полная копия файлов диска всего кластера
Что копирует Одну базу, схему или даже 1 конкретную таблицу Весь кластер целиком (все базы, роли, индексы)
Скорость восстановления Медленнее на больших БД (нужно заново строить индексы) Очень быстро (просто распаковываем готовые файлы)
Откат на точную секунду (PITR) Нет (только на момент старта pg_dump) Да! Вместе с архивом WAL — с точностью до миллисекунды
Когда использовать Малые/средние БД (до ~50–100 ГБ), перенос таблиц, апгрейды Боевые продакшен-кластеры любого размера

Практика 1: Делаем логический бэкап, «уничтожаем» таблицу и спасаем её через pg_restore

В нашем docker-compose.yaml папка ./backups на твоём компьютере уже примонтирована внутрь контейнера course_pg_primary как /backups. Давай проведём полный цикл спасения данных: создадим таблицу, снимем сжатый бинарный дамп (формат -Fc — custom, лучший формат для pg_dump!), случайно удалим таблицу и восстановим её!

Bash · Шаг 1: создаём важные данные и снимаем бэкап в /backups 
# 1. Создаём учебную таблицу с заказами на Primary
docker exec course_pg_primary psql -U student -d learning_db -c "
  DROP TABLE IF EXISTS critical_orders;
  CREATE TABLE critical_orders (
    id       SERIAL PRIMARY KEY,
    customer TEXT NOT NULL,
    total    NUMERIC(10, 2) NOT NULL
  );
  INSERT INTO critical_orders (customer, total) VALUES
    ('Алина', 14500.00),
    ('Тимур',  8900.00),
    ('Дамир', 23100.00);
"

# 2. Делаем сжатый логический бэкап (-Fc = custom format, -t = конкретная таблица)
docker exec course_pg_primary pg_dump \
  -U student -d learning_db -Fc -t critical_orders \
  -f /backups/critical_orders.dump

# 3. Проверяем, что файл бэкапа появился и не пустой!
docker exec course_pg_primary ls -lh /backups/critical_orders.dump
Ответ терминала
INSERT 0 3
-rw-r--r-- 1 root root 1.8K Nov 26 10:15 /backups/critical_orders.dump

А теперь моделируем катастрофу: кто-то по ошибке выполнил DROP TABLE critical_orders;! Проверим, как pg_restore мгновенно вернёт таблицу на место.

Bash · Шаг 2: катастрофа (DROP TABLE) и восстановление из дампа 
# 1. Имитируем ошибку инженера: удаляем таблицу
docker exec course_pg_primary psql -U student -d learning_db \
  -c "DROP TABLE critical_orders;"

# 2. Восстанавливаем таблицу из файла /backups/critical_orders.dump
docker exec course_pg_primary pg_restore \
  -U student -d learning_db --no-owner \
  /backups/critical_orders.dump

# 3. Проверяем, что все 3 заказа целы и невредимы!
docker exec course_pg_primary psql -U student -d learning_db \
  -c "SELECT * FROM critical_orders ORDER BY id;"
Ответ терминала
DROP TABLE
 id | customer |  total
----+----------+----------
  1 | Алина    | 14500.00
  2 | Тимур    |  8900.00
  3 | Дамир    | 23100.00

Таблица спасена! Но у pg_dump есть слабое место: если бэкап делался в 03:00 ночи, а катастрофа случилась в 15:40 дня, то все заказы за 12 часов потеряются. Чтобы не терять ни минуты, нам нужна «машина времени» — PITR!

02 Машина времени: PITR (Point-in-Time Recovery) и архивирование WAL

Представь видеокамеру наблюдения, которая в 00:00 делает чёткий базовый кадр (pg_basebackup), а дальше всю ночь и весь день складывает в несгораемый архив каждый листок журнала изменений (WAL Archiving).

В 14:05:12 стажёр случайно удалил таблицу клиентов. Что делает PITR (Point-in-Time Recovery) — восстановление на конкретный момент времени?

  1. Берём базовый ночной снимок pg_basebackup (состояние базы в 00:00).
  2. Кладём рядом файл-маркер recovery.signal и пишем команду: «Воспроизводи сохранённые в архиве WAL-сегменты от 00:00 до ровно 14:05:10 — и СТОП!»
  3. PostgreSQL перематывает историю вперёд, применяет все честные заказы за 14 часов и останавливается за 2 секунды до рокового DROP TABLE!

Практика 2: Включаем архивирование WAL и делаем базовый снимок для PITR

Загляни в наш docker-compose.yaml в блок pg_primary — там специально для Урока 5.4 уже подготовлены 4 закомментированные строки! Раскомментируй их (убери символ # в начале этих 4 строк):

YAML · Фрагмент docker-compose.yaml (сервис pg_primary) 
      - -c
      - archive_mode=on
      - -c
      - archive_command=mkdir -p /backups/wal && test ! -f /backups/wal/%f && cp %p /backups/wal/%f

Что означают загадочные %p и %f в archive_command? PostgreSQL сам подставляет вместо %p полный путь к заполненному 16-мегабайтному файлу WAL, а вместо %f — его короткое имя. Проверка test ! -f защищает от случайной перезаписи уже сохранённого архивного файла. Теперь применим изменение, сделаем базовый бэкап и проверим работу архиватора!

Bash · Перезапускаем Primary с архивированием и снимаем базу для PITR 
# 1. Пересоздаём контейнер pg_primary с включённым archive_mode=on
docker compose up -d pg_primary

# 2. Делаем физический базовый бэкап в /backups/base_pitr
docker exec course_pg_primary bash -c "
  rm -rf /backups/base_pitr &&
  pg_basebackup -U student -D /backups/base_pitr -Ft -z -P
"

# 3. Записываем данные и ставим именованную точку восстановления (restore point)
docker exec course_pg_primary psql -U student -d learning_db -c "
  DROP TABLE IF EXISTS pitr_ledger;
  CREATE TABLE pitr_ledger (id SERIAL PRIMARY KEY, note TEXT, ts TIMESTAMPTZ DEFAULT now());
  INSERT INTO pitr_ledger (note) VALUES ('Платёж №1 — валидный'), ('Платёж №2 — валидный');

  -- Ставим закладку в WAL перед опасной операцией!
  SELECT pg_create_restore_point('before_danger_release');

  -- Имитируем ошибку после релиза
  DELETE FROM pitr_ledger;

  -- Принудительно закрываем текущий сегмент WAL, чтобы он сразу ушёл в /backups/wal
  SELECT pg_switch_wal();
"

# 4. Проверяем статистику архиватора и реальные файлы WAL на диске!
docker exec course_pg_primary psql -U student -d learning_db -c "
  SELECT archived_count, last_archived_wal, failed_count FROM pg_stat_archiver;
"
docker exec course_pg_primary ls -lh /backups/wal | tail -n 5

Практика 3: Как запускается само восстановление PITR (конфиг и частая ошибка)

Когда наступает реальная авария, ты разворачиваешь base.tar.gz из /backups/base_pitr на чистый экземпляр PostgreSQL (никогда не затирай живую папку данных без копии!), кладёшь в каталог данных пустой файл recovery.signal и добавляешь в postgresql.auto.conf всего 3 строчки:

INI · Настройки PITR в postgresql.auto.conf для восстановления до нашей закладки 
# Откуда забирать архивные 16-мегабайтные сегменты WAL
restore_command = 'cp /backups/wal/%f %p'

# Остановиться ровно на нашей закладке (или recovery_target_time = '2026-11-26 10:19:50+05')
recovery_target_name = 'before_danger_release'

# После достижения цели открыть базу на запись (или 'pause', чтобы сначала проверить SELECT!)
recovery_target_action = 'promote'

А что будет, если в archive_command забыли создать папку, закончилось место или права на запись пропали? PostgreSQL не удалит неархивированные сегменты WAL и начнёт ругаться в логах, пока failed_count в pg_stat_archiver не вырастет до небес (и не забьёт диск Primary!):

Ошибка в логах PostgreSQL при сломанном archive_command
LOG:  archive command failed with exit code 1
DETAIL:  The failed archive command was: cp pg_wal/000000010000000000000006 /backups/wal/000000010000000000000006
WARNING:  archiving write-ahead log file "000000010000000000000006" failed too many times, will try again
✗ Как НЕ надо
# 1. Хранить бэкапы на том же сервере, где живёт база
# 2. Написать cron-скрипт 2 года назад и НИ РАЗУ не проверять восстановление!

Это «бэкап Шрёдингера»: он вроде лежит на диске, но в день аварии выясняется, что файл пустой, побитый или диск сгорел вместе с сервером.

✓ Как правильно
# Правило 3-2-1 + боевые инструменты (pgBackRest / WAL-G) + автотест восстановления
# 3 копии данных · 2 разных хранилища · 1 копия в другом дата-центре / S3
# Раз в неделю скрипт сам разворачивает последний бэкап на тестовый сервер и сверяет данные!

В продакшене вместо ручного cp используют pgBackRest или WAL-G: они умеют сжимать, шифровать, делать инкрементальные копии прямо в S3 и проверять целостность.

Золотой закон SRE: У тебя нет бэкапов, пока ты не прогнал восстановление из них. При PITR ставь recovery_target_action = 'pause', если хочешь сначала подключиться к восстановленной копии через SELECT, убедиться, что нужные строки на месте, и только потом вручную выполнить SELECT pg_wal_replay_resume();.

03 Проблема «тысячи соединений» и зачем нужен PgBouncer

С отказоустойчивостью и бэкапами мы разобрались. Теперь давай решим самую частую проблему эксплуатации растущего сайта!

Представь ресторан на 500 гостей. Большинство гостей 98% времени просто болтают друг с другом (в базе данных это состояние idle) и лишь на пару секунд просят принести кофе. Как работает «голый» PostgreSQL без помощников? Он использует архитектуру process-per-connection: на каждое входящее подключение клиента операционная система запускает отдельный тяжёлый процесс ОС (fork()), который съедает 5–10 МБ оперативной памяти!

Если 50 микросервисов откроют по 20 соединений (итого 1000 процессов), наш ресторан наймёт 1000 личных официантов. Они будут толкаться локтями на кухне (переключение контекста CPU и борьба за блокировки внутри PostgreSQL), съедят 10 ГБ RAM впустую — и сервер либо упадёт по нехватке памяти (OOM Killer), либо начнёт отказывать новым клиентам с ошибкой:

Знаменитая ошибка перегрузки соединений PostgreSQL
FATAL:  sorry, too many clients already

Как спасти ресторан? Поставить на входе метрдотеля — пулер соединений PgBouncer!

PgBouncer — это сверхлёгкий прокси-сервер (написанный на C, он тратит всего ~2 КБ памяти на одного клиента!). Он принимает хоть 2000 клиентских подключений, но внутрь PostgreSQL держит открытым маленький эффективный пул из 10–50 реальных соединений (DEFAULT_POOL_SIZE). Пока клиент думает или рендерит страницу, его реальное соединение к PostgreSQL мгновенно отдаётся другому клиенту!

У PgBouncer есть 3 режима работы (pool_mode), которые определяют, как часто метрдотель забирает официанта у одного клиента и передаёт другому:

Режим pool_mode Когда соединение возвращается в пул Плюсы и минусы
session Только когда клиент полностью отключился 100% совместимость со всеми фичами Postgres, но слабая экономия соединений (простаивающие idle-клиенты всё равно держат процесс).
transaction (стандарт!) Сразу после каждого COMMIT или ROLLBACK Огромная экономия (10x–50x)! Именно этот режим настроен у нас в docker-compose.yaml. Но нельзя полагаться на «память сессии» между транзакциями.
statement После каждого отдельного SQL-запроса Максимальная плотность, но нельзя использовать многозапросные транзакции BEGIN ... COMMIT (применяется очень редко).

04 Практика с PgBouncer: админ-консоль, тест пула и ловушки transaction mode

В нашем docker-compose.yaml сервис pgbouncer (контейнер course_pgbouncer) уже настроен со следующими параметрами: POOL_MODE=transaction, MAX_CLIENT_CONN=200, DEFAULT_POOL_SIZE=10. Снаружи он доступен на порту 6432, а внутри сети Docker — по адресу host=pgbouncer port=5432.

Практика 4: Заглядываем внутрь пула через админ-консоль PgBouncer

У PgBouncer есть встроенная «виртуальная» база данных с именем pgbouncer. Если подключиться к ней через psql, можно отдавать команды мониторинга SHOW POOLS;, SHOW DATABASES; и SHOW STATS;! Запусти (убедись, что профиль запущен через docker compose --profile mod5 up -d):

Bash · Проверка работы и статистики course_pgbouncer 
# 1. Делаем обычный SQL-запрос к learning_db ЧЕРЕЗ PgBouncer
docker exec -e PGPASSWORD=student_pass course_pg_primary \
  psql -h pgbouncer -p 5432 -U student -d learning_db \
  -c "SELECT 'Привет через PgBouncer!' AS greeting, pg_backend_pid() AS pg_pid;"

# 2. Подключаемся к виртуальной админ-базе pgbouncer и смотрим пулы
docker exec -e PGPASSWORD=student_pass course_pg_primary \
  psql -h pgbouncer -p 5432 -U student -d pgbouncer \
  -c "SHOW POOLS;" -c "SHOW DATABASES;"
Ответ PgBouncer

Главные колонки в SHOW POOLS, на которые смотрят инженеры на дежурстве:

  • cl_active — сколько клиентов сейчас подключено к PgBouncer.
  • cl_waiting — сколько клиентов стоят в очереди, потому что все 10 соединений пула заняты. В норме здесь 0!
  • sv_active / sv_idle — сколько реальных соединений к PostgreSQL сейчас работают или ждут задачу.
  • maxwait — сколько секунд самый невезучий клиент прождал в очереди. Если maxwait > 0 постоянно — пора ускорять медленные запросы или слегка увеличить pool_size.

Практика 5: Доказываем экономию — 25 клиентов работают через пул из 10 процессов

Давай прямо сейчас запустим 25 одновременных клиентских соединений к PgBouncer (каждое сделает SELECT pg_sleep(2)) и одновременно посмотрим в pg_stat_activity на Primary, сколько реальных процессов PostgreSQL при этом занято!

Bash · Нагружаем PgBouncer 25 клиентами и считаем процессы на Primary 
# Запускаем 25 параллельных клиентов через PgBouncer в фоне
for i in $(seq 1 25); do
  docker exec -e PGPASSWORD=student_pass course_pg_primary \
    psql -h pgbouncer -p 5432 -U student -d learning_db \
    -q -c "SELECT pg_sleep(2);" &
done

# Через 0.5 секунды снимаем срез со стороны PgBouncer и со стороны PostgreSQL Primary
sleep 0.5

echo "--- Взгляд PgBouncer (cl_active + cl_waiting vs sv_active) ---"
docker exec -e PGPASSWORD=student_pass course_pg_primary \
  psql -h pgbouncer -p 5432 -U student -d pgbouncer \
  -c "SELECT database, cl_active, cl_waiting, sv_active, sv_idle FROM (VALUES (1)) t;" 2>/dev/null || \
docker exec -e PGPASSWORD=student_pass course_pg_primary \
  psql -h pgbouncer -p 5432 -U student -d pgbouncer -c "SHOW POOLS;"

echo "--- Взгляд PostgreSQL Primary (реальных процессов НЕ больше 10!) ---"
docker exec course_pg_primary psql -U student -d learning_db -c "
  SELECT state, count(*) AS real_pg_backends
  FROM pg_stat_activity
  WHERE datname = 'learning_db' AND pid <> pg_backend_pid()
  GROUP BY state;
"

wait
Ответ терминала (во время работы 25 клиентов)

-------------+---------+-----------+------------+-----------+---------
 learning_db | student |        10 |         15 |        10 |       0

--- Взгляд PostgreSQL Primary (реальных процессов НЕ больше 10!) ---

--------+------------------

Посмотри на эту красоту! К PgBouncer пришли 25 клиентов: 10 мгновенно получили работу (sv_active = 10), а 15 вежливо подождали 2 секунды в очереди (cl_waiting = 15), и ни один не получил ошибку too many clients! При этом PostgreSQL Primary спокойно обслуживал ровно 10 процессов без лишней нагрузки на RAM и CPU. Проблема «тысячи официантов» полностью решена!

Практика 6: Главная ловушка Transaction Pooling (PREPARE и SET)

У режима transaction есть один важный подвох, о который обжигаются разработчики, впервые включившие PgBouncer. Поскольку после каждого COMMIT клиент может получить другой процесс PostgreSQL (другой pg_backend_pid()), всё, что хранилось в «памяти сессии» (TEMP TABLE, LISTEN / NOTIFY, сессионный SET и старые версии PREPARE), может внезапно исчезнуть или «протечь» в чужой запрос!

Давай поймаем эту ошибку вживую: создадим временную таблицу вне транзакции (автокоммит!), параллельно «пошевелим» пул другим запросом и попробуем прочитать её.

SQL · Опасный паттерн в PgBouncer (transaction mode) 
-- Транзакция 1: создаём временную таблицу (попала на backend PID 142)
CREATE TEMP TABLE my_cart (item TEXT);
INSERT INTO my_cart VALUES ('Кроссовки');

-- (Между запросами другой клиент забрал PID 142, а нам выдали PID 149!)

-- Транзакция 2: пытаемся прочитать свою временную таблицу на другом backend!
SELECT * FROM my_cart;
Ошибка при переключении серверного соединения в Transaction Mode
ERROR:  relation "my_cart" does not exist
LINE 1: SELECT * FROM my_cart;
✗ Как НЕ надо (в transaction mode)
-- Утечёт к чужому клиенту!
SET search_path TO analytics;
SELECT * FROM reports;

-- Может пропасть после COMMIT:
CREATE TEMP TABLE tmp (id INT);

Обычный SET остаётся висеть на бэкенде после возврата в пул и ломает следующего клиента!

✓ Как правильно (в transaction mode)
-- Внутри одной транзакции:
BEGIN;
SET LOCAL search_path TO analytics;
SELECT * FROM reports;
COMMIT; -- сам сбросится!

SET LOCAL и CREATE TEMP TABLE ... ON COMMIT DROP действуют строго внутри одной транзакции и безопасны в пуле.

Сколько ставить в DEFAULT_POOL_SIZE? Новички часто ставят 500, но от этого база только замедляется! В реальных проектах оптимальный размер пула к PostgreSQL — примерно 2–4 соединения на одно ядро CPU (например, 20–40 для 8-ядерного сервера), тогда как MAX_CLIENT_CONN в PgBouncer можно смело ставить 1000–5000.

Инструмент / правило Зачем нужен
pg_dump -Fc + pg_restore Логический сжатый бэкап отдельных баз или таблиц и быстрое выборочное восстановление.

Задание 1 (Базовый). Точечный бэкап и проверка содержимого архива без восстановления

Создай на Primary (5432) таблицу backup_lab (id INT PRIMARY KEY, title TEXT) с двумя строками. Сделай её сжатый бэкап в файл /backups/backup_lab.dump с помощью pg_dump -Fc. Затем, не восстанавливая таблицу, выведи оглавление (список объектов внутри дампа) командой pg_restore --list, а потом удали таблицу, восстанови её из дампа и проверь SELECT.

Показать решение
Bash · Бэкап, инспекция через --list и восстановление 
# 1. Готовим таблицу
docker exec course_pg_primary psql -U student -d learning_db -c "
  DROP TABLE IF EXISTS backup_lab;
  CREATE TABLE backup_lab (id INT PRIMARY KEY, title TEXT NOT NULL);
  INSERT INTO backup_lab VALUES (1, 'Ноутбук'), (2, 'Монитор');
"

# 2. Снимаем сжатый дамп одной таблицы
docker exec course_pg_primary pg_dump \
  -U student -d learning_db -Fc -t backup_lab \
  -f /backups/backup_lab.dump

# 3. Инспектируем оглавление дампа без восстановления
docker exec course_pg_primary pg_restore --list /backups/backup_lab.dump

# 4. Удаляем, восстанавливаем и проверяем
docker exec course_pg_primary psql -U student -d learning_db -c "DROP TABLE backup_lab;"
docker exec course_pg_primary pg_restore -U student -d learning_db --no-owner /backups/backup_lab.dump
docker exec course_pg_primary psql -U student -d learning_db -c "SELECT * FROM backup_lab ORDER BY id;"
Задание 2 (Практический). Мониторинг здоровья WAL-архиватора

Напиши SQL-запрос для Primary (5432) к pg_stat_archiver, который проверит: включён ли archive_mode, сколько файлов успешно заархивировано (archived_count), сколько было ошибок (failed_count), и выведет понятный статус archiver_health: 'DISABLED' (если archive_mode = 'off'), 'ERROR' (если последняя ошибка была позже последнего успешного архивирования: last_failed_time > last_archived_time или успешных ещё не было при failed_count > 0) или 'OK'.

Показать решение
SQL · Выполнять на Primary (порт 5432) 
SELECT
    current_setting('archive_mode') AS archive_mode,
    archived_count,
    failed_count,
    last_archived_wal,
    CASE
        WHEN current_setting('archive_mode') = 'off' THEN 'DISABLED'
        WHEN failed_count > 0
             AND (last_archived_time IS NULL OR last_failed_time > last_archived_time)
            THEN 'ERROR'
        ELSE 'OK'
    END AS archiver_health
FROM pg_stat_archiver;
Задание 3 (Инженерный). Аудит соединений в pg_stat_activity (аргумент в пользу PgBouncer)

Напиши SQL-запрос для Primary (5432), который покажет текущую картину всех клиентских подключений из pg_stat_activity (где backend_type = 'client backend'): сгруппируй их по state (active, idle, idle in transaction), посчитай количество соединений в каждом состоянии, а рядом в той же строке выведи лимит сервера max_connections и процент занятости лимита (округлённый до 1 знака после запятой).

Показать решение
SQL · Выполнять на Primary (порт 5432) 
WITH limits AS (
    SELECT current_setting('max_connections')::INT AS max_conn
)
SELECT
    COALESCE(a.state, 'unknown') AS conn_state,
    count(*) AS connections_cnt,
    l.max_conn,
    round(100.0 * count(*) / l.max_conn, 1) AS pct_of_limit
FROM pg_stat_activity AS a
CROSS JOIN limits AS l
WHERE a.backend_type = 'client backend'
GROUP BY a.state, l.max_conn
ORDER BY connections_cnt DESC;
Задание 4 (Отладка). Исправляем «протекающий» запрос для работы через PgBouncer (transaction mode)

Разработчик переключил сервис на course_pgbouncer (порт 6432, режим transaction), и его скрипт начал портить настройки соседним запросам! В скрипте выполнялось: SET work_mem = '32MB'; CREATE TEMP TABLE tmp_calc (x INT); INSERT INTO tmp_calc SELECT generate_series(1, 5); SELECT sum(x) FROM tmp_calc;. Перепиши этот блок так, чтобы он выполнялся через PgBouncer в одной транзакции, гарантированно сбрасывал work_mem и автоматически удалял tmp_calc после завершения (подсказка: SET LOCAL и ON COMMIT DROP), и проверь его выполнение!

Показать решение
Bash · Безопасный запуск через course_pgbouncer 
docker exec -e PGPASSWORD=student_pass course_pg_primary \
  psql -h pgbouncer -p 5432 -U student -d learning_db -c "
  BEGIN;
    -- Настройка действует ТОЛЬКО внутри этой транзакции
    SET LOCAL work_mem = '32MB';

    -- Временная таблица автоматически исчезнет при COMMIT
    CREATE TEMP TABLE tmp_calc (x INT) ON COMMIT DROP;
    INSERT INTO tmp_calc SELECT generate_series(1, 5);

    SELECT
      sum(x) AS total_sum,
      current_setting('work_mem') AS tx_work_mem
    FROM tmp_calc;
  COMMIT;

  -- Проверяем: после COMMIT настройка work_mem вернулась к дефолту (4MB)!
  SHOW work_mem;
"
