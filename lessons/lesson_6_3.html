Главное в этом уроке

01 Построчное против Колончатого: почему PostgreSQL устаёт на миллиардах строк

Представь школьный журнал, в котором у каждого ученика заполнена длинная карточка на 40 полей: фамилия, имя, дата рождения, адрес, телефон мамы, группа крови, рост, вес, оценки по 20 предметам, любимый кружок… Теперь директор школы спрашивает: «Какой средний рост у всех учеников нашей школы?»

Если карточки лежат в папках «по одному ученику на лист» (так хранит данные построчная БД вроде PostgreSQL или MySQL), тебе придётся перелистать все 1 000 карточек и каждый раз пробегать глазами мимо адреса, телефонов и оценок, чтобы выцепить одно-единственное число «рост». Ты потратишь 95% усилий на чтение совершенно ненужных данных!

А теперь представь другой способ: мы разрезали журнал на отдельные узкие блокноты по колонкам. В одном блокноте — только фамилии. В другом — только адреса. В третьем — только рост всех учеников подряд столбиком: 158, 162, 165, 160.... Чтобы найти средний рост, ты открываешь один-единственный тонкий блокнот «Рост» и вообще не прикасаешься к остальным 39 блокнотам!

Именно так работают колончатые OLAP-движки (Column-oriented DBMS) — такие как ClickHouse (для огромных кластеров и миллиардов строк) и DuckDB (лёгкий встраиваемый движок для аналитики прямо на ноутбуке).

Задача Построчная БД (PostgreSQL) Колончатая БД (ClickHouse / DuckDB)
Выдать 1 чек со всеми 40 полями по id Молниеносно — вся строка лежит в одном месте Медленнее — нужно собрать 1 строку из 40 разных файлов
Посчитать SUM(amount) по 50 млн строк Долго — читает с диска все ненужные колонки Молниеносно — читает только сжатый файл amount
Частые точечные UPDATE и DELETE Родная стихия (MVCC, транзакции ACID) Больно и дорого — данные рассчитаны на дописывание пачками
Степень сжатия на диске Обычно 1.5–2x (в строке намешаны числа и текст) Легко 5–20x (в колонке лежат однотипные похожие значения)

Пример 1. Главная ошибка новичка при создании таблицы в ClickHouse

Главный рабочий движок таблиц в ClickHouse называется MergeTree (дерево слияний). Он автоматически сортирует данные на диске и режет их на аккуратные кусочки-пачки. Если после PostgreSQL попробовать создать таблицу MergeTree просто со списком колонок, ClickHouse сразу остановит тебя:

SQL · Попытка создать MergeTree без ORDER BY 
CREATE TABLE sales_broken (
    sale_id UInt64,
    amount  UInt32
) ENGINE = MergeTree();
Ошибка ClickHouse
Received exception from server:
Code: 36. DB::Exception: You must provide an ORDER BY or PRIMARY KEY expression in the table definition. (BAD_ARGUMENTS)

Почему ClickHouse такой строгий? Потому что вся его бешеная скорость держится на том, что данные на диске физически отсортированы по ключу ORDER BY! Без указания порядка сортировки движок MergeTree просто не знает, как разложить колонки и построить индекс. (Если сортировка совсем не нужна, явно пишут ORDER BY tuple().)

Пример 2. Создаём sales_raw на 2 000 000 строк и считаем выручку

Сгенерируем 2 миллиона покупок с помощью встроенной функции numbers(2000000) — это аналог generate_series() из PostgreSQL, только космически быстрый. В таблице намеренно добавим длинную текстовую колонку comment, которая в отчёте не нужна, чтобы увидеть силу колончатого хранения.

SQL · Генерация 2 млн продаж и аналитический отчёт в ClickHouse 
DROP TABLE IF EXISTS sales_raw;

CREATE TABLE sales_raw (
    sale_id   UInt64,
    sale_date Date,
    city      String,
    category  String,
    qty       UInt16,
    amount    UInt32,
    comment   String
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(sale_date)
ORDER BY (city, sale_date);

-- Вставляем 2 000 000 строк одной пачкой (~1 секунда!)
INSERT INTO sales_raw
SELECT
    number + 1 AS sale_id,
    addDays(toDate('2026-01-01'), number % 90) AS sale_date,
    arrayElement(['Алматы', 'Астана', 'Костанай', 'Москва'], (number % 4) + 1) AS city,
    arrayElement(['Электроника', 'Мерч', 'Аксессуары'], (number % 3) + 1) AS category,
    1 + (number % 3) AS qty,
    (1 + (number % 3)) * (5000 + (number % 5) * 3000) AS amount,
    concat('Подробный комментарий менеджера к чеку номер #', toString(number + 1)) AS comment
FROM numbers(2000000);

-- Запускаем тяжёлый аналитический отчёт по 2 млн строк!
SELECT
    city,
    category,
    count()        AS orders_cnt,
    sum(qty)       AS items_sold,
    sum(amount)    AS total_revenue,
    round(avg(amount), 2) AS avg_check
FROM sales_raw
GROUP BY city, category
ORDER BY total_revenue DESC;

03 Сжатие данных: как упаковать 200 МБ в крошечный рюкзак

Представь, что тебе нужно записать в тетрадь 100 000 раз подряд слово «Алматы», а потом 100 000 раз подряд слово «Астана». Умный школьник не станет исписывать 50 страниц — он сделает словарик: 1 = Алматы, 2 = Астана, а в тетради напишет: 1 × 100 000, 2 × 100 000. Место сократилось в тысячи раз!

А если у тебя идёт длинный ряд растущих чисел 1001, 1002, 1003, 1004, 1005? Зачем хранить огромные 8-байтные числа, если достаточно сохранить первое число 1001, а дальше хранить только разницу (дельту) между соседями: +1, +1, +1, +1?

Поскольку в колончатой БД значения одной колонки лежат вплотную друг к другу и вдобавок отсортированы по ORDER BY, ClickHouse применяет два уровня магии:

  • Словарное кодирование (LowCardinality(String)) — идеально для колонок, где много строк, но мало уникальных значений (города, страны, категории, статусы). Вместо текста база хранит крошечные номера из словаря.
  • Кодеки сжатия (CODEC) — например, Delta / DoubleDelta (хранят разницу для дат и монотонных ID) в паре с мощным архиватором ZSTD (по умолчанию ClickHouse использует более быстрый LZ4).
Колонка Было в sales_raw Стало в sales_opt
sale_id UInt64 (сжатие LZ4 по умолчанию) UInt64 CODEC(Delta, ZSTD(3)) — хранит дельты
sale_date Date (LZ4) Date CODEC(DoubleDelta, ZSTD(3)) — идеально для отсортированных дат
city, category Обычный String LowCardinality(String) — словарь вместо повторов текста
comment Обычный String (LZ4) String CODEC(ZSTD(3)) — плотное сжатие текста

Пример 3. Сравниваем вес колонок на диске в system.columns

Создадим оптимизированную копию таблицы sales_opt, зальём туда те же 2 миллиона строк и посмотрим в системную таблицу system.columns, во сколько раз сжались данные!

SQL · Сжатие: sales_raw против sales_opt 
DROP TABLE IF EXISTS sales_opt;

CREATE TABLE sales_opt (
    sale_id   UInt64 CODEC(Delta, ZSTD(3)),
    sale_date Date CODEC(DoubleDelta, ZSTD(3)),
    city      LowCardinality(String),
    category  LowCardinality(String),
    qty       UInt16 CODEC(ZSTD(3)),
    amount    UInt32 CODEC(ZSTD(3)),
    comment   String CODEC(ZSTD(3))
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(sale_date)
ORDER BY (city, sale_date);

-- Переливаем те же 2 000 000 строк
INSERT INTO sales_opt SELECT * FROM sales_raw;

-- Сравниваем общий размер обеих таблиц на диске!
SELECT
    table,
    formatReadableSize(sum(data_uncompressed_bytes)) AS raw_size,
    formatReadableSize(sum(data_compressed_bytes))   AS disk_size,
    round(sum(data_uncompressed_bytes) / sum(data_compressed_bytes), 1) AS compress_ratio
FROM system.columns
WHERE database = currentDatabase()
  AND table IN ('sales_raw', 'sales_opt')
GROUP BY table
ORDER BY table;
Ответ ClickHouse
┌─table─────┬─raw_size───┬─disk_size─┬─compress_ratio─┐
│ sales_opt │ 195.84 MiB │ 11.42 MiB │           17.1 │
│ sales_raw │ 240.38 MiB │ 29.85 MiB │            8.1 │
└───────────┴────────────┴───────────┴────────────────┘

Впечатляет, правда? Двести сорок мегабайт исходных данных сжались до 11.4 МБ — коэффициент сжатия 17.1x! И самое главное: сжатие экономит не только место на диске, но и ускоряет запросы, потому что жёсткий диск читает в 17 раз меньше байт, а современный процессор распаковывает LZ4 и ZSTD со скоростью гигабайты в секунду.

04 Гранулы (разреженный индекс) и Векторизация (SIMD)

Почему ClickHouse обсчитывает 2 миллиона строк за 28 миллисекунд, даже когда процессор вроде бы один и тот же? Здесь работают два секретных ускорителя: разреженный первичный индекс по гранулам и векторное выполнение.

Аналогия 1 — Разреженный индекс (Sparse Primary Index): Представь толстый телефонный справочник, отсортированный по фамилиям. В PostgreSQL (B-Tree) закладка стоит на каждую фамилию — из-за этого сам каталог закладок весит гигабайты. В ClickHouse закладка ставится один раз на каждые 8 192 строки (такой блок из 8 192 строк называется гранулой). Весь индекс для таблицы на 1 миллиард строк легко помещается в оперативной памяти! Когда ты ищешь city = 'Алматы', ClickHouse по закладкам мгновенно отсекает все чужие гранулы.

Аналогия 2 — Векторизация и SIMD: Представь, что тебе нужно переложить 1 000 яблок из одного ящика в другой. Классическая построчная БД берёт по одному яблоку: взял → проверил спелость → положил (и так миллион вызовов функций подряд). Векторизованный движок (ClickHouse / DuckDB) берёт целую лопату-пачку (вектор) из нескольких тысяч чисел одной колонки и с помощью аппаратных инструкций процессора SIMD (Single Instruction, Multiple Data) складывает сразу по 4–16 чисел за один такт процессора!

Пример 4. Смотрим отсечение гранул через EXPLAIN indexes = 1

В нашей таблице sales_opt ключ сортировки — ORDER BY (city, sale_date). Давай сравним, сколько гранул прочитает ClickHouse, когда мы фильтруем по city (стоит первым в ключе) и когда фильтруем по category (вообще нет в ключе):

Пример 5. Векторная аналитика: точный 95-й перцентиль и уникальные суммы по 2 млн строк

Давай нагрузим векторный движок по-взрослому: посчитаем одновременно количество заказов, общую выручку, число уникальных дат (uniqExact) и 95-й перцентиль чека (quantile(0.95)) — в обычной OLTP-базе такой запрос заставил бы вентилятор ноутбука взлететь!

SQL · Сложные агрегаты на векторном движке 
SELECT
    city,
    count()               AS orders_cnt,
    uniqExact(sale_date)  AS active_days,
    sum(amount)           AS total_revenue,
    quantile(0.95)(amount) AS p95_check
FROM sales_opt
WHERE city IN ('Алматы', 'Костанай')
  AND sale_date >= toDate('2026-02-01')
  AND sale_date <  toDate('2026-03-01')
GROUP BY city
ORDER BY total_revenue DESC;
Ответ ClickHouse
┌─city─────┬─orders_cnt─┬─active_days─┬─total_revenue─┬─p95_check─┐
│ Алматы   │     155556 │          28 │    6844464000 │     51000 │
│ Костанай │     155556 │          28 │    6844464000 │     51000 │
└──────────┴────────────┴─────────────┴───────────────┴───────────┘
2 rows in set. Elapsed: 0.011 sec. Processed 311.11 thousand rows, 1.98 MB.

Всего 11 миллисекунд и меньше 2 мегабайт прочитанных данных! Сработали сразу три ускорителя: отсечение партиции (взят только февраль), отсечение гранул (взяты только Алматы и Костанай) и SIMD-векторизация поверх сжатых колонок.

✗ Как НЕ надо
-- Вставка по 1 строке в цикле!
INSERT INTO sales_opt VALUES (...);
INSERT INTO sales_opt VALUES (...);
-- 10 000 раз подряд = Too many parts!

Каждый INSERT создаёт новую пачку файлов (part) на диске. Частые мелкие вставки «задушат» MergeTree ошибкой Too many parts.

✓ Как правильно
-- Вставлять большими пачками!
INSERT INTO sales_opt
VALUES (...), (...), (...);
-- От 10 000 строк за 1 запрос

Собирай события в буфер и записывай в ClickHouse крупными батчами (1 раз в секунду по 10–100 тысяч строк) — это его родной режим.

05 Основы MPP и шардирования: когда одного сервера уже мало

Представь, что твой интернет-магазин вырос до масштабов гигантского маркетплейса, и за год накопилось 50 миллиардов событий (50 терабайт). Даже самый быстрый одиночный сервер захлебнётся: один жёсткий диск просто не сможет прочитать столько данных за пару секунд.

Как на огромной кухне готовят обед на тысячу гостей? Не нанимают одного «суперповара с десятью руками» (это называется вертикальное масштабирование — покупать всё более дорогой сервер). Вместо этого нанимают 10 обычных поваров, каждому дают свой стол, свой нож и свой отдельный мешок картошки. Все 10 поваров чистят и режут картошку одновременно, а в конце шеф-повар быстро ссыпает готовые тарелки в один общий котёл!

В мире аналитических БД эта архитектура называется MPP (Massively Parallel Processing — массивно-параллельная обработка), а разбиение огромной таблицы на куски между разными серверами — шардированием (Sharding):

  • Шард (Shard) — отдельный сервер, хранящий только свою долю данных (например, Шард 1 хранит заказы Казахстана, Шард 2 — заказы Европы, или данные поделены по hash(user_id)).
  • Реплика (Replica) — копия того же шарда на соседнем сервере для страховки на случай поломки диска.
  • Координатор / Distributed-таблица — «шеф-повар». Когда аналитик шлёт SELECT city, sum(amount), координатор рассылает запрос на все шарды сразу, каждый шард параллельно считает свою промежуточную сумму, а координатор лишь складывает 3 готовых числа!

Пример 6. Мини-MPP на одном контейнере: шарды + объединяющая таблица Merge

В продакшене шарды лежат на разных серверах и объединяются движком Distributed. Но прямо сейчас у себя в одном контейнере ClickHouse ты можешь пощупать ровно тот же принцип с помощью встроенного движка Merge: разложим данные по двум независимым таблицам-шардам (sales_shard_kz и sales_shard_ru) и опросим их одновременно через единую точку входа sales_global!

SQL · Имитация 2 шардов и единая точка входа Merge 
DROP TABLE IF EXISTS sales_global;
DROP TABLE IF EXISTS sales_shard_kz;
DROP TABLE IF EXISTS sales_shard_ru;

-- Шард 1: хранит только продажи Казахстана
CREATE TABLE sales_shard_kz (
    sale_date Date,
    city      LowCardinality(String),
    amount    UInt32
) ENGINE = MergeTree()
ORDER BY (city, sale_date);

-- Шард 2: хранит только продажи России
CREATE TABLE sales_shard_ru (
    sale_date Date,
    city      LowCardinality(String),
    amount    UInt32
) ENGINE = MergeTree()
ORDER BY (city, sale_date);

-- Раскладываем данные из sales_opt по двум шардам
INSERT INTO sales_shard_kz
SELECT sale_date, city, amount
FROM sales_opt
WHERE city IN ('Алматы', 'Астана', 'Костанай');

INSERT INTO sales_shard_ru
SELECT sale_date, city, amount
FROM sales_opt
WHERE city = 'Москва';

-- Создаём «координатор» поверх всех таблиц, чьё имя начинается на sales_shard_
CREATE TABLE sales_global AS sales_shard_kz
ENGINE = Merge(currentDatabase(), '^sales_shard_');

-- Один запрос автоматически опрашивает оба шарда параллельно!
-- Виртуальная колонка _table показывает, с какого шарда пришли данные
SELECT
    _table      AS shard_name,
    city,
    count()     AS orders_cnt,
    sum(amount) AS total_revenue
FROM sales_global
GROUP BY _table, city
ORDER BY shard_name, total_revenue DESC;

✗ Как НЕ надо
-- Перекошенный ключ шардирования
SHARD KEY: country_code
-- 90% трафика идёт на Шард KZ,
-- остальные 9 шардов скучают!

Перекос данных (Data Skew) убивает весь смысл MPP: один «горячий» сервер перегружен, пока соседи простаивают.

✓ Как правильно
-- Равномерный хэш-ключ
SHARD KEY: cityHash64(user_id)
-- Все 10 шардов получают по 10%
-- нагрузки равномерно!

Хороший ключ шардирования равномерно размазывает данные по всем серверам, чтобы все «повара» заканчивали работу одновременно.

А где в этой истории DuckDB? ClickHouse — это мощный серверный комбайн для команд, дашбордов 24/7 и кластеров на десятки терабайт. Если же тебе нужно разово проанализировать тяжёлый файл Parquet или CSV на 50 миллионов строк прямо у себя на ноутбуке без поднятия серверов, на помощь приходит DuckDB — он использует те же принципы (колончатое хранение, сжатие, SIMD-векторизацию), но запускается как маленькая библиотека внутри Python или одной консольной утилитой, словно «SQLite для аналитики».
Правило проектирования ключа ORDER BY в ClickHouse: Ставь в начало ключа колонки, по которым фильтруешь чаще всего, и иди от меньшего числа уникальных значений к большему — например, ORDER BY (city, category, sale_date), а не (sale_id, city). Так и сжатие будет максимальным, и отсечение гранул сработает идеально!

06 Шпаргалка урока перед практикой

Пять главных идей этого урока, которые отличают колончатые OLAP-движки от классических баз:

Понятие Короткий смысл
Колончатое хранение Каждая колонка лежит в своём файле. Запрос читает только те колонки, которые указаны в SELECT и WHERE.
Сжатие (LowCardinality, CODEC) Однотипные и отсортированные колонки сжимаются в 5–20 раз: словарное кодирование для повторяющихся строк, Delta/DoubleDelta для дат и ID, ZSTD для плотной упаковки.
Гранулы и ORDER BY MergeTree сортирует данные по ORDER BY и ставит закладку раз в 8 192 строки. Проверяй отсечение гранул через EXPLAIN indexes = 1.
Векторизация (SIMD) Процессор обрабатывает данные не по одной строке, а сразу пачками-векторами по тысячи чисел одной колонки за такт.
MPP и шардирование Разбиение огромной таблицы на серверы-шарды, которые считают промежуточные итоги параллельно. Избегай перекоса данных (Data Skew) и мелких вставок по 1 строке!

07 Мини-практикум для закрепления

Выполни 4 автономных задания в ClickHouse (база analytics_db через clickhouse-client или веб-интерфейс http://localhost:8123/play). Каждая задача сама создаёт свои таблицы и работает независимо от остальных.

Задание 1 (Базовый). Полгода игровой статистики за миллисекунды

Создай в analytics_db таблицу lab_game_matches на движке MergeTree() с колонками match_id UInt64, match_date Date, map_name LowCardinality(String), score UInt16, отсортированную по (map_name, match_date). Загрузи в неё 500 000 матчей через numbers(500000) с четырьмя картами ('Dust2', 'Mirage', 'Inferno', 'Nuke') и случайным счётом 10 + (number % 91). Напиши запрос, который выведет для каждой карты количество матчей, средний счёт (округлённый до 2 знаков) и максимальный счёт.

Показать решение
SQL (ClickHouse) · Эталонное решение задания 1 
DROP TABLE IF EXISTS lab_game_matches;

CREATE TABLE lab_game_matches (
    match_id   UInt64,
    match_date Date,
    map_name   LowCardinality(String),
    score      UInt16
)
ENGINE = MergeTree()
ORDER BY (map_name, match_date);

INSERT INTO lab_game_matches
SELECT
    number + 1,
    addDays(toDate('2026-01-01'), number % 180),
    arrayElement(['Dust2', 'Mirage', 'Inferno', 'Nuke'], (number % 4) + 1),
    10 + (number % 91)
FROM numbers(500000);

SELECT
    map_name,
    count()               AS matches_cnt,
    round(avg(score), 2)  AS avg_score,
    max(score)            AS max_score
FROM lab_game_matches
GROUP BY map_name
ORDER BY avg_score DESC;
Задание 2 (Средний). Битва сжатия: String против LowCardinality + ZSTD

Создай две таблицы на 1 000 000 строк: lab_logs_plain (event_time DateTime, service String, level String) и lab_logs_tiny (event_time DateTime CODEC(DoubleDelta, ZSTD(3)), service LowCardinality(String), level LowCardinality(String)), обе с ORDER BY (service, level, event_time). Заполни их одинаковым миллионом логов через numbers(1000000) и выведи запрос к system.columns, сравнивающий их сжатый размер на диске (disk_size) и коэффициент сжатия.

Показать решение
SQL (ClickHouse) · Эталонное решение задания 2 
DROP TABLE IF EXISTS lab_logs_plain;
DROP TABLE IF EXISTS lab_logs_tiny;

CREATE TABLE lab_logs_plain (
    event_time DateTime,
    service    String,
    level      String
)
ENGINE = MergeTree()
ORDER BY (service, level, event_time);

CREATE TABLE lab_logs_tiny (
    event_time DateTime CODEC(DoubleDelta, ZSTD(3)),
    service    LowCardinality(String),
    level      LowCardinality(String)
)
ENGINE = MergeTree()
ORDER BY (service, level, event_time);

INSERT INTO lab_logs_plain
SELECT
    toDateTime('2026-01-01 00:00:00') + number,
    arrayElement(['auth-service', 'billing-api', 'checkout-web', 'catalog'], (number % 4) + 1),
    arrayElement(['INFO', 'WARN', 'ERROR'], (number % 3) + 1)
FROM numbers(1000000);

INSERT INTO lab_logs_tiny SELECT * FROM lab_logs_plain;

SELECT
    table,
    formatReadableSize(sum(data_uncompressed_bytes)) AS raw_size,
    formatReadableSize(sum(data_compressed_bytes))   AS disk_size,
    round(sum(data_uncompressed_bytes) / sum(data_compressed_bytes), 1) AS ratio
FROM system.columns
WHERE database = currentDatabase()
  AND table IN ('lab_logs_plain', 'lab_logs_tiny')
GROUP BY table
ORDER BY table;
Задание 3 (Продвинутый). Почини порядок колонок в ORDER BY

Аналитики каждый день запускают запрос SELECT sum(price) FROM lab_orders WHERE status = 'refunded'. Кто-то по ошибке создал таблицу с ORDER BY (order_id, status) — из-за этого индекс по status не работает и читаются все гранулы. Создай две таблицы по 500 000 строк: lab_orders_bad с ORDER BY (order_id, status) и lab_orders_good с ORDER BY (status, order_id) (статусы: 'paid' — 80%, 'cancelled' — 10%, 'refunded' — 10%). Докажи через EXPLAIN indexes = 1, что во второй таблице количество прочитанных гранул сократилось примерно в 10 раз!

Показать решение
SQL (ClickHouse) · Эталонное решение задания 3 
DROP TABLE IF EXISTS lab_orders_bad;
DROP TABLE IF EXISTS lab_orders_good;

CREATE TABLE lab_orders_bad (
    order_id UInt64,
    status   LowCardinality(String),
    price    UInt32
) ENGINE = MergeTree()
ORDER BY (order_id, status);

CREATE TABLE lab_orders_good (
    order_id UInt64,
    status   LowCardinality(String),
    price    UInt32
) ENGINE = MergeTree()
ORDER BY (status, order_id);

INSERT INTO lab_orders_bad
SELECT
    number + 1,
    multiIf(number % 10 = 0, 'refunded', number % 10 = 1, 'cancelled', 'paid'),
    1000 + (number % 50) * 500
FROM numbers(500000);

INSERT INTO lab_orders_good SELECT * FROM lab_orders_bad;

-- Плохой ключ: прочитает ~62/62 гранул (100%)
EXPLAIN indexes = 1
SELECT sum(price) FROM lab_orders_bad WHERE status = 'refunded';

-- Правильный ключ: прочитает только ~7/62 гранул (~11%)!
EXPLAIN indexes = 1
SELECT sum(price) FROM lab_orders_good WHERE status = 'refunded';
Задание 4 (Проектирование). Мини-MPP витрина для сети кофеен

Сеть кофеен разнесла чеки по двум локальным шардам: lab_coffee_shard_east (Алматы, Астана) и lab_coffee_shard_west (Костанай, Актобе). Создай обе таблицы с колонками city LowCardinality(String), drink LowCardinality(String), price UInt16, наполни каждый шард тремя тестовыми чеками, а сверху поставь объединяющую таблицу lab_coffee_all на движке Merge(currentDatabase(), '^lab_coffee_shard_'). Выведи одним запросом к lab_coffee_all выручку по каждому напитку и укажи, сколько шардов (uniqExact(_table)) продавали этот напиток.

Показать решение
SQL (ClickHouse) · Эталонное решение задания 4 
DROP TABLE IF EXISTS lab_coffee_all;
DROP TABLE IF EXISTS lab_coffee_shard_east;
DROP TABLE IF EXISTS lab_coffee_shard_west;

CREATE TABLE lab_coffee_shard_east (
    city  LowCardinality(String),
    drink LowCardinality(String),
    price UInt16
) ENGINE = MergeTree() ORDER BY (city, drink);

CREATE TABLE lab_coffee_shard_west (
    city  LowCardinality(String),
    drink LowCardinality(String),
    price UInt16
) ENGINE = MergeTree() ORDER BY (city, drink);

INSERT INTO lab_coffee_shard_east VALUES
    ('Алматы', 'Капучино', 1400),
    ('Астана', 'Латте',    1600),
    ('Алматы', 'Раф',      1800);

INSERT INTO lab_coffee_shard_west VALUES
    ('Костанай', 'Капучино', 1300),
    ('Актобе',   'Латте',    1500),
    ('Костанай', 'Эспрессо',  900);

CREATE TABLE lab_coffee_all AS lab_coffee_shard_east
ENGINE = Merge(currentDatabase(), '^lab_coffee_shard_');

SELECT
    drink,
    uniqExact(_table) AS shards_count,
    count()           AS cups_sold,
    sum(price)        AS total_revenue
FROM lab_coffee_all
GROUP BY drink
ORDER BY total_revenue DESC;

Итог урока и мостик дальше Ты увидел под капотом, почему колончатые OLAP-движки вроде ClickHouse и DuckDB перемалывают миллионы строк за считаные миллисекунды: они читают с диска только нужные колонки, сжимают их в 10–20 раз, отсекают лишние гранулы по разреженному индексу ORDER BY, считают пачками через SIMD-векторизацию и масштабируются горизонтально с помощью MPP и шардирования. Но сегодня мы генерировали данные искусственно через numbers() — а как в реальной компании данные каждый день перетекают из боевого PostgreSQL в хранилище, не дублируются при повторном запуске скрипта и сохраняют историю изменений (например, если клиент сменил город или тариф)?
