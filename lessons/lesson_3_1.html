Урок 3.1. Физическая архитектура PostgreSQL: страницы (8 КБ), Heap и Shared Buffers

Главное в этом уроке
  • Узнаешь, как таблицы на самом деле хранятся на диске: файлы и страницы по 8 КБ (8192 байта).
  • Разберёшься, почему таблица называется кучей (Heap), что означает скрытый адрес строки ctid и почему UPDATE создаёт копию строки вместо перезаписи.
  • Поймёшь устройство оперативной памяти PostgreSQL — общего буферного кэша (Shared Buffers), и разницу между shared hit и shared read.
  • Научишься заглядывать «под капот» базы learning_db с помощью pg_relation_filepath(), EXPLAIN (ANALYZE, BUFFERS) и расширения pg_buffercache.

01 Как таблица живёт на диске: файлы и страницы по 8 КБ

Когда ты пишешь запрос вроде SELECT * FROM game_items WHERE id = 42;, легко представить, что внутри сервера лежит красивая таблица, похожая на лист Excel. Но жёсткий диск и SSD понятия не имеют про строки, колонки и SQL — для диска существуют только обычные файлы с нулями и единицами. Возникает вопрос: как PostgreSQL раскладывает миллионы строк по файлам, чтобы быстро доставать нужные данные?

Представь толстую школьную тетрадь, в которой каждый лист строго одинакового размера. Даже если тебе нужно прочитать одно-единственное слово с 5-й страницы, ты открываешь и держишь перед глазами весь лист целиком, а не вырезаешь ножницами одно слово.

В PostgreSQL каждая таблица — это отдельный файл на диске (а если таблица вырастет больше 1 ГБ, файл нарежется на куски по 1 ГБ). Внутри этот файл поделён на одинаковые «листы» размером ровно 8 КБ (8192 байта). Инженеры называют их страницами (Pages) или блоками (Blocks). Это минимальная порция данных: PostgreSQL никогда не читает с диска 50 байт — он всегда забирает целую страницу 8 КБ!

Зачем указатели растут сверху вниз, а сами строки — снизу вверх? Это гениальный приём экономии! Представь, что вверху листа ты пишешь короткое оглавление («запись №1 — в самом низу», «запись №2 — чуть выше»), а сами заметки разной длины дописываешь с нижней кромки. Пока посередине остаётся свободное место, тебе не нужно переписывать весь лист при каждом добавлении строки.

А если строка больше 8 КБ? Например, ты сохраняешь целый рассказ на 50 КБ в колонку TEXT. PostgreSQL не ломается: автоматически включается механизм TOAST (The Oversized-Attribute Storage Technique). База сжимает огромный текст, нарезает его на кусочки и прячет в отдельную скрытую таблицу, а на основной странице 8 КБ оставляет короткий «ярлычок-ссылку» размером в пару десятков байт.

Практика №1. Проверяем размер страницы и находим файл таблицы на диске

Давай заглянем прямо в нашу учебную базу learning_db. Сначала создадим таблицу игровых предметов game_items, положим туда 1 000 строк и спросим у PostgreSQL, где лежит её файл и сколько 8-килобайтных страниц он занимает.

SQL · Подготовка таблицы game_items (1 000 строк) 
-- Безопасно пересоздаём таблицу для экспериментов
DROP TABLE IF EXISTS game_items;

CREATE TABLE game_items (
    id     SERIAL PRIMARY KEY,
    title  TEXT NOT NULL,
    rarity TEXT NOT NULL,
    price  NUMERIC(10, 2) NOT NULL
);

-- Наполняем таблицу 1 000 игровых предметов
INSERT INTO game_items (title, rarity, price)
SELECT
    'Меч героя #' || g,
    CASE WHEN g % 5 = 0 THEN 'epic' ELSE 'common' END,
    (100 + (g * 7) % 900)::NUMERIC(10, 2)
FROM generate_series(1, 1000) AS g;
SQL · Смотрим размер блока, путь к файлу и число страниц 
-- 1. Узнаём размер одной страницы (по умолчанию всегда 8192 байта)
SHOW block_size;

-- 2. Находим физический файл таблицы и считаем количество страниц по 8 КБ
SELECT
    pg_relation_filepath('game_items') AS file_path,
    pg_relation_size('game_items') AS size_bytes,
    pg_size_pretty(pg_relation_size('game_items')) AS size_pretty,
    pg_relation_size('game_items') / 8192 AS pages_count;
Ответ PostgreSQL
 block_size
------------
 8192
(1 row)

     file_path     | size_bytes | size_pretty | pages_count
-------------------+------------+-------------+-------------
 base/16384/16412  |      73728 | 72 kB       |           9
(1 row)

Посмотри на результат: вся наша таблица на 1 000 строк — это обычный файл base/16384/16412 внутри каталога данных PostgreSQL. Его размер 73728 байт — это ровно 9 страниц по 8192 байта (примерно по 111 строк на каждом «листе»). Так мы решили первую загадку: строки не висят в воздухе, они плотно упакованы в пронумерованные страницы по 8 КБ.

02 Куча (Heap), адрес ctid и тайна команды UPDATE

А теперь загадка поинтереснее. Допустим, мы добавили в рюкзак героя 5 предметов, потом обновили цену первому предмету, а второй удалили. Если сделать SELECT * FROM backpack; без ORDER BY, обновлённый первый предмет внезапно окажется… в самом конце списка! Почему строка «убежала» со своего места?

Представь коробку с анкетами учеников на столе у секретаря. Новые анкеты кладут на первое свободное место — никто не сортирует их по алфавиту. А если ученик сменил номер телефона, секретарь не стирает старую анкету ластиком (вдруг прямо в эту секунду её читает директор!). Вместо этого секретарь выписывает новую карточку и кладёт её на свободное место, а на старой аккуратно ставит пометку карандашом: «устарела».

Именно так устроена таблица в PostgreSQL. Её основное хранилище называется Heap (куча) — строки в страницах лежат без гарантированного порядка. У каждой конкретной версии строки (инженеры зовут её кортеж, или tuple) есть точный физический адрес — скрытая системная колонка ctid. Она выглядит как пара чисел (номер_страницы, номер_слота). Например, (0, 3) означает: «страница №0, указатель №3».

Зачем столько сложностей? Благодаря этому механизму (он называется MVCC — многоверсионность) одни пользователи могут спокойно читать таблицу, пока другие её обновляют: никто никого не блокирует. А старые «мёртвые» версии строк (dead tuples) позже убирает специальный фоновый уборщик VACUUM, освобождая место внутри страниц для новых записей.

Практика №2. Ловим «переезд» строки по адресу ctid

Проверим эту механику своими руками! Создадим крошечную таблицу backpack на 3 предмета, посмотрим на скрытую колонку ctid, обновим первый предмет и удалим второй.

SQL · Наблюдаем за адресом ctid при UPDATE и DELETE 
-- Подготовка маленькой таблицы для эксперимента
DROP TABLE IF EXISTS backpack;

CREATE TABLE backpack (
    id    INT PRIMARY KEY,
    item  TEXT NOT NULL,
    price INT NOT NULL
);

INSERT INTO backpack (id, item, price) VALUES
    (1, 'Железный меч', 500),
    (2, 'Деревянный щит', 300),
    (3, 'Зелье здоровья', 50);

-- Смотрим начальные физические адреса строк
SELECT ctid, id, item, price FROM backpack;
Ответ PostgreSQL (до изменений)
 ctid  | id |      item      | price
-------+----+----------------+-------
 (0,1) |  1 | Железный меч   |   500
 (0,2) |  2 | Деревянный щит |   300
 (0,3) |  3 | Зелье здоровья |    50
(3 rows)
SQL · Обновляем меч, удаляем щит и снова смотрим ctid 
-- Меняем цену меча и удаляем щит
UPDATE backpack SET price = 750 WHERE id = 1;
DELETE FROM backpack WHERE id = 2;

-- Смотрим, куда «переехал» Железный меч!
SELECT ctid, id, item, price FROM backpack;
Ответ PostgreSQL (после UPDATE и DELETE)
 ctid  | id |      item      | price
-------+----+----------------+-------
 (0,3) |  3 | Зелье здоровья |    50
 (0,4) |  1 | Железный меч   |   750
(2 rows)

Вот и разгадка нашей задачи из начала раздела! «Железный меч» переехал с адреса (0,1) на новый слот (0,4), а слоты (0,1) и (0,2) остались лежать в странице как «мёртвые» строки до прихода VACUUM. Поскольку PostgreSQL при обычном SELECT просто читает страницу сверху вниз, сначала попалось зелье на (0,3), и только потом меч на (0,4).

✗ Как НЕ надо
-- Обновляем даже те строки,
-- где уже стоит 'epic'
UPDATE game_items
SET rarity = 'epic'
WHERE price >= 500;

PostgreSQL всё равно создаст новые версии строк в Heap и раздует таблицу мёртвыми кортежами, даже если значение не изменилось!

✓ Как правильно
-- Трогаем только строки,
-- которые реально меняются
UPDATE game_items
SET rarity = 'epic'
WHERE price >= 500
  AND rarity IS DISTINCT FROM 'epic';

Неизменённые строки не перезаписываются: страницы 8 КБ не захламляются лишним мусором, а запрос работает быстрее.

Частая ошибка: Никогда не сохраняй ctid в приложении как постоянный идентификатор строки! Как мы только что увидели, любой UPDATE (а также переупаковка таблицы VACUUM FULL) мгновенно меняет ctid. Для постоянных ссылок всегда используй PRIMARY KEY (например, id).

03 Shared Buffers: как оперативная память ускоряет PostgreSQL

Теперь представим реальный интернет-магазин. За одну секунду на сайт заходят 2 000 человек и смотрят каталог товаров. Если бы PostgreSQL каждый раз бегал за 8-килобайтными страницами на жёсткий диск или даже на быстрый SSD, диск быстро бы захлебнулся, а сайт начал грузиться по 10 секунд. Как же база умудряется отвечать за доли миллисекунды?

Представь, что ты делаешь уроки дома. Все твои 50 учебников стоят в большом шкафу в коридоре — это диск (SSD/HDD). А прямо перед тобой — широкий письменный стол. Это оперативная память (RAM), а точнее — специально выделенная для PostgreSQL область Shared Buffers (общий буферный кэш).

Когда тебе нужна 12-я страница учебника по физике, ты сначала смотришь на свой стол. Если страница уже лежит перед тобой — ты читаешь её мгновенно! В PostgreSQL это называется попадание в кэш (Buffer Hit / shared hit). Если её на столе нет — это промах (Buffer Miss / shared read): приходится встать, сходить к шкафу, принести лист 8 КБ и положить на стол. А когда стол полностью забит, самую редко используемую страницу приходится убрать со стола, чтобы освободить место.

Обрати внимание на пунктирную стрелку внизу схемы! Когда ты делаешь INSERT или UPDATE, PostgreSQL меняет страницу прямо в Shared Buffers и помечает её флажком «грязная» (Dirty Buffer). Она не пишется в файл таблицы сию секунду — это было бы слишком медленно. Специальные фоновые рабочие (Background Writer и Checkpointer) спокойно сбрасывают «грязные» страницы на диск пачками, пока ты продолжаешь работать. (А почему данные не пропадут, если внезапно выдернуть вилку из розетки, мы узнаем в уроке 3.4 про журнал WAL!)

Уровень памяти Жизненная аналогия Где хранится Примерная скорость чтения
Shared Buffers Твой письменный стол RAM, управляет PostgreSQL ~0.0001 мс (мгновенно)
OS Page Cache Тумбочка рядом со столом RAM, управляет ОС (Linux) ~0.005 мс (очень быстро)
NVMe SSD Шкаф в коридоре Твердотельный диск ~0.05–0.1 мс (в сотни раз медленнее RAM)
HDD Библиотека на соседней улице Магнитный диск ~5–10 мс (в десятки тысяч раз медленнее RAM)

Практика №3. Проверяем размер shared_buffers и ловим реальную ошибку

Давай посмотрим, какой размер «письменного стола» выделен в нашем Docker-контейнере прямо сейчас, и попробуем увеличить его обычной командой SET.

SQL · Проверяем и пытаемся изменить shared_buffers на лету 
-- Сколько оперативной памяти сейчас отдано под Shared Buffers?
SHOW shared_buffers;

-- Попробуем увеличить размер кэша прямо в текущей сессии
SET shared_buffers = '256MB';
Ответ PostgreSQL (первая команда)
 shared_buffers
----------------
 128MB
(1 row)
Ошибка PostgreSQL (вторая команда)
ERROR:  parameter "shared_buffers" cannot be changed without restarting the server

Почему PostgreSQL отказался менять shared_buffers на лету? Потому что этот общий кусок памяти запрашивается у операционной системы один раз при запуске сервера и делится между всеми подключениями. Поменять его можно только через конфиг (postgresql.conf, параметры запуска Docker или команду ALTER SYSTEM SET shared_buffers = '256MB';) с последующим перезапуском PostgreSQL.

✗ Как НЕ надо
-- На сервере 16 ГБ RAM:
-- отдаём 90% под shared_buffers!
ALTER SYSTEM SET
  shared_buffers = '14GB';

Операционной системе не останется памяти на OS Page Cache и сортировки запросов (work_mem). Сервер начнёт дико тормозить или упадёт от нехватки памяти (OOM).

✓ Как правильно
-- На сервере 16 ГБ RAM:
-- классический старт ~25% RAM
ALTER SYSTEM SET
  shared_buffers = '4GB';
-- Затем перезапуск сервера!

PostgreSQL работает в паре с кэшем ОС: 25% RAM идёт в Shared Buffers, а остальная память помогает ОС кэшировать файлы и обслуживать подключения.

04 Рентген памяти: смотрим в Shared Buffers своими глазами

Хватит верить на слово — давай устроим настоящую лабораторную работу! Мы хотим своими глазами увидеть:

  1. Сколько 8-килобайтных страниц читает запрос с диска при первом запуске и сколько берёт из Shared Buffers при повторном.
  2. Какие именно таблицы прямо сейчас лежат в оперативной памяти PostgreSQL.
  3. Как таблица раздувается от мёртвых строк после UPDATE и как ведёт себя после VACUUM.

Практика №4. Сравниваем холодное и горячее чтение через EXPLAIN (ANALYZE, BUFFERS)

Перед запуском посмотри на таблицу «Было → Стало»: она подскажет, на какую именно строчку в отчёте EXPLAIN смотреть.

Ситуация Что увидим в Buffers: Что произошло физически
Было: первый запрос после рестарта сервера («холодный» кэш) shared read=417 Стол пустой — все 417 страниц по 8 КБ пришлось загрузить из ОС / с диска.
Стало: повторный запуск того же запроса («горячий» кэш) shared hit=417 Все 417 страниц уже лежат в Shared Buffers — диск вообще не трогали!
SQL · Создаём таблицу orders_big на 50 000 строк 
DROP TABLE IF EXISTS orders_big;

CREATE TABLE orders_big (
    id            INT NOT NULL,
    customer_name TEXT NOT NULL,
    amount        NUMERIC(10, 2) NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL
);

-- Генерируем 50 000 заказов (~3.3 МБ на диске)
INSERT INTO orders_big (id, customer_name, amount, created_at)
SELECT
    g,
    'Покупатель #' || (g % 5000),
    (500 + (g * 13) % 9500)::NUMERIC(10, 2),
    now() - (g || ' minutes')::INTERVAL
FROM generate_series(1, 50000) AS g;

-- Обновляем статистику и убираем служебные «хвосты» после загрузки
VACUUM ANALYZE orders_big;

Пока таблица только что создана, её страницы уже лежат в памяти. Чтобы честно смоделировать «пустой стол», перезапусти контейнер PostgreSQL одной командой в терминале, а затем дважды выполни один и тот же запрос с EXPLAIN (ANALYZE, BUFFERS).

Bash · Очищаем Shared Buffers перезапуском контейнера 
docker compose restart pg_primary
SQL · Запускаем один и тот же запрос ДВА раза подряд 
-- Первый запуск (после перезапуска сервера)
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM orders_big
WHERE amount > 5000;

-- Второй запуск (сразу же следом)
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM orders_big
WHERE amount > 5000;
Ответ PostgreSQL (1-й запуск: «холодный» Shared Buffers)

   Buffers: shared read=417
   ->  Seq Scan on orders_big  (cost=0.00..1042.00 rows=26310 width=0) (actual time=0.095..12.640 rows=26315 loops=1)
         Filter: (amount > '5000'::numeric)
         Rows Removed by Filter: 23685
         Buffers: shared read=417
 Planning Time: 0.412 ms
 Execution Time: 14.910 ms
Ответ PostgreSQL (2-й запуск: «горячий» Shared Buffers)
 Aggregate  (cost=1042.00..1042.01 rows=1 width=8) (actual time=4.112..4.113 rows=1 loops=1)
   Buffers: shared hit=417
   ->  Seq Scan on orders_big  (cost=0.00..1042.00 rows=26310 width=0) (actual time=0.014..2.890 rows=26315 loops=1)
         Filter: (amount > '5000'::numeric)
         Rows Removed by Filter: 23685

Сравни два вывода! В первый раз мы увидели shared read=417 и время 14.9 мс. Во второй раз — ровно те же 417 страниц, но уже shared hit=417, и время рухнуло до 4.1 мс (почти в 4 раза быстрее!). Мы буквально поймали работу Shared Buffers за руку.

Практика №5. Заглядываем внутрь кэша через расширение pg_buffercache

В PostgreSQL есть встроенный «рентген» памяти — расширение pg_buffercache. Оно показывает каждый 8-килобайтный слот Shared Buffers в виде обычной таблицы! Если попробовать прочитать его сразу, не включив расширение, PostgreSQL выдаст ошибку:

SQL · Попытка прочитать pg_buffercache до установки расширения 
SELECT count(*) FROM pg_buffercache;
Ошибка PostgreSQL
ERROR:  relation "pg_buffercache" does not exist
LINE 1: SELECT count(*) FROM pg_buffercache;
                             ^

Расширение уже лежит внутри Docker-образа PostgreSQL 16, но его нужно активировать в базе командой CREATE EXTENSION. Сделаем это и посмотрим, какие наши таблицы прямо сейчас заняли место на «письменном столе» памяти.

SQL · Включаем pg_buffercache и смотрим содержимое Shared Buffers 
-- Активируем расширение в текущей базе learning_db
CREATE EXTENSION IF NOT EXISTS pg_buffercache;

-- Смотрим, сколько страниц 8 КБ занимают наши таблицы в Shared Buffers
SELECT
    c.relname AS table_name,
    count(*) AS buffers_count,
    pg_size_pretty(count(*) * 8192) AS cached_size,
    count(*) FILTER (WHERE b.isdirty) AS dirty_buffers
FROM pg_buffercache AS b
JOIN pg_class AS c
  ON b.relfilenode = pg_relation_filenode(c.oid)
WHERE b.reldatabase = (
    SELECT oid FROM pg_database WHERE datname = current_database()
)
  AND c.relnamespace = 'public'::regnamespace
  AND c.relkind = 'r'
GROUP BY c.relname
ORDER BY buffers_count DESC;
Ответ PostgreSQL
 table_name | buffers_count | cached_size | dirty_buffers
------------+---------------+-------------+---------------
 orders_big |           417 | 3336 kB     |             0
 game_items |             9 | 72 kB       |             0
 backpack   |             1 | 8192 bytes  |             0
(3 rows)

Посмотри на совпадение до единого байта: orders_big занимает в памяти ровно 417 буферов (3336 kB), game_items — 9 буферов (72 kB), а крошечная backpack — всего 1 буфер (8192 bytes). Колонка dirty_buffers = 0 означает, что все эти страницы чистые и уже совпадают с файлами на диске.

Практика №6. Раздувание Heap (dead tuples) и работа VACUUM

Напоследок объединим всё, что узнали о Heap и страницах 8 КБ. Обновим 10 000 строк в таблице orders_big и посмотрим, как вырастет её размер, сколько появится мёртвых строк и «грязных» страниц, а потом запустим уборщика VACUUM.

SQL · Массовый UPDATE и проверка состояния таблицы 
-- Обновляем 10 000 заказов (создаём 10 000 новых версий строк в Heap)
UPDATE orders_big
SET amount = amount + 100
WHERE id <= 10000;

-- Проверяем размер таблицы и число живых/мёртвых строк
SELECT
    relname AS table_name,
    n_live_tup,
    n_dead_tup,
    pg_size_pretty(pg_relation_size('orders_big')) AS heap_size,
    pg_relation_size('orders_big') / 8192 AS pages_count
FROM pg_stat_user_tables
WHERE relname = 'orders_big';
Ответ PostgreSQL (после UPDATE 10 000 строк)
 table_name | n_live_tup | n_dead_tup | heap_size | pages_count
------------+------------+------------+-----------+-------------
 orders_big |      50000 |      10000 | 4008 kB   |         501
(1 row)
SQL · Запускаем VACUUM и проверяем результат 
-- Запускаем уборщика мёртвых строк
VACUUM orders_big;

-- Снова смотрим статистику и размер Heap
SELECT
    relname AS table_name,
    n_live_tup,
    n_dead_tup,
    pg_size_pretty(pg_relation_size('orders_big')) AS heap_size,
    pg_relation_size('orders_big') / 8192 AS pages_count
FROM pg_stat_user_tables
WHERE relname = 'orders_big';
Ответ PostgreSQL (после VACUUM)
 table_name | n_live_tup | n_dead_tup | heap_size | pages_count
------------+------------+------------+-----------+-------------
 orders_big |      50000 |          0 | 4008 kB   |         501
(1 row)

Заметил хитрую деталь? После UPDATE таблица выросла с 417 до 501 страницы, потому что 10 000 новых версий строк не поместились в старые листы. После VACUUM счётчик n_dead_tup обнулился, но размер файла остался 4008 kB! Обычный VACUUM не отдаёт пустое место обратно операционной системе — он просто помечает освободившиеся слоты внутри 8-килобайтных страниц как пригодные для будущих INSERT и UPDATE (чтобы не дёргать диск лишний раз).

Совет для реальных проектов: В продакшене инженеры всегда следят за метрикой Cache Hit Ratio — процентом чтений, попавших прямо в Shared Buffers. Для обычных веб-приложений (магазины, мессенджеры, CRM) здоровый показатель — 99% и выше. Если процент падает ниже 95%, значит, рабочие данные не помещаются на «письменный стол» RAM и сервер слишком часто бегает на диск.

05 Шпаргалка перед практикой

Короткий мини-словарик главных терминов урока — пробегись глазами перед тем, как решать задачи:

  • Страница (Page / Block) — минимальный кирпичик хранения и чтения данных в PostgreSQL. По умолчанию равен ровно 8 КБ (8192 байта).
  • Куча (Heap) — файлы таблицы, в которых строки лежат без сортировки, просто на свободных местах внутри страниц.
  • ctid — временный физический адрес строки вида (страница, слот). При любом UPDATE строка получает новый ctid, а старая версия становится «мёртвым» кортежем (dead tuple).
  • Shared Buffers — кэш страниц 8 КБ в оперативной памяти. shared hit означает чтение из памяти (мгновенно), shared read — чтение из кэша ОС или с диска, isdirty = true — страница изменена в памяти и ждёт сброса на диск.
  • Золотое правило диагностики — всегда пиши EXPLAIN (ANALYZE, BUFFERS), чтобы видеть не только время выполнения, но и точное число прочитанных страниц.

Задание 1 (Базовый). Разведка файла и подсчёт страниц 8 КБ

Создай автономную таблицу lab_books с колонками id INT и title TEXT, заполни её 500 строками через generate_series. Затем одним SELECT выведи путь к файлу таблицы на диске (pg_relation_filepath), её размер в байтах, читаемый размер (pg_size_pretty) и точное количество 8-килобайтных страниц.

Показать решение

DROP TABLE IF EXISTS lab_books;

CREATE TABLE lab_books (

Задание 2 (Средний). Поймай двойной переезд строки в Heap

Создай автономную таблицу lab_players (id INT, nickname TEXT, score INT) и вставь 3 игроков (с id 1, 2, 3). Выведи их ctid. Затем дважды обнови поле score у игрока с id = 1, снова выведи ctid всех строк (убедись, что адрес игрока 1 перескочил на (0,5)) и проверь в pg_stat_user_tables, что у таблицы появилось 2 мёртвые строки (n_dead_tup).

Показать решение

DROP TABLE IF EXISTS lab_players;

);

Задание 3 (Средний+). Цена поиска одной строки без индекса

Создай автономную таблицу lab_events (id INT, payload TEXT) без первичного ключа и индексов, вставь 20 000 строк и выполни VACUUM ANALYZE lab_events;. С помощью EXPLAIN (ANALYZE, BUFFERS) найди всего одну строку с id = 15000. Посмотри в выводе, сколько страниц 8 КБ пришлось перечитать ради одной записи (Seq Scan), и убедись, что повторный запуск даёт 100% shared hit.

Показать решение
SQL · Эталонное решение задания 3 
DROP TABLE IF EXISTS lab_events;

CREATE TABLE lab_events (
    id      INT NOT NULL,
    payload TEXT NOT NULL
);

INSERT INTO lab_events (id, payload)
SELECT g, 'Событие системы #' || g || ' — успешно обработано'
FROM generate_series(1, 20000) AS g;

VACUUM ANALYZE lab_events;

-- Ищем одну строку: без индекса Postgres просканирует ВСЕ страницы Heap!
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM lab_events
WHERE id = 15000;

-- Повторный запуск: все прочитанные страницы уже в Shared Buffers (shared hit)
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM lab_events
WHERE id = 15000;
Задание 4 (Продвинутый). Топ-5 таблиц в Shared Buffers и поиск «грязных» страниц

Убедись, что включено расширение pg_buffercache. Создай автономную таблицу lab_cache_test (id INT, note TEXT) на 15 000 строк, обнови в ней первые 1 000 строк (чтобы появились «грязные» буферы), а затем напиши запрос к pg_buffercache и pg_class, который выведет топ-5 таблиц схемы public в текущей базе данных: имя таблицы, число занятых буферов, размер в памяти (pg_size_pretty) и количество «грязных» страниц (isdirty).

Показать решение
SQL · Эталонное решение задания 4 
CREATE EXTENSION IF NOT EXISTS pg_buffercache;

DROP TABLE IF EXISTS lab_cache_test;

CREATE TABLE lab_cache_test (
    id   INT NOT NULL,
    note TEXT NOT NULL
);

INSERT INTO lab_cache_test (id, note)
SELECT g, 'Тестовая запись для кэша #' || g
FROM generate_series(1, 15000) AS g;

-- Создаём «грязные» страницы в Shared Buffers
UPDATE lab_cache_test
SET note = note || ' [обновлено]'
WHERE id <= 1000;

-- Топ-5 таблиц схемы public по занятым слотам в Shared Buffers
SELECT
    c.relname AS table_name,
    count(*) AS buffers_count,
    pg_size_pretty(count(*) * 8192) AS cached_size,
    count(*) FILTER (WHERE b.isdirty) AS dirty_buffers
FROM pg_buffercache AS b
JOIN pg_class AS c
  ON b.relfilenode = pg_relation_filenode(c.oid)
WHERE b.reldatabase = (
    SELECT oid FROM pg_database WHERE datname = current_database()
)
  AND c.relnamespace = 'public'::regnamespace
  AND c.relkind = 'r'
GROUP BY c.relname
ORDER BY buffers_count DESC
LIMIT 5;
