01 Готовим стенд: наш мини-магазин в learning_db

В прошлом уроке мы научились раскладывать данные по аккуратным нормализованным таблицам и связывать их «многие-ко-многим». Теперь настало время собирать из этих таблиц ответы на живые вопросы бизнеса: кто из клиентов пропал, какие товары не продаются и сколько денег приносит каждый город.

Открой консоль psql внутри своего контейнера PostgreSQL и выполни стартовый скрипт ниже. Он безопасен для повторного запуска (сначала очищает старые учебные таблицы через DROP TABLE IF EXISTS ... CASCADE) и создаёт 5 таблиц нашего магазина IT-мерча.

BASH · Подключение к learning_db

SQL · Подготовка таблиц и тестовых данных (безопасный перезапуск) 
-- Сбрасываем учебные таблицы урока, если они уже существуют
DROP TABLE IF EXISTS order_items CASCADE;
DROP TABLE IF EXISTS orders CASCADE;
DROP TABLE IF EXISTS products CASCADE;
DROP TABLE IF EXISTS customers CASCADE;
DROP TABLE IF EXISTS newsletter_leads CASCADE;

-- 1. Покупатели магазина
CREATE TABLE customers (
    id        INTEGER PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    email     VARCHAR(100) NOT NULL UNIQUE,
    city      VARCHAR(60)  NOT NULL
);

-- 2. Каталог товаров
CREATE TABLE products (
    id       INTEGER PRIMARY KEY,
    title    VARCHAR(100)   NOT NULL,
    category VARCHAR(50)    NOT NULL,
    price    NUMERIC(10, 2) NOT NULL CHECK (price > 0)
);

-- 3. Заказы (связь 1-ко-многим с customers)
CREATE TABLE orders (
    id          INTEGER PRIMARY KEY,
    customer_id INTEGER     NOT NULL REFERENCES customers(id),
    status      VARCHAR(20) NOT NULL CHECK (status IN ('paid', 'cancelled')),
    created_at  DATE        NOT NULL
);

-- 4. Позиции внутри заказа (связь многие-ко-многим между orders и products)
CREATE TABLE order_items (
    order_id   INTEGER NOT NULL REFERENCES orders(id),
    product_id INTEGER NOT NULL REFERENCES products(id),
    quantity   INTEGER NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, product_id)
);

-- 5. Подписчики рассылки с рекламного лендинга (часть из них уже клиенты!)
CREATE TABLE newsletter_leads (
    id        INTEGER PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    email     VARCHAR(100) NOT NULL UNIQUE
);

02 Внешние объединения (LEFT JOIN): как не потерять «молчунов»

Проблема: Маркетолог просит список всех зарегистрированных клиентов и номера их заказов, чтобы понять, кто уже покупал, а кому пора отправить приветственный промокод. Если просто соединить customers и orders обычным INNER JOIN, Глеб Орлов просто исчезнет из таблицы!

Представь школьного учителя со списком класса в журнале и стопкой сданных контрольных на столе. Если учитель выпишет только тех, чьи тетради нашлись в стопке, двоечники и прогульщики просто пропадут из ведомости — это и есть внутреннее объединение (INNER JOIN). А если учитель оставит весь список класса целиком и напротив не сдавших поставит прочерк — это левое внешнее объединение (LEFT OUTER JOIN, в коде почти всегда пишут коротко LEFT JOIN).

А как же RIGHT JOIN и FULL JOIN? RIGHT JOIN — это зеркальная копия LEFT JOIN (сохраняет всю правую таблицу). Инженеры редко его пишут: проще поменять таблицы местами и использовать привычный LEFT JOIN. А FULL OUTER JOIN сохраняет несовпавшие строки сразу с обеих сторон (удобно для сверки двух прайс-листов).

Пример 1. Все клиенты + поиск тех, кто ничего не купил

Сначала посмотрим всех покупателей и их заказы. В консольном выводе psql значения NULL по умолчанию отображаются пустыми ячейками.

SQL · Пример 1А: LEFT JOIN сохраняет всех клиентов 
-- Берём ВСЕХ клиентов из левой таблицы и подтягиваем их заказы (если они есть)
SELECT
    c.id AS customer_id,
    c.full_name,
    o.id AS order_id,
    o.status
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
ORDER BY c.id, o.id;
Ответ PostgreSQL
 customer_id |   full_name    | order_id |  status
-------------+----------------+----------+-----------
           1 | Алиса Смирнова |      101 | paid
           1 | Алиса Смирнова |      102 | paid
           2 | Борис Волков   |      103 | paid
           2 | Борис Волков   |      104 | cancelled
           3 | Вера Ли        |      105 | cancelled
           4 | Глеб Орлов     |          |
           5 | Дина Ким       |      106 | paid
(7 rows)

Смотри на строчку с Глебом Орловым: в колонках order_id и status пусто (там лежит NULL). Этот трюк используют каждый день, чтобы искать «потеряшек» — такой приём называют анти-джойн (LEFT JOIN ... WHERE right.id IS NULL).

SQL · Пример 1Б: Находим клиентов без единого заказа 
-- Оставляем только те строки, которым не нашлось пары в таблице orders
SELECT
    c.id,
    c.full_name,
    c.email
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
WHERE o.id IS NULL;
Ответ PostgreSQL
 id | full_name  |    email
----+------------+--------------
  4 | Глеб Орлов | gleb@mail.ru
(1 row)

Задача решена: теперь маркетолог видит не только активных покупателей, но и точно знает, что приветственный промокод нужно отправить именно Глебу на gleb@mail.ru.

Главная ловушка LEFT JOIN: фильтр в WHERE против ON

Допустим, задача слегка изменилась: «Покажи ВСЕХ клиентов и только их оплаченные (paid) заказы. Если оплаченных заказов нет — клиент всё равно должен остаться в списке». Здесь ошибается 9 из 10 новичков!

✗ Как НЕ надо
SELECT c.full_name, o.id
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.id
WHERE o.status = 'paid';

WHERE срабатывает после склейки! Строки Веры (cancelled) и Глеба (NULL) не пройдут проверку o.status = 'paid' и исчезнут — LEFT JOIN тайно превратится в INNER JOIN.

✓ Как правильно
SELECT c.full_name, o.id
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.id
 AND o.status = 'paid';

Условие в ON отсеивает отменённые заказы до присоединения. Алиса, Борис и Дина получат номера оплаченных заказов, а Вера и Глеб честно останутся в списке с NULL.

Запомни железное правило: если ты пишешь условие на колонку правой таблицы внутри WHERE (кроме проверки IS NULL), ты уничтожаешь смысл LEFT JOIN. Фильтры правой таблицы переноси в блок ON.

03 Объединение выборок (UNION и UNION ALL): склеиваем списки вниз

Проблема: В нашем магазине есть база покупателей (customers) и отдельная таблица подписчиков рассылки с лендинга (newsletter_leads). Перед выходом новой коллекции нужно собрать единый список контактов, чтобы отправить анонс всем — но не засыпать Алису и Бориса двумя одинаковыми письмами.

Если JOIN склеивает таблицы вбок (приставляет новые колонки справа, как расширение анкеты), то оператор объединения выборок (UNION) склеивает результаты двух SELECT вертикально, один под другим. Представь, что ты собираешь список гостей на день рождения: один список написан у тебя в блокноте, второй — у друга. Склеиваешь два листка скотчем:

  • UNION — склеивает листки и аккуратно вычёркивает повторяющиеся строки (удаляет полные дубликаты).
  • UNION ALL — просто склеивает листки как есть, вместе с дубликатами, зато работает быстрее, потому что базе не нужно перепроверять все строки на совпадение.

Пример 2. Единая база контактов для рассылки

Чтобы два запроса состыковались через UNION, у них должно быть одинаковое количество колонок и совместимые типы данных на одних и тех же позициях. Названия итоговых колонок PostgreSQL берёт из первого SELECT, а общий ORDER BY ставится в самом конце.

SQL · Пример 2: Уникальный список email из двух таблиц 
-- Склеиваем покупателей и подписчиков лендинга без дубликатов
SELECT full_name, email
FROM customers

UNION

SELECT full_name, email
FROM newsletter_leads
ORDER BY full_name;
Ответ PostgreSQL
   full_name    |     email
----------------+----------------
 Алиса Смирнова | alice@mail.ru
 Борис Волков   | boris@mail.ru
 Вера Ли        | vera@mail.ru
 Глеб Орлов     | gleb@mail.ru
 Дина Ким       | dina@mail.ru
 Егор Савин     | egor@mail.ru
 Жанна Нур      | zhanna@mail.ru
(7 rows)

В таблице customers было 5 строк, в newsletter_leads — 4 строки (в сумме 9). Но UNION заметил, что Алиса и Борис есть в обоих списках, убрал повторы и вернул ровно 7 уникальных получателей. Задача рассылки решена!

А что произойдёт, если перепутать порядок колонок и попытаться склеить число (id) со строкой (full_name)? PostgreSQL мгновенно остановит тебя ошибкой:

Ошибка PostgreSQL · Несовпадение типов в UNION
ERROR:  UNION types integer and character varying cannot be matched
LINE 3: SELECT full_name, email
               ^
Совет для больших баз: Используй UNION ALL по умолчанию везде, где дублей заведомо быть не может (например, склеиваешь архив заказов за 2024 год и свежие заказы за 2025-й). Обычный UNION вынуждает PostgreSQL выполнять лишнюю сортировку или хеширование ради поиска повторов — на миллионах строк это ощутимо тормозит запрос.

04 Условная логика (CASE WHEN): «если… то…» внутри SQL

Проблема: Магазин хочет повесить на сайте цветные бейджи ценовых категорий: всё дешевле 5 000 ₸ — «Бюджетный», от 5 000 до 15 000 ₸ — «Средний», а дороже 15 000 ₸ — «Премиум». Заводить ради этого отдельную колонку в таблице не нужно — достаточно вычислять ярлык на лету.

Представь сортировщика на складе доставки. По конвейеру едут посылки, а он смотрит на вес каждой коробки и клеит наклейку: лёгкая — на верхнюю полку, средняя — на среднюю, тяжёлая — вниз. В SQL роль такого сортировщика играет условное выражение CASE WHEN ... THEN ... ELSE ... END.

PostgreSQL проверяет ветки WHEN строго сверху вниз и останавливается на самом первом условии, которое оказалось истинным. Если ни одно условие не подошло — срабатывает запасная ветка ELSE.

Пример 3. Размечаем каталог по ценовым сегментам

SQL · Пример 3: Классификация товаров через CASE WHEN 
-- Вычисляем ценовую категорию на лету без изменения таблицы products
SELECT
    title,
    price,
    CASE
        WHEN price < 5000  THEN 'Бюджетный'
        WHEN price <= 15000 THEN 'Средний'
        ELSE 'Премиум'
    END AS price_tier
FROM products
ORDER BY price;
Ответ PostgreSQL
          title          |  price   | price_tier
-------------------------+----------+------------
 Брелок «Слон Postgres»  |   900.00 | Бюджетный
 Стикерпак «Postgres»    |  1200.00 | Бюджетный
 Термокружка кодера      |  6900.00 | Средний
 Футболка «JOIN Me»      |  8500.00 | Средний
 Худи «SQL Master»       | 14500.00 | Средний
 Механическая клавиатура | 32000.00 | Премиум
(6 rows)
Две частые оплошности в CASE WHEN: 1) Если забыть ветку ELSE, для всех неподошедших строк вернётся NULL.
2) Следи за порядком условий! Если первым написать WHEN price > 1000, а вторым WHEN price > 15000, то клавиатура за 32 000 остановится на первой же ветке и никогда не станет «Премиумом».

05 Агрегация (GROUP BY и HAVING): сворачиваем строки в итоги

Проблема: Директор магазина спрашивает: «Сколько товаров и какая средняя цена в каждой категории? Но не показывай мне категории, где всего один товар — для анализа там мало данных».

Представь, что ты высыпал на стол полную копилку монет и хочешь подсчитать итоги по номиналам:

  1. Сначала убираешь в сторону иностранные и гнутые монеты — это WHERE (отсеивает сырые строки до группировки).
  2. Раскладываешь оставшиеся монеты по стопкам: 10, 50, 100 тенге — это группировка (GROUP BY).
  3. Считаешь количество монет и сумму в каждой стопке — это агрегатные функции (COUNT, SUM, AVG, MIN, MAX).
  4. Оставляешь на столе только те стопки, где набралось больше 5 монет — это HAVING (фильтрует уже готовые группы).

Хотя в коде мы пишем SELECT в самом начале, внутри PostgreSQL запрос выполняется совсем в другом порядке — по чёткому конвейеру:

Пример 4. Статистика по категориям с фильтром HAVING

SQL · Пример 4: GROUP BY + HAVING по категориям товаров 
-- Сворачиваем каталог по категориям и отсеиваем одиночные категории
SELECT
    category,
    COUNT(*)             AS products_cnt,
    ROUND(AVG(price), 2) AS avg_price,
    MAX(price)           AS max_price
FROM products
GROUP BY category
HAVING COUNT(*) >= 2
ORDER BY avg_price DESC;
Ответ PostgreSQL
  category  | products_cnt | avg_price | max_price
------------+--------------+-----------+-----------
 Одежда     |            2 |  11500.00 |  14500.00
 Аксессуары |            3 |   3000.00 |   6900.00
(2 rows)

Категория Гаджеты (где лежит одна клавиатура) аккуратно отфильтровалась блоком HAVING COUNT(*) >= 2. Проблема директора решена за один короткий запрос!

Две знаменитые ошибки PostgreSQL при агрегации

Если ты попробуешь вывести в SELECT колонку title, не добавив её в GROUP BY, PostgreSQL не поймёт, какое именно название товара показать для целой стопки из трёх аксессуаров, и выдаст ошибку:

Ошибка PostgreSQL · Колонка забыта в GROUP BY
ERROR:  column "products.title" must appear in the GROUP BY clause or be used in an aggregate function
LINE 1: SELECT category, title, COUNT(*)
                         ^

А если попытаться поставить проверку COUNT(*) >= 2 в WHERE вместо HAVING, база напомнит о порядке выполнения конвейера с Рис. 2 — на шаге WHERE никаких групп ещё не существует:

Ошибка PostgreSQL · Агрегатная функция внутри WHERE
ERROR:  aggregate functions are not allowed in WHERE
LINE 3: WHERE COUNT(*) >= 2;
              ^

Ловушка №2: COUNT(*) против COUNT(колонка) после LEFT JOIN

Что будет, если совместить LEFT JOIN и GROUP BY, чтобы посчитать количество заказов у каждого клиента? Тут кроется коварный баг с COUNT(*)!

✗ Как НЕ надо
SELECT
  c.full_name,
  COUNT(*) AS orders_cnt
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.id
GROUP BY c.id, c.full_name;

COUNT(*) считает количество строк. У Глеба после LEFT JOIN есть одна строка с NULL, поэтому запрос соврёт и покажет Глебу 1 заказ!

✓ Как правильно
SELECT
  c.full_name,
  COUNT(o.id) AS orders_cnt
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.id
GROUP BY c.id, c.full_name;

COUNT(o.id) игнорирует NULL и считает только реальные номера заказов. У Глеба o.id пустой, поэтому результат будет честный 0.

Пример 5. Выручка по городам: проверяем на живых данных

Давай закрепим связку LEFT JOIN + GROUP BY + COALESCE (функция COALESCE(a, b) подставляет b, если a оказалось NULL). Посчитаем для каждого города число клиентов и их оплаченную выручку:

SQL · Пример 5: Аналитика выручки по городам 
-- Считаем клиентов и оплаченную выручку по каждому городу (включая Шымкент с 0)
SELECT
    c.city,
    COUNT(DISTINCT c.id) AS customers_cnt,
    COUNT(DISTINCT o.id) AS paid_orders_cnt,
    COALESCE(SUM(oi.quantity * p.price), 0.00) AS total_revenue
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
   AND o.status = 'paid'
LEFT JOIN order_items AS oi
    ON oi.order_id = o.id
LEFT JOIN products AS p
    ON p.id = oi.product_id
GROUP BY c.city

06 Комбо-удар: клиентский отчёт лояльности на 4 таблицах

Реальная боевая задача: Руководитель отдела продаж просит единую сводку по каждому клиенту магазина: сколько у него оплаченных заказов, сколько отменённых, на какую сумму он реально выкупил товаров и к какому сегменту лояльности относится (VIP от 30 000 ₸, Активный при любых покупках, Спящий при 0 ₸).

Запрос затронет сразу 4 таблицы (customers, orders, order_items, products) и объединит все инструменты сегодняшнего урока — включая условную агрегацию (когда CASE WHEN кладётся прямо внутрь COUNT или SUM!). Прежде чем писать код, посмотрим на трансформацию данных «Было → Стало»:

Этап Что происходит с данными
Было (4 таблицы) Разрозненные строки: 5 клиентов, 6 заказов (часть paid, часть cancelled), 9 товарных позиций и 6 цен в каталоге. У Глеба вообще нет строк в orders.
Склейка (LEFT JOIN) Прикрепляем к клиентам все их заказы, позиции и цены. Благодаря LEFT JOIN ни один клиент не теряется.
Свёртка (GROUP BY + CASE) Схлопываем все строки в 1 строку на клиента. Внутри COUNT(DISTINCT CASE ...) раздельно считаем оплаченные и отменённые заказы, а в SUM(CASE ...) суммируем только оплаченные чеки.
Стало (Отчёт) Аккуратная таблица из 5 строк с готовым статусом VIP / Активный / Спящий для CRM-системы.

Пример 6. Единый отчёт лояльности клиентов

SQL · Пример 6: LEFT JOIN + условная агрегация (CASE внутри SUM/COUNT) 
-- Полный профиль лояльности по каждому клиенту магазина
SELECT
    c.full_name,
    -- Считаем уникальные оплаченные заказы (DISTINCT защищает от размножения строк товарами)
    COUNT(DISTINCT CASE WHEN o.status = 'paid' THEN o.id END)      AS paid_orders,
    -- Считаем уникальные отменённые заказы
    COUNT(DISTINCT CASE WHEN o.status = 'cancelled' THEN o.id END) AS cancelled_orders,
    -- Суммируем выручку только по оплаченным заказам; вместо NULL выводим 0.00
    COALESCE(
        SUM(CASE WHEN o.status = 'paid' THEN oi.quantity * p.price ELSE 0.00 END),
        0.00
    ) AS total_spent,
    -- Присваиваем сегмент лояльности по итоговой сумме покупок
    CASE
        WHEN COALESCE(
            SUM(CASE WHEN o.status = 'paid' THEN oi.quantity * p.price ELSE 0.00 END),
            0.00
        ) >= 30000 THEN 'VIP'
        WHEN COALESCE(
            SUM(CASE WHEN o.status = 'paid' THEN oi.quantity * p.price ELSE 0.00 END),
            0.00
        ) > 0 THEN 'Активный'
        ELSE 'Спящий'
    END AS segment
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
LEFT JOIN order_items AS oi
    ON oi.order_id = o.id
LEFT JOIN products AS p
    ON p.id = oi.product_id
GROUP BY c.id, c.full_name
ORDER BY total_spent DESC, c.id;
Ответ PostgreSQL
   full_name    | paid_orders | cancelled_orders | total_spent | segment
----------------+-------------+------------------+-------------+----------
 Алиса Смирнова |           2 |                0 |    48900.00 | VIP
 Дина Ким       |           1 |                0 |    22300.00 | Активный
 Борис Волков   |           1 |                1 |     8100.00 | Активный
 Вера Ли        |           0 |                1 |        0.00 | Спящий
 Глеб Орлов     |           0 |                0 |        0.00 | Спящий
(5 rows)

Смотри, как красиво решилась задача руководителя: Алиса — наш главный VIP-клиент (48 900 ₸), у Бориса и Веры сразу видны отменённые заказы (можно выяснить причину отказа), а Глеб не потерялся и попал в сегмент «Спящий» с честными нулями.

Фишка PostgreSQL — клауза FILTER: В PostgreSQL условную агрегацию можно записывать ещё изящнее, без громоздкого CASE внутри скобок: COUNT(DISTINCT o.id) FILTER (WHERE o.status = 'paid'). Это официальный стандарт SQL, который отлично читается и работает так же быстро.

07 Шпаргалка урока перед практикой

Пробегись глазами по этому чек-листу — он спасёт тебя от 90% ошибок в задачах ниже и на реальных проектах:

Инструмент Что делает простыми словами Главное правило безопасности
LEFT JOIN Сохраняет все строки левой таблицы, подставляя NULL там, где справа нет пары. Фильтр для правой таблицы пиши в ON, а не в WHERE; для подсчёта используй COUNT(right.id).
UNION / UNION ALL Склеивает результаты двух SELECT вертикально (UNION убирает дубли, UNION ALL — нет). Число колонок и их типы данных в обоих запросах должны совпадать один-в-один.
CASE WHEN Размечает строки по условиям «если… то…» прямо внутри запроса. Условия проверяются сверху вниз до первого совпадения; всегда добавляй ELSE.
GROUP BY Сворачивает одинаковые значения в группы для расчёта COUNT, SUM, AVG, MIN, MAX. Любая колонка в SELECT должна либо быть в GROUP BY, либо лежать внутри агрегатной функции.
HAVING Отсеивает уже готовые группы по результатам агрегатных функций. WHERE режет строки до группировки, а HAVING — группы после неё.

Задание 1 (Базовый уровень). Находим товары-«невидимки»

Найди в таблице products товары, которые ещё ни разу не попадали ни в один заказ (даже отменённый). Выведи колонки id, title и price, отсортировав по id. Ожидаемый результат: 1 строка — брелок за 900.00.

Показать решение
SQL · Эталонное решение задания 1 
-- Анти-джойн: ищем товары без единого совпадения в order_items
SELECT
    p.id,
    p.title,
    p.price
FROM products AS p
LEFT JOIN order_items AS oi
    ON oi.product_id = p.id
WHERE oi.product_id IS NULL
ORDER BY p.id;
Задание 2 (Уверенный уровень). Сверка баз контактов с меткой источника

Собери общий список записей из таблиц customers и newsletter_leads без удаления дублей, чтобы увидеть, кто числится сразу в обеих базах. Выведи три колонки: full_name, email и текстовую метку source ('Покупатель' для таблицы клиентов и 'Подписчик' для лендинга). Отсортируй по email, затем по source. Ожидаемый результат: 9 строк.

Показать решение
SQL · Эталонное решение задания 2 
-- UNION ALL сохраняет все строки, а константа source показывает, откуда пришла запись
SELECT

    email,
    'Покупатель' AS source

Задание 3 (Продвинутый уровень). Города-лидеры по выручке

Посчитай для каждого города (customers.city) количество уникальных клиентов и общую сумму их оплаченных (status = 'paid') заказов. Оставь в результате только те города, где суммарная выручка строго больше 20000, и отсортируй по убыванию выручки. Ожидаемый результат: 2 строки (Алматы и Астана).

Показать решение
SQL · Эталонное решение задания 3 
-- Фильтруем оплаченные заказы в ON, группируем по городу и режем слабые города в HAVING
SELECT
    c.city,
    COUNT(DISTINCT c.id) AS customers_cnt,
    COALESCE(SUM(oi.quantity * p.price), 0.00) AS city_revenue
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
   AND o.status = 'paid'
LEFT JOIN order_items AS oi
    ON oi.order_id = o.id
LEFT JOIN products AS p
    ON p.id = oi.product_id
GROUP BY c.city
HAVING COALESCE(SUM(oi.quantity * p.price), 0.00) > 20000
ORDER BY city_revenue DESC;
Задание 4 (Со звёздочкой). Отчёт спроса по всему каталогу

Выведи список всех 6 товаров из products с колонками: название (title), количество проданных штук в оплаченных заказах (sold_qty, если продаж не было — 0) и метку спроса (demand_label) через CASE WHEN: 'Хит продаж' (если продано >= 3 шт.), 'Есть спрос' (если 1 или 2 шт.) и 'Нет продаж' (если 0 шт.). Отсортируй по sold_qty по убыванию, затем по title. Подсказка: аккуратно обработай отменённые заказы, чтобы они не попали в сумму!

Показать решение
SQL · Эталонное решение задания 4 
-- Используем условную сумму, чтобы отменённые заказы (cancelled) давали 0, а не теряли товар
SELECT
    p.title,
    SUM(CASE WHEN o.status = 'paid' THEN oi.quantity ELSE 0 END) AS sold_qty,
    CASE
        WHEN SUM(CASE WHEN o.status = 'paid' THEN oi.quantity ELSE 0 END) >= 3
            THEN 'Хит продаж'
        WHEN SUM(CASE WHEN o.status = 'paid' THEN oi.quantity ELSE 0 END) >= 1
            THEN 'Есть спрос'
        ELSE 'Нет продаж'
    END AS demand_label
FROM products AS p
LEFT JOIN order_items AS oi
    ON oi.product_id = p.id
LEFT JOIN orders AS o
    ON o.id = oi.order_id
GROUP BY p.id, p.title
ORDER BY sold_qty DESC, p.title;
