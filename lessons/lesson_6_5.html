Модуль 6 · Архитектура DWH, OLAP-движки и итоговый проект Урок 6.5 · Итоговый проект PostgreSQL 16 + ClickHouse · Docker Compose

Итоговый проект: сквозной контур OLTP (PostgreSQL) → ELT → аналитическая витрина в OLAP

Главное в этом итоговом проекте
  • Соединишь все кирпичики Модуля 6 в единую боевую систему: живой магазин PostgreSQL (OLTP) → идемпотентный ELT с SCD Type 2 → колончатая витрина в ClickHouse (OLAP).
  • Настроишь прямой мост между контейнерами pg_primary и clickhouse по внутренней Docker-сети db_net с помощью табличной функции postgresql().
  • Реализуешь атомарную идемпотентную загрузку партиций в ClickHouse через ALTER TABLE ... REPLACE PARTITION — без дубликатов даже при повторных запусках.
  • Проведёшь автоматическую сверку качества данных (Data Quality Reconciliation) между PostgreSQL и ClickHouse и построишь итоговый дашборд директора.

01 Архитектура проекта: как мы соберём «фабрику данных»

Представь современную кондитерскую фабрику. В приёмном цехе (это наша OLTP-база PostgreSQL) непрерывно регистрируют заказы покупателей и правят карточки клиентов. В цехе подготовки (наш слой ELT / DWH) отбраковывают отменённые заказы, фиксируют историю переездов клиентов через SCD Type 2 и раскладывают всё по схеме «Звезда». А затем готовые коробки по конвейеру уезжают в скоростной выставочный зал (колончатый ClickHouse), где директора и аналитики за доли секунды строят любые графики!

В нашем docker-compose.yaml контейнеры course_pg_primary (сетевое имя pg_primary) и course_clickhouse уже подключены к одной внутренней сети db_net. Это значит, что ClickHouse может забирать данные из PostgreSQL напрямую по сети — без промежуточных CSV-файлов и ручной пересылки!

Этап конвейера Где живёт За что отвечает
1. Источник OLTP PostgreSQL · proj_oltp Принимает заказы, статусы и обновления клиентов (январь и февраль 2026)
2. Слой DWH / ELT PostgreSQL · proj_dwh Ведёт историю SCD Type 2, фильтрует 'paid', готовит плоскую витрину export_sales_mart
3. Слой OLAP ClickHouse · analytics_db Забирает данные по сети, атомарно обновляет месячные партиции (REPLACE PARTITION) и считает отчёты
4. Контроль качества (DQ) ClickHouse ↔ PostgreSQL Сверяет число строк и сумму выручки между источником и витриной до копейки

Сначала убедись, что оба контейнера (pg_primary и clickhouse) запущены. Для удобства открой два окна терминала: в первом будешь работать с PostgreSQL, во втором — с ClickHouse.

Bash · Запуск обоих контейнеров и подключение 
# Запускаем PostgreSQL и ClickHouse одной командой
docker compose --profile mod6 up -d

# Окно 1: вход в PostgreSQL (база learning_db)
docker exec -it course_pg_primary psql -U student -d learning_db

# Окно 2: вход в ClickHouse (база analytics_db)
docker exec -it course_clickhouse clickhouse-client \
  -u student --password student_pass -d analytics_db

Пример 2. Слой ELT / DWH: создаём SCD Type 2, таблицу фактов и витрину экспорта

Теперь создадим в том же PostgreSQL аналитический слой proj_dwh. Чтобы не копировать длинный код обновления каждый месяц, завернём всю нашу идемпотентную ELT-логику в аккуратную процедуру proj_dwh.run_elt(p_load_date DATE)! Она за один вызов делает 4 шага:

  1. Обновляет справочник товаров dim_product через ON CONFLICT DO UPDATE.
  2. Ведёт полную историю клиентов в dim_customer_scd2 (закрывает изменившиеся версии и открывает новые).
  3. Идемпотентно загружает оплаченные позиции в fact_sales через Point-in-Time JOIN (order_date BETWEEN valid_from AND valid_to).
  4. Атомарно пересобирает плоскую экспортную таблицу export_sales_mart, из которой ClickHouse заберёт готовые строки по сети.
SQL (PostgreSQL) · Создание схемы proj_dwh и процедуры run_elt() 
DROP SCHEMA IF EXISTS proj_dwh CASCADE;
CREATE SCHEMA proj_dwh;

-- Измерение 1: Товары (SCD Type 1)
CREATE TABLE proj_dwh.dim_product (
    product_sk    SERIAL PRIMARY KEY,
    product_bk    INT NOT NULL UNIQUE,
    product_title TEXT NOT NULL,
    category_name TEXT NOT NULL
);

-- Измерение 2: Клиенты с полной историей (SCD Type 2)
CREATE TABLE proj_dwh.dim_customer_scd2 (
    customer_sk SERIAL PRIMARY KEY,
    customer_bk INT NOT NULL,
    full_name   TEXT NOT NULL,
    city_name   TEXT NOT NULL,
    segment     TEXT NOT NULL,
    valid_from  DATE NOT NULL,
    valid_to    DATE NOT NULL DEFAULT DATE '9999-12-31',
    is_current  BOOLEAN NOT NULL DEFAULT true
);

CREATE UNIQUE INDEX idx_proj_cust_scd2_active
    ON proj_dwh.dim_customer_scd2 (customer_bk)
    WHERE is_current = true;

-- Таблица фактов: зерно = 1 позиция в оплаченном заказе
CREATE TABLE proj_dwh.fact_sales (
    item_bk         INT PRIMARY KEY,
    order_bk        INT NOT NULL,
    order_date      DATE NOT NULL,
    product_sk      INT NOT NULL REFERENCES proj_dwh.dim_product(product_sk),
    customer_sk     INT NOT NULL REFERENCES proj_dwh.dim_customer_scd2(customer_sk),
    qty             INT NOT NULL,
    total_amount    NUMERIC(12, 2) NOT NULL
);

-- Плоская витрина-шлюз, которую читает ClickHouse по сети db_net
CREATE TABLE proj_dwh.export_sales_mart (
    item_bk       INT PRIMARY KEY,
    order_bk      INT NOT NULL,
    order_date    DATE NOT NULL,
    customer_bk   INT NOT NULL,
    city_name     TEXT NOT NULL,
    segment       TEXT NOT NULL,
    product_title TEXT NOT NULL,
    category_name TEXT NOT NULL,
    qty           INT NOT NULL,
    total_amount  NUMERIC(12, 2) NOT NULL
);

-- Идемпотентная процедура ELT: можно запускать сколько угодно раз!
CREATE OR REPLACE PROCEDURE proj_dwh.run_elt(p_load_date DATE)
LANGUAGE plpgsql AS $$
BEGIN
    -- 1. Обновляем dim_product (UPSERT)
    INSERT INTO proj_dwh.dim_product (product_bk, product_title, category_name)
    SELECT product_id, title, category_name
    FROM proj_oltp.products
    ON CONFLICT (product_bk) DO UPDATE
    SET product_title = EXCLUDED.product_title,
        category_name = EXCLUDED.category_name
    WHERE proj_dwh.dim_product.product_title IS DISTINCT FROM EXCLUDED.product_title
       OR proj_dwh.dim_product.category_name IS DISTINCT FROM EXCLUDED.category_name;

    -- 2А. SCD Type 2: закрываем устаревшие версии изменившихся клиентов
    UPDATE proj_dwh.dim_customer_scd2 d
    SET valid_to   = p_load_date - INTERVAL '1 day',
        is_current = false
    FROM proj_oltp.customers s
    WHERE d.customer_bk = s.customer_id
      AND d.is_current = true
      AND (
          d.full_name IS DISTINCT FROM s.full_name
          OR d.city_name IS DISTINCT FROM s.city_name
          OR d.segment   IS DISTINCT FROM s.segment
      );

    -- 2Б. SCD Type 2: открываем новые версии (для новых и изменившихся клиентов)
    INSERT INTO proj_dwh.dim_customer_scd2
        (customer_bk, full_name, city_name, segment, valid_from, valid_to, is_current)
    SELECT s.customer_id, s.full_name, s.city_name, s.segment,
           p_load_date, DATE '9999-12-31', true
    FROM proj_oltp.customers s
    LEFT JOIN proj_dwh.dim_customer_scd2 d
           ON d.customer_bk = s.customer_id AND d.is_current = true
    WHERE d.customer_bk IS NULL;

    -- 3. Загружаем оплаченные факты через Point-in-Time JOIN (UPSERT)
    INSERT INTO proj_dwh.fact_sales
        (item_bk, order_bk, order_date, product_sk, customer_sk, qty, total_amount)
    SELECT
        oi.item_id,
        o.order_id,
        o.order_date,
        dp.product_sk,
        dc.customer_sk,
        oi.qty,
        (oi.qty * oi.unit_price - oi.discount)
    FROM proj_oltp.order_items oi
    JOIN proj_oltp.orders o ON o.order_id = oi.order_id
    JOIN proj_dwh.dim_product dp ON dp.product_bk = oi.product_id
    JOIN proj_dwh.dim_customer_scd2 dc
      ON dc.customer_bk = o.customer_id
     AND o.order_date BETWEEN dc.valid_from AND dc.valid_to
    WHERE o.status = 'paid'
    ON CONFLICT (item_bk) DO UPDATE
    SET qty          = EXCLUDED.qty,
        total_amount = EXCLUDED.total_amount;

    -- 4. Обновляем плоскую витрину для передачи в ClickHouse
    TRUNCATE TABLE proj_dwh.export_sales_mart;
    INSERT INTO proj_dwh.export_sales_mart
    SELECT
        f.item_bk, f.order_bk, f.order_date,
        dc.customer_bk, dc.city_name, dc.segment,
        dp.product_title, dp.category_name,
        f.qty, f.total_amount
    FROM proj_dwh.fact_sales f
    JOIN proj_dwh.dim_customer_scd2 dc ON dc.customer_sk = f.customer_sk
    JOIN proj_dwh.dim_product       dp ON dp.product_sk  = f.product_sk;
END;
$$;

-- Запускаем ELT за Январь 2026!
CALL proj_dwh.run_elt(DATE '2026-01-01');

SELECT order_date, city_name, segment, category_name, qty, total_amount
FROM proj_dwh.export_sales_mart
ORDER BY item_bk;

03 Шаг 3 (ClickHouse): мост по сети Docker и атомарная загрузка партиций

Представь, что два соседа живут в разных квартирах одного дома (наши контейнеры pg_primary и clickhouse в сети db_net). Если сосед из ClickHouse позвонит по домашнему телефону на номер «моя собственная квартира» (localhost:5432), то PostgreSQL трубку не возьмёт — потому что внутри контейнера ClickHouse на порту 5432 никого нет!

Пример 4. Самая частая ошибка Docker-новичка при подключении ClickHouse → PostgreSQL

Переключись в Окно 2 (ClickHouse, база analytics_db) и посмотри, что случится, если по привычке указать localhost:5432:

SQL (ClickHouse) · Попытка достучаться до localhost:5432 
SELECT count()
FROM postgresql(
    'localhost:5432', 'learning_db', 'export_sales_mart',
    'student', 'student_pass', 'proj_dwh'
);
Ошибка ClickHouse
Received exception from server:
Code: 1001. DB::Exception: pqxx::broken_connection: could not connect to server: Connection refused
	Is the server running on host "localhost" (127.0.0.1) and accepting TCP/IP connections on port 5432?

Запомни это золотое правило Docker Compose: внутри контейнера localhost — это сам контейнер! Чтобы ClickHouse достучался до PostgreSQL по сети db_net, нужно указать имя сервиса из docker-compose.yaml — pg_primary:5432.

Пример 5. Идемпотентная загрузка в ClickHouse через REPLACE PARTITION

Но как загрузить данные из PostgreSQL в ClickHouse так, чтобы повторный запуск скрипта не задвоил строки? Вспомни Урок 6.3: в ClickHouse нет классического ON CONFLICT DO UPDATE как в PostgreSQL! Вместо этого инженеры данных используют потрясающий приём — атомарную подмену партиции (REPLACE PARTITION):

Давай создадим боевую колончатую витрину mart_sales (с партиционированием по месяцам, LowCardinality и кодеком ZSTD), буферную таблицу mart_sales_stage и зальём январь и февраль напрямую из PostgreSQL:

SQL (ClickHouse) · Прямая загрузка из PostgreSQL + REPLACE PARTITION 
DROP TABLE IF EXISTS mart_sales;
DROP TABLE IF EXISTS mart_sales_stage;

-- 1. Боевая колончатая витрина в ClickHouse (оптимизирована под BI)
CREATE TABLE mart_sales (
    item_bk       UInt32 CODEC(Delta, ZSTD(3)),
    order_bk      UInt32 CODEC(Delta, ZSTD(3)),
    order_date    Date   CODEC(DoubleDelta, ZSTD(3)),
    customer_bk   UInt32,
    city_name     LowCardinality(String),
    segment       LowCardinality(String),
    product_title LowCardinality(String),
    category_name LowCardinality(String),
    qty           UInt16,
    total_amount  Decimal(12, 2)
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(order_date)
ORDER BY (city_name, category_name, order_date);

-- 2. Буферная таблица с точно такой же структурой
CREATE TABLE mart_sales_stage AS mart_sales;

-- 3. Забираем свежие данные напрямую из PostgreSQL по сети db_net!
TRUNCATE TABLE mart_sales_stage;

INSERT INTO mart_sales_stage
SELECT
    item_bk, order_bk, order_date, customer_bk,
    city_name, segment, product_title, category_name,
    qty, total_amount
FROM postgresql(
    'pg_primary:5432', 'learning_db', 'export_sales_mart',
    'student', 'student_pass', 'proj_dwh'
);

-- 4. Атомарно и идемпотентно подменяем партиции за январь и февраль!
-- Попробуй запустить эти 2 команды хоть 5 раз подряд — дубликатов не будет!
ALTER TABLE mart_sales REPLACE PARTITION 202601 FROM mart_sales_stage;
ALTER TABLE mart_sales REPLACE PARTITION 202602 FROM mart_sales_stage;

-- 5. Проверяем содержимое витрины в ClickHouse
SELECT
    toYYYYMM(order_date) AS part_month,
    city_name,
    segment,
    sum(qty)             AS items_sold,
    sum(total_amount)    AS revenue
FROM mart_sales
GROUP BY part_month, city_name, segment
ORDER BY part_month, revenue DESC;
Ответ ClickHouse (сквозной контур сработал!)
┌─part_month─┬─city_name─┬─segment──┬─items_sold─┬──revenue─┐
│     202601 │ Костанай  │ Standard │          3 │ 49000.00 │
│     202601 │ Алматы    │ VIP      │          2 │ 40000.00 │
│     202602 │ Астана    │ Standard │          2 │ 43000.00 │
│     202602 │ Алматы    │ VIP      │          1 │ 20000.00 │
└────────────┴───────────┴──────────┴────────────┴──────────┘

✗ Как НЕ надо
-- Прямой INSERT без очистки!
INSERT INTO mart_sales
SELECT * FROM postgresql(...);
-- Повторный запуск = дубли ×2!

Движок MergeTree не проверяет уникальность при INSERT. Повторный запуск тихо удвоит всю выручку!

✓ Как правильно
-- Заливка в stage + подмена!
ALTER TABLE mart_sales
  REPLACE PARTITION 202602
  FROM mart_sales_stage;

Старая февральская папка мгновенно меняется на новую без паузы для пользователей и без единого дубля.

04 Шаг 4: Автоматическая сверка (Data Quality) и дашборд директора

Представь, что на кондитерской фабрике со склада отгрузили ровно 100 коробок конфет, а в магазин приехало только 98. Хороший начальник смены никогда не открывает магазин, пока не сверит накладные на входе и выходе!

В инженерии данных такая проверка называется Data Quality Reconciliation (сверка качества данных). Настоящий инженер никогда не говорит «вроде загрузилось» — он запускает автоматический SQL-тест, который сравнивает источник (PostgreSQL) и витрину (ClickHouse) и выносит чёткий вердикт OK или MISMATCH.

Пример 6. Единый DQ-запрос «PostgreSQL vs ClickHouse» и итоговый BI-отчёт

Выполни этот блок в Окне 2 (ClickHouse) — он прямо на лету сравнит обе базы данных между собой, а затем покажет директору красивую аналитическую сводку по категориям с долей каждой категории в процентах:

SQL (ClickHouse) · Автоматическая сверка DQ и итоговый BI-отчёт 
-- 1. Автоматический тест качества данных (Reconciliation: PG DWH vs ClickHouse OLAP)
WITH
    pg_stats AS (
        SELECT
            count()           AS pg_rows,
            sum(total_amount) AS pg_revenue
        FROM postgresql(
            'pg_primary:5432', 'learning_db', 'export_sales_mart',
            'student', 'student_pass', 'proj_dwh'
        )
    ),
    ch_stats AS (
        SELECT
            count()           AS ch_rows,
            sum(total_amount) AS ch_revenue
        FROM mart_sales
    )
SELECT
    pg_rows,
    ch_rows,
    pg_revenue,
    ch_revenue,
    if(pg_rows = ch_rows AND pg_revenue = ch_revenue, 'OK ✓', 'MISMATCH ✗') AS dq_status
FROM pg_stats, ch_stats;

-- 2. Итоговый дашборд директора по категориям (выручка, заказы, доля в %)
SELECT
    category_name,
    uniqExact(order_bk) AS orders_cnt,
    sum(qty)            AS items_sold,
    sum(total_amount)   AS revenue,
    round(100.0 * sum(total_amount) / sum(sum(total_amount)) OVER (), 1) AS share_pct
FROM mart_sales
GROUP BY category_name
ORDER BY revenue DESC;
Ответ ClickHouse (DQ = OK ✓ и готовый дашборд)

└─────────┴─────────┴────────────┴────────────┴───────────┘

│ Электроника   │          2 │          2 │ 68000.00 │      44.7 │

Посмотри на результат: pg_rows = 6, ch_rows = 6, 152000.00 = 152000.00, статус OK ✓! Мы полностью прошли путь от проблемы первого урока — «как строить быструю и честную аналитику, не тормозя боевой магазин» — до готового, проверенного и самозащищённого конвейера данных.

Важно про масштабирование в реальной компании: В учебном проекте ClickHouse ходит напрямую в pg_primary. В крупном продакшене с высокой нагрузкой аналитические выгрузки направляют не в основной мастер, а в физическую Read-реплику (pg_standby из Модуля 5!) или используют потоковый CDC (Debezium + Kafka), чтобы вообще не касаться боевого мастера.
Как автоматизировать такой контур? В реальной работе команды не запускают эти SQL-команды руками: всю цепочку CALL proj_dwh.run_elt(...) → INSERT INTO stage → REPLACE PARTITION → DQ Check ставят на расписание в оркестратор (например, Apache Airflow или Dagster), а трансформации SQL версионируют в Git с помощью dbt.

05 Шпаргалка архитектора DWH перед финальной практикой

Короткий чек-лист сквозного пайплайна, который пригодится тебе на реальных проектах и технических собеседованиях:

Шаг конвейера Главное инженерное правило
1. Сбор из OLTP Не вешай тяжёлые BI-запросы на боевую кассу; выгружай данные в слой DWH (а в хайлоаде — с Read-реплики).
2. Трансформация ELT Фильтруй отменённые операции, веди историю важных атрибутов через SCD Type 2 и привязывай факты через Point-in-Time JOIN.
3. Сетевой мост в Docker Внутри контейнера обращайся к соседней БД по имени сервиса (pg_primary:5432), а не через localhost.
4. Идемпотентная заливка OLAP В ClickHouse используй связку stage-таблица → ALTER TABLE ... REPLACE PARTITION, чтобы повторный запуск не плодил дубли.
5. Сверка DQ (Reconciliation) После каждой загрузки автоматически сверяй COUNT(*) и SUM(amount) между источником и витриной.

Задание 1 (Базовый · PostgreSQL). Контроль качества (DQ-проверка) входных заказов

Создай в learning_db схему proj_lab и таблицу proj_lab.raw_orders (order_id INT, status TEXT, amount NUMERIC(10, 2)). Вставь 4 заказа: два оплаченных положительных (12000 и 8000), один отменённый (5000) и один битый оплаченный заказ с отрицательной суммой (-300). Напиши один SQL-запрос контроля качества, который посчитает: 1) число корректных оплаченных заказов (valid_paid_cnt), 2) их сумму (valid_revenue), 3) число битых строк (bad_rows_cnt, где amount <= 0) и 4) статус 'FAIL', если битых строк больше 0, иначе 'PASS'.

Показать решение
SQL (PostgreSQL) · Эталонное решение задания 1 
CREATE SCHEMA IF NOT EXISTS proj_lab;
DROP TABLE IF EXISTS proj_lab.raw_orders;

CREATE TABLE proj_lab.raw_orders (
    order_id INT PRIMARY KEY,
    status   TEXT NOT NULL,
    amount   NUMERIC(10, 2) NOT NULL
);

INSERT INTO proj_lab.raw_orders VALUES
    (1, 'paid',      12000.00),
    (2, 'paid',       8000.00),
    (3, 'cancelled',  5000.00),
    (4, 'paid',       -300.00); -- битая строка!

SELECT
    COUNT(*) FILTER (WHERE status = 'paid' AND amount > 0)               AS valid_paid_cnt,
    COALESCE(SUM(amount) FILTER (WHERE status = 'paid' AND amount > 0), 0) AS valid_revenue,
    COUNT(*) FILTER (WHERE amount <= 0)                                  AS bad_rows_cnt,
    CASE WHEN COUNT(*) FILTER (WHERE amount <= 0) > 0
         THEN 'FAIL' ELSE 'PASS' END                                     AS dq_status
FROM proj_lab.raw_orders;
-- Ожидаемый результат: valid_paid_cnt=2, valid_revenue=20000.00, bad_rows_cnt=1, dq_status='FAIL'

Задание 3 (Продвинутый · ClickHouse). Точечная исправляющая перезаливка через REPLACE PARTITION

Создай в analytics_db боевую таблицу lab_kpi_mart (kpi_date Date, city LowCardinality(String), revenue UInt32, PARTITION BY toYYYYMM(kpi_date), ORDER BY (city, kpi_date)) и буфер lab_kpi_stage AS lab_kpi_mart. Вставь в боевую таблицу 2 строки: за январь (2026-01-15, 'Алматы', 50000) и ошибочную за февраль (2026-02-10, 'Алматы', 999999). Затем загрузи в lab_kpi_stage правильный февраль (2026-02-10, 'Алматы', 70000), замени только партицию 202602 командой REPLACE PARTITION и проверь, что январь не пострадал, а февраль исправился.

SQL (ClickHouse) · Эталонное решение задания 3

DROP TABLE IF EXISTS lab_kpi_stage;

CREATE TABLE lab_kpi_mart (
    kpi_date Date,
    city     LowCardinality(String),
    revenue  UInt32
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(kpi_date)
ORDER BY (city, kpi_date);

CREATE TABLE lab_kpi_stage AS lab_kpi_mart;

-- Начальное состояние (в феврале закралась ошибка!)
INSERT INTO lab_kpi_mart VALUES

    ('2026-02-10', 'Алматы', 999999);

Задание 4 (Проектирование · ClickHouse). Автоматическая потоковая витрина (MATERIALIZED VIEW + SummingMergeTree)

В отличие от PostgreSQL, в ClickHouse MATERIALIZED VIEW работает как автоматический триггер на вставку: как только строки прилетают в сырую таблицу, витрина сама на лету суммирует их! Создай в analytics_db три объекта: 1) сырую таблицу lab_raw_clicks (click_date Date, page LowCardinality(String), clicks UInt32); 2) целевую таблицу lab_daily_clicks_agg на движке SummingMergeTree() ORDER BY (click_date, page); 3) материализованное представление mv_daily_clicks TO lab_daily_clicks_agg, перекладывающее суммы. Вставь две отдельные пачки кликов в lab_raw_clicks и проверь, что lab_daily_clicks_agg автоматически собрала общие итоги без ручного REFRESH!

Показать решение
SQL (ClickHouse) · Эталонное решение задания 4 
DROP VIEW IF EXISTS mv_daily_clicks;
DROP TABLE IF EXISTS lab_daily_clicks_agg;
DROP TABLE IF EXISTS lab_raw_clicks;

-- 1. Таблица входящего потока событий
CREATE TABLE lab_raw_clicks (
    click_date Date,
    page       LowCardinality(String),
    clicks     UInt32
) ENGINE = MergeTree()
ORDER BY (click_date, page);

-- 2. Целевая витрина-накопитель (SummingMergeTree сам схлопывает суммы при слияниях)
CREATE TABLE lab_daily_clicks_agg (
    click_date Date,
    page       LowCardinality(String),
    clicks     UInt64
) ENGINE = SummingMergeTree()
ORDER BY (click_date, page);

-- 3. Материализованное представление-триггер: срабатывает АВТОМАТИЧЕСКИ на каждый INSERT!
CREATE MATERIALIZED VIEW mv_daily_clicks
TO lab_daily_clicks_agg AS
SELECT
    click_date,
    page,
    sum(clicks) AS clicks
FROM lab_raw_clicks
GROUP BY click_date, page;

-- Вставляем 2 пачки событий в сырую таблицу (витрину руками не трогаем!)
INSERT INTO lab_raw_clicks VALUES
    ('2026-03-01', '/home',    120),
    ('2026-03-01', '/catalog',  80);

INSERT INTO lab_raw_clicks VALUES
    ('2026-03-01', '/home',     30),
    ('2026-03-01', '/checkout', 45);

-- Читаем готовые агрегаты из витрины (всегда добавляем sum() на случай ещё не слитых пачек)
SELECT click_date, page, sum(clicks) AS total_clicks
FROM lab_daily_clicks_agg
GROUP BY click_date, page
ORDER BY total_clicks DESC;
-- Ожидаемый результат: /home (150), /catalog (80), /checkout (45)
