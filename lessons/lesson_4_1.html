Транзакции, ACID и аномалии параллельного доступа

Главное в этом уроке
  • Поймёшь, как объединять несколько SQL-команд в неделимую операцию через BEGIN, COMMIT, ROLLBACK и чекпоинты SAVEPOINT.
  • Разберёшься в 4 железных правилах надёжных баз данных — ACID — и научишься выходить из «зависшего» состояния ошибки в PostgreSQL.
  • Познакомишься с 4 классическими аномалиями, которые возникают, когда два пользователя меняют данные одновременно: Dirty Read, Non-Repeatable Read, Phantom Read и Lost Update.
  • Воспроизведёшь настоящую гонку двух подключений в двух окнах psql на базе learning_db и увидишь, как её обезвредить.

01 Зачем нужны транзакции? Правило «всё или ничего»

Представь, что вы с другом играете в онлайн-игру и решили обменяться: ты отдаёшь ему 300 золотых монет, а система должна списать их с твоего счёта и зачислить ему. Это два отдельных шага: минус 300 у тебя и плюс 300 у друга.

А теперь представь катастрофу: сервер успел вычесть 300 монет из твоего кошелька, и ровно в следующую миллисекунду пропал свет. Сервер перезагрузился. У тебя на счёте на 300 монет меньше, а у друга ничего не прибавилось — золото просто испарилось в космос!

Чтобы такого никогда не случалось, в базах данных придумали транзакцию (Transaction). Это специальная «обёртка» вокруг группы SQL-команд, которая работает по строгому правилу «всё или ничего»: либо успешно выполняются все команды внутри, либо не выполняется ни одна, и база возвращается в исходное состояние.

Простая аналогия: Транзакция похожа на редактирование школьного реферата в текстовом редакторе. Пока ты вносишь правки (после BEGIN), файл на диске ещё не испорчен. Нажал «Сохранить» (COMMIT) — все изменения закрепились. Нажал «Закрыть без сохранения» (ROLLBACK) — документ остался точно таким, как был до открытия.

Готовим игровую песочницу в learning_db

Для всех экспериментов этого урока создадим в нашей сквозной базе learning_db три компактные таблицы: кошельки игроков (wallets), историю переводов (transfer_log) и лавку предметов (shop_items). Обрати внимание на ограничения CHECK — они запретят балансу и остатку на складе уходить в минус.

SQL · Пример 1: Подготовка данных в learning_db 
-- Безопасно пересоздаём учебные таблицы для Модуля 4
DROP TABLE IF EXISTS transfer_log;
DROP TABLE IF EXISTS wallets;
DROP TABLE IF EXISTS shop_items;

CREATE TABLE wallets (
    id      SERIAL PRIMARY KEY,
    owner   TEXT NOT NULL UNIQUE,
    balance NUMERIC(10, 2) NOT NULL CHECK (balance >= 0)
);

CREATE TABLE transfer_log (
    id          SERIAL PRIMARY KEY,
    from_owner  TEXT NOT NULL,
    to_owner    TEXT NOT NULL,
    amount      NUMERIC(10, 2) NOT NULL CHECK (amount > 0),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE shop_items (
    id    SERIAL PRIMARY KEY,
    title TEXT NOT NULL UNIQUE,
    price NUMERIC(10, 2) NOT NULL CHECK (price > 0),
    stock INT NOT NULL CHECK (stock >= 0)
);

-- Наполняем стартовыми данными
INSERT INTO wallets (owner, balance) VALUES
    ('Алиса', 1000.00),
    ('Боб',    500.00),
    ('Чарли',  200.00);

INSERT INTO shop_items (title, price, stock) VALUES
    ('Алмазный меч', 600.00, 2),
    ('Зелье маны',   150.00, 5),
    ('Щит новичка',  300.00, 1);

-- Проверяем начальное состояние кошельков
SELECT id, owner, balance FROM wallets ORDER BY id;
Ответ PostgreSQL

----+-------+---------
  1 | Алиса | 1000.00
  2 | Боб   |  500.00
  3 | Чарли |  200.00
(3 rows)

02 BEGIN, COMMIT, ROLLBACK и чекпоинты SAVEPOINT

Сюрприз: ты уже пользовался транзакциями с самого первого урока! По умолчанию PostgreSQL работает в режиме автоподтверждения (Autocommit). Это значит, что любая одиночная команда INSERT, UPDATE или DELETE автоматически оборачивается в невидимую мини-транзакцию и сразу сохраняется на диск.

Когда тебе нужно выполнить несколько шагов как одно целое, ты вручную берёшь управление в свои руки с помощью BEGIN. Давай посмотрим, что должно произойти при переводе 300 монет от Алисы к Бобу с записью в журнал:

Таблица / строка Было Стало после COMMIT
wallets · Алиса 1000.00 700.00 (-300.00)
wallets · Боб 500.00 800.00 (+300.00)
transfer_log 0 записей 1 запись (Алиса → Боб, 300.00)
SQL · Пример 2: Успешный перевод внутри транзакции 
BEGIN;

-- Шаг 1: списываем 300 монет у Алисы
UPDATE wallets
SET balance = balance - 300.00
WHERE owner = 'Алиса';

-- Шаг 2: начисляем 300 монет Бобу
UPDATE wallets
SET balance = balance + 300.00
WHERE owner = 'Боб';

-- Шаг 3: фиксируем перевод в истории
INSERT INTO transfer_log (from_owner, to_owner, amount)
VALUES ('Алиса', 'Боб', 300.00);

-- Фиксируем все 3 изменения одновременно!
COMMIT;

-- Проверяем итог
SELECT owner, balance FROM wallets ORDER BY id;
Ответ PostgreSQL
BEGIN
UPDATE 1
UPDATE 1
INSERT 0 1
COMMIT
 owner | balance
-------+---------
 Алиса |  700.00
 Боб   |  800.00
 Чарли |  200.00
(3 rows)

Вернёмся к нашей проблеме со сбоем света: если сервер выключится после шага 1, но до команды COMMIT, PostgreSQL при запуске увидит незавершённую транзакцию и сам полностью отменит списание у Алисы. Деньги больше никогда не пропадут.

✗ Как НЕ надо
-- Без BEGIN (Autocommit!)
UPDATE wallets
SET balance = balance - 300
WHERE owner = 'Алиса';
-- Тут обрыв сети или сбой!
UPDATE wallets
SET balance = balance + 300
WHERE owner = 'Боб';

Первый UPDATE уже сохранился навсегда. Если второй не дойдёт до сервера, 300 монет исчезнут бесследно.

✓ Как правильно
BEGIN;
UPDATE wallets
SET balance = balance - 300
WHERE owner = 'Алиса';
UPDATE wallets
SET balance = balance + 300
WHERE owner = 'Боб';
COMMIT;

При любом обрыве до COMMIT PostgreSQL автоматически откатит первый шаг. Балансы останутся честными.

Что происходит при ошибке внутри транзакции?

Представь строгого судью на экзамене: если ты допустил критическую ошибку на середине билета, он перечёркивает весь лист и не даст писать дальше, пока ты не возьмёшь чистый бланк. В PostgreSQL транзакция работает точно так же!

Давай попробуем перевести от Алисы Чарли 5000 монет (хотя у неё только 700), а затем, как ни в чём не бывало, посмотрим таблицу wallets внутри той же транзакции.

SQL · Пример 3: Ошибка внутри транзакции и режим aborted 
BEGIN;

-- Попытка списать больше, чем есть на счёте (700 - 5000 = -4300)
UPDATE wallets
SET balance = balance - 5000.00
WHERE owner = 'Алиса';
Ошибка PostgreSQL
ERROR:  new row for relation "wallets" violates check constraint "wallets_balance_check"
DETAIL:  Failing row contains (1, Алиса, -4300.00).

А теперь попробуй выполнить любой запрос — даже безобидный SELECT — не закрыв эту сломанную транзакцию:

SQL · Попытка продолжить после ошибки 
SELECT * FROM wallets;
Ошибка PostgreSQL
ERROR:  current transaction is aborted, commands ignored until end of transaction block

Почему так вышло? После первой ошибки PostgreSQL перевёл транзакцию в аварийный режим (aborted) и игнорирует все дальнейшие команды, чтобы ты случайно не сохранил полусломанные данные. Выйти из этого тупика можно только командой ROLLBACK; (кстати, если написать COMMIT; в таком состоянии, PostgreSQL всё равно выполнит ROLLBACK).

SQL · Выходим из аварийного состояния 
ROLLBACK;
Ответ PostgreSQL
ROLLBACK

Точки сохранения (SAVEPOINT): чекпоинты как в видеоигре

А если транзакция длинная и состоит из 10 шагов, и только 9-й шаг оказался рискованным? Обидно сбрасывать всю проделанную работу! В видеоиграх перед сложным боссом ты сохраняешься на чекпоинте: если проиграл, возрождаешься не в самом начале игры, а прямо перед дверью к боссу.

В SQL такой чекпоинт называется точкой сохранения (SAVEPOINT). Если после неё случилась ошибка, команда ROLLBACK TO SAVEPOINT имя вернёт тебя точно к чекпоинту, сняв статус aborted и сохранив всё, что было сделано до него.

SQL · Пример 4: Спасаем награду Чарли с помощью SAVEPOINT 
BEGIN;

-- Шаг 1: Чарли прошёл квест и получил +100 монет (стало 300)
UPDATE wallets
SET balance = balance + 100.00
WHERE owner = 'Чарли';

-- Ставим игровой чекпоинт!
SAVEPOINT after_quest;

-- Шаг 2: Чарли пытается купить меч за 600 монет (не хватает!)
UPDATE wallets
SET balance = balance - 600.00
WHERE owner = 'Чарли';
-- Здесь возникнет ERROR: violates check constraint "wallets_balance_check"

-- Откатываемся НЕ в начало, а к чекпоинту!
ROLLBACK TO SAVEPOINT after_quest;

-- Награда за квест спасена! Подтверждаем транзакцию
COMMIT;

SELECT owner, balance FROM wallets WHERE owner = 'Чарли';
Ответ PostgreSQL
 owner | balance
-------+---------
 Чарли |  300.00
(1 row)
✗ Как НЕ надо: «зависшая» транзакция
BEGIN;
UPDATE wallets SET balance = balance - 100 WHERE owner = 'Алиса';
-- А теперь код приложения пошёл вызывать медленный платёжный API на 15 секунд
-- или вообще ждёт, пока пользователь нажмёт «Подтвердить» на сайте...

Пока транзакция висит в статусе idle in transaction, она держит блокировки строк и мешает уборщику памяти. Если так сделают 100 пользователей — сайт встанет колом.

✓ Как правильно: короткая и быстрая транзакция
-- Сначала сделали все расчёты и запросы к внешним API в коде,
-- и только когда всё готово — открываем транзакцию на доли секунды:
BEGIN;
UPDATE wallets SET balance = balance - 100 WHERE owner = 'Алиса';
UPDATE wallets SET balance = balance + 100 WHERE owner = 'Боб';
COMMIT;

Золотое правило инженеров БД: транзакция должна быть максимально короткой — миллисекунды, а не секунды или минуты.

Частая ошибка в psql: Если ты набрал BEGIN; и забыл сделать COMMIT; или ROLLBACK;, обрати внимание на приглашение командной строки — в psql оно меняется с learning_db=# на learning_db=*# (активная транзакция) или learning_db=!# (сломанная транзакция, ждёт ROLLBACK).

03 Четыре столпа надёжности: что такое ACID

Когда программисты выбирают базу данных для банка, интернет-магазина или крупной игры, первый вопрос звучит так: «Она поддерживает ACID?». За страшноватой аббревиатурой ACID (по-английски звучит как «кислота») скрываются четыре простых обещания, которые надёжная база данных даёт тебе при каждой транзакции.

Буква Термин Аналогия из жизни Что гарантирует PostgreSQL
A Atomicity
(Атомарность)		 Покупка в автомате с едой: либо деньги списались и шоколадка выпала, либо деньги вернулись. Транзакция выполняется неделимо: всё или ничего. Частично выполненный перевод невозможен.
C Consistency
(Согласованность)		 Закон сохранения энергии: сколько монет ушло из одного кармана, ровно столько появилось в другом. После COMMIT соблюдены все правила базы (CHECK, UNIQUE, FOREIGN KEY, NOT NULL) и логика данных.
I Isolation
(Изолированность)		 Кабинки для переодевания: пока ты примеряешь вещи, другие не видят твоих промежуточных попыток. Параллельные транзакции не мешают друг другу и не видят незавершённых («сырых») правок соседей.
D Durability
(Долговечность)		 Запись ручкой в прошитой книге учёта, а не мелом на доске. Если база ответила COMMIT, данные записаны на диск и переживут отключение питания.

Проверяем Atomicity и Consistency на покупке в магазине

Представь, что Боб (у него сейчас 800 монет) хочет купить сразу 2 «Щита новичка» по 300 монет. Денег у него хватает (800 >= 600), поэтому первый шаг — списание денег — пройдёт идеально! Но на складе остался всего 1 щит. Посмотрим, спасёт ли транзакция деньги Боба.

SQL · Пример 5: Сбой на втором шаге покупки 
BEGIN;

-- Шаг 1: списываем 600 монет у Боба (800 - 600 = 200, всё ок!)
UPDATE wallets
SET balance = balance - 600.00
WHERE owner = 'Боб';

-- Шаг 2: пытаемся забрать 2 щита со склада (1 - 2 = -1 -> нарушение CHECK!)
UPDATE shop_items
SET stock = stock - 2
WHERE title = 'Щит новичка';
Ошибка PostgreSQL
ERROR:  new row for relation "shop_items" violates check constraint "shop_items_stock_check"
DETAIL:  Failing row contains (3, Щит новичка, 300.00, -1).

Теперь делаем ROLLBACK; и проверяем, что ни деньги Боба, ни остаток щитов не пострадали:

SQL · Откат и проверка целостности 
ROLLBACK;

SELECT owner, balance FROM wallets WHERE owner = 'Боб';
SELECT title, stock FROM shop_items WHERE title = 'Щит новичка';
Ответ PostgreSQL
ROLLBACK
 owner | balance
-------+---------
 Боб   |  800.00
(1 row)

    title    | stock
-------------+-------
 Щит новичка |     1
(1 row)

Сработали сразу два принципа ACID: Consistency поймал попытку продать несуществующий щит (stock >= 0), а Atomicity целиком отменил списание 600 монет у Боба.

Как работает Durability под капотом? PostgreSQL использует механизм WAL (Write-Ahead Logging) — журнал упреждающей записи. Прежде чем ответить тебе COMMIT, сервер гарантированно дописывает строчку с изменениями в этот файл на диске. Даже если через долю секунды выдернуть шнур питания, при следующем старте Postgres прочитает WAL и восстановит все подтверждённые транзакции.

04 Когда пользователей много: 4 аномалии параллельного доступа

Пока ты работаешь с базой в одиночку, всё идеально. Но реальный сайт или игра — это шумный супермаркет в Чёрную пятницу: сотни людей одновременно читают цены, кладут товары в корзину и оплачивают заказы.

Если две транзакции работают с одними и теми же строками одновременно, возникают странные баги — аномалии параллельного доступа (Concurrency Anomalies). Давай разберём 4 главные аномалии на понятных примерах из жизни.

  1. Грязное чтение (Dirty Read) — «Подглядел в черновик». Одноклассник написал в черновике ответ «42», ты списал его себе, а через секунду он понял, что ошибся, и стёр «42» (сделал ROLLBACK). В итоге у тебя в тетради данные, которых официально никогда не существовало!
  2. Неповторяемое чтение (Non-Repeatable Read) — «Переклеили ценник за спиной». Ты зашёл в магазин, увидел на полке меч за 600 монет, отвернулся взять корзинку, снова посмотрел на ту же самую полку — а продавец уже успел поменять ценник на 900. Два одинаковых SELECT одной и той же строки внутри одной транзакции вернули разные числа.
  3. Фантомное чтение (Phantom Read) — «Невидимка зашёл в класс». Учитель пересчитал всех учеников в кабинете — их ровно 20. Пока он записывал число в журнал, в класс тихо зашёл опоздавший и сел за парту. Пересчитал снова — уже 21! Сами ученики не менялись, но в выборке по условию WHERE появилась новая («фантомная») строка.
  4. Потерянное обновление (Lost Update) — «Перезаписали чужую работу». Два кассира одновременно посмотрели на баланс Алисы (700 монет). Первый решил добавить +100 и записал в базу 800. Второй в ту же секунду добавил +200 к своим устаревшим 700 и записал 900. Пополнение первого кассира бесследно пропало!
Аномалия Что произошло Возможно ли по умолчанию в PostgreSQL?
Dirty Read
(Грязное чтение)		 Прочитали чужие неподтверждённые изменения. Нет! В PostgreSQL грязное чтение запрещено полностью на всех уровнях.
Non-Repeatable Read
(Неповторяемое чтение)		 Повторный SELECT той же строки вернул другое значение. Да, на уровне по умолчанию (READ COMMITTED).
Phantom Read
(Фантомное чтение)		 Повторный SELECT с тем же WHERE вернул другое число строк. Да, на уровне по умолчанию (READ COMMITTED).
Lost Update
(Потерянное обновление)		 Две транзакции перезаписали изменения друг друга. Да, если вычислять новое значение в коде, а не внутри SQL.

Эксперимент 1: ловим Non-Repeatable Read в двух окнах psql

Открой два окна терминала рядом и в обоих подключись к learning_db командой:

Bash · Подключение в двух терминалах 
docker exec -it course_pg_primary psql -U student -d learning_db

Теперь выполни шаги строго по порядку: сначала в Терминале 1, потом в Терминале 2, потом снова в Терминале 1.

SQL · Пример 6: Неповторяемое чтение (Non-Repeatable Read) 
-- [ШАГ 1 — ТЕРМИНАЛ 1] Открываем транзакцию и смотрим цену меча
BEGIN;
SELECT title, price FROM shop_items WHERE title = 'Алмазный меч';
-- Увидим: 600.00. Пока НЕ делаем COMMIT!

-- [ШАГ 2 — ТЕРМИНАЛ 2] Админ меняет цену и сразу сохраняет
BEGIN;
UPDATE shop_items SET price = 900.00 WHERE title = 'Алмазный меч';
COMMIT;

-- [ШАГ 3 — ТЕРМИНАЛ 1] Снова читаем ту же строку в ТОЙ ЖЕ транзакции!
SELECT title, price FROM shop_items WHERE title = 'Алмазный меч';
COMMIT;
Ответ PostgreSQL в Терминале 1 (Шаг 1 vs Шаг 3)
-- Шаг 1:
    title     | price
--------------+--------
 Алмазный меч | 600.00
(1 row)

-- Шаг 3 (в той же самой транзакции!):
    title     | price
--------------+--------
 Алмазный меч | 900.00
(1 row)

Обрати внимание на два важных факта:

  • Пока Терминал 2 не выполнил COMMIT, Терминал 1 всё ещё видел старую цену 600.00 — поэтому Dirty Read не случился.
  • Но сразу после COMMIT Терминала 2 та же самая транзакция в Терминале 1 увидела уже 900.00 — мы вживую поймали Non-Repeatable Read!

Эксперимент 2: как возникает Lost Update и как починить его за 10 секунд

Вернёмся к ситуации с двумя кассирами, которые одновременно пополняют баланс Алисы (сейчас у неё 700.00) на +100 и +200 монет. В итоге у Алисы обязано стать 1000.00.

Если программа сначала делает SELECT balance, прибавляет сумму в Python/JS и отправляет в базу уже готовое число (SET balance = 800 и SET balance = 900), последний запрос просто сотрёт работу первого. А вот если переложить сложение на сам PostgreSQL — база не потеряет ни копейки!

SQL · Пример 7: Побеждаем Lost Update атомарным UPDATE 
-- Сбрасываем баланс Алисы на 700.00 для чистоты эксперимента
UPDATE wallets SET balance = 700.00 WHERE owner = 'Алиса';

-- [ШАГ 1 — ТЕРМИНАЛ 1] Начинаем пополнение +100 (НЕ коммитим сразу)
BEGIN;
UPDATE wallets
SET balance = balance + 100.00
WHERE owner = 'Алиса';

-- [ШАГ 2 — ТЕРМИНАЛ 2] Одновременно начинаем пополнение +200
BEGIN;
UPDATE wallets
SET balance = balance + 200.00
WHERE owner = 'Алиса';
-- Смотри: Терминал 2 вежливо ЗАМРЁТ и будет ждать!

-- [ШАГ 3 — ТЕРМИНАЛ 1] Завершаем первую транзакцию
COMMIT;

-- [ШАГ 4 — ТЕРМИНАЛ 2] Как только Терминал 1 сделал COMMIT,
-- Терминал 2 «проснётся», возьмёт свежие 800.00 и прибавит 200.00!
COMMIT;

-- Проверяем итог в любом терминале
SELECT owner, balance FROM wallets WHERE owner = 'Алиса';
Ответ PostgreSQL
 owner | balance
-------+---------
 Алиса | 1000.00
(1 row)

Задача с двумя кассирами решена! Когда ты пишешь SET balance = balance + 200, PostgreSQL не даёт двум UPDATE одновременно править одну строку: второй запрос ждёт завершения первого, перечитывает свежее значение 800.00 и честно вычисляет 1000.00.

Спойлер на будущее: А можно ли вообще запретить и Non-Repeatable Read, и Phantom Read? Да! Для этого в SQL существуют уровни изоляции (READ COMMITTED, REPEATABLE READ, SERIALIZABLE) и явные блокировки строк — их мы детально разберём в уроке 4.3.

05 Шпаргалка урока перед практикой

Быстрый чек-лист терминов и правил — пробегись глазами перед тем, как решать задачи практикума:

  • Транзакция (BEGIN … COMMIT / ROLLBACK) — неделимый пакет SQL-команд. Без BEGIN каждая команда подтверждается сразу (режим Autocommit).
  • Режим aborted — если внутри транзакции случилась ошибка, PostgreSQL заблокирует все следующие команды до ROLLBACK или отката к чекпоинту.
  • SAVEPOINT имя и ROLLBACK TO SAVEPOINT имя — точка сохранения внутри транзакции, позволяющая отменить только неудачный шаг, не теряя успешные.
  • ACID — Atomicity (всё или ничего), Consistency (правила и ограничения соблюдены), Isolation (транзакции не мешают друг другу), Durability (сохранённое переживёт сбой питания благодаря WAL).
  • 4 аномалии — Dirty Read (в Postgres невозможна), Non-Repeatable Read (изменилась строка), Phantom Read (появились/исчезли строки по WHERE), Lost Update (перезаписали чужой апдейт — лечится через balance = balance + X).

06 Мини-практикум для закрепления

Выполни 4 автономных задания в своей базе learning_db. Каждая задача сама подготавливает нужные данные и не зависит от того, выполнял ли ты предыдущую. Сначала попробуй написать решение самостоятельно, и только потом открывай спойлер!

Задание 1 (Базовый). Безопасный перевод с записью в журнал

Убедись, что у Боба на счёте 500.00, а у Чарли 200.00 (с помощью стартового UPDATE или создания записей). Затем в одной транзакции переведи 150.00 монет от Боба к Чарли и добавь запись об этом в таблицу transfer_log. В конце выведи балансы обоих игроков.

Показать решение
SQL · Решение задания 1 
-- Подготовка (делает задачу полностью автономной)
INSERT INTO wallets (owner, balance) VALUES
    ('Боб', 500.00),
    ('Чарли', 200.00)
ON CONFLICT (owner) DO UPDATE SET balance = EXCLUDED.balance;

-- Основное решение: неделимый перевод
BEGIN;

UPDATE wallets
SET balance = balance - 150.00
WHERE owner = 'Боб';

UPDATE wallets
SET balance = balance + 150.00
WHERE owner = 'Чарли';

INSERT INTO transfer_log (from_owner, to_owner, amount)
VALUES ('Боб', 'Чарли', 150.00);

COMMIT;

-- Проверка результата (Боб: 350.00, Чарли: 350.00)
SELECT owner, balance
FROM wallets
WHERE owner IN ('Боб', 'Чарли')
ORDER BY owner;
Задание 2 (Средний). Покупка двух предметов с чекпоинтом SAVEPOINT

У Алисы на счёте 400.00 монет. Внутри одной транзакции она сначала покупает «Зелье маны» за 150.00 (списываем деньги и уменьшаем stock на 1), ставит точку сохранения after_potion, а затем пытается купить «Алмазный меч» за 600.00 (денег не хватит — сработает CHECK). Откати только неудачную покупку меча и сохрани покупку зелья.

Показать решение
SQL · Решение задания 2 
-- Подготовка данных
INSERT INTO wallets (owner, balance) VALUES ('Алиса', 400.00)
ON CONFLICT (owner) DO UPDATE SET balance = 400.00;

INSERT INTO shop_items (title, price, stock) VALUES
    ('Зелье маны', 150.00, 5),
    ('Алмазный меч', 600.00, 2)
ON CONFLICT (title) DO UPDATE SET price = EXCLUDED.price, stock = EXCLUDED.stock;

-- Основное решение
BEGIN;

-- Покупка №1: Зелье маны (успешно)
UPDATE wallets SET balance = balance - 150.00 WHERE owner = 'Алиса';
UPDATE shop_items SET stock = stock - 1 WHERE title = 'Зелье маны';

-- Ставим чекпоинт
SAVEPOINT after_potion;

-- Покупка №2: Алмазный меч (упадёт с ошибкой CHECK balance >= 0)
UPDATE wallets SET balance = balance - 600.00 WHERE owner = 'Алиса';

-- Откатываемся к чекпоинту (выходим из состояния aborted)
ROLLBACK TO SAVEPOINT after_potion;

-- Сохраняем покупку зелья!
COMMIT;

-- Проверка: у Алисы 250.00, зелий осталось 4
SELECT owner, balance FROM wallets WHERE owner = 'Алиса';
SELECT title, stock FROM shop_items WHERE title = 'Зелье маны';
Задание 3 (Продвинутый). Почини сломанную транзакцию и проверь Consistency

Коллега написал скрипт для списания штрафа 50.00 с Чарли и выдачи бонуса 100.00 Алисе, но случайно списал с Чарли 9999.00, получил ошибку, а потом попытался просто дописать UPDATE для Алисы и COMMIT. Перепиши сценарий так, чтобы: 1) при ошибке списания у Чарли транзакция корректно откатывалась к точке сохранения, 2) бонус Алисе всё равно начислился, 3) в конце отдельным запросом проверь сумму всех балансов (SUM(balance)).

Показать решение
SQL · Решение задания 3 
-- Подготовка: фиксируем стартовые балансы (сумма = 1200.00)
INSERT INTO wallets (owner, balance) VALUES
    ('Алиса', 700.00),
    ('Боб',   300.00),
    ('Чарли', 200.00)
ON CONFLICT (owner) DO UPDATE SET balance = EXCLUDED.balance;

-- Исправленная транзакция
BEGIN;

SAVEPOINT before_penalty;

-- Ошибочное списание (упадёт по CHECK balance >= 0)
UPDATE wallets SET balance = balance - 9999.00 WHERE owner = 'Чарли';

-- Сбрасываем ошибку и возвращаемся к чекпоинту
ROLLBACK TO SAVEPOINT before_penalty;

-- Начисляем бонус Алисе
UPDATE wallets SET balance = balance + 100.00 WHERE owner = 'Алиса';

COMMIT;

-- Проверяем Consistency: общая сумма выросла ровно на 100.00 (стало 1300.00)
SELECT SUM(balance) AS total_gold FROM wallets;
Задание 4 (Две сессии). Поймай Фантомное чтение (Phantom Read)

Открой два терминала psql к базе learning_db. В Терминале 1 начни транзакцию и посчитай количество товаров в shop_items дешевле 500.00. Не закрывая транзакцию, в Терминале 2 вставь новый товар 'Деревянный лук' за 250.00 (остаток 3) и сделай COMMIT. Вернись в Терминал 1, повтори тот же SELECT COUNT(*) и убедись, что число товаров выросло на 1 прямо внутри открытой транзакции.

Показать решение
SQL · Решение задания 4 (Терминал 1 и Терминал 2) 
-- Предварительная очистка (в любом терминале), чтобы лук можно было добавить заново
DELETE FROM shop_items WHERE title = 'Деревянный лук';

-- [ШАГ 1 — ТЕРМИНАЛ 1] Считаем товары дешевле 500
BEGIN;
SELECT COUNT(*) AS cheap_items
FROM shop_items
WHERE price < 500.00;
-- Запомни число (например, 2). НЕ делай COMMIT!

-- [ШАГ 2 — ТЕРМИНАЛ 2] Добавляем «фантомный» товар и подтверждаем
BEGIN;
INSERT INTO shop_items (title, price, stock)
VALUES ('Деревянный лук', 250.00, 3);
COMMIT;

-- [ШАГ 3 — ТЕРМИНАЛ 1] Снова считаем в той же самой транзакции!
SELECT COUNT(*) AS cheap_items
FROM shop_items
WHERE price < 500.00;
-- Число выросло на 1 (стало 3) — это и есть Phantom Read!
COMMIT;
