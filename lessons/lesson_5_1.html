Физическая потоковая репликация (Streaming Replication): Primary и Standby

Главное в этом уроке
  • Поймёшь, зачем базе данных нужен «близнец» и чем роли Primary и Standby (Hot Standby) отличаются друг от друга.
  • Разберёшь механику физической потоковой репликации (Streaming Replication): как pg_basebackup, журнал WAL и процессы walsender / walreceiver держат две базы одинаковыми байт-в-байт.
  • Запустишь реальный кластер из двух серверов PostgreSQL 16 в Docker Compose, проведёшь живую запись и чтение, поймаешь ошибку read-only transaction и научишься читать статистику pg_stat_replication.
  • Узнаешь, как слоты репликации (Replication Slots) спасают реплику от потери журнала и почему забытый слот способен положить диск главного сервера.

01 Зачем базе «близнец»: проблема одного сервера, Primary и Standby

Представь популярную школьную библиотеку, в которой все выданные книги записываются в одну-единственную бумажную тетрадь. У такого подхода сразу две беды:

  • Отказ (потеря доступности): если на тетрадь прольётся чай или библиотекарь заболеет и не откроет кабинет, выдача книг встанет полностью. В инженерии это называется единой точкой отказа (Single Point of Failure, SPOF).
  • Очередь на чтение: пока библиотекарь вписывает новых читателей, у стола выстраиваются 200 школьников, которым просто нужно посмотреть, свободна ли книга. Из-за толпы замедляются и запись, и чтение.

Как решить обе проблемы? Посадить рядом второго библиотекаря с точной копией тетради, куда мгновенно переписывается каждая новая строчка! Тогда:

  • Первый сервер — Primary (главный, ведущий) — принимает все изменения (INSERT, UPDATE, DELETE, DDL) и обычные чтения.
  • Второй сервер — Standby (резервный, ведомый) — постоянно получает свежие изменения с Primary. Если включён режим Hot Standby, он параллельно отвечает на «тяжёлые» запросы чтения (SELECT для отчётов и аналитики), разгружая главный сервер. А если Primary внезапно сломается, Standby сможет занять его место.
Простая аналогия: Физическая репликация (Physical Replication) работает как «живой ксерокс» всего шкафа с дисками. Она копирует не отдельные таблицы или SQL-команды, а весь кластер PostgreSQL целиком — все базы данных, пользователей, индексы и настройки хранилища байт-в-байт.

02 Как это работает под капотом: WAL, pg_basebackup, walsender и walreceiver

Чтобы понять, как две базы остаются одинаковыми без отправки гигабайтов таблиц каждую секунду, представь двух шеф-поваров на двух одинаковых кухнях:

  1. Базовый снимок (pg_basebackup): сначала помощник фотографирует главную кухню целиком и расставляет у себя на полках точно такие же продукты. В PostgreSQL утилита pg_basebackup копирует каталог данных $PGDATA с Primary на Standby.
  2. Дневник действий (WAL): шеф на Primary никогда не меняет блюда молча — каждое микродействие (изменение конкретных байтов на 8-килобайтной странице диска) он сначала записывает в пронумерованный журнал Write-Ahead Log (WAL). Каждая запись получает свой уникальный адрес — LSN (Log Sequence Number), например 0/3000148 (это просто счётчик байтов от начала жизни журнала).
  3. Прямой эфир по рации (walsender и walreceiver): процесс walsender на Primary берёт каждую новую строчку из WAL и по сети мгновенно диктует её процессу walreceiver на Standby.
  4. Повтор движений (startup process): внутренний процесс восстановления на Standby читает принятый WAL и применяет те же самые байтовые правки к своим файлам на диске (WAL Replay).
Термин / файл Жизненная аналогия Что делает в PostgreSQL
pg_basebackup -R Ксерокопия всей кухни + визитка шефа Копирует файлы Primary, а флаг -R сам создаёт standby.signal и записывает строку подключения primary_conninfo в postgresql.auto.conf.
standby.signal Бейджик «Я — дублёр!» Пустой файл-маркер в $PGDATA. Пока он лежит в папке, сервер запускается в режиме непрерывного восстановления (Standby).
wal_level Подробность дневника Должен быть не ниже replica (в нашем docker-compose.yaml стоит logical — он включает в себя всё нужное и для физической репликации).
hot_standby = on Разрешение пускать читателей Позволяет выполнять запросы SELECT на Standby, пока он догоняет Primary. При off клиенты вообще не смогут подключиться к реплике.
max_wal_senders Количество раций у шефа Максимальное число одновременных подключений от реплик и pg_basebackup (у нас задано 10).

Практика 2: Заглядываем внутрь обоих серверов и проверяем их роли

Давай убедимся, что PostgreSQL сам прекрасно знает, кто из контейнеров главный, а кто — реплика. Для этого есть встроенная функция pg_is_in_recovery(): на Primary она возвращает f (false), а на Standby — t (true, потому что Standby живёт в режиме бесконечного восстановления из WAL).

Bash · Проверка ролей и настроек Primary и Standby 
# 1. Спрашиваем роль и настройки у Primary (порт 5432)
docker exec course_pg_primary psql -U student -d learning_db -c "
  SELECT
    pg_is_in_recovery() AS is_standby,
    current_setting('wal_level') AS wal_level,
    current_setting('max_wal_senders') AS wal_senders,
    current_setting('wal_keep_size') AS wal_keep_size;
"

# 2. Спрашиваем роль и режим Hot Standby у Standby (порт 5433)
docker exec course_pg_standby psql -U student -d learning_db -c "
  SELECT
    pg_is_in_recovery() AS is_standby,
    current_setting('hot_standby') AS hot_standby;
"

# 3. Проверяем файл-маркер и строку подключения, созданные pg_basebackup -R
docker exec course_pg_standby ls -l /var/lib/postgresql/data/standby.signal
docker exec course_pg_standby cat /var/lib/postgresql/data/postgresql.auto.conf

Практика 3: Создаём таблицу и записываем события на Primary

Подключись к Primary (docker exec -it course_pg_primary psql -U student -d learning_db) и выполни безопасный блок подготовки данных.

SQL · Выполнять на Primary (порт 5432) 
-- Безопасный перезапуск: удаляем старую учебную таблицу, если она была
DROP TABLE IF EXISTS replication_events;

-- Создаём журнал событий интернет-магазина
CREATE TABLE replication_events (
    id          BIGSERIAL PRIMARY KEY,
    event_type  TEXT NOT NULL,
    amount      NUMERIC(10, 2) NOT NULL CHECK (amount >= 0),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Добавляем 3 тестовых события
INSERT INTO replication_events (event_type, amount) VALUES
    ('order_paid',    14500.00),
    ('order_paid',     6900.00),
    ('bonus_accrued',   500.00);

-- Фиксируем текущую позицию WAL на Primary (LSN)
SELECT

Практика 4: Проверяем данные на Standby и пробуем туда записать

Теперь открой второе окно терминала и подключись к Standby (docker exec -it course_pg_standby psql -U student -d learning_db). Проверим, доехала ли таблица replication_events, и заодно испытаем, что случится при попытке сделать INSERT на реплике.

SQL · Выполнять на Standby (порт 5433) 
-- 1. Читаем данные на Standby: они уже здесь!
SELECT id, event_type, amount
FROM replication_events
ORDER BY id;

-- 2. Смотрим, до какого LSN реплика уже применила журнал WAL
SELECT pg_last_wal_replay_lsn() AS standby_replay_lsn;

-- 3. Пытаемся записать новую строку прямо на Standby
INSERT INTO replication_events (event_type, amount)
VALUES ('hack_attempt', 999.00);

----+---------------+----------

  3 | bonus_accrued |   500.00

--------------------

Ошибка PostgreSQL (Standby · 5433 — третий запрос)
ERROR:  cannot execute INSERT in a read-only transaction

Почему PostgreSQL жёстко запретил запись на Standby? Вспомни аналогию с ксероксом: физическая репликация копирует сырые 8-килобайтные страницы диска по точным байтовым смещениям. Если разрешить Standby дописать хоть один свой байт на страницу №42, то следующая WAL-запись с Primary («измени байты 120–140 на странице №42») попадёт мимо и мгновенно повредит структуру таблицы! Поэтому физическая реплика всегда строго Read-Only, пока её не повысят до роли Primary (об этом поговорим в Уроке 5.3).

Возвращаясь к проблеме из начала урока: теперь тяжёлые аналитические запросы (например, подсчёт выручки за год) можно спокойно перенести на порт 5433, а прием новых заказов оставить на порту 5432 — библиотека больше не захлёбывается от очередей!

✗ Как НЕ надо
# Все сервисы идут на Primary
# Отчёты тормозят оплаты!
APP_DB_PORT=5432
BI_REPORTS_PORT=5432

Один тяжёлый SELECT от аналитиков съедает CPU и диск, из-за чего клиенты не могут оформить заказ.

✓ Как правильно
# Запись и транзакции → Primary
APP_WRITE_PORT=5432
# Тяжёлые отчёты → Standby
BI_READ_PORT=5433

Разделение трафика (Read/Write Splitting) снимает нагрузку чтения с главного сервера без изменения данных.

Совет на будущее: Не направляй на Standby запросы, которым критично увидеть данные в ту же миллисекунду после записи (например, страница «Спасибо за заказ!» сразу после нажатия «Оплатить»). Из-за сетевой задержки реплика может отстать на доли секунды, и пользователь на мгновение не увидит свой заказ. Такое чтение оставляют на Primary.

04 Диагностика репликации: pg_stat_replication и pg_stat_wal_receiver

Представь диспетчерскую вышку аэропорта: диспетчер вылета видит, какой самолёт вылетел и где он сейчас летит, а диспетчер прилёта подтверждает, что борт сел и багаж выгружен. В PostgreSQL мониторинг устроен точно так же — с двух сторон:

  • На Primary системное представление pg_stat_replication показывает по одной строке на каждую подключённую реплику и её текущий прогресс по LSN.
  • На Standby системное представление pg_stat_wal_receiver показывает, к какому Primary подключена реплика и до какого адреса LSN она дочитала поток.

Практика 5: Смотрим здоровье реплики со стороны Primary

Выполни этот запрос на Primary (порт 5432). Мы сразу посчитаем отставание в байтах с помощью встроенной функции pg_wal_lsn_diff(lsn1, lsn2).

SQL · Выполнять на Primary (порт 5432) 
-- Диагностика всех подключённых реплик на главном сервере
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    sync_state,
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
FROM pg_stat_replication;
Ответ PostgreSQL (Primary · 5432)
 pid | usename | application_name | client_addr |   state   | sync_state | sent_lsn  | write_lsn | flush_lsn | replay_lsn | lag_bytes
-----+---------+------------------+-------------+-----------+------------+-----------+-----------+-----------+------------+-----------
  84 | student | walreceiver      | 172.18.0.3  | streaming | async      | 0/301A8C0 | 0/301A8C0 | 0/301A8C0 | 0/301A8C0  |         0
(1 row)

Обрати внимание на четыре колонки с LSN — это четыре контрольные точки пути каждой записи WAL:

  1. sent_lsn — отправлено по сети процессом walsender с Primary.
  2. write_lsn — принято walreceiver и записано в память ОС на Standby.
  3. flush_lsn — надёжно сброшено на диск Standby (fsync).
  4. replay_lsn — применено к файлам таблиц Standby и уже видно в SELECT.

Когда state = 'streaming', а lag_bytes = 0, твоя реплика идеально догнала Primary!

05 Слоты репликации (Replication Slots) и ловушка переполнения диска

Представь, что у нашей реплики course_pg_standby на 2 часа пропал интернет. Пока она «спит», главный сервер Primary продолжает работать и записывать тысячи новых заказов. Чтобы диск не лопнул, Primary автоматически удаляет старые сегменты WAL (файлы по 16 МБ), оставляя в запасе лишь то, что помещается в wal_keep_size (у нас — 128MB).

Когда сеть восстановится и Standby попросит: «Пришли мне WAL начиная с сегмента №5», Primary разведёт руками — сегмент №5 уже ушёл в шредер! В логах Standby появится критическая ошибка, и реплику придётся пересоздавать заново через долгий pg_basebackup:

Ошибка в логах Standby при потере нужного WAL
FATAL:  could not receive data from WAL stream: ERROR:  requested WAL segment 000000010000000000000005 has already been removed

Чтобы этого не случалось, в PostgreSQL придумали слот репликации (Replication Slot). Это как официальная закладка в архиве журналов на Primary с надписью: «Ни в коем случае не выбрасывай страницы WAL новее вот этой отметки restart_lsn, пока реплика лично не подтвердит, что забрала их!»

Практика 7: Создаём, исследуем и безопасно удаляем физический слот

Выполни этот эксперимент на Primary (порт 5432). Второй аргумент true в функции создания слота просит PostgreSQL сразу зафиксировать текущую точку restart_lsn.

SQL · Выполнять на Primary (порт 5432) 
-- 1. Создаём физический слот с немедленным резервированием WAL
SELECT * FROM pg_create_physical_replication_slot('standby_slot_1', true);

-- 2. Смотрим, сколько байт WAL удерживает наш слот
SELECT
    slot_name,
    slot_type,
    active,
    restart_lsn,
    wal_status,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
    ) AS retained_wal
FROM pg_replication_slots;

-- 3. Обязательно удаляем учебный слот, раз к нему никто не подключён!
SELECT pg_drop_replication_slot('standby_slot_1');
Ответ PostgreSQL (Primary · 5432)
   slot_name    |    lsn
----------------+-----------
 standby_slot_1 | 0/301A8C0
(1 row)

   slot_name    | slot_type | active | restart_lsn | wal_status | retained_wal
----------------+-----------+--------+-------------+------------+--------------
 standby_slot_1 | physical  | f      | 0/301A8C0   | reserved   | 0 bytes
(1 row)

 pg_drop_replication_slot
--------------------------

(1 row)

Почему в третьем шаге мы сразу удалили неактивный слот? Потому что слот работает безотказно, но слепо: если реплика умерла навсегда (active = f), а слот остался, Primary будет копить гигабайты WAL до тех пор, пока на диске не останется 0 байт свободного места — и тогда упадёт сам главный сервер!

✗ Как НЕ надо
-- Создать слот и забыть выключенную реплику без лимита
SELECT pg_create_physical_replication_slot('old_replica_slot', true);
-- max_slot_wal_keep_size = -1 (без ограничений по умолчанию!)

Слот с active = f заблокирует очистку WAL. Через несколько часов активной работы Primary забьёт весь диск и аварийно остановится.

✓ Как правильно
-- 1. Задать предохранитель в postgresql.conf (например, 2 ГБ)
ALTER SYSTEM SET max_slot_wal_keep_size = '2GB';
SELECT pg_reload_conf();

-- 2. Мониторить «заброшенные» слоты (active = false) и удалять лишние
SELECT slot_name, active, wal_status FROM pg_replication_slots;

Параметр max_slot_wal_keep_size ограничивает аппетит слота: лучше потерять одну сломанную реплику, чем уронить главный сервер.

Частая ошибка в продакшене: Инженеры удаляют контейнер или виртуальную машину со Standby, но забывают выполнить pg_drop_replication_slot(...) на Primary. В 3 часа ночи приходит алерт «No space left on device» на главной базе. Всегда настраивай алерт на active = false в pg_replication_slots и включай max_slot_wal_keep_size!

Задание 1 (Базовый). Универсальный «паспорт» узла

Напиши один SQL-запрос, который можно без ошибок запустить и на Primary (5432), и на Standby (5433). Запрос должен возвращать 3 колонки: понятную подпись роли ('PRIMARY (Read/Write)' или 'STANDBY (Read-Only)'), текущее имя базы (current_database()) и актуальный LSN этого сервера (подсказка: на Standby функция pg_current_wal_lsn() выдаст ошибку — обойди это с помощью CASE WHEN pg_is_in_recovery() ...).

Показать решение
SQL · Работает и на 5432, и на 5433 
-- CASE вычисляет только подходящую ветку, поэтому ошибки на Standby не будет
SELECT
    CASE
        WHEN pg_is_in_recovery() THEN 'STANDBY (Read-Only)'
        ELSE 'PRIMARY (Read/Write)'
    END AS node_role,
    current_database() AS db_name,
    CASE
        WHEN pg_is_in_recovery() THEN pg_last_wal_replay_lsn()
        ELSE pg_current_wal_lsn()
    END AS current_lsn;
Задание 2 (Практический). Сквозной тест репликации на изменении данных

На Primary (5432) создай таблицу ha_heartbeat (id INT PRIMARY KEY, status TEXT, updated_at TIMESTAMPTZ) с безопасным DROP TABLE IF EXISTS, вставь 2 строки (id = 1 и id = 2), затем обнови строку id = 1 на статус 'verified'. На Standby (5433) прочитай таблицу и проверь, что статус обновился. Наконец, на Primary запроси pg_stat_replication и убедись, что state = 'streaming' и отставание в байтах между sent_lsn и replay_lsn равно 0.

Показать решение
SQL · Шаг 1: выполнить на Primary (5432) 
DROP TABLE IF EXISTS ha_heartbeat;

CREATE TABLE ha_heartbeat (
    id         INT PRIMARY KEY,
    status     TEXT NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

INSERT INTO ha_heartbeat (id, status) VALUES
    (1, 'pending'),
    (2, 'pending');

UPDATE ha_heartbeat
SET status = 'verified', updated_at = now()
WHERE id = 1;

-- Проверяем статус потока и разницу между sent_lsn и replay_lsn
SELECT
    application_name,
    state,
    pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_gap_bytes
FROM pg_stat_replication;
SQL · Шаг 2: проверить на Standby (5433) 
SELECT id, status, updated_at
FROM ha_heartbeat
ORDER BY id;
Задание 3 (Инженерный). Измеряем «аппетит» неактивного слота репликации

На Primary (5432) создай физический слот audit_slot_demo (с немедленным резервированием WAL). Затем сгенерируй немного записи в журнал: создай таблицу slot_load_test и вставь в неё 5000 строк через generate_series(1, 5000). Посмотри в pg_replication_slots, сколько байт WAL уже удерживает этот неактивный слот (в человекочитаемом виде через pg_size_pretty). В конце обязательно удали и слот, и тестовую таблицу!

Показать решение
SQL · Выполнять на Primary (5432) 
-- 1. Создаём слот (если остался от прошлых запусков — сначала удалим)
SELECT pg_drop_replication_slot(slot_name)
FROM pg_replication_slots
WHERE slot_name = 'audit_slot_demo';

SELECT * FROM pg_create_physical_replication_slot('audit_slot_demo', true);

-- 2. Генерируем нагрузку записи в WAL
DROP TABLE IF EXISTS slot_load_test;
CREATE TABLE slot_load_test AS
SELECT g AS id, repeat('x', 100) AS payload
FROM generate_series(1, 5000) AS g;

-- 3. Измеряем объём WAL, удерживаемый неактивным слотом
SELECT
    slot_name,
    active,
    restart_lsn,
    pg_current_wal_lsn() AS current_lsn,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
    ) AS retained_wal_size
FROM pg_replication_slots
WHERE slot_name = 'audit_slot_demo';

-- 4. Убираем за собой, чтобы не копить WAL на диске
SELECT pg_drop_replication_slot('audit_slot_demo');
DROP TABLE IF EXISTS slot_load_test;
Задание 4 (Отладка). Почему на Standby упал отчёт с временной таблицей?

Аналитик перенёс ежедневный отчёт на Standby (5433), но его скрипт упал с ошибкой ERROR: cannot execute CREATE TABLE in a read-only transaction, хотя он создавал всего лишь временную таблицу CREATE TEMP TABLE top_orders AS ...! Объясни, почему даже временные таблицы запрещены на физическом Standby, и перепиши запрос через CTE (WITH ...) так, чтобы он находил категории с суммарной выручкой больше 10000 и безопасно выполнялся на Standby.

Показать решение

Причина ошибки: создание даже TEMP TABLE требует записи новой строки в системный каталог pg_class (метаданные базы) и выдачи номера транзакции (XID). Но физический Standby не имеет права менять ни одну таблицу, включая системные каталоги. Решение — заменить временную таблицу на выражение WITH (CTE), которое выполняется целиком в режиме чтения.

SQL · Шаг 1: подготовка тестовых данных на Primary (5432) 
DROP TABLE IF EXISTS sales_report_demo;

CREATE TABLE sales_report_demo (
    id        SERIAL PRIMARY KEY,
    category  TEXT NOT NULL,
    amount    NUMERIC(10, 2) NOT NULL
);

INSERT INTO sales_report_demo (category, amount) VALUES
    ('Одежда',    14500.00),
    ('Одежда',     6900.00),
    ('Аксессуары', 1200.00),
    ('Книги',      8500.00),
    ('Книги',      4200.00);
SQL · Шаг 2: исправленный Read-Only отчёт на Standby (5433) 
-- Вместо CREATE TEMP TABLE используем CTE — это чистый SELECT
WITH category_totals AS (
    SELECT
        category,
        count(*) AS orders_cnt,
        sum(amount) AS total_revenue
    FROM sales_report_demo
    GROUP BY category
)
SELECT category, orders_cnt, total_revenue
FROM category_totals
WHERE total_revenue > 10000
ORDER BY total_revenue DESC;
