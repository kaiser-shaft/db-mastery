Урок 3.3: Чтение планов выполнения запросов: EXPLAIN и EXPLAIN ANALYZE

Главное в этом уроке
  • Как PostgreSQL выбирает маршрут для твоего SQL-запроса и чем отличается прогноз EXPLAIN от реального замера EXPLAIN (ANALYZE, BUFFERS).
  • Как расшифровывать главные цифры плана: cost, rows, actual time, loops и счётчики 8-килобайтных страниц shared hit / read.
  • Как отличать способы чтения и соединения таблиц (Seq Scan, Index Scan, Index Only Scan, Bitmap Scan, Nested Loop, Hash Join, Merge Join) и читать дерево плана снизу вверх.
  • Как ловить главные причины тормозов и не удалить базу по ошибке при запуске EXPLAIN ANALYZE.

01 Навигатор внутри PostgreSQL: EXPLAIN vs EXPLAIN ANALYZE

Представь, что тебе нужно добраться от дома до торгового центра. Ты открываешь навигатор в телефоне. Навигатор смотрит на карту, прикидывает пробки и предлагает два маршрута: через центр — примерно 25 минут, а по объездной — 14 минут. Он выбирает самый выгодный маршрут и показывает его тебе на экране.

В PostgreSQL работает точно такой же «навигатор». Когда ты отправляешь SQL-запрос, ты говоришь что хочешь получить (например, «дай заказы клиента №42»), но не говоришь как именно их доставать. В этот момент включается планировщик (Planner / Optimizer): он заглядывает в статистику таблиц, прикидывает разные способы поиска (перебрать всю таблицу или пойти по B-Tree индексу из Урока 3.2) и составляет пошаговую инструкцию — план выполнения (Execution Plan).

Чтобы заглянуть в голову планировщику, в PostgreSQL есть две волшебные приставки перед любым запросом:

  • EXPLAIN — спрашивает навигатор: «Как ты собираешься ехать и сколько это примерно будет стоить?» Запрос не выполняется, данные не читаются и не меняются.
  • EXPLAIN ANALYZE — реально садится за руль, проезжает весь маршрут с секундомером и в конце показывает два столбца: что навигатор обещал и сколько времени ушло на самом деле.
Простая аналогия: EXPLAIN — это прогноз погоды в телефоне («завтра обещают +20°C»). EXPLAIN ANALYZE — это выйти на улицу с градусником и проверить реальную температуру. Если прогноз и реальность сильно разошлись, значит, у планировщика «сломалась» статистика!

02 Готовим полигон и расшифровываем первый план

Если в таблице всего 10 строк, PostgreSQL даже не станет открывать индекс — ему проще прочитать одну 8-килобайтную страницу целиком (как пробежать глазами стикер, вместо того чтобы лезть в оглавление). Поэтому для честных экспериментов создадим в базе learning_db учебный магазин из 3 таблиц на 100 000 заказов.

SQL · Подготовка данных в learning_db (безопасный перезапуск) 
-- Сносим старые учебные таблицы этого урока, если они уже есть
DROP TABLE IF EXISTS plan_orders, plan_products, plan_customers CASCADE;

-- 1. Клиенты (1 000 человек)
CREATE TABLE plan_customers (
    id         INT PRIMARY KEY,
    full_name  TEXT NOT NULL,
    city       TEXT NOT NULL,
    email      TEXT NOT NULL
);

-- 2. Товары (200 позиций)
CREATE TABLE plan_products (
    id         INT PRIMARY KEY,
    title      TEXT NOT NULL,
    category   TEXT NOT NULL,
    price      NUMERIC(10, 2) NOT NULL
);

-- 3. Заказы (100 000 строк, пока БЕЗ дополнительных индексов)
CREATE TABLE plan_orders (
    id          SERIAL PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES plan_customers(id),
    product_id  INT NOT NULL REFERENCES plan_products(id),
    status      TEXT NOT NULL,
    amount      NUMERIC(10, 2) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL
);

-- Наполняем таблицы генератором generate_series
INSERT INTO plan_customers (id, full_name, city, email)
SELECT
    g,
    'Клиент #' || g,
    (ARRAY['Алматы', 'Астана', 'Костанай', 'Шымкент', 'Караганда'])[1 + (g % 5)],
    'user' || g || '@shop.example'
FROM generate_series(1, 1000) AS g;

INSERT INTO plan_products (id, title, category, price)
SELECT
    g,
    'Товар #' || g,
    (ARRAY['electronics', 'books', 'clothes', 'games'])[1 + (g % 4)],
    round((500 + (g * 37 % 15000))::numeric, 2)
FROM generate_series(1, 200) AS g;

INSERT INTO plan_orders (customer_id, product_id, status, amount, created_at)
SELECT
    1 + (g % 1000),
    1 + (g % 200),
    CASE
        WHEN g % 20 = 0 THEN 'cancelled'
        WHEN g % 5  = 0 THEN 'pending'
        ELSE 'paid'
    END,
    round((1000 + (g * 19 % 45000))::numeric, 2),
    TIMESTAMPTZ '2024-01-01 00:00:00+00' + (g || ' minutes')::interval
FROM generate_series(1, 100000) AS g;

-- Обновляем статистику для планировщика, чтобы его прогнозы были точными
ANALYZE plan_customers, plan_products, plan_orders;

Отлично, полигон готов! Представь боевую проблему: менеджер жалуется, что страница «История заказов клиента №42» открывается медленно и нагружает диск. Давай сделаем первый рентген этого запроса с помощью EXPLAIN (ANALYZE, BUFFERS).

SQL · Пример 1: первый EXPLAIN (ANALYZE, BUFFERS) без индекса 
-- Запускаем запрос с замером времени и подсчётом прочитанных страниц (8 КБ)
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, amount, created_at
FROM plan_orders
WHERE customer_id = 42;
Ответ PostgreSQL

-------------------------------------------------------------------------------------------------------------
 Seq Scan on plan_orders  (cost=0.00..2185.00 rows=100 width=25) (actual time=0.048..14.620 rows=100 loops=1)
   Filter: (customer_id = 42)
   Rows Removed by Filter: 99900
   Buffers: shared hit=310 read=625
 Planning Time: 0.145 ms
 Execution Time: 14.682 ms
(6 rows)

На первый взгляд вывод похож на шифровку с космической станции. На самом деле тут всего 6 понятных показателей — давай переведём их на человеческий язык:

Что написано в плане Как перевести на простой язык На что смотреть инженеру
cost=0.00..2185.00 Прогноз стоимости в условных «попугаях»: 0.00 — сколько работы нужно до выдачи первой строки, 2185.00 — до выдачи всех строк. Это не миллисекунды! За единицу (1.0) принято чтение одной 8 КБ страницы с диска подряд. Чем меньше вторая цифра, тем дешевле маршрут.
rows=100 (слева) и rows=100 (справа) Слева — сколько строк планировщик ожидал найти. Справа — сколько нашлось на самом деле. Если прогноз rows=1, а в реальности rows=50000 — планировщик слепой и почти наверняка выбрал плохой план!
width=25 Средний «вес» одной возвращаемой строки в байтах. Если делаешь SELECT * с огромными текстами, width растёт, и сортировки перестают влезать в память.
actual time=0.048..14.620 Реальное время в миллисекундах: первая строка нашлась через 0.048 мс, последняя — через 14.620 мс. Указывается время одной итерации узла. Чтобы узнать полное время, умножай на loops!
Rows Removed by Filter: 99900 Сколько лишних строк PostgreSQL прочитал, проверил и выкинул в мусорку. Огромное число здесь — главный крик базы: «Мне нужен индекс!» Мы прочитали 100 000 строк ради 100 нужных.
Buffers: shared hit=310 read=625 Прямой привет из Урока 3.1! hit — страниц по 8 КБ найдено мгновенно в оперативной памяти (Shared Buffers); read — пришлось сходить на медленный диск. Всего прочитано 310 + 625 = 935 страниц (≈ 7.5 МБ данных) ради пары килобайт ответа. Это главная метрика реальной нагрузки!
Совет на будущее: Возьми в привычку всегда писать EXPLAIN (ANALYZE, BUFFERS) вместо голого EXPLAIN ANALYZE. Время в миллисекундах скачет (фоном обновился браузер — и запрос замедлился вдвое), а количество прочитанных страниц Buffers всегда честно показывает объём проделанной работы.

03 Четыре способа чтения таблицы: Scan-узлы на практике

Представь, что тебе нужно найти в толстом учебнике истории все упоминания слова «Наполеон». У тебя есть четыре совершенно разные стратегии — и ровно те же четыре стратегии есть у PostgreSQL:

Узел в плане Жизненная аналогия с учебником Когда PostgreSQL его выбирает
Seq Scan
Последовательное чтение		 Листаешь книгу с 1-й страницы до последней подряд. Нет подходящего индекса, таблица крошечная, или нужно забрать большую часть строк (обычно >15–20% таблицы).
Index Scan
Чтение по индексу		 Открываешь предметный указатель в конце, видишь номер страницы и прыгаешь туда (в Heap) за полным текстом. Нужно найти мало строк (единицы или десятки), и на колонке есть подходящий B-Tree индекс.
Bitmap Index Scan +
Bitmap Heap Scan		 Сначала выписываешь на черновик номера всех нужных страниц из указателя, сортируешь их по возрастанию и спокойно проходишь книгу один раз. Найдено «среднее» количество строк (сотни или тысячи): прыгать по одной строке вразнобой дорого, а читать всю книгу — ещё дороже.
Index Only Scan
Чтение только из индекса		 Ответ на вопрос уже написан прямо в оглавлении! На страницы самой книги (Heap) даже не ходим. Все колонки из SELECT и WHERE уже лежат внутри индекса, и карта видимости (Visibility Map) актуальна.

Лечим медленный запрос из Раздела 02

В прошлом примере поиск заказов клиента №42 прочитал 935 страниц (100 000 строк) и потратил 14.68 мс. Давай создадим B-Tree индекс по customer_id и снова посмотрим план!

SQL · Пример 2: создаём индекс и смотрим Bitmap Heap Scan 
-- Создаём B-Tree индекс на колонку customer_id
CREATE INDEX idx_plan_orders_customer_id
    ON plan_orders (customer_id);

-- Повторяем тот же самый запрос
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, status, amount, created_at
FROM plan_orders
WHERE customer_id = 42;
Ответ PostgreSQL
                                                                QUERY PLAN
------------------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on plan_orders  (cost=5.06..312.40 rows=100 width=25) (actual time=0.061..0.245 rows=100 loops=1)
   Recheck Cond: (customer_id = 42)
   Heap Blocks: exact=100
   Buffers: shared hit=103
   ->  Bitmap Index Scan on idx_plan_orders_customer_id  (cost=0.00..5.04 rows=100 width=0) (actual time=0.032..0.032 rows=100 loops=1)
         Index Cond: (customer_id = 42)
         Buffers: shared hit=3
 Planning Time: 0.190 ms
 Execution Time: 0.278 ms
(9 rows)

Смотри, что случилось! Поскольку заказы клиента №42 разбросаны по 100 разным страницам (Heap Blocks: exact=100), PostgreSQL выбрал умную связку Bitmap Index Scan + Bitmap Heap Scan: за 3 страницы в индексе он собрал адреса нужных блоков, упорядочил их и забрал строки. Время упало в 52 раза — с 14.68 мс до 0.278 мс, а чтение страниц сократилось с 935 до 103!

Уровень «магия»: выходим на Index Only Scan

А можно ещё быстрее? Допустим, на главной странице кабинета нам нужна только сумма всех заказов клиента №42. Если мы «подложим» колонку amount прямо в листья B-Tree индекса через INCLUDE (покрывающий индекс), PostgreSQL вообще не придётся заходить в таблицу (Heap)!

SQL · Пример 3: покрывающий индекс и Index Only Scan 
-- Создаём покрывающий индекс: ищем по customer_id, а amount храним рядом
CREATE INDEX idx_plan_orders_customer_inc_amount
    ON plan_orders (customer_id) INCLUDE (amount);

-- Обновляем карту видимости (Visibility Map), чтобы не проверять Heap
VACUUM ANALYZE plan_orders;

-- Считаем сумму заказов клиента №42
EXPLAIN (ANALYZE, BUFFERS)
SELECT sum(amount)
FROM plan_orders
WHERE customer_id = 42;
Ответ PostgreSQL
                                                                         QUERY PLAN
------------------------------------------------------------------------------------------------------------------------------------------------------------
 Aggregate  (cost=6.78..6.79 rows=1 width=32) (actual time=0.049..0.050 rows=1 loops=1)
   Buffers: shared hit=4
   ->  Index Only Scan using idx_plan_orders_customer_inc_amount on plan_orders  (cost=0.29..6.53 rows=100 width=6) (actual time=0.018..0.036 rows=100 loops=1)
         Index Cond: (customer_id = 42)
         Heap Fetches: 0
         Buffers: shared hit=4
 Planning Time: 0.112 ms
 Execution Time: 0.068 ms
(8 rows)

Обрати внимание на две строчки: Heap Fetches: 0 и Buffers: shared hit=4! Проблема из начала раздела решена подчистую: вместо чтения 935 страниц (7.5 МБ) и 14.68 мс база прочитала всего 4 страницы из памяти за 0.068 мс — ускорение более чем в 215 раз!

04 Как читать дерево плана и разбираться в JOIN-ах

Когда в запросе соединяются 2–3 таблицы, добавляются фильтры, сортировка и LIMIT, план превращается в многоуровневое дерево со стрелками ->. Новички часто пытаются читать его сверху вниз и сразу путаются.

Представь кухню бургерной: сначала на нижних станциях жарят котлету и режут салат, потом передают их сборщику бургера, а на самом верху кассир кладёт готовый заказ в пакет и отдаёт тебе. План PostgreSQL работает точно так же! Главное правило чтения: всегда начинай с самых глубоких узлов (с наибольшим отступом вправо) и поднимайся вверх к корню.

Три способа соединять таблицы (JOIN)

  • Nested Loop (Вложенный цикл) — как школьник, который для каждого из 5 друзей в тетради открывает телефонную книгу и ищет его номер. Работает молниеносно, когда с одной стороны мало строк, а на второй таблице есть индекс.
  • Hash Join (Хеш-соединение) — берёшь меньшую таблицу, раскладываешь её строки по пронумерованным «ящикам» в оперативной памяти (узел Hash), а потом за один быстрый проход по большой таблице заглядываешь в нужный ящик. Идеален для соединения больших объёмов данных без индексов.
  • Merge Join (Соединение слиянием) — когда оба списка уже отсортированы по алфавиту, ты ведёшь двумя пальцами сверху вниз и собираешь совпадения за один проход.

Перед тем как смотреть сложный запрос по всем трём таблицам (plan_orders, plan_customers и plan_products), взгляни на схему того, как данные потекут снизу вверх:

Теперь решим реальную аналитическую задачу: найти 5 самых дорогих заказов электроники от клиентов из Костаная, где сумма заказа больше 40 000. Запустим запрос и посмотрим реальный план!

SQL · Пример 4: план соединения трёх таблиц с сортировкой и LIMIT 
-- Соединяем 3 таблицы: заказы + клиенты + товары
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    o.id AS order_id,
    c.full_name,
    p.title,
    o.amount
FROM plan_orders o
JOIN plan_customers c ON c.id = o.customer_id
JOIN plan_products  p ON p.id = o.product_id
WHERE c.city = 'Костанай'
  AND p.category = 'electronics'
  AND o.amount > 40000
ORDER BY o.amount DESC
LIMIT 5;

Посмотри, как легко теперь читается этот «страшный» план из 32 строк, когда мы идём снизу вверх:

  1. Из 15.49 мс общего времени почти всё (12.84 мс и 935 из 948 страниц!) съел один узел — Seq Scan on plan_orders, который отбрасывал 87 555 заказов с суммой <= 40000.
  2. Маленькие таблицы клиентов (200 строк) и товаров (50 строк) PostgreSQL мгновенно сложил в память (Hash, всего 18 КБ и 11 КБ) и прогнал через два Hash Join.
  3. Наверху сработала крутая оптимизация Sort Method: top-N heapsort Memory: 25kB — PostgreSQL не стал сортировать все 620 строк, а просто держал в памяти пятёрку лидеров!

Значит, узкое место найдено точно: нам не хватает индекса по plan_orders(amount DESC), чтобы сразу брать дорогие заказы с конца и остановиться, как только наберётся 5 штук! Посмотрим, что будет в таблице «Было → Стало», если добавить этот индекс:

Чтение plan_orders Seq Scan (100 000 строк) Index Scan Backward (читает только ~100 самых дорогих заказов до заполнения LIMIT 5!)
Прочитано страниц (Buffers) 948 страниц (≈ 7.6 МБ) ~110 страниц (в 8.5 раз меньше!)
Время выполнения 15.49 мс ~0.65 мс (ускорение в 23 раза!)

CREATE INDEX idx_plan_orders_amount ON plan_orders (amount);

FROM plan_orders o
JOIN plan_customers c ON c.id = o.customer_id
JOIN plan_products  p ON p.id = o.product_id
WHERE c.city = 'Костанай'
  AND p.category = 'electronics'
  AND o.amount > 40000
ORDER BY o.amount DESC
LIMIT 5;

05 Опасные ловушки EXPLAIN и разбор реальных ошибок

EXPLAIN ANALYZE — мощнейший скальпель, но если держать его неправильно, можно больно порезаться. Разберём три главные ловушки, на которых спотыкаются даже опытные разработчики.

Ловушка №1: EXPLAIN ANALYZE реально изменяет данные!

Помнишь аналогию с машиной? EXPLAIN ANALYZE действительно запускает запрос. Если ты напишешь EXPLAIN ANALYZE DELETE FROM plan_orders; — таблица станет пустой! Чтобы проверить план для INSERT, UPDATE или DELETE и ничего не сломать, всегда оборачивай его в транзакцию с откатом ROLLBACK.

✗ Как НЕ надо
EXPLAIN ANALYZE
DELETE FROM plan_orders
WHERE status = 'cancelled';

Запрос покажет красивый план… и навсегда удалит 5 000 заказов из базы!

✓ Как правильно
BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
DELETE FROM plan_orders
WHERE status = 'cancelled';
ROLLBACK;

Запрос выполнится, замерит время, а команда ROLLBACK мгновенно вернёт все строки назад.

Убедимся на практике, что EXPLAIN ANALYZE реально пытается менять данные — попробуем «просто посмотреть план» удаления клиента №1 (на которого ссылаются заказы через внешний ключ) и заодно посмотрим частую ошибку с опцией TIMING.

SQL · Пример 5: реальные ошибки при работе с EXPLAIN 
-- Ошибка А: просим замерить реальное время (TIMING), но забыли включить ANALYZE
EXPLAIN (TIMING true)
SELECT * FROM plan_customers WHERE id = 1;

-- Ошибка Б: доказательство, что EXPLAIN ANALYZE реально пытается удалить строку!
BEGIN;
EXPLAIN ANALYZE
DELETE FROM plan_customers WHERE id = 1;
ROLLBACK;
Ошибка PostgreSQL (запрос А)
ERROR:  EXPLAIN option TIMING requires ANALYZE
Ошибка PostgreSQL (запрос Б)
ERROR:  update or delete on table "plan_customers" violates foreign key constraint "plan_orders_customer_id_fkey" on table "plan_orders"
DETAIL:  Key (id)=(1) is still referenced from table "plan_orders".

В первом случае PostgreSQL честно отвечает: нельзя замерить реальное время (TIMING), если не включён ANALYZE (запрос ведь не запускается). Во втором случае сработало ограничение внешнего ключа — лучшее доказательство, что EXPLAIN ANALYZE по-настоящему удаляет данные, если его не остановить!

Ловушка №2: «слепой» индекс из-за функции в WHERE

В Уроке 3.2 ты уже узнал, что обёртка колонки в функцию ломает обычный B-Tree индекс. Давай посмотрим, как это выглядит прямо в EXPLAIN (ANALYZE, BUFFERS) на примере поиска заказов за январь 2024 года!

SQL · Пример 6: сравниваем план с функцией и с диапазоном дат 
-- Создаём индекс по дате создания заказа
CREATE INDEX idx_plan_orders_created_at ON plan_orders (created_at);

-- Вариант 1 (ловушка): прячем колонку внутрь функции date_trunc
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM plan_orders
WHERE date_trunc('month', created_at AT TIME ZONE 'UTC') = TIMESTAMP '2024-01-01';

-- Вариант 2 (правильный): оставляем колонку чистой и задаём диапазон
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*)
FROM plan_orders
WHERE created_at >= TIMESTAMPTZ '2024-01-01 00:00:00+00'
  AND created_at <  TIMESTAMPTZ '2024-02-01 00:00:00+00';
✗ Как НЕ надо: функция вокруг колонки
Aggregate  (actual time=36.410..36.411 rows=1 loops=1)
  -> Seq Scan on plan_orders  (cost=0.00..2685.00 rows=500 width=0) (actual time=0.032..34.810 rows=44639 loops=1)
       Filter: (date_trunc('month', timezone('UTC', created_at)) = '2024-01-01 00:00:00')
       Rows Removed by Filter: 55361
       Buffers: shared hit=935

Обрати внимание на две катастрофы сразу: индекс полностью проигнорирован (Seq Scan, 935 страниц), а прогноз ошибся в 89 раз (планировщик ждал rows=500, а реально нашлось 44639 строк)!

✓ Как правильно: чистая колонка и диапазон дат
Aggregate  (actual time=6.120..6.121 rows=1 loops=1)
  -> Index Only Scan using idx_plan_orders_created_at on plan_orders
       (cost=0.29..1124.50 rows=44600 width=0) (actual time=0.035..4.210 rows=44639 loops=1)
       Index Cond: ((created_at >= '2024-01-01 00:00:00+00') AND (created_at < '2024-02-01 00:00:00+00'))
       Heap Fetches: 0
       Buffers: shared hit=124

Сработал Index Only Scan, прогноз точен почти до строки (44600 vs 44639), прочитано в 7.5 раз меньше страниц (124 вместо 935), а время упало с 36.4 мс до 6.1 мс!

Частая ошибка (ловушка «холодного кеша»): Если ты запускаешь запрос в первый раз, он идёт на диск (shared read) и работает 50 мс. После создания индекса ты запускаешь его второй раз, и данные уже лежат в памяти (shared hit) — выходит 2 мс. Всегда прогоняй EXPLAIN (ANALYZE, BUFFERS) дважды до и после оптимизации, и сравнивай в первую очередь суммарное число страниц (hit + read), а не только миллисекунды!

06 Шпаргалка детектива и мини-практикум

Перед тем как решать задачи, сохрани короткий чек-лист «красных флагов». Если видишь любой из этих 5 пунктов в выводе EXPLAIN (ANALYZE, BUFFERS) — ты нашёл виновника тормозов:

Шпаргалка перед практикой: 5 красных флагов в плане
  • Seq Scan + огромный Rows Removed by Filter — база прочитала полтаблицы и выкинула 99% строк. Нужен индекс (или ты спрятал колонку в функцию).
  • Прогноз rows отличается от actual rows в 10+ раз — статистика устарела (запусти ANALYZE имя_таблицы;) или условие слишком хитрое для планировщика.
  • Огромные Buffers (shared hit + read) — запрос перелопачивает десятки мегабайт ради маленького ответа.
  • Sort Method: external merge Disk — сортировка не влезла в оперативную память (work_mem) и свалилась на медленный диск!
  • Большой loops внутри Nested Loop — если внутренний узел выполняется loops=50000, даже 0.1 мс на шаг превратятся в 5 секунд ожидания.

Теперь твоя очередь! Все 4 задания ниже автономны и работают на таблицах plan_customers, plan_products и plan_orders из Раздела 02 (убедись, что выполнил скрипт подготовки данных). Попробуй решить каждое самостоятельно, прежде чем открывать ответ.

Задание 2 (Средний уровень). Почини «сломанный» поиск по email

Коллега создал обычный индекс CREATE INDEX idx_task2_email ON plan_customers (email);, но запрос SELECT * FROM plan_customers WHERE lower(email) = 'user42@shop.example'; всё равно делает Seq Scan. Создай функциональный индекс по lower(email) (или перепиши запрос без функции, если email уже в нижнем регистре) и докажи через EXPLAIN (ANALYZE, BUFFERS), что появился Index Scan.

Показать решение
SQL

CREATE INDEX idx_task2_email_lower

Задание 3 (Продвинутый уровень). Добейся Index Only Scan с нулевым чтением Heap

Для отчёта часто запускается запрос: найти count(*) и avg(amount) по всем заказам товара product_id = 15. Создай такой покрывающий индекс, чтобы EXPLAIN (ANALYZE, BUFFERS) показал Index Only Scan и ровно Heap Fetches: 0. Не забудь команду, которая обновляет карту видимости!

Показать решение
SQL 
-- Автономная очистка перед созданием
DROP INDEX IF EXISTS idx_task3_product_inc_amount;

-- Покрывающий индекс: поиск по product_id, значение amount внутри листа
CREATE INDEX idx_task3_product_inc_amount
    ON plan_orders (product_id) INCLUDE (amount);

-- ВАЖНО: обновляем Visibility Map, иначе Heap Fetches будет больше 0
VACUUM ANALYZE plan_orders;

-- Проверяем: в плане Index Only Scan и Heap Fetches: 0
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*), round(avg(amount), 2)
FROM plan_orders
WHERE product_id = 15;
Задание 4 (Боевой сценарий). Безопасный профиль массового UPDATE

Тебе нужно проверить, сколько времени и страниц займёт повышение цены (price = price * 1.10) для всех товаров категории 'electronics' в таблице plan_products. Выполни EXPLAIN (ANALYZE, BUFFERS) так, чтобы реальные цены в базе не изменились, и после отката проверь сумму цен товаров этой категории.

Показать решение
SQL 
-- 1. Запоминаем исходную сумму цен электроники
SELECT sum(price) AS price_before
FROM plan_products
WHERE category = 'electronics';

-- 2. Безопасно профилируем UPDATE внутри транзакции с откатом
BEGIN;

EXPLAIN (ANALYZE, BUFFERS)
UPDATE plan_products
SET price = round(price * 1.10, 2)
WHERE category = 'electronics';

ROLLBACK;

-- 3. Убеждаемся, что сумма цен осталась прежней
SELECT sum(price) AS price_after
FROM plan_products
WHERE category = 'electronics';
