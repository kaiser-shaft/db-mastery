Главное в этом уроке

  • Разберёшься, как устроена связь «многие-ко-многим» (M:N), и соберёшь таблицу-мостик с составным PRIMARY KEY и внешними ключами FOREIGN KEY.
  • Научишься безопасно менять живую базу через миграции схемы БД (UP и DOWN) внутри транзакций (BEGIN ... COMMIT), не теряя данные клиентов.

01 Зачем наводить порядок в таблицах: три главные ловушки

Представь, что ты с друзьями открыл небольшой онлайн-магазин мерча для программистов — продаёте худи, термокружки и стикерпаки. Сначала вы ведёте учёт заказов в одной школьной тетради или в одном листе Excel: в каждой строчке пишете номер заказа, имя покупателя, его телефон, город, часовой пояс города и список купленных товаров прямо через запятую.

Пока заказов пять штук, кажется, что всё удобно. Но как только заказов становится хотя бы сотня, начинаются три классические проблемы — инженеры называют их аномалиями данных (Data Anomalies):

  • Аномалия обновления (Update Anomaly): покупательница Алиса сменила номер телефона. Ты исправил его в новом заказе, но забыл поменять в двух старых. Теперь база сама себе противоречит: у одной Алисы два разных номера!
  • Аномалия вставки (Insert Anomaly): вы привезли новую кепку «EXPLAIN», но не можете добавить её в таблицу — ведь её ещё никто не заказал, а в строчке обязательно должен быть клиент и номер заказа.
  • Аномалия удаления (Delete Anomaly): Тимур отменил свой единственный заказ на термокружку. Ты удалил строчку — и вместе с заказом навсегда стёр и телефон Тимура, и информацию о самой термокружке.

Давай посмотрим на эту «свалку» вживую! Подключайся к нашей сквозной базе learning_db и создай «плохую» таблицу bad_orders_sheet.

Простая аналогия: Нормализация (Normalization) — это как разложить детали конструктора LEGO по отдельным прозрачным контейнерам вместо одной огромной коробки на полу. Каждый факт хранится ровно в одном месте — инженеры называют это принципом единого источника правды (Single Source of Truth).

02 Три ступени порядка: 1НФ, 2НФ и 3НФ

Чтобы не гадать на кофейной гуще, как именно резать большую таблицу на маленькие, математик Эдгар Кодд ещё в 1970-х придумал пошаговый чек-лист — нормальные формы (Normal Forms). В 95% реальных проектов хватает первых трёх ступеней: 1НФ, 2НФ и 3НФ. Каждая следующая ступень включает в себя правила всех предыдущих.

Первая нормальная форма (1НФ): один карман — одна вещь

Представь школьный рюкзак, где в одном кармане вперемешку лежат ключи, флешка и ручка — пока найдёшь нужное, всё перевернёшь. Первая нормальная форма (1NF) требует двух простых вещей:

  1. В каждой ячейке лежит ровно одно неделимое (атомарное) значение — никаких списков через запятую вроде 'Худи SQL, Стикерпак'.
  2. У каждой строки есть уникальный идентификатор (первичный ключ / PRIMARY KEY), и в таблице нет повторяющихся колонок вроде item_1, item_2, item_3.
✗ Как НЕ надо (нарушение 1НФ)
-- Товары в одной строке:
SELECT *
FROM bad_orders_sheet
WHERE items_list
  LIKE '%Стикерпак%';

Нельзя посчитать количество штук, нельзя задать цену каждому товару, а поиск по %...% медленный и часто ошибается.

✓ Как правильно (соблюдаем 1НФ)
-- 1 товар = 1 строка:
SELECT order_id,
       product_id,
       quantity
FROM shop_order_items
WHERE product_id = 2;

В каждой ячейке одно чистое значение: легко считать суммы, фильтровать и проверять наличие товара на складе.

Вторая нормальная форма (2НФ): факт зависит от ВСЕГО ключа

Представь школьный журнал, где каждая оценка определяется сразу парой значений — (ученик, предмет). Это составной ключ (Composite Key). Если учитель рядом с каждой оценкой приписывает номер кабинета («Математика — каб. 305»), то кабинет зависит только от предмета, но никак не от ученика! Переедет математика в 402-й кабинет — придётся переписывать весь журнал.

В нашем магазине та же история с позициями заказа: ключ — пара (order_id, product_id). Количество штук (qty) зависит от всей пары. А вот название товара (title) зависит только от половинки ключа (product_id). По правилу второй нормальной формы (2NF) отрезаем каталог товаров в отдельную таблицу!

Третья нормальная форма (3НФ): никаких «передач через третье лицо»

Теперь посмотри на таблицу покупателей: в ней ключ простой — один столбец id. Но рядом лежат city и tz (часовой пояс). Замечаешь цепочку? Часовой пояс зависит от города, а город уже указан у покупателя (customer_id → city → tz). В инженерии это называется транзитивной зависимостью (Transitive Dependency).

Если страна переведёт стрелки часов и часовой пояс города изменится, придётся обновлять тысячи строк клиентов. По правилу третьей нормальной формы (3NF) выносим города и их часовые пояса в справочник cities, а у покупателя оставляем только короткую ссылку city_id. Посмотри глазами, как аккуратно «разрезается» таблица:

Форма Простое правило Пример нарушения Как исправляем
1НФ Одна ячейка = одно значение, есть PRIMARY KEY В поле items лежит 'Худи, Кепка' Выносим позиции заказа в отдельные строки таблицы shop_order_items
2НФ 1НФ + колонки зависят от всего ключа, а не от его части В таблице (order_id, product_id) хранится название товара Переносим название и цену каталога в таблицу shop_products
3НФ 2НФ + неключевые поля не зависят друг от друга У клиента лежат и city, и city_timezone Создаём справочник cities, а клиенту даём внешний ключ city_id

Чтобы запомнить все три правила разом, инженеры повторяют знаменитую шутливую клятву: «Каждый столбец должен зависеть от ключа, от всего ключа и ни от чего, кроме ключа!»

Итоговая карта нашего магазина перед тем, как писать SQL

Прежде чем запускать код создания базы, посмотри на схему всех пяти таблиц целиком. Стрелки показывают, кто на кого ссылается через внешний ключ (FOREIGN KEY):

Теперь перевод этой картинки в SQL читается на одном дыхании! Давай пересоберём магазин в learning_db по всем канонам 3НФ.

SQL · Пример 2: Создаём чистую схему магазина в 3НФ 
-- Удаляем таблицы в обратном порядке (CASCADE чистит зависимые связи)
DROP TABLE IF EXISTS product_tags, tags, shop_order_items, shop_orders, shop_products, shop_customers, cities CASCADE;

-- 1. Справочник городов (убираем транзитивную зависимость — 3НФ)
CREATE TABLE cities (
    id       INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name     VARCHAR(100) NOT NULL UNIQUE,
    timezone VARCHAR(20)  NOT NULL
);

-- 2. Покупатели: храним телефон ровно один раз + ссылка на город
CREATE TABLE shop_customers (
    id        INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    phone     VARCHAR(30)  NOT NULL UNIQUE,
    city_id   INT NOT NULL REFERENCES cities(id)
);

-- 3. Каталог товаров (убираем частичную зависимость — 2НФ)
CREATE TABLE shop_products (
    id    INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title VARCHAR(150)   NOT NULL,
    price NUMERIC(10, 2) NOT NULL CHECK (price >= 0)
);

-- 4. Шапка заказов (кто и когда заказал)
CREATE TABLE shop_orders (
    id          INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES shop_customers(id),
    created_at  TIMESTAMP NOT NULL DEFAULT NOW()
);

-- 5. Состав заказов (атомарные строки — 1НФ, составной ключ)
CREATE TABLE shop_order_items (
    order_id   INT NOT NULL REFERENCES shop_orders(id) ON DELETE CASCADE,
    product_id INT NOT NULL REFERENCES shop_products(id),
    quantity   INT NOT NULL CHECK (quantity > 0),
    unit_price NUMERIC(10, 2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);

-- Собираем читаемый чек из нормализованных таблиц через INNER JOIN
SELECT
    o.id        AS order_id,
    c.full_name AS customer,
    ci.name     AS city,
    p.title     AS product,
    oi.quantity,
    oi.unit_price
FROM shop_orders o
JOIN shop_customers   c  ON c.id  = o.customer_id
JOIN cities           ci ON ci.id = c.city_id
JOIN shop_order_items oi ON oi.order_id = o.id
JOIN shop_products    p  ON p.id  = oi.product_id
ORDER BY o.id, p.id;

Проверяем на деле: исчезли ли все три аномалии?

Помнишь три главные боли из начала урока? Давай прямо сейчас проверим, как наша чистая схема расправляется с ними за пару строчек SQL!

SQL · Пример 3: Побеждаем аномалии обновления и вставки 
-- 1. Нет аномалии обновления: меняем телефон Алисы ОДИН раз в таблице клиентов
UPDATE shop_customers
SET phone = '+7-701-555-00-00'
WHERE id = 1;

-- 2. Нет аномалии вставки: свободно добавляем новый товар без единого заказа
INSERT INTO shop_products (title, price)
VALUES ('Блокнот «ACID»', 2500.00);

-- Проверяем заказы: во ВСЕХ заказах Алисы телефон обновился автоматически!
SELECT o.id AS order_id, c.full_name, c.phone
FROM shop_orders o
JOIN shop_customers c ON c.id = o.customer_id
ORDER BY o.id;
Ответ PostgreSQL
 order_id |   full_name  |      phone
----------+--------------+------------------
        1 | Алиса Ким    | +7-701-555-00-00
        2 | Тимур Омаров | +7-702-444-55-66
        3 | Алиса Ким    | +7-701-555-00-00
(3 rows)

А если Тимур отменит свой заказ № 2 (DELETE FROM shop_orders WHERE id = 2), то удалятся только шапка заказа и его позиции, а сам Тимур в shop_customers и термокружка в shop_products останутся на месте — аномалия удаления тоже побеждена!

Хитрость из реальных магазинов: Заметил, что цена товара лежит и в shop_products.price, и в shop_order_items.unit_price? Это не ошибка нормализации! В каталоге хранится текущая цена товара, а в строке заказа — историческая цена на момент покупки. Если завтра худи подорожает до 16 000, старый чек Алисы останется честным.
Не доводи до абсурда: Бывает «перенормализация», когда разработчики выносят в отдельные таблицы даже имена и фамилии или названия улиц. Каждый лишний JOIN усложняет запросы. Золотой стандарт для обычных веб-приложений — остановиться на 3НФ и дробить таблицу только тогда, когда данные действительно повторяются и меняются независимо.

03 Связь «многие-ко-многим» (M:N) и таблица-мостик

Подумай о школьных кружках: один ученик может ходить и на робототехнику, и на шахматы. При этом в кружок робототехники ходит 15 разных учеников. Или возьмём теги в нашем магазине мерча: у «Худи SQL Master» сразу два тега — #хит и #одежда, а тег #хит приклеен ещё и к стикерпаку.

Как сохранить такую связь в базе? Если добавить колонку tag_id прямо в таблицу товаров shop_products, то у каждого товара сможет быть только один тег. Если добавить product_id в таблицу тегов tags, то каждый тег достанется только одному товару. А писать теги через запятую нам уже запретила 1НФ!

Выход гениально прост: поставить между двумя таблицами третью — связующую таблицу, или таблицу-мостик (Junction Table / Bridge Table). Она превращает одну сложную связь «многие-ко-многим» (Many-to-Many, M:N) в две простые связи «один-ко-многим» (1:N).

Кстати, ты уже незаметно построил одну таблицу-мостик пару минут назад! Посмотри на shop_order_items из Примера 2: один заказ содержит много товаров, а один товар попадает во много заказов. Разница лишь в том, что у shop_order_items есть дополнительные поля самой связи (quantity, unit_price), а у чистой таблицы тегов — только два ключа.

Давай добавим в нашу learning_db справочник tags и таблицу-мостик product_tags.

SQL · Пример 4: Реализуем связь M:N для тегов товаров 
-- Справочник уникальных тегов
CREATE TABLE tags (
    id   INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(50) NOT NULL UNIQUE
);

-- Таблица-мостик: составной PRIMARY KEY запрещает вешать один и тот же тег дважды
CREATE TABLE product_tags (
    product_id INT NOT NULL REFERENCES shop_products(id) ON DELETE CASCADE,
    tag_id     INT NOT NULL REFERENCES tags(id)          ON DELETE CASCADE,
    PRIMARY KEY (product_id, tag_id)
);

-- Добавляем теги
INSERT INTO tags (name) VALUES
    ('хит'),      -- id = 1
    ('новинка'),  -- id = 2
    ('одежда'),   -- id = 3
    ('подарок');  -- id = 4

-- Привязываем теги к товарам (у блокнота №5 тегов пока нет — это пригодится в Уроке 2.2!)
INSERT INTO product_tags (product_id, tag_id) VALUES
    (1, 1), (1, 3),  -- Худи: хит, одежда
    (2, 1), (2, 4),  -- Стикерпак: хит, подарок
    (3, 2), (3, 4),  -- Термокружка: новинка, подарок
    (4, 2), (4, 3);  -- Кепка: новинка, одежда

-- Выводим все товары с их тегами
SELECT p.title AS product, t.name AS tag
FROM shop_products p
JOIN product_tags pt ON pt.product_id = p.id
JOIN tags         t  ON t.id = pt.tag_id
ORDER BY p.id, t.name;

Как база сама защищает мостик от мусора

В таблице product_tags работают сразу два телохранителя: составной PRIMARY KEY (product_id, tag_id) и внешние ключи REFERENCES. Попробуем специально сломать оба правила — повесить тег #хит на худи во второй раз и привязать несуществующий тег № 999.

SQL · Пример 5: Проверяем защиту таблицы-мостика 
-- Попытка 1: дубликат пары (товар 1, тег 1)
INSERT INTO product_tags (product_id, tag_id) VALUES (1, 1);

-- Попытка 2: несуществующий tag_id = 999
INSERT INTO product_tags (product_id, tag_id) VALUES (1, 999);
Ошибка PostgreSQL · Попытка 1 (дубликат в составном ключе)
ERROR:  duplicate key value violates unique constraint "product_tags_pkey"
DETAIL:  Key (product_id, tag_id)=(1, 1) already exists.
Ошибка PostgreSQL · Попытка 2 (битая ссылка)
ERROR:  insert or update on table "product_tags" violates foreign key constraint "product_tags_tag_id_fkey"
DETAIL:  Key (tag_id)=(999) is not present in table "tags".

Видишь, как здорово? Тебе не нужно молиться, чтобы программист на сайте не забыл проверку в коде — сам PostgreSQL намертво пресечёт и дубликаты, и «висячие» ссылки в никуда. А благодаря ON DELETE CASCADE, если ты удалишь тег #новинка, все его строчки в product_tags подчистятся автоматически.

Совет по именованию: Называй таблицу-мостик склейкой двух сущностей — product_tags, student_clubs, user_roles. Любой коллега за секунду поймёт, что это связь M:N, даже не заглядывая в схему!

04 Основы миграций схемы БД: ремонт в живом доме

Когда ты делаешь учебный проект один, легко написать DROP TABLE и создать всё заново. Но представь, что твой магазин уже работает полгода: в базе 50 000 живых заказов и 10 000 покупателей. Сносить таблицы нельзя — ты потеряешь все деньги и историю клиентов! При этом бизнес просит добавить новую колонку, например артикул товара sku.

Это похоже на ремонт в доме, где прямо сейчас живут люди, или на систему сохранений в компьютерной игре: ты фиксируешь каждое изменение структуры базы в отдельном пронумерованном файле-шаге. Такой файл называется миграцией схемы БД (Database Schema Migration).

Зачем нужны файлы миграций вместо того, чтобы просто «покликать мышкой» в программе или вручную набрать пару команд? Потому что твой код запускается минимум в трёх местах: у тебя на ноутбуке, у напарника по команде и на боевом сервере (production). Когда все изменения лежат в пронумерованных SQL-файлах рядом с кодом в Git, на любом компьютере база собирается в точности до запятой одинаково.

Классическая ловушка: добавляем NOT NULL в непустую таблицу

Допустим, мы хотим добавить обязательный уникальный артикул sku в уже заполненную таблицу shop_products. Что произойдёт, если сделать это «в лоб» одной командой? Давай проверим!

SQL · Пример 6: Наивная миграция, которая падает с ошибкой 
-- Пытаемся сразу добавить обязательную колонку без значения по умолчанию
ALTER TABLE shop_products
ADD COLUMN sku VARCHAR(30) NOT NULL;
Ошибка PostgreSQL
ERROR:  column "sku" of relation "shop_products" contains null values

PostgreSQL абсолютно прав: в таблице уже лежат 5 товаров, и база понятия не имеет, какой артикул записать им прямо сейчас, а оставить пустоту (NULL) ты сам ей запретил!

✗ Как НЕ надо
-- Сразу NOT NULL без BEGIN:
ALTER TABLE shop_products
  ADD COLUMN sku VARCHAR(30)
  NOT NULL;

Запрос падает на непустой таблице. А если в скрипте 5 команд без транзакции и 3-я упала — база застрянет «наполовину переделанной».

✓ Как правильно
BEGIN;
ALTER TABLE shop_products
  ADD COLUMN sku VARCHAR(30);
UPDATE shop_products
  SET sku = 'MERCH-' || id;
ALTER TABLE shop_products
  ALTER COLUMN sku
  SET NOT NULL;
COMMIT;

Три безопасных шага в транзакции: 1) добавить nullable-колонку, 2) заполнить старые строки (backfill), 3) затянуть гайки (NOT NULL, UNIQUE).

Пишем настоящую транзакционную миграцию в learning_db

Одно из суперсвойств PostgreSQL — транзакционный DDL: если внутри BEGIN; ... COMMIT; на десятой строчке случится ошибка, откатятся даже команды CREATE TABLE и ALTER TABLE! База останется целой и невредимой, как будто ничего не запускали.

Создадим сначала служебную таблицу schema_migrations (журнал применённых версий), а затем выполним безопасную UP-миграцию 001_add_product_sku.up.sql.

SQL · Пример 7: Журнал версий + безопасная UP-миграция 001 
-- Шаг 0: создаём журнал применённых миграций (один раз на всю базу)
CREATE TABLE IF NOT EXISTS schema_migrations (
    version    VARCHAR(100) PRIMARY KEY,
    applied_at TIMESTAMP NOT NULL DEFAULT NOW()
);

-- === Миграция 001_add_product_sku.up.sql ===
BEGIN;

-- 1. Добавляем колонку пока БЕЗ ограничения NOT NULL
ALTER TABLE shop_products
    ADD COLUMN sku VARCHAR(30);

-- 2. Заполняем существующие строки (backfill): MERCH-0001, MERCH-0002...
UPDATE shop_products
SET sku = 'MERCH-' || LPAD(id::TEXT, 4, '0')
WHERE sku IS NULL;

-- 3. Теперь, когда пустых ячеек нет, включаем NOT NULL и уникальность
ALTER TABLE shop_products
    ALTER COLUMN sku SET NOT NULL,
    ADD CONSTRAINT shop_products_sku_unique UNIQUE (sku);

-- 4. Отмечаем в журнале, что миграция 001 успешно применена
INSERT INTO schema_migrations (version)
VALUES ('001_add_product_sku');

COMMIT;

-- Проверяем обновлённый каталог товаров и журнал миграций
SELECT id, title, sku, price FROM shop_products ORDER BY id;
SELECT * FROM schema_migrations;

Два главных вопроса: повторный запуск и откат (DOWN-миграция)

У внимательного инженера сразу появляются два вопроса:

  • Что будет, если случайно запустить файл 001 второй раз? В нашей транзакции PostgreSQL сразу увидит, что колонка sku уже существует (а в конце ещё и ключ '001_add_product_sku' в schema_migrations уже занят), выдаст ошибку и аккуратно откатит всю транзакцию — база не сломается. А настоящие инструменты миграций (Flyway, Goose, Alembic) вообще сначала заглядывают в schema_migrations и просто пропускают все файлы, которые там уже отмечены.
  • Как вернуть всё обратно, если передумал? Для этого рядом с файлом .up.sql хранят парный файл отката .down.sql, который отменяет изменения в строго обратном порядке:
SQL · Пример файла отката 001_add_product_sku.down.sql (для справки) 
-- Не запускай сейчас, если хочешь оставить колонку sku в learning_db!
BEGIN;

-- Удаляем ограничение и колонку в обратном порядке
ALTER TABLE shop_products
    DROP CONSTRAINT IF EXISTS shop_products_sku_unique,
    DROP COLUMN IF EXISTS sku;

-- Убираем отметку из журнала версий
DELETE FROM schema_migrations
WHERE version = '001_add_product_sku';

COMMIT;

А если сохранить UP-миграцию в файл migrations/001_add_product_sku.up.sql рядом с твоим docker-compose.yaml, то применить её к контейнеру PostgreSQL из терминала можно одной аккуратной командой:

Bash · Применение файла миграции в Docker 
# Флаг ON_ERROR_STOP=1 заставит psql немедленно остановиться при любой ошибке
docker exec -i course_pg_primary psql -U student -d learning_db \
  -v ON_ERROR_STOP=1 < migrations/001_add_product_sku.up.sql
Золотое правило миграций: Никогда не редактируй файл миграции, который уже применился на сервере или у коллег! Если допустил опечатку или передумал — создавай новую миграцию 002_...up.sql. И будь предельно осторожен с DROP COLUMN в DOWN-миграциях на живом проекте: удалить колонку легко, а вот вернуть стёртые данные можно только из резервной копии (бэкапа).

05 Шпаргалка перед практикой

Прежде чем писать CREATE TABLE в задачах ниже, задай своей будущей таблице три быстрых вопроса:

  1. Есть ли в ячейке список через запятую или колонки item_1, item_2? → Если да, выноси в отдельные строки (1НФ).
  2. У таблицы составной ключ из двух ID, но какая-то колонка описывает только один из них? → Если да, переноси её в собственный справочник (2НФ).
  3. Зависит ли колонка Б от колонки А, хотя ни А, ни Б не являются ключом? → Если да, выноси пару (А, Б) в отдельную таблицу-справочник (3НФ).
Термин Короткий перевод на человеческий
Атомарность (1НФ) В одной ячейке лежит одно неделимое значение, а не список.
Составной ключ Первичный ключ из двух и более колонок сразу, например PRIMARY KEY (order_id, product_id).
Транзитивная зависимость Цепочка через посредника: клиент → город → часовой пояс (убираем в 3НФ).
Таблица-мостик (M:N) Промежуточная таблица, хранящая пары внешних ключей для связи «многие-ко-многим».
Backfill Заполнение пустых значений в уже существующих строках перед включением NOT NULL.
UP / DOWN миграция Пара SQL-файлов: первый двигает схему вперёд, второй умеет аккуратно откатить шаг назад.

06 Мини-практикум для закрепления

Запусти свою базу learning_db (через docker compose up -d) и попробуй решить 4 задачи разной сложности. Каждая задача полностью автономна — не подглядывай в спойлер, пока не проверишь свой вариант в psql!

Задание 1 (Базовое). Наводим порядок в школьной библиотеке (1НФ–3НФ)

В библиотеке хранят записи в одной «плохой» таблице: (loan_id, student_name, class_name, homeroom_teacher, books_list), где в books_list через запятую записаны взятые книги, а у каждого класса свой классный руководитель (homeroom_teacher). Спроектируй и создай в learning_db чистую схему в 3НФ из 5 таблиц с первичными и внешними ключами.

Показать решение
SQL · Эталонное решение 
DROP TABLE IF EXISTS loan_books, loans, books, school_students, school_classes CASCADE;

-- 3НФ: классный руководитель зависит от класса, а не от конкретного ученика
CREATE TABLE school_classes (
    id               INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name             VARCHAR(10)  NOT NULL UNIQUE, -- например, '9А'
    homeroom_teacher VARCHAR(120) NOT NULL
);

CREATE TABLE school_students (
    id        INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL,
    class_id  INT NOT NULL REFERENCES school_classes(id)
);

-- 2НФ: справочник книг хранится отдельно от фактов выдачи
CREATE TABLE books (
    id     INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title  VARCHAR(200) NOT NULL,
    author VARCHAR(120) NOT NULL
);

CREATE TABLE loans (
    id         INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    student_id INT  NOT NULL REFERENCES school_students(id),
    loan_date  DATE NOT NULL DEFAULT CURRENT_DATE
);

-- 1НФ + M:N: каждая книга в выдаче — отдельная строка (таблица-мостик)
CREATE TABLE loan_books (
    loan_id INT NOT NULL REFERENCES loans(id) ON DELETE CASCADE,
    book_id INT NOT NULL REFERENCES books(id),
    PRIMARY KEY (loan_id, book_id)
);
Задание 2 (Среднее). Школьные кружки и таблица-мостик (M:N)

Создай три таблицы для системы школьных кружков: club_students (id, full_name), clubs (id, title) и таблицу-мостик student_clubs. Добавь в мостик колонку joined_at DATE DEFAULT CURRENT_DATE и запрети записывать одного ученика в один и тот же кружок дважды. Добавь 2 учеников, 3 кружка, запиши учеников в несколько кружков и выведи список пар «ученик — кружок — дата записи».

Показать решение
SQL · Эталонное решение 
DROP TABLE IF EXISTS student_clubs, clubs, club_students CASCADE;

CREATE TABLE club_students (
    id        INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name VARCHAR(120) NOT NULL
);

CREATE TABLE clubs (
    id    INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title VARCHAR(100) NOT NULL UNIQUE
);

-- Таблица-мостик с дополнительным полем joined_at и защитой от дублей
CREATE TABLE student_clubs (
    student_id INT  NOT NULL REFERENCES club_students(id) ON DELETE CASCADE,
    club_id    INT  NOT NULL REFERENCES clubs(id)         ON DELETE CASCADE,
    joined_at  DATE NOT NULL DEFAULT CURRENT_DATE,
    PRIMARY KEY (student_id, club_id)
);

INSERT INTO club_students (full_name) VALUES
    ('Данияр Беков'),
    ('София Ли');

INSERT INTO clubs (title) VALUES
    ('Робототехника'),
    ('Шахматы'),
    ('Геймдев');

INSERT INTO student_clubs (student_id, club_id) VALUES
    (1, 1), (1, 3),
    (2, 1), (2, 2);

SELECT s.full_name, c.title AS club, sc.joined_at
FROM club_students s
JOIN student_clubs sc ON sc.student_id = s.id
JOIN clubs         c  ON c.id = sc.club_id
ORDER BY s.full_name, c.title;
Задание 3 (Среднее+). Безопасная миграция 002 с заполнением старых строк

Напиши транзакционную миграцию 002_add_customer_loyalty для таблицы shop_customers: добавь колонку loyalty_level VARCHAR(20), заполни всем текущим покупателям значение 'bronze', установи ограничение NOT NULL, значение по умолчанию 'bronze' и проверку CHECK (loyalty_level IN ('bronze', 'silver', 'gold')). Запиши факт выполнения в schema_migrations.

Показать решение
SQL · Эталонное решение 
BEGIN;

-- 1. Добавляем колонку без NOT NULL
ALTER TABLE shop_customers
    ADD COLUMN loyalty_level VARCHAR(20);

-- 2. Заполняем старые строки (backfill)
UPDATE shop_customers
SET loyalty_level = 'bronze'
WHERE loyalty_level IS NULL;

-- 3. Включаем NOT NULL, DEFAULT и проверку допустимых уровней
ALTER TABLE shop_customers
    ALTER COLUMN loyalty_level SET DEFAULT 'bronze',
    ALTER COLUMN loyalty_level SET NOT NULL,
    ADD CONSTRAINT shop_customers_loyalty_check
        CHECK (loyalty_level IN ('bronze', 'silver', 'gold'));

-- 4. Фиксируем миграцию в журнале
INSERT INTO schema_migrations (version)
VALUES ('002_add_customer_loyalty');

COMMIT;

-- Проверка результата
SELECT id, full_name, loyalty_level FROM shop_customers;
Задание 4 (Продвинутое). Разбираем «грязную» строку в 1НФ прямо в SQL

Помнишь таблицу bad_orders_sheet из Примера 1, где в items_list товары склеены через запятую ('Худи SQL, Стикерпак')? Напиши SELECT-запрос, который превратит её в вид 1НФ — чтобы каждый товар оказался в отдельной строке рядом со своим order_id и customer_name.
Подсказка: в PostgreSQL для разрезания текста по разделителю в отдельные строки отлично работает связка TRIM(unnest(string_to_array(items_list, ','))).

Показать решение
SQL · Эталонное решение 
-- Разрезаем строку по запятой в массив, разворачиваем в строки и убираем пробелы по краям
SELECT
    order_id,
    customer_name,
    TRIM(unnest(string_to_array(items_list, ','))) AS item_name
FROM bad_orders_sheet
ORDER BY order_id, item_name;
