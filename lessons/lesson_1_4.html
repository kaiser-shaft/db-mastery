Урок 1.4: Изменение и удаление данных (UPDATE, DELETE) и первое объединение таблиц (INNER JOIN)

Главное в этом уроке
  • Научишься точечно и массово менять строки через UPDATE и сразу видеть результат с помощью фишки PostgreSQL — RETURNING.
  • Освоишь безопасное удаление через DELETE, поймёшь, как FOREIGN KEY страхует базу от поломки, и узнаешь про «мягкое удаление» (soft delete).
  • Разберёшься, как склеивать две и три связанные таблицы в один понятный отчёт с помощью INNER JOIN и псевдонимов таблиц.
  • Закроешь полный цикл CRUD (Create, Read, Update, Delete) — фундамент любого веб-приложения и бэкенда.

01 Подготовка связанных таблиц и редактирование через UPDATE

В жизни ни один магазин не застывает во времени: сегодня привезли новую партию ковриков для мыши, завтра объявили распродажу на одежду, а старый тестовый товар нужно вообще убрать с витрины. Кроме того, хранить название категории и имя её менеджера текстом в каждой строчке товара неудобно — если менеджер сменится, пришлось бы переписывать тысячи строк.

Поэтому в этом уроке мы вынесем категории в отдельную таблицу categories и свяжем с ней products через внешний ключ category_id. Запусти этот блок подготовки в своей базе learning_db, чтобы стартовые данные точно совпали со всеми примерами.

SQL · Подготовка связанных таблиц categories и products 
-- Удаляем старые таблицы в правильном порядке (сначала зависимые)
DROP TABLE IF EXISTS orders;
DROP TABLE IF EXISTS products;
DROP TABLE IF EXISTS categories;

CREATE TABLE categories (
  id      INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name    TEXT NOT NULL UNIQUE,
  manager TEXT NOT NULL
);

CREATE TABLE products (
  id          INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title       TEXT NOT NULL,
  category_id INT REFERENCES categories(id), -- может быть NULL у черновиков
  price       NUMERIC(10, 2) NOT NULL CHECK (price > 0),
  stock       INT NOT NULL DEFAULT 0 CHECK (stock >= 0),
  is_active   BOOLEAN NOT NULL DEFAULT true
);

INSERT INTO categories (name, manager) VALUES
  ('Одежда',          'Алина'),
  ('Аксессуары',      'Тимур'),
  ('Книги',           'Алина'),
  ('Гаджеты',         'Даниил'),
  ('Настольные игры', 'Тимур'); -- пока без единого товара!

INSERT INTO products (title, category_id, price, stock, is_active) VALUES
  ('Худи «SQL Master»',          1, 14500.00,  12, true),
  ('Футболка «SELECT *»',        1,  5900.00,  25, true),
  ('Стикерпак «Postgres»',       2,  1200.00, 100, true),
  ('Термокружка кодера',         2,  6900.00,   8, true),
  ('Книга «SQL за 7 дней»',      3,  4200.00,  14, true),
  ('Коврик для мыши XL',         2,  3500.00,   0, true),
  ('Клавиатура «MechPro»',       4, 18900.00,   3, true),
  ('Секретный мерч (черновик)', NULL, 990.00,   0, false),
  ('Тестовый баг-товар',         2,   100.00,   0, false);

Как работает UPDATE: переклеиваем ценник на полке

Команда UPDATE похожа на работу продавца в магазине, которому сказали: «Найди товар №6, допиши к остатку +15 штук и переклей ценник на 3900». Тебе не нужно удалять строку и вставлять её заново — ты просто указываешь таблицу (UPDATE), какие колонки поменять (SET) и к каким именно строкам это относится (WHERE).

А в конце в PostgreSQL можно дописать суперполезное слово RETURNING — тогда база не просто сухо ответит UPDATE 1, а сразу вернёт тебе обновлённые строки, чтобы ты глазами убедился, что всё сработало идеально.

SQL · Пример 1: точечное обновление товара и просмотр через RETURNING 
-- На склад привезли 15 ковриков (id = 6), а цена выросла до 3900
UPDATE products
SET stock = stock + 15,
    price = 3900.00
WHERE id = 6
RETURNING id, title, price, stock;
Ответ PostgreSQL
 id |       title        |  price  | stock
----+--------------------+---------+-------
  6 | Коврик для мыши XL | 3900.00 |    15
(1 row)

UPDATE 1

А теперь давай устроим массовую акцию: снизим цену на 10% сразу для всей одежды (category_id = 1). Внутри SET можно смело использовать текущее значение колонки и математические функции вроде ROUND().

SQL · Пример 2: массовая скидка 10% на категорию «Одежда» 
-- Уменьшаем цену всех товаров из категории 1 (Одежда) на 10%
UPDATE products
SET price = ROUND(price * 0.9, 2)
WHERE category_id = 1
RETURNING id, title, price;
Ответ PostgreSQL
 id |        title        |  price
----+---------------------+----------
  1 | Худи «SQL Master»   | 13050.00
  2 | Футболка «SELECT *» |  5310.00
(2 rows)

UPDATE 2

Помнишь ограничения CHECK из Урока 1.2? Они бдительно дежурят не только при вставке INSERT, но и при каждом UPDATE. Если кто-то случайно попробует поставить отрицательную цену (SET price = -100), PostgreSQL остановит запрос и оставит старые данные в полной сохранности.

SQL · Проверка защиты: попытка записать отрицательную цену 
UPDATE products
SET price = -100.00
WHERE id = 3;
Ошибка PostgreSQL
ERROR:  new row for relation "products" violates check constraint "products_price_check"
DETAIL:  Failing row contains (3, Стикерпак «Postgres», 2, -100.00, 100, t).
✗ Как НЕ надо
-- ЗАБЫЛИ WHERE!
UPDATE products
SET price = 1.00;

Катастрофа! Без WHERE PostgreSQL молча выставит цену 1 рубль абсолютно всем товарам в магазине. Настоящий кошмар начинающего разработчика.

✓ Как правильно
-- 1) Сначала проверяем SELECT-ом
SELECT id, title, price
FROM products WHERE id = 3;

-- 2) Потом меняем ровно это
UPDATE products
SET price = 1500.00
WHERE id = 3
RETURNING id, title, price;

Привычка сначала запускать SELECT с тем же WHERE спасает базы данных в самых ответственных проектах.

02 Удаление записей (DELETE), охрана FOREIGN KEY и «мягкое удаление»

Если UPDATE — это правка карандашом и ластиком, то DELETE — это настоящий шредер для бумаг. Как только ты удалил строку и транзакция завершилась, кнопки «Ctrl+Z» в SQL нет. Поэтому правило «семь раз проверь WHERE, один раз нажми Enter» здесь ещё строже.

У нас в таблице болтается мусорная строка №9 — 'Тестовый баг-товар'. Давай аккуратно отправим её в шредер и попросим базу через RETURNING подтвердить, кого именно она удалила.

SQL · Пример 3: точечное удаление тестовой записи 
-- Удаляем строго тестовую строку по уникальному id
DELETE FROM products
WHERE id = 9
RETURNING id, title;
Ответ PostgreSQL
 id |       title
----+--------------------
  9 | Тестовый баг-товар
(1 row)

DELETE 1

Что будет, если удалить категорию, на которую ссылаются товары?

Представь школьную библиотеку: кто-то решил выбросить из каталога раздел «Книги» (id = 3), хотя на этой полке прямо сейчас стоит «Книга «SQL за 7 дней»». Чтобы в базе не появились «висящие в воздухе» ссылки на несуществующие категории, включается охранник FOREIGN KEY — и жёстко блокирует удаление!

SQL · Попытка удалить категорию «Книги», у которой есть товары 
DELETE FROM categories
WHERE id = 3;
Ошибка PostgreSQL
ERROR:  update or delete on table "categories" violates foreign key constraint "products_category_id_fkey" on table "products"
DETAIL:  Key (id)=(3) is still referenced from table "products".

Смотри, как вежливо и точно PostgreSQL объясняет проблему в строчке DETAIL: ключ (id)=(3) всё ещё используется в таблице products. А вот категорию 'Настольные игры' (id = 5), к которой не привязан ни один товар, удалить можно без проблем (мы сделаем это в практикуме, а пока оставим её для опытов с INNER JOIN!).

Совет на будущее — «мягкое удаление» (Soft Delete): В настоящих интернет-магазинах, банках и играх строки редко удаляют физически через DELETE. Если товар сняли с продажи, но его уже кто-то покупал месяц назад, удаление сломает историю заказов! Вместо этого делают флаг is_active = false (или колонку deleted_at) через UPDATE, а на витрине просто фильтруют WHERE is_active = true.

03 Первое объединение таблиц: магия INNER JOIN

Если ты сейчас сделаешь SELECT id, title, category_id FROM products, то вместо понятных названий категорий увидишь сухие цифры: 1, 2, 3, 4. Компьютеру с цифрами удобно, а вот человеку на сайте нужно видеть «Одежда» и имя ответственного менеджера — «Алина».

Чтобы собрать полную картину из двух таблиц, в SQL существует команда INNER JOIN (внутреннее соединение). Представь себе школьный вечер танцев или сборку пазла: каждая строка из левой таблицы (products) ищет себе пару в правой таблице (categories) по общему ключу — условию ON p.category_id = c.id.

  • Нашлась пара? Отлично — обе строчки склеиваются в одну длинную строку и попадают в результат!
  • Пары нет? INNER JOIN работает строго: одиночки в финальный список не попадают. Поэтому наш черновик 'Секретный мерч' (у которого category_id IS NULL) и пустая категория 'Настольные игры' (у которой 0 товаров) останутся за кадром.

Чтобы не писать каждый раз длинные названия таблиц products.title и categories.name, им дают короткие псевдонимы прямо в запросе: products AS p и categories AS c (слово AS для таблиц даже можно опускать, но для ясности на старте его удобно писать).

SQL · Пример 4: склеиваем товары и категории через INNER JOIN 
-- Склеиваем каждую строку товара (p) с её категорией (c)
SELECT
  p.id,
  p.title,
  c.name AS category_name,
  c.manager,
  p.price
FROM products AS p
INNER JOIN categories AS c
  ON p.category_id = c.id
ORDER BY p.id ASC;
Ответ PostgreSQL
 id |         title         | category_name | manager |  price
----+-----------------------+---------------+---------+----------
  1 | Худи «SQL Master»     | Одежда        | Алина   | 13050.00
  2 | Футболка «SELECT *»   | Одежда        | Алина   |  5310.00
  3 | Стикерпак «Postgres»  | Аксессуары    | Тимур   |  1200.00
  4 | Термокружка кодера    | Аксессуары    | Тимур   |  6900.00
  5 | Книга «SQL за 7 дней» | Книги         | Алина   |  4200.00
  6 | Коврик для мыши XL    | Аксессуары    | Тимур   |  3900.00
  7 | Клавиатура «MechPro»  | Гаджеты       | Даниил  | 18900.00
(7 rows)

Обрати внимание: в таблице products осталось 8 товаров (после удаления тестового №9), а запрос вернул 7 строк. Товар №8 ('Секретный мерч (черновик)') не прошёл, потому что его category_id равен NULL, а NULL = id никогда не бывает TRUE!

Классическая ошибка новичка при JOIN: «двусмысленная колонка»

Если в обеих склеиваемых таблицах есть колонка с одинаковым именем — например, id есть и в products, и в categories — нельзя просто написать SELECT id. PostgreSQL остановится и вежливо спросит: «А какой именно id тебе нужен — товара или категории?».

SQL · Забыли указать префикс таблицы перед общей колонкой id 
SELECT id, title, name
FROM products AS p
INNER JOIN categories AS c ON p.category_id = c.id;
Ошибка PostgreSQL
ERROR:  column reference "id" is ambiguous
LINE 1: SELECT id, title, name
               ^

Лечится за секунду: в запросах с JOIN всегда пиши перед каждой колонкой префикс псевдонима (p.id, p.title, c.name). Так и база никогда не запутается, и другой программист мгновенно поймёт, из какой таблицы взято каждое поле.

04 Комбинируем всё вместе: JOIN + WHERE + третья таблица

После того как таблицы соединились на шаге FROM ... INNER JOIN ..., для PostgreSQL они превращаются в одну большую виртуальную таблицу. А значит, ты можешь применять к ней абсолютно все инструменты из Урока 1.3: фильтровать по колонкам обеих таблиц в WHERE, сортировать в ORDER BY и ограничивать через LIMIT!

SQL · Пример 5: активные товары менеджера Алины дешевле 15 000 
-- Фильтруем одновременно по колонке из categories (c.manager)
-- и по колонкам из products (p.is_active, p.price)
SELECT
  p.title,
  c.name AS category_name,
  p.price,
  p.stock
FROM products AS p
INNER JOIN categories AS c
  ON p.category_id = c.id
WHERE c.manager = 'Алина'
  AND p.is_active = true
  AND p.price < 15000
ORDER BY p.price DESC;
Ответ PostgreSQL
         title         | category_name |  price   | stock
-----------------------+---------------+----------+-------
 Худи «SQL Master»     | Одежда        | 13050.00 |    12
 Футболка «SELECT *»   | Одежда        |  5310.00 |    25
 Книга «SQL за 7 дней» | Книги         |  4200.00 |    14
(3 rows)

Собираем паровозик из трёх таблиц: заказы → товары → категории

На практике почти никогда не ограничиваются двумя таблицами. Представь, что в наш магазин начали приходить заказы от покупателей. Давай создадим таблицу orders, которая ссылается на products, и соберём красивый финансовый отчёт по всем оплаченным заказам — сразу с названием товара, его категорией и итоговой суммой!

SQL · Подготовка третьей таблицы orders 
CREATE TABLE orders (
  id         INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer   TEXT NOT NULL,
  product_id INT NOT NULL REFERENCES products(id),
  qty        INT NOT NULL CHECK (qty > 0),
  status     TEXT NOT NULL DEFAULT 'new'
);

INSERT INTO orders (customer, product_id, qty, status) VALUES
  ('Максим', 1, 1, 'paid'),
  ('София',  3, 5, 'paid'),
  ('Артём',  7, 1, 'new'),
  ('София',  5, 2, 'paid');

Объединение трёх таблиц выглядит как цепочка конструктора LEGO: сначала к orders пристёгиваем products по o.product_id = p.id, а затем к получившейся связке пристёгиваем categories по p.category_id = c.id.

SQL · Пример 6: отчёт по оплаченным заказам из 3 таблиц 
-- Склеиваем orders -> products -> categories и считаем сумму каждого заказа
SELECT
  o.id AS order_id,
  o.customer,
  p.title,
  c.name AS category,
  o.qty,
  p.price * o.qty AS total_sum
FROM orders AS o
INNER JOIN products AS p
  ON o.product_id = p.id
INNER JOIN categories AS c
  ON p.category_id = c.id
WHERE o.status = 'paid'
ORDER BY total_sum DESC;
Ответ PostgreSQL
 order_id | customer |         title         |  category  | qty | total_sum
----------+----------+-----------------------+------------+-----+-----------
        1 | Максим   | Худи «SQL Master»     | Одежда     |   1 |  13050.00
        4 | София    | Книга «SQL за 7 дней» | Книги      |   2 |   8400.00
        2 | София    | Стикерпак «Postgres»  | Аксессуары |   5 |   6000.00
(3 rows)
✗ Как НЕ надо
-- Устаревший стиль через запятую
-- Если забыть условие связи в WHERE,
-- каждый товар умножится на каждую категорию!
SELECT p.title, c.name
FROM products p, categories c;

Такой запрос создаст декартово произведение (8 × 5 = 40 бессмысленных строк, где «Худи» окажется в категории «Книги» и «Гаджеты»).

✓ Как правильно
-- Современный явный INNER JOIN ... ON
SELECT p.title, c.name
FROM products AS p
INNER JOIN categories AS c
  ON p.category_id = c.id;

Условие склейки всегда чётко отделено в ON, а бизнес-фильтры живут в WHERE. Забыть ON синтаксис SQL просто не позволит!

Частая ошибка: Не путай простое слово JOIN с «каким-то другим типом соединения». В PostgreSQL (и стандарте SQL) короткая запись JOIN — это точный синоним INNER JOIN. Пока ты учишься, лучше писать INNER JOIN полностью, чтобы всегда помнить: строки без пары будут отброшены.

05 Мини-практикум для закрепления

Выполни 4 задания в своей базе learning_db на таблицах categories, products и orders. Не торопись открывать спойлер — сначала попробуй написать запрос самостоятельно и проверь ответ в psql.

Задание 1 (Базовое · UPDATE). Подорожание гаджетов

Увеличь цену всех товаров из категории 'Гаджеты' (category_id = 4) ровно на 1000.00 рублей. С помощью RETURNING сразу выведи id, title и новую цену price.

Показать решение
SQL 
UPDATE products
SET price = price + 1000.00
WHERE category_id = 4
RETURNING id, title, price;
Задание 2 (Безопасное удаление · UPDATE и DELETE). Архивация и уборка

Выполни два отдельных запроса:
1) Сделай «мягкое удаление» товара 'Термокружка кодера' (id = 4) — переведи его колонку is_active в false и верни id, title, is_active.
2) Полностью удали из таблицы categories пустую категорию 'Настольные игры' (id = 5), вернув её id и name.

Показать решение
SQL 
-- 1. Мягкое удаление товара (история остаётся целой)
UPDATE products
SET is_active = false
WHERE id = 4
RETURNING id, title, is_active;

-- 2. Физическое удаление пустой категории (ссылок на неё нет, FK пропустит)
DELETE FROM categories
WHERE id = 5
RETURNING id, name;
Задание 3 (INNER JOIN + WHERE). История покупок Софии

Объедини таблицы orders и products, чтобы вывести все заказы покупателя 'София'. В результате покажи номер заказа (o.id), название товара (p.title), количество (o.qty) и статус (o.status). Отсортируй результат по номеру заказа по возрастанию.

Показать решение
SQL 
SELECT
  o.id AS order_id,
  p.title,
  o.qty,
  o.status
FROM orders AS o
INNER JOIN products AS p
  ON o.product_id = p.id
WHERE o.customer = 'София'
ORDER BY o.id ASC;
Задание 4 (Со звёздочкой · 3 таблицы + формула). Отчёт для менеджера Тимура

Склей три таблицы (orders, products, categories) и выведи все заказы товаров из категорий, за которые отвечает менеджер 'Тимур'. Покажи колонки: order_id (o.id), customer, title, category_name (c.name) и total_sum (p.price * o.qty). Отсортируй от самой большой суммы к меньшей.

Показать решение
SQL 
SELECT
  o.id AS order_id,
  o.customer,
  p.title,
  c.name AS category_name,
  p.price * o.qty AS total_sum
FROM orders AS o
INNER JOIN products AS p
  ON o.product_id = p.id
INNER JOIN categories AS c
  ON p.category_id = c.id
WHERE c.manager = 'Тимур'
ORDER BY total_sum DESC, o.id ASC;

А в следующем модуле мы выйдем на уровень настоящей аналитики: узнаем, как не терять строки без пары (например, пустые категории и товары без заказов) с помощью LEFT JOIN, и научимся считать выручку, средние чеки и отчёты через группировку GROUP BY и агрегатные функции!
