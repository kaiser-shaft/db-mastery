01 Откуда данные попадают в хранилище: ETL против ELT

Представь ресторан, в который фермер каждый день привозит свежие овощи. Есть два способа организовать доставку на кухню:

  • Старый способ — ETL (Extract → Transform → Load): Повара залезают прямо в кузов грузовика на дороге, там моют, чистят и режут картошку для супа, а очистки выбрасывают в окно. На кухню попадает уже нарезанная заготовка. Проблема: если завтра шеф-повар решит сделать запечённый картофель в кожуре, кожуру уже не вернуть — придётся снова ехать к фермеру!
  • Современный способ — ELT (Extract → Load → Transform): Водитель просто забирает ящики у фермера (Extract) и максимально быстро сгружает их в большую кладовку прямо как есть (Load). А уже внутри мощной кухни повара с помощью SQL-запросов моют, чистят и готовят из этих сырых запасов любые блюда (Transform). Если рецепт изменится, сырые овощи всегда под рукой в кладовке!

В современном хранилище данных (DWH) поток ELT почти всегда делят на три аккуратных слоя (схемы):

Критерий ETL (Преобразование в пути) ELT (Преобразование внутри DWH)
Где чистятся данные На отдельном сервере-обработчике до записи в DWH Прямо внутри DWH на чистом SQL (например, через dbt)
Если в формуле нашли баг Нужно заново выгружать сырые данные из боевой OLTP-базы Пересчитываем слой DWH из уже сохранённого слоя RAW
Скорость добавления нового отчёта Долго — нужно менять скрипты выгрузки Быстро — аналитик просто пишет новый SQL-запрос к RAW/DWH
Аналогия фотографа: Хранить слой RAW в базе — это как снимать на фотоаппарат в формате RAW, а не сразу в сжатый JPEG. Ты всегда можешь переделать цветокоррекцию (пересчитать формулу выручки), не переснимая кадр заново!

02 Идемпотентность: кнопка лифта вместо кнопки оплаты

Представь две кнопки из жизни. Первая — кнопка вызова лифта: нажмёшь ты на неё 1 раз или в нетерпении 10 раз подряд, результат будет одинаковым — приедет ровно один лифт. Вторая — кнопка «Перевести 5 000 тенге» в плохо написанном банке: если интернет моргнул и ты нажал её дважды, со счёта улетит 10 000 тенге!

В инженерии данных свойство «кнопки лифта» называется идемпотентностью (Idempotency): сколько бы раз ты ни запустил скрипт загрузки с одними и теми же входными данными (1 раз, 2 раза или 50 раз), итоговое состояние базы должно оставаться абсолютно одинаковым — без ошибок и без дубликатов.

Зачем это жизненно важно? Ночные ELT-конвейеры работают в 3 часа утра. Если на середине загрузки моргнёт сеть, планировщик (например, Apache Airflow) автоматически перезапустит задачу ещё раз. Если твой SQL-скрипт не идемпотентен, утром директор увидит в отчёте двойную выручку!

docker compose up -d
docker exec -it course_pg_primary psql -U student -d learning_db

Пример 1. Как ломается наивная (неидемпотентная) загрузка

Создадим учебную схему elt_lab со «складом входящих пачек» raw_orders и целевой таблицей dwh_orders. Попробуем загрузить пачку заказов обычным INSERT два раза подряд (имитируя повторный запуск после сбоя):

SQL · Подготовка elt_lab и повторный наивный INSERT 
DROP SCHEMA IF EXISTS elt_lab CASCADE;
CREATE SCHEMA elt_lab;

-- Слой RAW: входящая пачка заказов за январь
CREATE TABLE elt_lab.raw_orders (
    order_id    INT NOT NULL,
    order_date  DATE NOT NULL,
    customer_bk INT NOT NULL,
    amount      NUMERIC(10, 2) NOT NULL
);

-- Слой DWH: целевая таблица заказов с первичным ключом
CREATE TABLE elt_lab.dwh_orders (
    order_id    INT PRIMARY KEY,
    order_date  DATE NOT NULL,
    customer_bk INT NOT NULL,
    amount      NUMERIC(10, 2) NOT NULL
);

INSERT INTO elt_lab.raw_orders VALUES
    (101, '2026-01-10', 1, 35000.00),
    (102, '2026-01-15', 2, 22000.00),
    (103, '2026-01-20', 3, 18000.00);

-- Запуск №1: прошёл успешно
INSERT INTO elt_lab.dwh_orders
SELECT order_id, order_date, customer_bk, amount
FROM elt_lab.raw_orders;

-- Запуск №2 (повторный запуск после сбоя сети): падает с ошибкой!
INSERT INTO elt_lab.dwh_orders
SELECT order_id, order_date, customer_bk, amount
FROM elt_lab.raw_orders;
Ошибка PostgreSQL
ERROR:  duplicate key value violates unique constraint "dwh_orders_pkey"
DETAIL:  Key (order_id)=(101) already exists.

Хорошо ещё, что у нас стоял PRIMARY KEY — он хотя бы остановил загрузку! Если бы первичного ключа не было (как часто бывает в сырых таблицах), второй запуск тихо вставил бы ещё 3 копии тех же заказов, и выручка выросла бы с 75 000 до 150 000!

Пример 2. Делаем загрузку идемпотентной через UPSERT (ON CONFLICT DO UPDATE)

Представь, что пришла новая выгрузка: в заказе 102 применили скидку (сумма изменилась с 22 000 на 20 000), а ещё добавился новый заказ 104. Напишем идемпотентный запрос UPSERT (Update + Insert) и намеренно запустим его дважды подряд!

SQL · Идемпотентный UPSERT: двойной запуск без дубликатов 
-- Обновляем входящий буфер: заказ 102 исправлен, добавлен 104
TRUNCATE TABLE elt_lab.raw_orders;
INSERT INTO elt_lab.raw_orders VALUES
    (101, '2026-01-10', 1, 35000.00), -- без изменений
    (102, '2026-01-15', 2, 20000.00), -- сумма исправлена!
    (103, '2026-01-20', 3, 18000.00), -- без изменений
    (104, '2026-01-25', 1, 15000.00); -- новый заказ

-- Попытка №1: вставляет новые и обновляет изменившиеся заказы
INSERT INTO elt_lab.dwh_orders (order_id, order_date, customer_bk, amount)
SELECT order_id, order_date, customer_bk, amount
FROM elt_lab.raw_orders
ON CONFLICT (order_id) DO UPDATE
SET
    order_date  = EXCLUDED.order_date,
    customer_bk = EXCLUDED.customer_bk,
    amount      = EXCLUDED.amount
WHERE elt_lab.dwh_orders.amount IS DISTINCT FROM EXCLUDED.amount;

-- Попытка №2: запускаем ТОЧНО ТОТ ЖЕ запрос ещё раз!
INSERT INTO elt_lab.dwh_orders (order_id, order_date, customer_bk, amount)
SELECT order_id, order_date, customer_bk, amount
FROM elt_lab.raw_orders
ON CONFLICT (order_id) DO UPDATE
SET
    order_date  = EXCLUDED.order_date,
    customer_bk = EXCLUDED.customer_bk,
    amount      = EXCLUDED.amount
WHERE elt_lab.dwh_orders.amount IS DISTINCT FROM EXCLUDED.amount;

-- Проверяем результат: ни одной лишней строки, сумма точная!
SELECT COUNT(*) AS orders_cnt, SUM(amount) AS total_revenue
FROM elt_lab.dwh_orders;
Ответ PostgreSQL
 orders_cnt | total_revenue 
------------+---------------
          4 |      88000.00
(1 row)

Обрати внимание на строчку WHERE elt_lab.dwh_orders.amount IS DISTINCT FROM EXCLUDED.amount — это профессиональный штрих: PostgreSQL даже не тратит диск на перезапись тех строк, которые не изменились (в нашем случае 101 и 103)!

✗ Как НЕ надо
-- Без транзакции!
DELETE FROM dwh_orders
WHERE order_date = '2026-01-25';
-- БАХ! Упала сеть!
INSERT INTO dwh_orders ...;

Если скрипт упадёт между DELETE и INSERT, день 25 января пропадёт с дашбордов!

✓ Как правильно
-- Атомарный Delete-Insert
BEGIN;
DELETE FROM dwh_orders
WHERE order_date = '2026-01-25';
INSERT INTO dwh_orders ...;
COMMIT;

Внутри BEGIN ... COMMIT замена окна дат проходит целиком или никак — и при этом абсолютно идемпотентна.

Вернёмся к нашей задаче из начала раздела: теперь наш ELT-конвейер стал похож на кнопку лифта. Даже если ночной планировщик перезапустит загрузку пять раз подряд, данные останутся кристально чистыми.

03 Загадка переехавшего клиента: что такое SCD (Type 0, 1, 2)

А теперь представь детективную историю из жизни нашего интернет-магазина. В январе покупательница Айгерим жила в Костанае и купила клавиатуру за 35 000 тенге. Управляющий филиалом в Костанае честно получил за этот заказ премию.

А 1 февраля Айгерим переехала жить в Алматы, поменяла город в личном кабинете и купила худи за 22 000 тенге. Если в таблице измерений dim_customer мы просто сделаем обычный UPDATE SET city = 'Алматы', то в марте случится катастрофа: когда бухгалтерия заново откроет отчёт за январь, окажется, что Костанай в январе заработал 0 тенге, а вся январская покупка Айгерим чудесным образом «переехала» в Алматы!

Такие справочники, атрибуты которых меняются не каждую секунду, а изредка (город клиента, сегмент Standard → VIP, категория товара, тариф подписки), называются медленно меняющимися измерениями — SCD (Slowly Changing Dimensions). В DWH есть три классических способа обращаться с такими изменениями:

Тип SCD Как поступает с изменением Когда применять
SCD Type 0 (Неизменяемое) Вообще игнорирует изменения — хранит только самое первое значение Дата рождения, дата первой регистрации клиента
SCD Type 1 (Перезапись) Делает обычный UPDATE — старое значение стирается навсегда Исправление опечатки в имени (Айгеримм → Айгерим), когда история не нужна
SCD Type 2 (Полная история) Закрывает старую строку датой окончания и добавляет новую строку-версию Город клиента, тариф, сегмент, должность сотрудника — везде, где нужна правда о прошлом!

Посмотри, как выглядит судьба Айгерим в таблице SCD Type 2. Вместо одной строки у неё появляются две «серии» с разными суррогатными ключами (customer_sk) и чёткими границами действия valid_from — valid_to:

Зачем писать 9999-12-31 вместо NULL в valid_to? Если для активной строки оставить valid_to IS NULL, то простой и красивый запрос WHERE order_date BETWEEN valid_from AND valid_to перестанет находить актуальные записи! Условная «бесконечная дата» 9999-12-31 избавляет от лишних COALESCE в каждом отчёте.

04 Собираем живой конвейер SCD Type 2 в PostgreSQL

Давай проживём два дня из жизни нашего хранилища: 1 января (первая загрузка 3 клиентов) и 1 февраля (приходит новый снимок из OLTP с изменениями). Вот что должно произойти с каждым клиентом:

Клиент (customer_bk) Было 1 января Пришло 1 февраля Что сделает SCD Type 2
1 · Айгерим Сатова Костанай, VIP Алматы, VIP Закроет версию 1 (2026-01-31) и создаст версию 2
2 · Тимур Искаков Астана, Standard Астана, VIP Закроет версию 1 (2026-01-31) и создаст версию 2
3 · Елена Морозова Алматы, VIP Алматы, VIP Ничего не тронет! (Лишние версии не плодим)
4 · Данияр Алимов Не было Костанай, Standard Вставит новую активную запись с 2026-02-01

Пример 3. Создаём таблицу SCD Type 2 с защитой от двойных активных версий

Обрати внимание на частичный уникальный индекс (Partial Unique Index) в конце этого блока: он физически запрещает базе иметь одновременно две строки с is_current = true для одного и того же клиента!

SQL · Таблица dim_customer_scd2 и загрузка Дня 1 (2026-01-01) 
DROP TABLE IF EXISTS elt_lab.fact_sales_hist;
DROP TABLE IF EXISTS elt_lab.dim_customer_scd2;
DROP TABLE IF EXISTS elt_lab.raw_customers_stage;

-- Входящий буфер (снимок клиентов из OLTP)
CREATE TABLE elt_lab.raw_customers_stage (
    customer_bk INT PRIMARY KEY,
    full_name   TEXT NOT NULL,
    city        TEXT NOT NULL,
    segment     TEXT NOT NULL
);

-- Измерение с полной историей SCD Type 2
CREATE TABLE elt_lab.dim_customer_scd2 (
    customer_sk SERIAL PRIMARY KEY,           -- уникальный ключ конкретной ВЕРСИИ
    customer_bk INT NOT NULL,                 -- бизнес-ключ клиента (может повторяться!)
    full_name   TEXT NOT NULL,
    city        TEXT NOT NULL,
    segment     TEXT NOT NULL,
    valid_from  DATE NOT NULL,
    valid_to    DATE NOT NULL DEFAULT DATE '9999-12-31',
    is_current  BOOLEAN NOT NULL DEFAULT true
);

-- Профессиональный предохранитель: у одного клиента максимум ОДНА активная версия!
CREATE UNIQUE INDEX idx_dim_customer_scd2_active
    ON elt_lab.dim_customer_scd2 (customer_bk)
    WHERE is_current = true;

-- День 1 (2026-01-01): первичная загрузка клиентов
INSERT INTO elt_lab.dim_customer_scd2 (customer_bk, full_name, city, segment, valid_from)
VALUES
    (1, 'Айгерим Сатова', 'Костанай', 'VIP',      '2026-01-01'),
    (2, 'Тимур Искаков',  'Астана',   'Standard', '2026-01-01'),
    (3, 'Елена Морозова', 'Алматы',   'VIP',      '2026-01-01');

SELECT customer_sk, customer_bk, full_name, city, segment, valid_from, valid_to, is_current
FROM elt_lab.dim_customer_scd2
ORDER BY customer_sk;
Ответ PostgreSQL (состояние на 1 января)

-------------+-------------+----------------+----------+----------+------------+------------+------------
           1 |           1 | Айгерим Сатова | Костанай | VIP      | 2026-01-01 | 9999-12-31 | t

Пример 4. Идемпотентная загрузка изменений Дня 2 (2026-02-01)

Алгоритм обновления SCD Type 2 всегда состоит из двух чётких шагов внутри одной транзакции BEGIN ... COMMIT: сначала закрываем устаревшие версии, потом открываем новые версии для изменившихся и новоприбывших клиентов. Причём этот блок полностью идемпотентен — можешь запустить транзакцию хоть 3 раза подряд, и лишних строк не появится!

SQL · Обработка изменений 1 февраля (SCD Type 2 в 2 шага) 
-- Пришёл снимок из OLTP за 2026-02-01
TRUNCATE TABLE elt_lab.raw_customers_stage;
INSERT INTO elt_lab.raw_customers_stage VALUES
    (1, 'Айгерим Сатова', 'Алматы',   'VIP'),      -- сменила город!
    (2, 'Тимур Искаков',  'Астана',   'VIP'),      -- вырос до VIP!
    (3, 'Елена Морозова', 'Алматы',   'VIP'),      -- без изменений
    (4, 'Данияр Алимов',  'Костанай', 'Standard'); -- новый клиент

BEGIN;

-- Шаг 1. Закрываем старые активные версии, у которых изменился хотя бы 1 атрибут
UPDATE elt_lab.dim_customer_scd2 d
SET
    valid_to   = DATE '2026-02-01' - INTERVAL '1 day',
    is_current = false
FROM elt_lab.raw_customers_stage s
WHERE d.customer_bk = s.customer_bk
  AND d.is_current = true
  AND (
      d.full_name IS DISTINCT FROM s.full_name
      OR d.city    IS DISTINCT FROM s.city
      OR d.segment IS DISTINCT FROM s.segment
  );

-- Шаг 2. Открываем новые активные версии (для изменившихся И для новых клиентов)
INSERT INTO elt_lab.dim_customer_scd2
    (customer_bk, full_name, city, segment, valid_from, valid_to, is_current)
SELECT
    s.customer_bk,
    s.full_name,
    s.city,
    s.segment,
    DATE '2026-02-01',
    DATE '9999-12-31',
    true
FROM elt_lab.raw_customers_stage s
LEFT JOIN elt_lab.dim_customer_scd2 d
       ON d.customer_bk = s.customer_bk
      AND d.is_current = true
WHERE d.customer_bk IS NULL
ORDER BY s.customer_bk;

COMMIT;

-- Смотрим полную историю измерений!
SELECT customer_sk, customer_bk, full_name, city, segment, valid_from, valid_to, is_current
FROM elt_lab.dim_customer_scd2
ORDER BY customer_bk, valid_from;

-------------+-------------+----------------+----------+----------+------------+------------+------------
           1 |           1 | Айгерим Сатова | Костанай | VIP      | 2026-01-01 | 2026-01-31 | f
           4 |           1 | Айгерим Сатова | Алматы   | VIP      | 2026-02-01 | 9999-12-31 | t

05 Машина времени в SQL: Point-in-Time JOIN

Теперь давай вернёмся к нашей детективной задаче из Раздела 03 и восстановим справедливость для директора костанайского филиала! Когда мы загружаем продажи в таблицу фактов fact_sales_hist, мы связываем каждый чек не просто с «клиентом №1», а с конкретной исторической версией customer_sk, действовавшей в день покупки:

o.order_date BETWEEN dc.valid_from AND dc.valid_to — этот приём называется Point-in-Time JOIN (соединение на момент времени).

Пример 6. Загружаем факты с привязкой ко времени и строим правдивый отчёт

SQL · Загрузка фактов через Point-in-Time JOIN и отчёт по городам 
CREATE TABLE elt_lab.fact_sales_hist (
    order_id    INT PRIMARY KEY,
    order_date  DATE NOT NULL,

✗ Как НЕ надо · Соединение с SCD Type 2 по customer_bk без фильтра дат
-- ОПАСНО: у Айгерим 2 строки в dim_customer_scd2!
-- Каждый её заказ задвоится, и выручка раздуется в 2 раза!
SELECT dc.city, SUM(s.amount)
FROM raw_orders s
JOIN elt_lab.dim_customer_scd2 dc ON dc.customer_bk = s.customer_bk
GROUP BY dc.city;

Забыть условие s.order_date BETWEEN dc.valid_from AND dc.valid_to (или dc.is_current = true) при соединении с SCD2-таблицей по бизнес-ключу — одна из самых частых причин размножения строк (Fan-out) в отчётах.

✓ Как правильно · Привязывать факт к суррогатному ключу customer_sk
-- На этапе ELT подбираем точный customer_sk через BETWEEN valid_from AND valid_to,
-- а в отчётах соединяем просто по первичному ключу customer_sk (1 к 1, без риска дублей!):
SELECT dc.city, SUM(f.amount)
FROM elt_lab.fact_sales_hist f
JOIN elt_lab.dim_customer_scd2 dc ON dc.customer_sk = f.customer_sk
GROUP BY dc.city;

Поскольку customer_sk — первичный ключ конкретной версии, такой JOIN никогда не задвоит сумму и работает максимально быстро.

Инженерный лайфхак с хэшем строки: Если в таблице измерений не 3, а 40 отслеживаемых колонок, писать 40 условий IS DISTINCT FROM утомительно. В продакшене в таблицу добавляют колонку row_hash TEXT и считают md5(concat_ws('|', col1, col2, ..., col40)). Тогда в Шаге 1 достаточно одного сравнения: WHERE d.row_hash <> s.row_hash!

06 Шпаргалка урока перед практикой

Пять золотых опорных пунктов, которые стоит запомнить навсегда:

Понятие / Приём Короткий смысл
Слои ELT RAW (сырые данные как есть) → DWH (чистая «Звезда» + история) → MART (готовые витрины).
Идемпотентность Повторный запуск загрузки с теми же данными даёт 100% тот же результат без ошибок и дублей (ON CONFLICT DO UPDATE или BEGIN; DELETE; INSERT; COMMIT;).
SCD Type 1 vs Type 2 Type 1 перезаписывает старое значение (опечатки). Type 2 закрывает старую версию (valid_to, is_current = false) и открывает новую.
Частичный уникальный индекс CREATE UNIQUE INDEX ... ON dim (bk) WHERE is_current = true; — страховка БД от двух активных версий одного объекта.
Point-in-Time JOIN event_date BETWEEN valid_from AND valid_to — позволяет привязать факт к версии справочника, действовавшей именно в день события.

Задание 1 (Базовый). Идемпотентная загрузка курсов валют (UPSERT)

Создай схему elt_lab (если её нет) и таблицу elt_lab.lab_rates (rate_date DATE, currency TEXT, rate_kzt NUMERIC(10, 2), составной PRIMARY KEY (rate_date, currency)). Вставь 2 курса за '2026-03-01': USD = 495.00, EUR = 535.00. Затем напиши идемпотентный запрос INSERT ... ON CONFLICT (rate_date, currency) DO UPDATE, который обновит курс USD до 498.50 и добавит RUB = 5.40. Запусти этот запрос дважды и проверь, что в таблице ровно 3 строки.

Показать решение
SQL · Эталонное решение задания 1 
CREATE SCHEMA IF NOT EXISTS elt_lab;
DROP TABLE IF EXISTS elt_lab.lab_rates;

CREATE TABLE elt_lab.lab_rates (
    rate_date DATE NOT NULL,
    currency  TEXT NOT NULL,
    rate_kzt  NUMERIC(10, 2) NOT NULL,
    PRIMARY KEY (rate_date, currency)
);

-- Первая загрузка
INSERT INTO elt_lab.lab_rates VALUES
    ('2026-03-01', 'USD', 495.00),
    ('2026-03-01', 'EUR', 535.00);

-- Идемпотентный блок обновления (запусти 2 раза — результат одинаковый!)
INSERT INTO elt_lab.lab_rates (rate_date, currency, rate_kzt) VALUES
    ('2026-03-01', 'USD', 498.50),

ON CONFLICT (rate_date, currency) DO UPDATE
SET rate_kzt = EXCLUDED.rate_kzt

Задание 3 (Продвинутый). SCD Type 2 для подписочных тарифов

Создай таблицу elt_lab.lab_dim_plan (plan_sk SERIAL PRIMARY KEY, plan_bk TEXT, monthly_price NUMERIC(10, 2), valid_from DATE, valid_to DATE DEFAULT '9999-12-31', is_current BOOLEAN DEFAULT true) и частичный уникальный индекс на активный plan_bk. Вставь 2 тарифа с 2026-01-01: 'Basic' = 2000 и 'Pro' = 5000. С 2026-03-01 тариф 'Pro' подорожал до 6500, а 'Basic' не изменился. Напиши 2-шаговую транзакцию SCD Type 2 из временной таблицы-снимка (CTE или stage-таблицы) и убедись, что у 'Pro' стало 2 версии, а у 'Basic' осталась 1.

Показать решение
SQL · Эталонное решение задания 3 
CREATE SCHEMA IF NOT EXISTS elt_lab;
DROP TABLE IF EXISTS elt_lab.lab_dim_plan;
DROP TABLE IF EXISTS elt_lab.lab_stage_plan;

CREATE TABLE elt_lab.lab_dim_plan (
    plan_sk       SERIAL PRIMARY KEY,
    plan_bk       TEXT NOT NULL,
    monthly_price NUMERIC(10, 2) NOT NULL,
    valid_from    DATE NOT NULL,
    valid_to      DATE NOT NULL DEFAULT DATE '9999-12-31',
    is_current    BOOLEAN NOT NULL DEFAULT true
);

CREATE UNIQUE INDEX idx_lab_dim_plan_active
    ON elt_lab.lab_dim_plan (plan_bk) WHERE is_current = true;

-- Начальное состояние (2026-01-01)
INSERT INTO elt_lab.lab_dim_plan (plan_bk, monthly_price, valid_from) VALUES
    ('Basic', 2000.00, '2026-01-01'),
    ('Pro',   5000.00, '2026-01-01');

-- Входящий снимок на 2026-03-01
CREATE TABLE elt_lab.lab_stage_plan (
    plan_bk       TEXT PRIMARY KEY,
    monthly_price NUMERIC(10, 2) NOT NULL
);
INSERT INTO elt_lab.lab_stage_plan VALUES
    ('Basic', 2000.00),
    ('Pro',   6500.00);

BEGIN;
    -- Шаг 1: закрываем изменившиеся тарифы
    UPDATE elt_lab.lab_dim_plan d
    SET valid_to = DATE '2026-03-01' - INTERVAL '1 day',
        is_current = false
    FROM elt_lab.lab_stage_plan s
    WHERE d.plan_bk = s.plan_bk
      AND d.is_current = true
      AND d.monthly_price IS DISTINCT FROM s.monthly_price;

    -- Шаг 2: открываем новые версии
    INSERT INTO elt_lab.lab_dim_plan (plan_bk, monthly_price, valid_from, valid_to, is_current)
    SELECT s.plan_bk, s.monthly_price, DATE '2026-03-01', DATE '9999-12-31', true
    FROM elt_lab.lab_stage_plan s
    LEFT JOIN elt_lab.lab_dim_plan d
           ON d.plan_bk = s.plan_bk AND d.is_current = true
    WHERE d.plan_bk IS NULL;
COMMIT;

SELECT * FROM elt_lab.lab_dim_plan ORDER BY plan_bk, valid_from;
Задание 4 (Проектирование). Point-in-Time отчёт по грейдам разработчика

Создай две автономные таблицы: elt_lab.lab_dim_emp (SCD2-история сотрудника №10: с 2026-01-01 по 2026-02-28 он был 'Junior', а с 2026-03-01 по 9999-12-31 стал 'Middle') и elt_lab.lab_tasks (4 закрытые задачи сотрудника №10: две в феврале и две в марте). Напиши запрос с Point-in-Time JOIN (BETWEEN valid_from AND valid_to), который посчитает, сколько задач разработчик закрыл в роли Junior и сколько — в роли Middle (должно получиться по 2 задачи, без задвоения!).

Показать решение
SQL · Эталонное решение задания 4 
CREATE SCHEMA IF NOT EXISTS elt_lab;
DROP TABLE IF EXISTS elt_lab.lab_tasks;
DROP TABLE IF EXISTS elt_lab.lab_dim_emp;

CREATE TABLE elt_lab.lab_dim_emp (
    emp_sk     SERIAL PRIMARY KEY,
    emp_bk     INT NOT NULL,
    grade      TEXT NOT NULL,
    valid_from DATE NOT NULL,
    valid_to   DATE NOT NULL,
    is_current BOOLEAN NOT NULL
);

INSERT INTO elt_lab.lab_dim_emp (emp_bk, grade, valid_from, valid_to, is_current) VALUES
    (10, 'Junior', '2026-01-01', '2026-02-28', false),
    (10, 'Middle', '2026-03-01', '9999-12-31', true);

CREATE TABLE elt_lab.lab_tasks (
    task_id   INT PRIMARY KEY,
    emp_bk    INT NOT NULL,
    task_date DATE NOT NULL
);

INSERT INTO elt_lab.lab_tasks VALUES
    (1, 10, '2026-02-10'),
    (2, 10, '2026-02-25'),
    (3, 10, '2026-03-05'),
    (4, 10, '2026-03-19');

-- Point-in-Time JOIN: точное попадание в историческую версию грейда!
SELECT
    e.grade,
    COUNT(t.task_id) AS tasks_completed
FROM elt_lab.lab_tasks t
JOIN elt_lab.lab_dim_emp e
  ON e.emp_bk = t.emp_bk
 AND t.task_date BETWEEN e.valid_from AND e.valid_to
GROUP BY e.grade
ORDER BY e.grade;
-- Ожидаемый результат: Junior (2), Middle (2)
