MVCC (многоверсионность) и VACUUM в PostgreSQL

Главное в этом уроке
  • Поймёшь, как работает MVCC — почему читатели в PostgreSQL никогда не блокируют писателей, а писатели не блокируют читателей.
  • Заглянешь в скрытые системные столбцы каждой строки: ctid, xmin и xmax, и увидишь, как UPDATE на самом деле создаёт копию строки.
  • Узнаешь, откуда берутся мёртвые строки (Dead Tuples) и почему база начинает «пухнуть» на диске (Table Bloat).
  • Научишься пользоваться VACUUM, VACUUM FULL, ANALYZE и мониторить работу автоматического уборщика Autovacuum через pg_stat_user_tables.

01 Как читатели не мешают писателям? Магия MVCC

Представь школьную библиотеку с единственным экземпляром редкой энциклопедии. Если Вася взял её, чтобы переписать абзац, а Петя в эту же секунду хочет просто прочитать ту же страницу, им придётся либо драться за книгу, либо стоять в очереди.

В старых базах данных всё работало именно так: пока кто-то менял строку, все остальные не могли её даже прочитать — сайт «подвисал». PostgreSQL решает эту задачу гениально и просто: он никогда не стирает старую строку ластиком! Вместо этого при любом UPDATE он оставляет старую версию на месте (просто ставит на ней пометку «устарела»), а рядом дописывает новую версию этой же строки.

Такой механизм называется MVCC (Multi-Version Concurrency Control) — управление параллельным доступом с помощью множества версий. В PostgreSQL действует золотое правило: читатели никогда не блокируют писателей, а писатели никогда не блокируют читателей.

Секретный паспорт каждой строки: В PostgreSQL у любой строки есть три невидимых системных столбца:
• ctid — точный физический адрес на диске: (номер_страницы, номер_строки);
• xmin — номер транзакции (ID), которая создала эту версию;
• xmax — номер транзакции, которая удалила или обновила эту версию (0, если версия живая).

Смотрим на невидимые столбцы в learning_db

Давай откроем рентген для PostgreSQL и посмотрим на ctid, xmin и xmax своими глазами! Создадим небольшую таблицу mvcc_heroes с тремя героями игры.

SQL · Пример 1: Подготовка таблицы и осмотр скрытых столбцов 
-- Безопасно пересоздаём учебную таблицу
DROP TABLE IF EXISTS mvcc_heroes;

CREATE TABLE mvcc_heroes (
    id   SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    gold INT NOT NULL
);

-- Вставляем три строки одной командой (в одной транзакции)
INSERT INTO mvcc_heroes (name, gold) VALUES
    ('Рыцарь', 100),
    ('Маг',    250),
    ('Лучник', 180);

-- Просим PostgreSQL показать скрытые системные столбцы
SELECT ctid, xmin, xmax, id, name, gold
FROM mvcc_heroes
ORDER BY id;
Ответ PostgreSQL
 ctid  | xmin | xmax | id |  name  | gold
-------+------+------+----+--------+------
 (0,1) |  742 |    0 |  1 | Рыцарь |  100
 (0,2) |  742 |    0 |  2 | Маг    |  250
 (0,3) |  742 |    0 |  3 | Лучник |  180
(3 rows)

Смотри, как красиво! Все три строки родились в одной транзакции (у тебя номер xmin будет свой, например 742), у всех xmax = 0 (никто их не трогал), а живут они на странице 0 в ячейках 1, 2 и 3.

Доказываем, что UPDATE — это «переезд» на новый адрес

А теперь дадим Рыцарю +50 золотых и снова посмотрим на скрытые столбцы. Если бы PostgreSQL менял данные прямо на месте, адрес ctid остался бы (0,1). Проверим, что случится на самом деле!

SQL · Пример 2: Проверяем, как меняется ctid после UPDATE 
-- Обновляем золото только у Рыцаря
UPDATE mvcc_heroes
SET gold = gold + 50
WHERE name = 'Рыцарь';

-- Смотрим, куда «переехала» строка Рыцаря!
SELECT ctid, xmin, xmax, id, name, gold
FROM mvcc_heroes
ORDER BY id;
Ответ PostgreSQL
 ctid  | xmin | xmax | id |  name  | gold
-------+------+------+----+--------+------
 (0,4) |  743 |    0 |  1 | Рыцарь |  150
 (0,2) |  742 |    0 |  2 | Маг    |  250
 (0,3) |  742 |    0 |  3 | Лучник |  180
(3 rows)

Видишь?! Адрес Рыцаря изменился с (0,1) на (0,4), а его xmin вырос с 742 до 743! Старая строка на месте (0,1) никуда не испарилась — она всё ещё лежит на диске, просто помечена xmax = 743 и скрыта от новых запросов. Так решилась наша загадка из прошлого урока: именно благодаря таким копиям читатели и писатели не толкаются в очереди!

02 Снимки времени (Snapshots): как два окна видят разное

Представь, что учитель пишет задачи на школьной доске. Ты достал телефон и сделал фотографию доски. Даже если учитель прямо сейчас начнёт стирать старый пример и писать новый, на твоём фото всё останется ровно таким, каким было в момент щелчка камеры.

Когда транзакция в PostgreSQL выполняет запрос, она получает свой снимок данных (Snapshot) — список номеров транзакций, которые уже завершились к этому моменту. Пробегая по строкам таблицы, PostgreSQL сравнивает xmin и xmax каждой версии с этим снимком и решает: «Эту версию я тебе покажу, а эту — скрою».

Что происходит в Терминале 2 Что лежит в таблице на диске Что видит Терминал 1
Ещё ничего не менял (0,2) Маг: 250 (xmax = 0) Маг: 250
Сделал UPDATE до 999, но без COMMIT (0,2) Маг: 250 (xmax = T2)
(0,5) Маг: 999 (xmin = T2)		 Маг: 250 (версия T2 ещё не подтверждена!)
Нажал COMMIT (0,2) — мёртвая строка
(0,5) — живая строка		 Маг: 999 (адрес стал (0,5))

Ловим момент смены версий в двух окнах psql

Открой два окна psql к базе learning_db и выполни шаги по очереди — ты вживую увидишь, как в старой строке появляется номер чужой незавершённой транзакции в столбце xmax!

SQL · Пример 3: Живой MVCC в двух терминалах 
-- [ШАГ 1 — ТЕРМИНАЛ 2] Начинаем транзакцию и меняем золото Мага (БЕЗ COMMIT!)
BEGIN;
SELECT pg_current_xact_id(); -- Запомни этот номер (например, 744)
UPDATE mvcc_heroes SET gold = 999 WHERE name = 'Маг';

-- [ШАГ 2 — ТЕРМИНАЛ 1] Читаем строку Мага, пока Терминал 2 ещё не закоммитил!
SELECT ctid, xmin, xmax, name, gold
FROM mvcc_heroes
WHERE name = 'Маг';
-- Обрати внимание: запрос НЕ завис, золото всё ещё 250, а xmax стал равен 744!

-- [ШАГ 3 — ТЕРМИНАЛ 2] Завершаем транзакцию
COMMIT;

-- [ШАГ 4 — ТЕРМИНАЛ 1] Читаем ещё раз
SELECT ctid, xmin, xmax, name, gold
FROM mvcc_heroes
WHERE name = 'Маг';
Ответ PostgreSQL в Терминале 1 (Шаг 2 vs Шаг 4)
-- Шаг 2 (пока Терминал 2 ещё не сделал COMMIT):
 ctid  | xmin | xmax | name | gold
-------+------+------+------+------
 (0,2) |  742 |  744 | Маг  |  250
(1 row)

-- Шаг 4 (сразу после COMMIT в Терминале 2):
 ctid  | xmin | xmax | name | gold
-------+------+------+------+------
 (0,5) |  744 |    0 | Маг  |  999
(1 row)

Круто, правда? На шаге 2 Терминал 1 увидел xmax = 744, проверил: «Ага, транзакция 744 ещё не завершилась! Значит, старая версия (0,2) со значением 250 для меня ещё жива, а новую (0,5) я проигнорирую». Ни одной секунды простоя!

03 Цена многоверсионности: мёртвые строки и раздувание (Bloat)

Но у каждой суперсилы есть обратная сторона. Представь школьную тетрадь, в которой тебе запретили пользоваться ластиком: если ты ошибся в слове, ты его зачёркиваешь и пишешь исправленное слово на следующей строчке. Если ты 500 раз поправишь одно и то же предложение, полезного текста останется одна строчка, а тетрадь будет исписана целиком!

Точно так же происходит в PostgreSQL. Старые версии строк после UPDATE и DELETE, которые уже никому не нужны, превращаются в мёртвые кортежи (Dead Tuples). Они лежат на диске мёртвым грузом, и таблица начинает раздуваться — инженеры называют это раздуванием таблицы (Table Bloat). Из-за него:

  • база занимает в разы больше места на SSD, чем нужно;
  • запросы SELECT начинают тормозить, потому что серверу приходится перелистывать тысячи «зачёркнутых» страниц в поисках живых строк.

Наблюдаем раздувание таблицы на реальных цифрах

Давай специально устроим мини-раздувание в learning_db: создадим таблицу bloat_lab на 10 000 строк, отключим на ней автоматическую уборку (только для нашего лабораторного опыта!), обновим все строки 4 раза и измерим, во сколько раз «растолстел» файл на диске.

SQL · Пример 4: Генерируем 40 000 мёртвых строк и измеряем Bloat 
DROP TABLE IF EXISTS bloat_lab;

-- Отключаем autovacuum ТОЛЬКО на этой тестовой таблице для наглядности опыта
CREATE TABLE bloat_lab (
    id      INT PRIMARY KEY,
    counter INT NOT NULL,
    payload TEXT NOT NULL
) WITH (autovacuum_enabled = false);

-- Вставляем 10 000 строк
INSERT INTO bloat_lab (id, counter, payload)
SELECT g, 0, repeat('x', 80)
FROM generate_series(1, 10000) AS g;

-- Смотрим исходный размер таблицы
SELECT pg_size_pretty(pg_relation_size('bloat_lab')) AS size_before;

-- 4 раза обновляем все 10 000 строк (= 40 000 мёртвых версий!)
UPDATE bloat_lab SET counter = counter + 1;
UPDATE bloat_lab SET counter = counter + 1;
UPDATE bloat_lab SET counter = counter + 1;
UPDATE bloat_lab SET counter = counter + 1;

-- Проверяем размер и статистику живых/мёртвых строк
SELECT
    pg_size_pretty(pg_relation_size('bloat_lab')) AS size_after,
    n_live_tup,
    n_dead_tup
FROM pg_stat_user_tables
WHERE relname = 'bloat_lab';
Ответ PostgreSQL
 size_before
-------------
 1280 kB
(1 row)

 size_after | n_live_tup | n_dead_tup
------------+------------+------------
 6400 kB    |      10000 |      40000
(1 row)

Посмотри на цифры: живых строк как было 10 000, так и осталось 10 000, но размер таблицы подскочил в 5 раз — с 1.28 МБ до 6.4 МБ, потому что внутри накопилось 40 000 мёртвых копий!

04 Уборщик VACUUM, VACUUM FULL и Autovacuum

Чтобы база не захлебнулась в собственных черновиках, в PostgreSQL работает специальный процесс-уборщик — VACUUM («пылесос»). У него есть два режима работы, которые критически важно не перепутать.

Представь два способа навести порядок в исписанной тетради:

  • Обычный VACUUM — аккуратный дежурный: он тихо ходит по страницам, стирает ластиком ненужные зачёркнутые строки и оставляет чистые пустые клеточки внутри той же тетради для будущих записей. Размер файла на диске обычно не уменьшается, зато новые INSERT и UPDATE будут заполнять эти пустоты, а не раздувать таблицу дальше. Главное — никто не заблокирован, все продолжают читать и писать!
  • VACUUM FULL — генеральная перепись: он забирает тетрадь у всех, вешает замок на дверь кабинета (ACCESS EXCLUSIVE LOCK — никто не может даже прочитать ни строчки!), переписывает только живые строки в новую тонкую тетрадку и возвращает освободившееся место операционной системе.

Запускаем обычный VACUUM VERBOSE на bloat_lab

Ключевое слово VERBOSE просит PostgreSQL рассказать подробный отчёт о том, сколько мусора он вычистил.

SQL · Пример 5: Обычный VACUUM VERBOSE и проверка статистики 
-- Убираем мёртвые строки без блокировки работы таблицы
VACUUM (VERBOSE, ANALYZE) bloat_lab;

-- Смотрим, что изменилось в статистике и размере файла
SELECT
    pg_size_pretty(pg_relation_size('bloat_lab')) AS size_after_vacuum,
    n_live_tup,
    n_dead_tup,
    last_vacuum
FROM pg_stat_user_tables
WHERE relname = 'bloat_lab';
Ответ PostgreSQL
INFO:  vacuuming "learning_db.public.bloat_lab"
INFO:  finished vacuuming "learning_db.public.bloat_lab": index scans: 1
tuples: 40000 removed, 10000 remain, 0 are dead but not yet removable
VACUUM

 size_after_vacuum | n_live_tup | n_dead_tup |          last_vacuum
-------------------+------------+------------+-------------------------------
 6400 kB           |      10000 |          0 | 2026-11-26 09:42:11.18421+05
(1 row)

Смотри на строчку отчёта: 40000 removed, 10000 remain, а n_dead_tup стало равно 0! Размер файла всё ещё 6400 kB, но теперь внутри него есть 5 МБ чистых свободных слотов — следующие 4 обновления вообще не увеличат файл на диске! А добавка ANALYZE заодно обновила статистику для планировщика запросов.

Частая ошибка: запуск VACUUM внутри транзакции

Если ты попробуешь запустить VACUUM после команды BEGIN;, PostgreSQL сразу откажет:

SQL · Попытка запустить VACUUM внутри BEGIN ... COMMIT 
BEGIN;
VACUUM bloat_lab;
Ошибка PostgreSQL
ERROR:  VACUUM cannot run inside a transaction block

Почему так? Уборка диска — это необратимая служебная операция, которую невозможно «откатить» через ROLLBACK. Не забудь закрыть ошибочный блок командой ROLLBACK; и запускай VACUUM всегда как самостоятельную команду вне BEGIN.

Сжимаем файл через VACUUM FULL и проверяем Autovacuum

В учебной песочнице (или ночью во время технического окна) можно выполнить VACUUM FULL, чтобы вернуть 5 МБ операционной системе. А затем давай проверим, включён ли в нашем PostgreSQL автоматический уборщик Autovacuum — он сам следит за всеми таблицами и запускает обычный VACUUM, когда мёртвых строк становится слишком много (по умолчанию: больше 50 + 20% от числа строк в таблице).

SQL · Пример 6: VACUUM FULL и проверка настроек Autovacuum 
-- Если осталась открытая транзакция после ошибки выше — откатываем
ROLLBACK;

-- Полностью переписываем таблицу (в проде будь осторожен: блокирует доступ!)
VACUUM FULL bloat_lab;

-- Проверяем размер на диске: файл снова стал компактным!
SELECT pg_size_pretty(pg_relation_size('bloat_lab')) AS size_after_full;

-- Проверяем настройки фонового уборщика Autovacuum
SHOW autovacuum;
SHOW autovacuum_vacuum_threshold;
SHOW autovacuum_vacuum_scale_factor;
Ответ PostgreSQL
 size_after_full
-----------------
 1280 kB
(1 row)

 autovacuum
------------
 on
(1 row)

 autovacuum_vacuum_threshold
-----------------------------
 50
(1 row)

 autovacuum_vacuum_scale_factor
--------------------------------
 0.2
(1 row)

Файл мгновенно похудел с 6400 kB обратно до 1280 kB! И возвращаем обратно автоуборку (или просто помним, что в реальных базах autovacuum должен быть всегда включён).

✗ Как НЕ надо
-- В час пик на таблице
-- с заказами на 50 ГБ:
VACUUM FULL orders;

Таблица orders полностью заблокируется на десятки минут. Никто не сможет ни оформить заказ, ни открыть личный кабинет.

✓ Как правильно
-- Регулярный автоуборщик
-- или ручной мягкий запуск:
VACUUM (ANALYZE) orders;

Обычный VACUUM не мешает пользователям, а для сжатия больших таблиц без простоя в проде используют утилиту pg_repack.

✗ Как НЕ надо: брошенная транзакция (парализует VACUUM!)
-- Аналитик открыл транзакцию утром и ушёл на обед, забыв COMMIT/ROLLBACK:
BEGIN;
SELECT count(*) FROM orders;
-- ...прошло 3 часа, транзакция всё ещё висит (idle in transaction)...

Пока эта старая транзакция открыта, её снимок времени (Snapshot) всё ещё активен. VACUUM не имеет права удалять ни одну мёртвую строку, созданную после утра — вся база будет стремительно пухнуть!

✓ Как правильно: закрывать транзакции и ставить таймаут
-- Всегда завершай транзакцию сразу после запроса, а в настройках сервера
-- защищайся параметром idle_in_transaction_session_timeout:
SET idle_in_transaction_session_timeout = '30s';

Через 30 секунд бездействия внутри открытой транзакции PostgreSQL сам принудительно прервёт забытую сессию и спасёт базу от раздувания.

Никогда не отключай Autovacuum в реальной базе! Помимо уборки мусора, он защищает PostgreSQL от страшной аварии — переполнения счётчика транзакций (Transaction ID Wraparound). Номер xmin хранится как 32-битное число (примерно 4 миллиарда значений — как одометр старой машины, который после 999 999 сбрасывается на 0). Чтобы старые строки не стали «из будущего», VACUUM периодически «замораживает» (FREEZE) древние строки. Без автоуборки база однажды просто откажется принимать новые записи!
Совет для больших таблиц: Порог autovacuum_vacuum_scale_factor = 0.2 означает «убираться, когда накопилось 20% мёртвых строк». Для таблицы на 100 строк это всего 70 изменений, а вот для таблицы на 100 миллионов строк — аж 20 миллионов мёртвых строк! Для горячих гигантских таблиц инженеры точечно уменьшают порог через ALTER TABLE big_table SET (autovacuum_vacuum_scale_factor = 0.01); (уборка при 1%).

05 Шпаргалка урока перед практикой

Короткий словарик-напоминалка перед решением задач:

  • MVCC — хранение нескольких версий одной строки, благодаря чему чтение (SELECT) и запись (UPDATE/DELETE) не блокируют друг друга.
  • ctid, xmin, xmax — скрытые системные столбцы: физический адрес строки на диске, ID создавшей транзакции и ID удалившей/обновившей транзакции.
  • Dead Tuples и Table Bloat — мёртвые версии строк после UPDATE/DELETE и вызванное ими раздувание размера таблицы на диске.
  • VACUUM vs VACUUM FULL — обычный VACUUM не блокирует работу и освобождает слоты внутри файла для новых строк; VACUUM FULL отдаёт место ОС, но намертво блокирует всю таблицу.
  • pg_stat_user_tables — главная системная таблица для мониторинга n_live_tup, n_dead_tup и времени последней уборки (last_vacuum / last_autovacuum).

06 Мини-практикум для закрепления

Выполни 4 автономные задачи в базе learning_db. Каждая задача сама создаёт свою таблицу и не зависит от предыдущих заданий.

Задание 1 (Базовый). Проследи три «жизни» одной строки

Создай таблицу task1_items (id SERIAL PRIMARY KEY, title TEXT, price INT), вставь одну строку ('Компас', 100) и выведи её ctid, xmin, xmax, price. Затем дважды выполни UPDATE (сначала подними цену до 120, потом до 150) и после каждого обновления снова выведи ctid, xmin, xmax, price. Убедись, что адрес ctid и xmin меняются каждый раз.

Показать решение
SQL · Решение задания 1 
DROP TABLE IF EXISTS task1_items;

CREATE TABLE task1_items (
    id    SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    price INT NOT NULL
);

INSERT INTO task1_items (title, price) VALUES ('Компас', 100);
SELECT ctid, xmin, xmax, title, price FROM task1_items;
-- Ожидаемо: ctid = (0,1), xmax = 0

UPDATE task1_items SET price = 120 WHERE title = 'Компас';
SELECT ctid, xmin, xmax, title, price FROM task1_items;
-- Ожидаемо: ctid = (0,2), xmin вырос на 1

UPDATE task1_items SET price = 150 WHERE title = 'Компас';
SELECT ctid, xmin, xmax, title, price FROM task1_items;
-- Ожидаемо: ctid = (0,3), xmin снова вырос на 1
Задание 2 (Средний). Найди мёртвые строки и запусти мягкую уборку

Создай таблицу task2_logs (id INT PRIMARY KEY, status TEXT) с отключённым автоуборщиком (WITH (autovacuum_enabled = false)). Заполни её 5000 строками со статусом 'new', затем удали половину строк (где id <= 2500). Посмотри n_live_tup и n_dead_tup в pg_stat_user_tables, выполни обычный VACUUM VERBOSE task2_logs; и проверь статистику ещё раз.

Показать решение
SQL · Решение задания 2 
DROP TABLE IF EXISTS task2_logs;

CREATE TABLE task2_logs (
    id     INT PRIMARY KEY,
    status TEXT NOT NULL
) WITH (autovacuum_enabled = false);

INSERT INTO task2_logs (id, status)
SELECT g, 'new' FROM generate_series(1, 5000) AS g;

-- Удаляем первую половину строк (создаём 2500 мёртвых кортежей)
DELETE FROM task2_logs WHERE id <= 2500;

-- Смотрим до уборки (n_dead_tup = 2500)
SELECT relname, n_live_tup, n_dead_tup
FROM pg_stat_user_tables
WHERE relname = 'task2_logs';

-- Мягкая уборка с отчётом и обновлением статистики
VACUUM (VERBOSE, ANALYZE) task2_logs;

-- Проверяем после уборки (n_dead_tup = 0, n_live_tup = 2500)
SELECT relname, n_live_tup, n_dead_tup, last_vacuum
FROM pg_stat_user_tables
WHERE relname = 'task2_logs';
Задание 3 (Продвинутый). Измерь реальную экономию диска после VACUUM FULL

Создай таблицу task3_archive (id INT PRIMARY KEY, body TEXT) с отключённым autovacuum. Вставь 20000 строк (в body положи repeat('A', 100)), затем удали 90% строк (оставь только те, где id > 18000). Сравни размер таблицы через pg_size_pretty(pg_relation_size('task3_archive')): 1) сразу после DELETE, 2) после обычного VACUUM, 3) после VACUUM FULL. В конце обнови статистику через ANALYZE.

Показать решение
SQL · Решение задания 3 
DROP TABLE IF EXISTS task3_archive;

CREATE TABLE task3_archive (
    id   INT PRIMARY KEY,
    body TEXT NOT NULL
) WITH (autovacuum_enabled = false);

INSERT INTO task3_archive (id, body)
SELECT g, repeat('A', 100) FROM generate_series(1, 20000) AS g;

-- Удаляем 18 000 строк из 20 000
DELETE FROM task3_archive WHERE id <= 18000;

-- 1. Размер сразу после DELETE (около 3.1 МБ)
SELECT pg_size_pretty(pg_relation_size('task3_archive')) AS after_delete;

-- 2. Обычный VACUUM (размер файла останется почти прежним)
VACUUM task3_archive;
SELECT pg_size_pretty(pg_relation_size('task3_archive')) AS after_vacuum;

-- 3. VACUUM FULL (размер резко упадёт до ~300 kB!)
VACUUM FULL task3_archive;
ANALYZE task3_archive;
SELECT pg_size_pretty(pg_relation_size('task3_archive')) AS after_vacuum_full;
Задание 4 (Две сессии). Поймай, как зависшая транзакция мешает VACUUM

Открой два терминала psql. Создай таблицу task4_trap (id INT PRIMARY KEY, val INT) с одной строкой (1, 10) и отключённым autovacuum. В Терминале 1 начни транзакцию BEGIN; и просто выполни SELECT * FROM task4_trap; (НЕ закрывай её!). В Терминале 2 обнови строку 3 раза и запусти VACUUM VERBOSE task4_trap; — найди в отчёте фразу dead but not yet removable! Затем закрой транзакцию в Терминале 1 (COMMIT;), снова запусти VACUUM VERBOSE task4_trap; в Терминале 2 и убедись, что теперь мусор удалён.

Показать решение
SQL · Решение задания 4 (Терминал 1 и Терминал 2) 
-- Подготовка (в любом терминале)
DROP TABLE IF EXISTS task4_trap;
CREATE TABLE task4_trap (
    id  INT PRIMARY KEY,
    val INT NOT NULL
) WITH (autovacuum_enabled = false);
INSERT INTO task4_trap VALUES (1, 10);

-- [ШАГ 1 — ТЕРМИНАЛ 1] Открываем «забытую» транзакцию с активным снимком
BEGIN;
SELECT * FROM task4_trap;
-- НЕ пишем COMMIT! Оставляем окно открытым.

-- [ШАГ 2 — ТЕРМИНАЛ 2] Создаём 3 мёртвые версии и зовём уборщика
UPDATE task4_trap SET val = 20 WHERE id = 1;
UPDATE task4_trap SET val = 30 WHERE id = 1;
UPDATE task4_trap SET val = 40 WHERE id = 1;
VACUUM VERBOSE task4_trap;
-- Увидишь: "0 removed, 1 remain, 3 are dead but not yet removable"!

-- [ШАГ 3 — ТЕРМИНАЛ 1] Наконец закрываем зависшую транзакцию
COMMIT;

-- [ШАГ 4 — ТЕРМИНАЛ 2] Снова запускаем уборку
VACUUM VERBOSE task4_trap;
-- Теперь увидишь: "3 removed, 1 remain, 0 are dead but not yet removable"!

Итог урока Теперь ты знаешь главный секрет скорости и надёжности PostgreSQL: механизм MVCC хранит версии строк со скрытыми метками ctid, xmin и xmax, позволяя читателям и писателям не мешать друг другу, а уборщик VACUUM (и автоматический Autovacuum) выметает мёртвые строки и защищает таблицы от раздувания. Но остался ещё один важный вопрос: читатели и писатели не блокируют друг друга, а что случается, когда два писателя одновременно пытаются изменить одну и ту же строку — или когда две транзакции вцепились друг в друга и ждут бесконечно?
