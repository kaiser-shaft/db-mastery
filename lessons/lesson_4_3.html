Уровни изоляции и блокировки (Row-level locks и Deadlocks)

Главное в этом уроке
  • Узнаешь, чем отличаются уровни изоляции READ COMMITTED, REPEATABLE READ и SERIALIZABLE, и как защитить отчёты и деньги от параллельных аномалий.
  • Научишься точечно бронировать нужные строки через SELECT ... FOR UPDATE, а также строить сверхбыстрые очереди задач с NOWAIT и SKIP LOCKED.
  • Воспроизведёшь в двух терминалах настоящий Deadlock (взаимную блокировку) и освоишь железное правило, как предотвращать его навсегда.
  • Освоишь «радар диспетчера»: как находить, кто кого заблокировал через pg_stat_activity и pg_blocking_pids(), и ставить предохранитель lock_timeout.

01 Уровни изоляции: от «общей комнаты» до «бункера»

Представь, что ты делаешь домашку по математике. Есть три режима тишины:

  • За общим столом на кухне — быстро и удобно, ты сразу слышишь свежие новости, но если мама переставит кружку или поменяет число на листке, ты увидишь это прямо посреди решения.
  • В своей комнате с закрытой дверью — ты сфотографировал условия задач на старте, и до самого конца домашней работы никто не подсунет тебе новые цифры.
  • В звуконепроницаемом бункере по очереди — полная гарантия, будто на всей планете домашки решаются строго по одной. Идеально надёжно, но иногда приходится начинать заново, если кто-то влез раньше.

В SQL эти режимы тишины называются уровнями изоляции транзакций (Transaction Isolation Levels). Чем выше уровень, тем меньше аномалий из урока 4.1 может случиться — но тем чаще база может попросить твоё приложение повторить конфликтную транзакцию.

Готовим стенд для экспериментов в learning_db

Создадим в базе learning_db две свежие таблицы: банковские счета lock_accounts и очередь заказов на доставку ticket_queue.

SQL · Пример 1: Подготовка таблиц для уроков по блокировкам 
DROP TABLE IF EXISTS lock_accounts;

CREATE TABLE lock_accounts (
    id      INT PRIMARY KEY,

    (1, 'Алиса', 1000.00),
    (2, 'Боб',   1000.00),

INSERT INTO ticket_queue (seat) VALUES
    ('Ряд 1, Место 1'),
    ('Ряд 1, Место 2'),

Побеждаем Non-Repeatable Read с помощью REPEATABLE READ

Помнишь проблему из урока 4.1, когда ценник менялся прямо посреди нашей транзакции? Давай решим её прямо сейчас! Открой два окна psql к базе learning_db и запусти в Терминале 1 транзакцию с уровнем REPEATABLE READ.

SQL · Пример 2: Снимок «заморожен» в REPEATABLE READ 
-- [ШАГ 1 — ТЕРМИНАЛ 1] Запускаем транзакцию в режиме REPEATABLE READ
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT owner, balance FROM lock_accounts WHERE id = 1;
-- Видим: Алиса | 1000.00. Снимок зафиксировался на всю транзакцию!

-- [ШАГ 2 — ТЕРМИНАЛ 2] Меняем баланс Алисы и сохраняем
BEGIN;
UPDATE lock_accounts SET balance = 1500.00 WHERE id = 1;
COMMIT;

-- [ШАГ 3 — ТЕРМИНАЛ 1] Снова читаем баланс Алисы в той же транзакции
SELECT owner, balance FROM lock_accounts WHERE id = 1;
-- Всё ещё 1000.00! Аномалия Non-Repeatable Read побеждена!

-- [ШАГ 4 — ТЕРМИНАЛ 1] А теперь попробуем ИЗМЕНИТЬ ту же строку Алисы!
UPDATE lock_accounts SET balance = balance - 100.00 WHERE id = 1;
Ошибка PostgreSQL в Терминале 1 на Шаге 4
ERROR:  could not serialize access due to concurrent update

Почему возникла ошибка на шаге 4? Потому что Терминал 1 живёт в снимке, где у Алисы 1000.00, но пока он думал, Терминал 2 уже перезаписал эту строку на 1500.00. Чтобы не потерять чужие деньги, PostgreSQL честно останавливает Терминал 1 и говорит: «Данные успели измениться — откатись и попробуй снова!» Не забудь сделать ROLLBACK; в Терминале 1.

А зачем нужен SERIALIZABLE? Представь больницу, где на дежурстве должно оставаться минимум 1 из 2 врачей. Оба врача одновременно проверяют в базе: «Ага, на смене 2 человека, значит, я могу уйти!» — и оба уходят. В REPEATABLE READ они правили разные строки, поэтому база их пропустит (это баг Write Skew). А вот SERIALIZABLE заметит логическую связь и отменит второго врача. Главное правило: используешь REPEATABLE READ или SERIALIZABLE — всегда делай в коде повтор (retry) при ошибке сериализации (код 40001)!

02 Строчные блокировки: FOR UPDATE, NOWAIT и SKIP LOCKED

Представь распродажу билетов на финал чемпионата: осталось ровно одно свободное место — «Ряд 1, Место 1». Двое болельщиков одновременно нажали «Оформить». Если просто сделать обычный SELECT, оба увидят статус 'free', и оба решат, что место их!

Как забронировать конкретную строку, чтобы никто другой не мог её изменить, пока ты проводишь оплату? Для этого в PostgreSQL есть строчные блокировки (Row-level locks). Самая важная команда — SELECT ... FOR UPDATE. Она похожа на табличку «ЗАНЯТО» на кресле:

  • FOR UPDATE — захватывает выбранные строки. Другой SELECT ... FOR UPDATE или UPDATE по этой строке будет вежливо ждать, пока ты не сделаешь COMMIT или ROLLBACK (обычный SELECT при этом не блокируется благодаря MVCC!).
  • FOR UPDATE NOWAIT — «я не люблю очереди»: если строка уже занята, не жди ни секунды — сразу верни ошибку.
  • FOR UPDATE SKIP LOCKED — «перескочи занятые»: молча пропусти заблокированные кем-то строки и возьми следующую свободную! Идеально для очередей задач и покупки билетов.
  • FOR SHARE — «только не меняйте!»: разрешает другим тоже читать и ставить FOR SHARE, но запрещает делать UPDATE или DELETE.

Эксперимент: бронируем билеты с FOR UPDATE и NOWAIT

Проверь в двух терминалах psql, как Терминал 1 «вешает табличку» на первое место, а Терминал 2 сначала натыкается на NOWAIT, а потом изящно забирает второе место через SKIP LOCKED!

SQL · Пример 3: Бронь строки через FOR UPDATE и мгновенный отказ NOWAIT 
-- [ШАГ 1 — ТЕРМИНАЛ 1] Берём первое свободное место и блокируем строку
BEGIN;
SELECT id, seat, status
FROM ticket_queue
WHERE status = 'free'
ORDER BY id
LIMIT 1
FOR UPDATE;
-- Выбрано и заблокировано: id = 1 ('Ряд 1, Место 1'). Не закрываем транзакцию!

-- [ШАГ 2 — ТЕРМИНАЛ 2] Пробуем забрать ту же строку с NOWAIT
BEGIN;
SELECT id, seat, status
FROM ticket_queue
WHERE id = 1
FOR UPDATE NOWAIT;
Ошибка PostgreSQL в Терминале 2 (из-за NOWAIT)
ERROR:  could not obtain lock on row in relation "ticket_queue"

Отлично! Терминал 2 не завис в очереди, а мгновенно узнал, что кресло занято. Теперь сделаем ROLLBACK; в Терминале 2 и попробуем волшебный SKIP LOCKED — пусть второй покупатель автоматически получит следующее свободное кресло, пока первый оплачивает своё!

SQL · Пример 4: Параллельная очередь без простоев через SKIP LOCKED 
-- [ШАГ 3 — ТЕРМИНАЛ 2] Откатываем ошибку и берём ЛЮБОЕ свободное незанятое место
ROLLBACK;
BEGIN;
SELECT id, seat, status
FROM ticket_queue
WHERE status = 'free'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- Моментально вернёт id = 2 ('Ряд 1, Место 2') без единой секунды ожидания!

-- Бронируем выбранное место за Бобом и сохраняем
UPDATE ticket_queue SET status = 'reserved', buyer = 'Боб' WHERE id = 2;
COMMIT;

-- [ШАГ 4 — ТЕРМИНАЛ 1] А первый покупатель спокойно завершает бронь Места 1
UPDATE ticket_queue SET status = 'reserved', buyer = 'Алиса' WHERE id = 1;
COMMIT;

-- Проверяем итоговый список билетов
SELECT id, seat, status, buyer FROM ticket_queue ORDER BY id;
Ответ PostgreSQL
 id |      seat      |  status  | buyer
----+----------------+----------+-------
  1 | Ряд 1, Место 1 | reserved | Алиса
  2 | Ряд 1, Место 2 | reserved | Боб
  3 | Ряд 1, Место 3 | free     |
(3 rows)

Проблема двойного бронирования решена красиво и без тормозов: Алиса и Боб получили разные места, ни один из них не ждал другого, и никто не купил одно кресло дважды.

✗ Как НЕ надо
-- Блокируем ВСЮ таблицу
-- ради одной строки!
BEGIN;
LOCK TABLE ticket_queue
IN EXCLUSIVE MODE;
UPDATE ticket_queue ...;
COMMIT;

Вы останавливаете продажу всех мест в зале на время одной покупки. Очередь покупателей мгновенно «встанет».

✓ Как правильно
-- Блокируем ТОЛЬКО одну
-- свободную строку:
BEGIN;
SELECT id FROM ticket_queue
WHERE status = 'free'
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- UPDATE и COMMIT

Замок вешается на одну-единственную строку. Остальные сотни покупателей спокойно разбирают другие места параллельно.

03 Взаимная блокировка (Deadlock): тупик на узком мостике

Помнишь детскую сказку про двух упрямых баранов, которые встретились посередине узкого мостика и никто не хотел уступать дорогу? Или ситуацию в школе: у тебя в руках единственная красная ручка и тебе нужна линейка друга, а у друга в руках линейка и ему нужна твоя ручка. Пока один не положит свой предмет, вы просидите так до конца урока!

В базах данных такой замкнутый круг называется взаимной блокировкой (Deadlock). Он возникает, когда Транзакция 1 держит замок на Строке А и ждёт Строку Б, а Транзакция 2 в ту же секунду держит Строку Б и ждёт Строку А.

Устраиваем настоящий Deadlock в двух окнах psql

Давай сами вызовем Deadlock на таблице lock_accounts — пусть Алиса переводит Бобу 100 монет, а Боб в ту же секунду переводит Алисе 50 монет! Выполни 4 шага строго по очереди в двух терминалах.

SQL · Пример 5: Воспроизводим Deadlock крест-накрест 
-- Предварительно обновим балансы до 1000 (в любом окне)
UPDATE lock_accounts SET balance = 1000.00 WHERE id IN (1, 2);

-- [ШАГ 1 — ТЕРМИНАЛ 1] Блокируем счёт 1 (Алиса)
BEGIN;
UPDATE lock_accounts SET balance = balance - 100.00 WHERE id = 1;

-- [ШАГ 2 — ТЕРМИНАЛ 2] Блокируем счёт 2 (Боб)
BEGIN;
UPDATE lock_accounts SET balance = balance - 50.00 WHERE id = 2;

-- [ШАГ 3 — ТЕРМИНАЛ 1] Пытаемся начислить на счёт 2 (Боб) -> ЗАМРЁТ В ОЖИДАНИИ!
UPDATE lock_accounts SET balance = balance + 100.00 WHERE id = 2;

-- [ШАГ 4 — ТЕРМИНАЛ 2] Пытаемся начислить на счёт 1 (Алиса) -> ЗАМЫКАЕМ ЦИКЛ!
UPDATE lock_accounts SET balance = balance + 50.00 WHERE id = 1;
Ошибка PostgreSQL в Терминале 2 (через ~1 секунду)
ERROR:  deadlock detected
DETAIL:  Process 1842 waits for ShareLock on transaction 815; blocked by process 1819.
Process 1819 waits for ShareLock on transaction 816; blocked by process 1842.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,4) in relation "lock_accounts"

Что только что сделал PostgreSQL? Он не позволил системе зависнуть навечно! Через deadlock_timeout (по умолчанию 1 секунда) сервер проанализировал граф ожиданий, обнаружил замкнутый круг и принудительно прервал одну из транзакций (Терминал 2), чтобы освободить дорогу для Терминала 1. Смотри: Терминал 1 тут же «отвис» и готов сделать COMMIT;, а в Терминале 2 нужно выполнить ROLLBACK;!

Главное лекарство от Deadlock — единый порядок блокировок

Как сделать так, чтобы переводы между Алисой и Бобом никогда в жизни не приводили к Deadlock? Очень просто: договариваемся, что любая транзакция всегда захватывает счета строго по возрастанию id (сначала id = 1, и только потом id = 2)! Тогда кто первый схватил меньший id — тот спокойно проходит весь перевод, а второй просто ждёт миллисекунду и проходит следом. Цикл становится математически невозможным!

✗ Как НЕ надо: разный порядок обновления строк
-- Перевод 1 (Алиса -> Боб): сначала id = 1, потом id = 2
-- Перевод 2 (Боб -> Алиса): сначала id = 2, потом id = 1
-- Итог при параллельном запуске: гарантированный DEADLOCK!

Транзакции идут навстречу друг другу и неизбежно сталкиваются лбами.

✓ Как правильно: блокируем строки в едином порядке (ORDER BY id)
-- В ЛЮБОМ переводе (хоть 1->2, хоть 2->1) сначала берём замки по возрастанию id:
BEGIN;
SELECT id FROM lock_accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
-- Теперь обе строки наши — можно обновлять в любом порядке!
UPDATE lock_accounts SET balance = balance - 50.00 WHERE id = 2;
UPDATE lock_accounts SET balance = balance + 50.00 WHERE id = 1;
COMMIT;

Единый порядок сортировки ORDER BY id полностью исключает возникновение замкнутого цикла между этими строками.

Deadlock — это не поломка сервера! Не пугайся ошибки 40P01 (deadlock detected) в логах: это защитный механизм PostgreSQL. В реальных проектах инженеры делают две вещи сразу: 1) соблюдают единый порядок блокировок, чтобы deadlocks почти не случались; 2) добавляют в код приложения автоматический повтор (retry) транзакции при ошибке 40P01.

04 Радар диспетчера: ищем виновника и ставим lock_timeout

Представь, что на сайте внезапно «завис» запрос пользователя. Он уже 20 секунд крутит спиннер и ничего не отвечает. Как инженеру баз данных за 3 секунды понять, кто именно держит замок и не даёт ему пройти?

В PostgreSQL есть встроенная «диспетчерская вышка» — системное представление pg_stat_activity (показывает все активные подключения) и удобнейшая функция pg_blocking_pids(pid), которая прямо называет номера процессов (PID), мешающих конкретному запросу!

А чтобы твои важные запросы (и особенно миграции ALTER TABLE) никогда не висели вечно и не собирали за собой километровую пробку, всегда ставь предохранитель lock_timeout.

SQL · Пример 6: Защищаемся через lock_timeout и ищем блокировщика 
-- [ШАГ 1 — ТЕРМИНАЛ 1] Удерживаем замок на счёте Чарли (id = 3)
BEGIN;
UPDATE lock_accounts SET balance = balance + 10.00 WHERE id = 3;
-- Пока не делаем COMMIT!

-- [ШАГ 2 — ТЕРМИНАЛ 2] Ставим предохранитель на 2 секунды и пробуем обновить id = 3
SET lock_timeout = '2s';
UPDATE lock_accounts SET balance = balance + 20.00 WHERE id = 3;
Ошибка PostgreSQL в Терминале 2 (ровно через 2 секунды)
ERROR:  canceling statement due to lock timeout
CONTEXT:  while updating tuple (0,3) in relation "lock_accounts"

А если убрать lock_timeout (RESET lock_timeout;), снова запустить ожидание в Терминале 2 и открыть третье окно (или выполнить запрос диспетчера, пока кто-то ждёт), вот наш главный диагностический запрос настоящего DBA:

SQL · Диагностика: кто кого заблокировал прямо сейчас 
SELECT
    pid AS waiting_pid,
    pg_blocking_pids(pid) AS blocked_by_pids,
    wait_event_type,
    wait_event,
    state,
    left(query, 60) AS waiting_query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
Ответ PostgreSQL
 waiting_pid | blocked_by_pids | wait_event_type |  wait_event   | state  |                        waiting_query
-------------+-----------------+-----------------+---------------+--------+--------------------------------------------------------------
        1842 | {1819}          | Lock            | transactionid | active | UPDATE lock_accounts SET balance = balance + 20.00 WHERE id
(1 row)

Смотри, как всё прозрачно: процесс 1842 ждёт замок transactionid, а виновник — процесс 1819! Теперь ты можешь посмотреть, что именно делает процесс 1819 (SELECT state, query FROM pg_stat_activity WHERE pid = 1819;), а в экстренной аварии даже вежливо завершить зависшую чужую сессию командой SELECT pg_terminate_backend(1819);. (Не забудь закрыть транзакцию в Терминале 1 через ROLLBACK;!)

Золотое правило продакшена: Перед выполнением ALTER TABLE на работающей базе всегда пиши SET lock_timeout = '2s';. Иначе, если ALTER TABLE встанет в очередь за каким-нибудь долгим SELECT, то все новые SELECT встанут в очередь уже за этим ALTER TABLE — и сайт ляжет за 5 секунд! С lock_timeout миграция просто вежливо отменится, не задев пользователей.

05 Шпаргалка урока перед практикой

Короткий чек-лист перед решением задач практикума:

  • Уровни изоляции: READ COMMITTED (по умолчанию — свежий снимок на каждый запрос), REPEATABLE READ (один снимок на всю транзакцию — нет Non-Repeatable и Phantom Read), SERIALIZABLE (полная защита, включая Write Skew).
  • SELECT ... FOR UPDATE — ставит строчную блокировку, чтобы другие писатели ждали; обычный SELECT при этом не ждёт.
  • NOWAIT и SKIP LOCKED — модификаторы FOR UPDATE: первый сразу бросает ошибку, если строка занята; второй перепрыгивает к следующей свободной строке (идеально для очередей!).
  • Deadlock — взаимное ожидание двух транзакций крест-накрест; PostgreSQL сам разрывает цикл через ~1 сек (deadlock_timeout), а лечится это единым порядком захвата строк (ORDER BY id).
  • Диагностика и защита: pg_blocking_pids(pid) + pg_stat_activity находят виновника зависания, а SET lock_timeout = '3s' спасает от бесконечного ожидания.

06 Мини-практикум для закрепления

Задание 1 (Базовый). Замораживаем отчёт через REPEATABLE READ

Создай таблицу task1_prices (id INT PRIMARY KEY, item TEXT, price INT) с двумя товарами: (1, 'Меч', 500) и (2, 'Щит', 300). В Терминале 1 открой транзакцию с уровнем REPEATABLE READ и посчитай общую сумму цен (SUM(price) = 800). В Терминале 2 подними цену меча до 700, добавь новый товар (3, 'Шлем', 200) и сделай COMMIT. Вернись в Терминал 1, снова посчитай SUM(price) и убедись, что отчёт остался неизменным (800) — ни Non-Repeatable, ни Phantom Read не просочились!

Показать решение
SQL · Решение задания 1 
-- Подготовка (в любом терминале)
DROP TABLE IF EXISTS task1_prices;
CREATE TABLE task1_prices (
    id    INT PRIMARY KEY,
    item  TEXT NOT NULL,
    price INT NOT NULL
);
INSERT INTO task1_prices VALUES (1, 'Меч', 500), (2, 'Щит', 300);

-- [ШАГ 1 — ТЕРМИНАЛ 1] Запускаем отчёт в REPEATABLE READ
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT SUM(price) AS total_price FROM task1_prices;
-- Вернёт: 800. Не закрываем транзакцию!

-- [ШАГ 2 — ТЕРМИНАЛ 2] Меняем старую строку и добавляем новую
BEGIN;
UPDATE task1_prices SET price = 700 WHERE id = 1;
INSERT INTO task1_prices VALUES (3, 'Шлем', 200);
COMMIT;

-- [ШАГ 3 — ТЕРМИНАЛ 1] Повторный расчёт внутри той же транзакции
SELECT SUM(price) AS total_price FROM task1_prices;
-- Всё ещё 800! Ни изменение, ни «фантом» не сломали отчёт.
COMMIT;

-- Проверка после COMMIT (уже в новом снимке): станет 1200
SELECT SUM(price) AS total_price FROM task1_prices;
Задание 2 (Средний). Два воркера разбирают очередь через SKIP LOCKED

Создай таблицу task2_jobs (id SERIAL PRIMARY KEY, task_name TEXT, status TEXT DEFAULT 'pending', worker TEXT) и добавь 3 задачи: 'Отправить письмо', 'Сжать видео', 'Собрать отчёт'. В Терминале 1 открой транзакцию и захвати одну pending-задачу через FOR UPDATE SKIP LOCKED (не коммить!). В Терминале 2 выполни точно такой же запрос — убедись, что воркер №2 мгновенно получил вторую задачу. Обнови статус обеих задач на 'done' с указанием 'worker_1' и 'worker_2' и закоммить оба окна.

Показать решение
SQL · Решение задания 2 
-- Подготовка
DROP TABLE IF EXISTS task2_jobs;
CREATE TABLE task2_jobs (
    id        SERIAL PRIMARY KEY,
    task_name TEXT NOT NULL,
    status    TEXT NOT NULL DEFAULT 'pending',
    worker    TEXT
);
INSERT INTO task2_jobs (task_name) VALUES
    ('Отправить письмо'),
    ('Сжать видео'),
    ('Собрать отчёт');

-- [ШАГ 1 — ТЕРМИНАЛ 1] Воркер 1 берёт первую свободную задачу (id = 1)
BEGIN;
SELECT id, task_name
FROM task2_jobs
WHERE status = 'pending'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- [ШАГ 2 — ТЕРМИНАЛ 2] Воркер 2 берёт следующую незанятую задачу (id = 2)
BEGIN;
SELECT id, task_name
FROM task2_jobs
WHERE status = 'pending'
ORDER BY id
LIMIT 1
FOR UPDATE SKIP LOCKED;

UPDATE task2_jobs SET status = 'done', worker = 'worker_2' WHERE id = 2;
COMMIT;

-- [ШАГ 3 — ТЕРМИНАЛ 1] Воркер 1 завершает задачу 1
UPDATE task2_jobs SET status = 'done', worker = 'worker_1' WHERE id = 1;
COMMIT;

-- Проверка итога
SELECT id, task_name, status, worker FROM task2_jobs ORDER BY id;
Задание 3 (Продвинутый). Почини Deadlock единым порядком блокировок

Создай таблицу task3_wallets (id INT PRIMARY KEY, name TEXT, gold INT) с двумя строками: (10, 'Игрок А', 500) и (20, 'Игрок Б', 500). Напиши шаблон безопасного перевода между id = 10 и id = 20 в обе стороны (в Терминале 1: 100 монет от А к Б; в Терминале 2: 50 монет от Б к А), используя предварительный захват SELECT id FROM task3_wallets WHERE id IN (10, 20) ORDER BY id FOR UPDATE. Запусти оба окна одновременно и убедись, что Deadlock не возникает, а итоговые балансы равны 450 и 550.

Показать решение
SQL · Решение задания 3 
-- Подготовка
DROP TABLE IF EXISTS task3_wallets;
CREATE TABLE task3_wallets (
    id   INT PRIMARY KEY,
    name TEXT NOT NULL,
    gold INT NOT NULL
);
INSERT INTO task3_wallets VALUES (10, 'Игрок А', 500), (20, 'Игрок Б', 500);

-- [ШАГ 1 — ТЕРМИНАЛ 1] Перевод 100 от 10 к 20: захватываем по порядку id!
BEGIN;
SELECT id FROM task3_wallets WHERE id IN (10, 20) ORDER BY id FOR UPDATE;
UPDATE task3_wallets SET gold = gold - 100 WHERE id = 10;
UPDATE task3_wallets SET gold = gold + 100 WHERE id = 20;
-- Пока НЕ коммитим, переходим в Терминал 2!

-- [ШАГ 2 — ТЕРМИНАЛ 2] Перевод 50 от 20 к 10: ТАКОЙ ЖЕ порядок ORDER BY id!
BEGIN;
SELECT id FROM task3_wallets WHERE id IN (10, 20) ORDER BY id FOR UPDATE;
-- Терминал 2 спокойно подождёт на id = 10 (никакого Deadlock!)

-- [ШАГ 3 — ТЕРМИНАЛ 1] Завершаем первый перевод
COMMIT;

-- [ШАГ 4 — ТЕРМИНАЛ 2] «Проснулся» сразу после COMMIT Терминала 1!
UPDATE task3_wallets SET gold = gold - 50 WHERE id = 20;
UPDATE task3_wallets SET gold = gold + 50 WHERE id = 10;
COMMIT;

-- Итог: Игрок А = 450, Игрок Б = 550
SELECT * FROM task3_wallets ORDER BY id;
Задание 4 (Диагностика). Предохранитель lock_timeout и поиск блокировщика

Создай таблицу task4_orders (id INT PRIMARY KEY, note TEXT) с одной строкой (1, 'новый'). В Терминале 1 открой транзакцию и заблокируй строку через UPDATE task4_orders SET note = 'в работе' WHERE id = 1; (не коммить!). В Терминале 2: сначала проверь, что при SET lock_timeout = '2s'; попытка обновить строку id = 1 отменится через 2 секунды с ошибкой; затем выполни запрос к pg_stat_activity, чтобы увидеть PID и статус открытой транзакции из Терминала 1 (ищи state = 'idle in transaction'). В конце закрой транзакцию в Терминале 1.

Показать решение
SQL · Решение задания 4 
-- Подготовка
DROP TABLE IF EXISTS task4_orders;
CREATE TABLE task4_orders (
    id   INT PRIMARY KEY,
    note TEXT NOT NULL
);
INSERT INTO task4_orders VALUES (1, 'новый');

-- [ШАГ 1 — ТЕРМИНАЛ 1] Удерживаем блокировку в открытой транзакции
BEGIN;
UPDATE task4_orders SET note = 'в работе' WHERE id = 1;

-- [ШАГ 2 — ТЕРМИНАЛ 2] Проверяем предохранитель lock_timeout
SET lock_timeout = '2s';
UPDATE task4_orders SET note = 'отменён' WHERE id = 1;
-- Через 2 секунды получишь: ERROR: canceling statement due to lock timeout

-- [ШАГ 3 — ТЕРМИНАЛ 2] Находим зависшую сессию-виновника
SELECT pid, state, left(query, 55) AS last_query
FROM pg_stat_activity
WHERE datname = 'learning_db'
  AND state = 'idle in transaction';

-- [ШАГ 4 — ТЕРМИНАЛ 1] Вежливо закрываем транзакцию
ROLLBACK;
