Логическая репликация и переключение при сбоях (Switchover / Failover)

Главное в этом уроке
  • Поймёшь, когда физического «ксерокса» уже не хватает и на сцену выходит логическая репликация (Publication / Subscription) — с фильтрацией строк, отдельными индексами и возможностью записи на подписчике.
  • Настроишь живую подписку между course_pg_primary (порт 5432) и course_pg_logical (порт 5434), поймаешь реальную ошибку отсутствия REPLICA IDENTITY и узнаешь, почему DDL не реплицируется автоматически.
  • Разберёшься в разнице между плановым переключением (Switchover) и аварийным спасением (Failover), поймёшь магию линий времени (Timeline) и смертельную опасность Split-Brain.
  • Проведёшь настоящее повышение реплики до главного сервера через pg_promote() и научишься чисто восстанавливать кластер после тренировки.

01 Зачем нужна логическая репликация: подписка на новости вместо ксерокса

В Уроках 5.1 и 5.2 мы работали с физической репликацией — она копировала весь кластер PostgreSQL целиком, байт-в-байт. Это идеальный вариант для высокой доступности, но представь три реальные задачи, где «слепой ксерокс» бессилен:

  • Нужна только одна таблица: отделу маркетинга нужна таблица orders (и только оплаченные заказы!), а таблицы с паролями пользователей отдавать им строго запрещено.
  • На реплике нужно писать и добавлять свои индексы: аналитики хотят на своей копии построить 5 тяжёлых индексов под отчёты и сохранять туда собственные таблицы с расчётами — но физический Standby строго Read-Only!
  • Обновление версии без простоя (Zero-Downtime Upgrade): ты хочешь переехать с PostgreSQL 14 на PostgreSQL 16. Физическая репликация требует одинаковой мажорной версии на обоих серверах, а значит — не подойдёт.

Решение — логическая репликация (Logical Replication). Вместо ксерокопии байтов диска она работает как подписка на школьную газету:

  • Издатель (Publisher) читает свой журнал WAL (для этого обязательно нужен wal_level = logical), декодирует сырые байты обратно в понятные события («В таблицу catalog_items вставили строку №5») и публикует их в именованный канал — публикацию (PUBLICATION).
  • Подписчик (Subscriber) оформляет подписку (SUBSCRIPTION), забирает начальный снимок выбранных таблиц, а затем в реальном времени применяет новые события INSERT / UPDATE / DELETE. При этом Подписчик остаётся полноценным Read/Write сервером!
Критерий Физическая репликация (Standby · 5433) Логическая репликация (Subscriber · 5434)
Что копируется Весь кластер целиком (байт-в-байт) Выбранные таблицы, колонки и даже отфильтрованные строки
Запись на приёмнике Запрещена (строго Read-Only) Разрешена! Можно создавать свои таблицы и индексы
Разные версии PostgreSQL Нет (строго одинаковая мажорная версия и ОС) Да! Отлично подходит для переезда с PG 14 на PG 16
Репликация DDL (ALTER TABLE) Да, автоматически Нет! Схему таблиц нужно обновлять на обоих серверах
Главная задача Отказоустойчивость (HA) и снятие нагрузки чтения Интеграция микросервисов, аналитика, апгрейд без простоя
Простая аналогия: Физическая репликация — это зеркало в комнате (ты видишь всю комнату целиком, но не можешь ничего переставить внутри отражения). Логическая репликация — это Telegram-канал с новостями магазина: ты сам выбираешь, на какие товары подписаться, и складываешь их на свои полки как угодно.

02 Настраиваем логическую репликацию в бою (Publication и Subscription)

В нашем файле docker-compose.yaml уже есть отдельный независимый сервер course_pg_logical на порту 5434. Убедись, что сервисы Модуля 5 запущены (docker compose --profile mod5 up -d), и давай настроим живой поток данных от course_pg_primary (5432) к course_pg_logical (5434)!

Практика 1: Создаём таблицу и публикацию на Publisher (порт 5432)

Подключись к Publisher (docker exec -it course_pg_primary psql -U student -d learning_db). Создадим таблицу товаров catalog_items с первичным ключом (почему он жизненно важен — узнаешь в следующем разделе!) и опубликуем её.

SQL · Выполнять на Publisher — course_pg_primary (порт 5432) 
-- 1. Убеждаемся, что включён уровень журнала logical
SHOW wal_level;

-- 2. Безопасный перезапуск: убираем старую публикацию и таблицу
DROP PUBLICATION IF EXISTS catalog_pub;
DROP TABLE IF EXISTS catalog_items;

-- 3. Создаём таблицу товаров с PRIMARY KEY
CREATE TABLE catalog_items (
    id          INT PRIMARY KEY,
    title       TEXT NOT NULL,
    category    TEXT NOT NULL,
    price       NUMERIC(10, 2) NOT NULL CHECK (price > 0),
    is_active   BOOLEAN NOT NULL DEFAULT true
);

-- 4. Наполняем начальными данными
INSERT INTO catalog_items (id, title, category, price, is_active) VALUES
    (1, 'Худи SQL Master',    14500.00, 'Одежда', true),
    (2, 'Термокружка DBA',     6900.00, 'Посуда', true),
    (3, 'Архивный стикерпак',   900.00, 'Мерч',   false)
ON CONFLICT (id) DO NOTHING;

Ой, присмотрись к порядку колонок в INSERT выше — category идёт третьей, а price четвёртой! Давай вставим строки с правильным порядком и сразу создадим публикацию с фильтром строк (фишка PostgreSQL 15+): пусть подписчик получает только активные товары (WHERE (is_active = true)) и без служебной колонки is_active!

SQL · Правильная вставка и публикация с фильтром на Publisher (5432) 
-- Очищаем и вставляем 3 товара с корректным порядком колонок
TRUNCATE TABLE catalog_items;

INSERT INTO catalog_items (id, title, category, price, is_active) VALUES
    (1, 'Худи SQL Master',    'Одежда', 14500.00, true),
    (2, 'Термокружка DBA',    'Посуда',  6900.00, true),
    (3, 'Архивный стикерпак', 'Мерч',     900.00, false);

-- Создаём публикацию: отдаём только 4 колонки и только активные строки!
CREATE PUBLICATION catalog_pub
    FOR TABLE catalog_items (id, title, category, price)
    WHERE (is_active = true);

-- Проверяем список публикаций и фильтры
SELECT pubname, schemaname, tablename, attnames, rowfilter
FROM pg_publication_tables
WHERE pubname = 'catalog_pub';
Ответ PostgreSQL (Publisher · 5432)
   pubname   | schemaname |   tablename   |         attnames          |      rowfilter
-------------+------------+---------------+---------------------------+---------------------
 catalog_pub | public     | catalog_items | {id,title,category,price} | (is_active = true)
(1 row)

Практика 2: Создаём таблицу и подписку на Subscriber (порт 5434)

Теперь подключись во втором окне к Subscriber (docker exec -it course_pg_logical psql -U student -d learning_db). Помни золотое правило: логическая репликация не создаёт таблицы сама, поэтому структуру таблицы catalog_items нужно создать заранее. Зато мы сразу можем повесить на неё собственный индекс и создать рядом локальную таблицу!

SQL · Выполнять на Subscriber — course_pg_logical (порт 5434) 
-- 1. Безопасная очистка прошлой подписки и таблицы
DROP SUBSCRIPTION IF EXISTS catalog_sub;
DROP TABLE IF EXISTS catalog_items, local_marketing_notes;

-- 2. Создаём таблицу-приёмник (колонки совпадают с публикацией!)
CREATE TABLE catalog_items (
    id        INT PRIMARY KEY,
    title     TEXT NOT NULL,
    category  TEXT NOT NULL,
    price     NUMERIC(10, 2) NOT NULL
);

-- 3. Добавляем СВОЙ аналитический индекс, которого нет на Publisher!
CREATE INDEX idx_catalog_category_price ON catalog_items (category, price);

-- 4. Оформляем подписку на course_pg_primary по внутренней сети Docker
CREATE SUBSCRIPTION catalog_sub
    CONNECTION 'host=pg_primary port=5432 dbname=learning_db user=student password=student_pass'
    PUBLICATION catalog_pub;
Ответ PostgreSQL (Subscriber · 5434)
NOTICE:  created replication slot "catalog_sub" on publisher
CREATE SUBSCRIPTION

Посмотри на строчку NOTICE: PostgreSQL сам создал логический слот репликации catalog_sub на сервере pg_primary и запустил начальное копирование! Проверим через пару секунд на Subscriber (5434), какие строки доехали, и заодно проверим, что мы можем спокойно писать в локальные таблицы.

SQL · Проверка данных и локальной записи на Subscriber (порт 5434) 
-- 1. Смотрим скопированные товары: архивного товара id=3 здесь НЕТ!
SELECT id, title, category, price
FROM catalog_items
ORDER BY id;

-- 2. Проверяем, что Subscriber — полноценный Read/Write сервер
CREATE TABLE local_marketing_notes (
    item_id INT PRIMARY KEY,
    note    TEXT NOT NULL
);
INSERT INTO local_marketing_notes VALUES (1, 'Хит продаж осени!');

-- 3. Проверяем статус фонового воркера подписки
SELECT subname, pid, received_lsn, latest_end_lsn
FROM pg_stat_subscription
WHERE subname = 'catalog_sub';
Ответ PostgreSQL (Subscriber · 5434)

----+-----------------+----------+----------

(2 rows)

Практика 3: Проверяем живой поток UPDATE и работу фильтра

А что будет, если на Publisher (5432) мы изменим цену у товара id = 2 и «оживим» архивный товар id = 3 (поставим is_active = true)? Запусти на Publisher (5432), а затем сделай SELECT на Subscriber (5434)!

SQL · Живое обновление на Publisher (порт 5432) 
-- Меняем цену кружки и возвращаем в продажу стикерпак
UPDATE catalog_items SET price = 7200.00 WHERE id = 2;
UPDATE catalog_items SET is_active = true WHERE id = 3;
SQL · Проверка на Subscriber (порт 5434) 
SELECT id, title, price FROM catalog_items ORDER BY id;
Ответ PostgreSQL (Subscriber · 5434)
 id |       title        |  price
----+--------------------+----------
  1 | Худи SQL Master    | 14500.00
  2 | Термокружка DBA    |  7200.00
  3 | Архивный стикерпак |   900.00
(3 rows)

Магия! Когда товар id = 3 стал соответствовать фильтру is_active = true, Publisher автоматически превратил наш UPDATE в команду INSERT для подписчика — и товар появился на 5434. Мы полностью решили задачу из начала раздела: маркетологи получили только нужные товары, смогли построить собственный индекс и записать свои заметки, не трогая главный сервер!

03 Главные грабли логической репликации: REPLICA IDENTITY и DDL

Логическая репликация очень гибкая, но у неё есть три строгих правила, о которые спотыкаются почти все новички.

Ловушка №1: нет ключа — нет UPDATE и DELETE! Представь, что ты отправил другу по рации сообщение: «Исправь оценку у ученика в списке на пятёрку». Друг спрашивает: «У какого именно? У них нет номеров, а Иванов в классе двое!». В PostgreSQL метка, по которой Subscriber однозначно находит строку для UPDATE или DELETE, называется REPLICA IDENTITY. По умолчанию ей служит Primary Key. Если у таблицы в публикации нет Primary Key, PostgreSQL просто не даст её обновить!

Практика 4: Ловим ошибку REPLICA IDENTITY и чиним таблицу

Выполни этот короткий эксперимент на Publisher (порт 5432): создадим таблицу заметок без Primary Key, добавим её в публикацию и попробуем обновить строку.

SQL · Выполнять на Publisher (порт 5432) 
-- Безопасная подготовка таблицы БЕЗ Primary Key
DROP PUBLICATION IF EXISTS broken_pub;
DROP TABLE IF EXISTS audit_notes;

CREATE TABLE audit_notes (
    author TEXT NOT NULL,
    note   TEXT NOT NULL
);

INSERT INTO audit_notes VALUES ('Аня', 'Проверить склад');

-- Создаём публикацию для таблицы без ключа (это сработает!)
CREATE PUBLICATION broken_pub FOR TABLE audit_notes;

-- А вот попытка UPDATE немедленно упадёт с ошибкой:
UPDATE audit_notes SET note = 'Склад проверен' WHERE author = 'Аня';
Ошибка PostgreSQL (Publisher · 5432)
ERROR:  cannot update table "audit_notes" because it does not have a replica identity and publishes updates
HINT:  To enable updating the table, set REPLICA IDENTITY using ALTER TABLE.

Посмотри на подсказку HINT: чтобы починить таблицу, есть два пути — добавить настоящий PRIMARY KEY (лучший вариант) или включить ALTER TABLE audit_notes REPLICA IDENTITY FULL (тогда в WAL будет записываться вся старая строка целиком, и подписчик будет искать её перебором!).

✗ Как НЕ надо
-- На огромной таблице без PK:
ALTER TABLE audit_notes
  REPLICA IDENTITY FULL;

Раздувает журнал WAL в разы и заставляет Subscriber делать полный перебор таблицы на каждый UPDATE/DELETE!

✓ Как правильно
-- Добавляем Primary Key:
ALTER TABLE audit_notes
  ADD COLUMN id BIGSERIAL
  PRIMARY KEY;

В WAL пишется только компактный id, а Subscriber мгновенно находит строку по индексу Primary Key.

Почистим за собой учебную публикацию на Publisher (5432), чтобы не оставлять лишних объектов: DROP PUBLICATION IF EXISTS broken_pub; DROP TABLE IF EXISTS audit_notes;.

Ловушки №2 и №3 (DDL и последовательности):
1. Если ты выполнишь ALTER TABLE catalog_items ADD COLUMN weight INT; только на Publisher, то при следующем INSERT репликация на Subscriber встанет с ошибкой! Правильный порядок миграций: сначала добавляй новую колонку (с NULL или DEFAULT) на Subscriber, и только потом — на Publisher.
2. В PostgreSQL 16 значения последовательностей (SERIAL / IDENTITY) не синхронизируются автоматически. При миграции на новый сервер обязательно подтяни счётчики через setval(), иначе новые вставки упадут с ошибкой duplicate key!

04 Переключение при сбоях: Switchover, Failover, Timeline и Split-Brain

Теперь вернёмся к нашему физическому кластеру Primary (5432) + Standby (5433) и зададим главный вопрос высокой доступности (High Availability): что делать, когда главному серверу нужно уйти на обслуживание или он внезапно сломался?

Представь кабину самолёта, где сидят капитан (Primary) и второй пилот (Standby):

  • Switchover (плановое переключение): капитан хочет сходить за кофе (в мире БД — обновить ядро Linux или заменить диск). Он спокойно говорит: «Убери руки с кнопок, дождись, пока приборы сравняются, теперь ты главный!». Primary останавливает приём новых транзакций, отправляет 100% оставшегося WAL на Standby, Standby становится новым Primary, а старый Primary превращается в Standby. Потеря данных: 0 байт (RPO = 0).
  • Failover (аварийное переключение): капитан внезапно потерял сознание (сервер Primary сгорел, пропало питание в дата-центре). Второй пилот немедленно перехватывает штурвал командой повышения роли — Promotion (pg_promote() или pg_ctl promote), чтобы спасти самолёт как можно быстрее (минимизировать время простоя — RTO, Recovery Time Objective). Если репликация была асинхронной, последние миллисекунды записи могут потеряться (RPO > 0).

Что такое Timeline (линия времени) и чем страшен Split-Brain?

Как только Standby повышается до роли Primary, PostgreSQL создаёт новую линию времени (Timeline ID, TLI): была Timeline 1 — стала Timeline 2. Зачем? Представь фильм про путешествия во времени: в момент аварии история кластера разветвилась на две параллельные вселенные. Нумерация Timeline гарантирует, что старые файлы WAL из «умершей вселенной 1» никогда случайно не перемешаются с новыми файлами из «вселенной 2»!

А теперь представь самый страшный кошмар инженера БД — Split-Brain («расщепление мозга»):

Между Primary и Standby на 30 секунд пропала сеть. На самом деле старый Primary жив, просто «оглох». Администратор в панике повысил Standby до нового Primary. Сеть починили — и теперь в системе работают ДВА Primary одновременно! Половина покупателей оформляет заказы на сервере A, половина — на сервере B. Базы разошлись навсегда, и автоматически склеить их обратно невозможно!

Характеристика Switchover (плановое) Failover (аварийное)
Причина Обслуживание, обновление ОС/железа, переезд Внезапный отказ Primary, сбой питания или диска
Потеря данных (RPO) 0 (всегда ждём полного совпадения LSN) 0 при sync; возможны потери при async
Время простоя (RTO) Обычно 1–5 секунд (контролируемо) 10–60 секунд (детекция сбоя + promote + переключение трафика)
Что со старым Primary Корректно переводится в роль Standby Изолируется (Fencing), а затем чинится через pg_rewind или pg_basebackup

Практика 5: Проводим реальный Failover (Promotion) на course_pg_standby

Давай проживём момент переключения своими руками! Сначала посмотрим текущий номер линии времени (timeline_id) на Standby (порт 5433), затем поднимем его в роль Primary функцией pg_promote() и проверим, что он стал принимать запись!

SQL · Шаг 1: проверяем роль и Timeline ДО повышения на Standby (порт 5433) 
-- Смотрим статус и номер линии времени до промоушена
SELECT
    pg_is_in_recovery() AS is_standby,
    (SELECT timeline_id FROM pg_control_checkpoint()) AS current_timeline;

-- ПРОИЗВОДИМ FAILOVER: превращаем Standby в самостоятельный Primary!
SELECT pg_promote(wait => true, wait_seconds => 30);
Ответ PostgreSQL (course_pg_standby · 5433)
 is_standby | current_timeline
------------+------------------
 t          |                1
(1 row)

 pg_promote
------------
 t
(1 row)
SQL · Шаг 2: проверяем новую роль, Timeline 2 и запись на бывшем Standby (5433) 
-- 1. Теперь is_standby = f, а current_timeline = 2!
SELECT
    pg_is_in_recovery() AS is_standby,
    (SELECT timeline_id FROM pg_control_checkpoint()) AS current_timeline;

-- 2. Пробуем записать данные туда, где минуту назад была ошибка Read-Only!
DROP TABLE IF EXISTS failover_proof;
CREATE TABLE failover_proof (
    id         SERIAL PRIMARY KEY,
    message    TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
INSERT INTO failover_proof (message)
VALUES ('Я новый Primary на Timeline 2!');

SELECT id, message FROM failover_proof;
Ответ PostgreSQL (course_pg_standby · 5433 — теперь это Primary!)
 is_standby | current_timeline
------------+------------------
 f          |                2
(1 row)

 id |            message
----+---------------------------------
  1 | Я новый Primary на Timeline 2!
(1 row)

Посмотри, что произошло за доли секунды: PostgreSQL сам удалил файл standby.signal, перешёл на Timeline 2, закрыл старый walreceiver и открыл сервер на запись! А на нашем старом course_pg_primary (порт 5432) представление pg_stat_replication сразу опустело — реплика отцепилась и стала независимым сервером.

Практика 6: Как вернуть учебную реплику в строй после тренировки

Сейчас в нашем учебном Docker Compose как раз получилась учебная модель Split-Brain: оба сервера (5432 и 5433) открыты на запись и живут в разных вселенных (TLI 1 и TLI 2)! В реальной жизни старый Primary возвращают в кластер с помощью утилиты pg_rewind (она быстро откатывает только разошедшиеся страницы без полного копирования) или пересоздают через pg_basebackup. Давай чисто сбросим том course_pg_standby, чтобы он снова стал послушной физической репликой для следующих уроков:

Bash · Возвращаем course_pg_standby в режим физической реплики 
# 1. Останавливаем и удаляем контейнер бывшей реплики
docker compose --profile mod5 stop pg_standby
docker compose --profile mod5 rm -f pg_standby

# 2. Удаляем её старый том с Timeline 2 (имя проекта в docker-compose.yaml = db-course)
docker volume rm db-course_pg_standby_data

# 3. Запускаем заново — скрипт сам выполнит свежий pg_basebackup с Primary!
docker compose --profile mod5 up -d pg_standby

# 4. Проверяем, что Standby снова в строю (должно вернуть t)
sleep 3
docker exec course_pg_standby psql -U student -d learning_db -c "SELECT pg_is_in_recovery();"
Ответ терминала
 pg_is_in_recovery
-------------------
 t
(1 row)
✗ Как НЕ надо
# Выполнить pg_promote() на Standby, не убедившись, что старый Primary выключен!
psql -h standby -c "SELECT pg_promote();"
# Приложение продолжает писать часть запросов на старый Primary → SPLIT-BRAIN!

Ручной failover без отключения старого Primary (Fencing / STONITH) и перенаправления трафика гарантированно приводит к расхождению данных.

✓ Как правильно
# В продакшене переключением управляет оркестратор с кворумом (Patroni + etcd)
patronictl -c /etc/patroni.yml switchover   # планово (RPO = 0)
# При аварии Patroni сам проверит кворум, изолирует старый узел, сделает promote и pg_rewind!

Оркестратор (Patroni) использует распределённое хранилище ключей (etcd / Consul) как «судью»: роль Primary всегда принадлежит ровно одному серверу, который удерживает лидерский замок (Leader Lock).

Совет на будущее: Запомни связку, которую спрашивают на каждом собеседовании по PostgreSQL HA: Patroni + etcd + HAProxy. etcd решает, кто сейчас главный (защита от Split-Brain), Patroni управляет запуском, pg_promote() и pg_rewind, а HAProxy (или VIP) мгновенно перенаправляет трафик приложения на актуальный Primary.

05 Шпаргалка урока и мини-практикум

Короткая шпаргалка перед практикой

Инструмент / понятие Зачем нужен и где выполняется
CREATE PUBLICATION ... FOR TABLE t WHERE (...) Создаёт канал логической репликации на Publisher (можно фильтровать колонки и строки).
CREATE SUBSCRIPTION ... CONNECTION '...' Подписывает Subscriber на публикацию; автоматически создаёт логический слот на Publisher.
REPLICA IDENTITY Способ идентификации строк при UPDATE/DELETE (по умолчанию PRIMARY KEY; без него изменения в опубликованной таблице упадут с ошибкой).
pg_stat_subscription / pg_stat_subscription_stats Мониторинг работы и счётчик ошибок (apply_error_count) на Subscriber.
pg_promote() и pg_control_checkpoint() Повышает физический Standby до Primary и позволяет проверить текущий timeline_id.
Switchover vs Failover Плановое переключение (RPO = 0) против аварийного спасения при смерти Primary (требует защиты от Split-Brain).

Убедись, что контейнеры course_pg_primary (5432), course_pg_standby (5433) и course_pg_logical (5434) запущены (docker compose --profile mod5 up -d). Все 4 задания полностью автономны.

Задание 1 (Базовый). Логическая репликация с фильтром «только крупные заказы»

На Publisher (5432) создай таблицу vip_sales (id INT PRIMARY KEY, customer TEXT, amount NUMERIC(10, 2)), вставь 3 заказа с суммами 1200, 8500 и 24000, и создай публикацию vip_sales_pub с фильтром WHERE (amount >= 5000). На Subscriber (5434) создай такую же таблицу и подписку vip_sales_sub. Проверь, что на 5434 приехали ровно 2 строки (заказ на 1200 отфильтровался).

Показать решение
SQL · Шаг 1: выполнить на Publisher (5432) 
DROP PUBLICATION IF EXISTS vip_sales_pub;
DROP TABLE IF EXISTS vip_sales;

CREATE TABLE vip_sales (
    id       INT PRIMARY KEY,
    customer TEXT NOT NULL,
    amount   NUMERIC(10, 2) NOT NULL
);

INSERT INTO vip_sales (id, customer, amount) VALUES
    (1, 'Иван',   1200.00),
    (2, 'Мария',  8500.00),
    (3, 'Алексей', 24000.00);

CREATE PUBLICATION vip_sales_pub
    FOR TABLE vip_sales
    WHERE (amount >= 5000);
SQL · Шаг 2: выполнить на Subscriber (5434) 
DROP SUBSCRIPTION IF EXISTS vip_sales_sub;
DROP TABLE IF EXISTS vip_sales;

CREATE TABLE vip_sales (
    id       INT PRIMARY KEY,
    customer TEXT NOT NULL,
    amount   NUMERIC(10, 2) NOT NULL
);

CREATE SUBSCRIPTION vip_sales_sub
    CONNECTION 'host=pg_primary port=5432 dbname=learning_db user=student password=student_pass'
    PUBLICATION vip_sales_pub;

-- Подожди 1–2 секунды и проверь результат:
SELECT id, customer, amount FROM vip_sales ORDER BY id;
Задание 2 (Практический). Сравниваем возможности записи на физическом Standby и логическом Subscriber

Проверь на практике ключевое архитектурное отличие двух видов репликации: напиши запрос, который создаёт аналитический индекс или локальную таблицу bi_custom_summary (metric TEXT PRIMARY KEY, val INT) и вставляет туда строку ('daily_kpi', 42). Попробуй выполнить его на Standby (5433) и на Subscriber (5434), а также проверь на обоих узлах значение pg_is_in_recovery(). Объясни, почему результаты противоположны.

Показать решение

На физическом Standby (5433) функция pg_is_in_recovery() вернёт t, а CREATE TABLE упадёт с ошибкой cannot execute CREATE TABLE in a read-only transaction — он копирует сырые страницы диска. На логическом Subscriber (5434) функция вернёт f (это самостоятельный Primary-сервер для своих баз!), поэтому таблица и строка создадутся без ошибок.

SQL · Выполнить на 5433 (будет ошибка) и на 5434 (успех) 
-- 1. Проверяем режим восстановления
SELECT pg_is_in_recovery() AS is_physical_standby;

-- 2. Создаём локальную таблицу аналитиков
DROP TABLE IF EXISTS bi_custom_summary;
CREATE TABLE bi_custom_summary (
    metric TEXT PRIMARY KEY,
    val    INT NOT NULL
);
INSERT INTO bi_custom_summary (metric, val) VALUES ('daily_kpi', 42);

SELECT * FROM bi_custom_summary;
Задание 3 (Инженерный). Мониторинг всех логических слотов на Publisher

Помнишь из Урока 5.1, что забытый слот может заполнить диск Primary? Каждая логическая подписка автоматически создаёт логический слот на Publisher! Напиши SQL-запрос для Publisher (5432) к pg_replication_slots, который покажет только слоты с slot_type = 'logical': имя слота, базу, статус active, wal_status, позицию confirmed_flush_lsn и объём удерживаемого WAL в читаемом виде (pg_size_pretty).

Показать решение
SQL · Выполнять на Publisher (порт 5432) 
SELECT
    slot_name,
    database,
    active,
    wal_status,
    confirmed_flush_lsn,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
    ) AS retained_wal_size
FROM pg_replication_slots
WHERE slot_type = 'logical'
ORDER BY slot_name;
Задание 4 (Отладка). Починить сломанную логическую репликацию после DDL-миграции

Смоделируй классический баг на проде: создай пару таблиц ddl_demo (id INT PRIMARY KEY, title TEXT), публикацию ddl_pub на Publisher (5432) и подписку ddl_sub на Subscriber (5434). Затем добавь новую колонку price NUMERIC DEFAULT 0 только на Publisher и вставь строку (1, 'Книга', 1500). Посмотри на Subscriber в представление pg_stat_subscription_stats (колонка apply_error_count должна вырасти!), а затем исправь схему на Subscriber так, чтобы строка автоматически доехала без пересоздания подписки!

Показать решение
SQL · Шаг 1: настройка на Publisher (5432) и Subscriber (5434) 
-- На Publisher (5432):
DROP PUBLICATION IF EXISTS ddl_pub;
DROP TABLE IF EXISTS ddl_demo;
CREATE TABLE ddl_demo (id INT PRIMARY KEY, title TEXT);
CREATE PUBLICATION ddl_pub FOR TABLE ddl_demo;

-- На Subscriber (5434):
DROP SUBSCRIPTION IF EXISTS ddl_sub;
DROP TABLE IF EXISTS ddl_demo;
CREATE TABLE ddl_demo (id INT PRIMARY KEY, title TEXT);
CREATE SUBSCRIPTION ddl_sub
    CONNECTION 'host=pg_primary port=5432 dbname=learning_db user=student password=student_pass'
    PUBLICATION ddl_pub;
SQL · Шаг 2: ломаем схему на Publisher (5432) 
ALTER TABLE ddl_demo ADD COLUMN price NUMERIC DEFAULT 0;
INSERT INTO ddl_demo (id, title, price) VALUES (1, 'Книга', 1500);
SQL · Шаг 3: диагностируем и чиним на Subscriber (5434) 
-- 1. Видим растущий счётчик ошибок применения (apply_error_count > 0)
SELECT subname, apply_error_count, sync_error_count
FROM pg_stat_subscription_stats
WHERE subname = 'ddl_sub';

-- 2. Добавляем недостающую колонку на Subscriber
ALTER TABLE ddl_demo ADD COLUMN price NUMERIC DEFAULT 0;

-- 3. Через несколько секунд apply worker сам повторит попытку, и строка появится!
SELECT id, title, price FROM ddl_demo;
