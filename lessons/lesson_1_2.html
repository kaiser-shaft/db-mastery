01 Типы данных: каждому грузу — своя коробка

Когда ты создаёшь таблицу, для каждой колонки нужно строго указать её тип данных. Представь склад: суп наливают в термос, обувь кладут в картонную коробку, а документы — в папку. Если налить суп в бумажный конверт, всё испортится.

В PostgreSQL точно так же: если колонка price имеет числовой тип, база не позволит записать туда текст 'бесплатно'. Кроме того, правильный тип экономит место на диске и позволяет базе быстро считать суммы, сортировать даты и сравнивать числа.

Тип в PostgreSQL Что внутри Когда использовать (примеры)
INT / BIGINT Целые числа (без запятой). INT — до 2 млрд, BIGINT — до 9 квинтиллионов. Возраст, остаток на складе (INT); главные номера id в крупных проектах (BIGINT).
NUMERIC(10, 2) Точные дробные числа: всего до 10 цифр, из них 2 после запятой (например, 12500.50). Всегда для денег, цен, скидок, процентов и точных весов.
TEXT или VARCHAR(n) Любой текст. VARCHAR(50) ограничивает длину 50 символами, TEXT — без лимита. Имя, email, название товара, статус заказа. В PostgreSQL TEXT работает так же быстро, как VARCHAR.
BOOLEAN Логическое «Да» или «Нет» (true / false). Оплачен ли заказ (is_paid), активен ли аккаунт (is_active).
DATE Только календарная дата без времени: '2026-11-25'. День рождения, дата начала акции, срок годности.
TIMESTAMPTZ Дата + точное время + часовой пояс (timestamp with time zone). Момент регистрации или покупки (created_at). Правильно учитывает разницу часовых поясов.

Эксперимент с «пропавшей копейкой»: почему не FLOAT?

В компьютерах есть «быстрые, но примерные» дробные числа — FLOAT (в PostgreSQL называется DOUBLE PRECISION). Они хороши для 3D-игр и физики, но из-за двоичной системы дают крошечные погрешности. Проверь сам в psql:

SQL · Складываем 0.1 + 0.2 двумя способами 
-- Двойное двоеточие :: превращает значение в указанный тип
SELECT
    0.1::DOUBLE PRECISION + 0.2::DOUBLE PRECISION AS float_sum,
    0.1::NUMERIC          + 0.2::NUMERIC          AS numeric_sum;
Ответ PostgreSQL
      float_sum      | numeric_sum
---------------------+-------------
 0.30000000000000004 |         0.3
(1 row)
✗ Как НЕ надо (для денег)
price DOUBLE PRECISION

На миллионах покупок «хвостики» вроде 0.00000000000000004 накопятся, и выручка магазина перестанет сходиться с банком.

✓ Как правильно (для денег)
price NUMERIC(10, 2)

Считает десятичные дроби с идеальной точностью до последней копейки/тиына.

02 Ограничения (Constraints): «охранники» на входе

Одних типов данных мало: число -5000 — вполне нормальный NUMERIC, но худи не может стоить минус пять тысяч! Чтобы в базу не пролез мусор, на колонки ставят ограничения (constraints). Как строгие охранники на входе, они проверяют каждую новую строку и отклоняют её с ошибкой, если нарушено хотя бы одно правило.

Ограничение Что проверяет «охранник» Жизненный пример
PRIMARY KEY Главный уникальный номер строки. Не повторяется и не бывает пустым. В таблице только один. id клиента или товара — как ИИН или номер паспорта.
NOT NULL Запрещает оставлять ячейку пустой (NULL). У товара обязательно должно быть название и цена.
UNIQUE Значение уникально во всей колонке (дубликаты запрещены). email или никнейм игрока.
CHECK (...) Любое твоё логическое правило (как if в коде). CHECK (price > 0), CHECK (rating BETWEEN 1 AND 5).
FOREIGN KEY Проверяет, что указанный id реально существует в другой таблице. Нельзя создать заказ для несуществующего клиента №999.
DEFAULT ... «Помощник»: подставит значение сам, если ты его не передал. created_at TIMESTAMPTZ DEFAULT now() — сам запишет текущее время.

Как база сама выдаёт номера? (Автоинкремент)

В Уроке 1.1 мы писали номера 1, 2, 3 вручную. В реальных проектах номера выдаёт сам PostgreSQL — как автомат с талончиками в поликлинике:

SQL · Современный автоинкремент 
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
А что такое SERIAL? В старых учебниках часто пишут id SERIAL PRIMARY KEY. Это до сих пор работает, но в современном PostgreSQL 16 стандартом считается GENERATED ALWAYS AS IDENTITY — оно безопаснее и защищает счётчик от случайных ручных правок.

Что будет, если удалить клиента с заказами? (Правило ON DELETE)

Когда таблица orders ссылается на customers через внешний ключ, ты сам выбираешь реакцию базы на попытку удалить клиента:

  • ON DELETE RESTRICT (по умолчанию) — «Не дам удалить!». База запретит удалять клиента, пока у него есть заказы. Лучший выбор для магазинов и банков.
  • ON DELETE CASCADE — «Эффект домино». Удалил клиента — база автоматически снесёт и все его заказы. Удобно для комментариев удалённого поста, но опасно для денег!
  • ON DELETE SET NULL — «Забыть автора». Клиент удалится, а в его заказах в поле customer_id запишется пустота NULL.

03 Строим базу магазина школьного мерча (CREATE TABLE)

Спроектируем сквозную базу нашего курса: покупатели (customers), товары (products) и заказы (orders). Посмотри на схему связей перед тем, как писать код:

Подключись к learning_db через psql:

BASH 
docker exec -it course_pg_primary psql -U student -d learning_db

Важен порядок создания: сначала создаём независимые таблицы (customers и products), а затем orders, которая на них ссылается:

SQL · Таблица 1: Покупатели (customers) 
CREATE TABLE customers (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name  TEXT NOT NULL,
    email      TEXT NOT NULL UNIQUE,
    age        INT CHECK (age >= 12 AND age <= 120),
    is_active  BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
SQL · Таблица 2: Товары (products) 
CREATE TABLE products (
    id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title     TEXT NOT NULL UNIQUE,
    price     NUMERIC(10, 2) NOT NULL CHECK (price > 0),
    stock_qty INT NOT NULL DEFAULT 0 CHECK (stock_qty >= 0)
);
SQL · Таблица 3: Заказы (orders) 
CREATE TABLE orders (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
    product_id  BIGINT NOT NULL REFERENCES products(id)  ON DELETE RESTRICT,
    quantity    INT NOT NULL CHECK (quantity > 0),
    -- Разрешаем только 4 конкретных статуса (никаких опечаток вроде 'payed'!)
    status      TEXT NOT NULL DEFAULT 'new'
                CHECK (status IN ('new', 'paid', 'shipped', 'cancelled')),
    ordered_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

Проверяем результат в psql:

SQL · Проверяем список таблиц 
\dt
Ответ PostgreSQL
          List of relations
 Schema |   Name    | Type  |  Owner
--------+-----------+-------+----------
 public | customers | table | postgres
 public | orders    | table | postgres
 public | products  | table | postgres
(3 rows)
Стиль имён в SQL: Пиши названия таблиц и колонок маленькими английскими буквами через подчёркивание (snake_case: full_name, stock_qty), а имена таблиц — во множественном числе (customers, orders).

04 Наполняем базу (INSERT) и тестируем «охранников»

Чтобы положить строки в таблицу, используется команда INSERT INTO. Разберём 5 главных приёмов на практике.

Пример 1. Вставка одной строки (DEFAULT и автоинкремент работают сами)

Заметь: мы не передаём id, is_active и created_at — PostgreSQL сам выдаст номер 1, поставит true и запишет текущее время.

SQL · Первая запись в customers 
INSERT INTO customers (full_name, email, age)
VALUES ('Артём Смирнов', 'artem@school.kz', 16);

SELECT id, full_name, email, age, is_active FROM customers;
Ответ PostgreSQL
 id |   full_name   |      email      | age | is_active
----+---------------+-----------------+-----+-----------
  1 | Артём Смирнов | artem@school.kz |  16 | t
(1 row)

Пример 2. Вставка пачкой (Multi-row INSERT) + суперсила RETURNING

Можно вставлять сразу десятки строк через запятую. А если дописать в конце RETURNING ..., база сразу покажет, что именно вставила (вместе со сгенерированными id) — отдельный SELECT не нужен!

SQL · Добавляем ещё покупателей и витрину товаров 
-- У Дины age = NULL (пусто), потому что NOT NULL на возраст мы не ставили
INSERT INTO customers (full_name, email, age)
VALUES
    ('Алина Нурланова', 'alina@school.kz', 15),
    ('Максим Волков',   'max@school.kz',   17),
    ('Дина Касымова',   'dina@school.kz',  NULL)
RETURNING id, full_name, age;

INSERT INTO products (title, price, stock_qty)
VALUES
    ('Худи «SQL Master»',    14500.00, 15),
    ('Стикерпак «Postgres»',  1200.50, 80),
    ('Значок со слоником',     850.00, 40),
    ('Термокружка кодера',    6900.00, 10)
RETURNING id, title, price;
Ответ PostgreSQL (второй запрос)
 id |        title         |  price
----+----------------------+----------
  1 | Худи «SQL Master»    | 14500.00
  2 | Стикерпак «Postgres» |  1200.50
  3 | Значок со слоником   |   850.00
  4 | Термокружка кодера   |  6900.00
(4 rows)

Пример 3. Оформляем заказы (связываем таблицы по id)

SQL · Вставляем 3 реальных заказа 
INSERT INTO orders (customer_id, product_id, quantity, status)
VALUES
    (1, 1, 1, 'paid'),    -- Артём (1) купил 1 Худи (1)
    (2, 2, 3, 'new'),     -- Алина (2) заказала 3 Стикерпака (2)
    (1, 3, 2, 'shipped')  -- Артём (1) заказал 2 Значка (3)
RETURNING id, customer_id, product_id, quantity, status;
Ответ PostgreSQL
 id | customer_id | product_id | quantity | status
----+-------------+------------+----------+---------
  1 |           1 |          1 |        1 | paid
  2 |           2 |          2 |        3 | new
  3 |           1 |          3 |        2 | shipped
(3 rows)

Пример 4. Краш-тест: пробуем «обмануть» наших охранников!

Лучший способ понять ограничения — специально их нарушить. Попробуй выполнить эти 4 «плохих» запроса по очереди и посмотри на реакцию PostgreSQL:

SQL · Тест 1 (UNIQUE) и Тест 2 (CHECK) 
-- 1. Пробуем занять уже существующую почту Артёма
INSERT INTO customers (full_name, email, age)
VALUES ('Клон Артёма', 'artem@school.kz', 16);

-- 2. Пробуем поставить отрицательную цену
INSERT INTO products (title, price, stock_qty)
VALUES ('Секретный баг', -500.00, 5);
Ошибки PostgreSQL
ERROR:  duplicate key value violates unique constraint "customers_email_key"
DETAIL:  Key (email)=(artem@school.kz) already exists.

ERROR:  new row for relation "products" violates check constraint "products_price_check"
DETAIL:  Failing row contains (5, Секретный баг, -500.00, 5).
SQL · Тест 3 (NOT NULL) и Тест 4 (FOREIGN KEY) 
-- 3. Забыли указать обязательное имя покупателя
INSERT INTO customers (email, age)
VALUES ('ghost@school.kz', 15);

-- 4. Пробуем оформить заказ для несуществующего клиента №999
INSERT INTO orders (customer_id, product_id, quantity)
VALUES (999, 1, 1);
Ошибки PostgreSQL
ERROR:  null value in column "full_name" of relation "customers" violates not-null constraint

ERROR:  insert or update on table "orders" violates foreign key constraint "orders_customer_id_fkey"
DETAIL:  Key (customer_id)=(999) is not present in table "customers".

Пример 5. Вежливая вставка без падений (ON CONFLICT)

Если ты повторно загружаешь прайс-лист и хочешь тихо пропустить уже существующие товары (а не ронять запрос ошибкой UNIQUE), допиши ON CONFLICT DO NOTHING:

SQL · Худи пропустится, а Кепка добавится 
INSERT INTO products (title, price, stock_qty)
VALUES
    ('Худи «SQL Master»', 14500.00, 15),
    ('Кепка «DB Admin»',   4200.00, 25)
ON CONFLICT (title) DO NOTHING
RETURNING id, title;
Ответ PostgreSQL
 id |      title
----+------------------
  5 | Кепка «DB Admin»
(1 row)
✗ Как НЕ надо
INSERT INTO products
VALUES (DEFAULT, 'Шарф', 3000, 5);

Без списка колонок запрос сломается, как только завтра в таблицу добавят новую колонку (например, discount).

✓ Как правильно
INSERT INTO products (title, price, stock_qty)
VALUES ('Шарф', 3000, 5);

Всегда явно перечисляй колонки — код читается легко и переживёт любые изменения таблицы.

05 Мини-практикум для закрепления

Выполни эти 4 задания в своей базе learning_db (таблицы customers, products и orders уже должны быть созданы), прежде чем открывать решение.

Задание 1. Новый клиент и его первый заказ

Добавь в customers нового покупателя и с помощью RETURNING id сразу узнай его номер. Затем оформи от его имени заказ в orders на 2 термокружки (product_id = 4) со статусом по умолчанию (не указывай колонку status!).

Показать решение
SQL 
-- Шаг 1: добавляем покупателя и узнаём его id (допустим, 5)
INSERT INTO customers (full_name, email, age)
VALUES ('Тимур Алиев', 'timur@school.kz', 16)
RETURNING id, full_name;

-- Шаг 2: оформляем заказ (подставь полученный id вместо 5)
INSERT INTO orders (customer_id, product_id, quantity)
VALUES (5, 4, 2)
RETURNING *;
Задание 2. Проектируем таблицу отзывов (reviews)

Создай таблицу reviews с колонками: id (автоинкремент BIGINT), customer_id и product_id (внешние ключи NOT NULL), rating (INT от 1 до 5), comment (TEXT, может быть пустым), created_at (TIMESTAMPTZ DEFAULT now()). Бонус: запрети одному клиенту оставлять два отзыва на один товар через UNIQUE (customer_id, product_id).

Показать решение
SQL 
CREATE TABLE reviews (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
    product_id  BIGINT NOT NULL REFERENCES products(id)  ON DELETE CASCADE,
    rating      INT NOT NULL CHECK (rating BETWEEN 1 AND 5),
    comment     TEXT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (customer_id, product_id)
);
Задание 3. Наполняем отзывы и ловим «тролля»

1) Вставь пачкой 2 корректных отзыва в reviews (например, Артём оценил худи на 5, а Алина — стикерпак на 4 без комментария).
2) Попробуй вставить отзыв с оценкой 10 (проверь CHECK).
3) Попробуй вставить второй отзыв от Артёма на то же худи (проверь составной UNIQUE).

Показать решение
SQL 
-- 1. Две правильные записи
INSERT INTO reviews (customer_id, product_id, rating, comment)
VALUES
    (1, 1, 5, 'Очень мягкое и тёплое худи!'),
    (2, 2, 4, NULL)
RETURNING *;

-- 2. Упадёт из-за CHECK (rating BETWEEN 1 AND 5)
INSERT INTO reviews (customer_id, product_id, rating, comment)
VALUES (3, 1, 10, 'Огонь!');

-- 3. Упадёт из-за UNIQUE (customer_id, product_id)
INSERT INTO reviews (customer_id, product_id, rating, comment)
VALUES (1, 1, 5, 'Ещё раз 5 звёзд!');
Задание 4. Проверка щита ON DELETE RESTRICT

Попробуй удалить Артёма (id = 1) командой DELETE FROM customers WHERE id = 1; и объясни, почему база отказала. А потом попробуй удалить Дину (id = 4), у которой нет заказов, и сравни результат (если захочешь вернуть Дину для Урока 1.3 — просто добавь её обратно!).

Показать решение
SQL 
-- Упадёт с ошибкой! На Артёма (id = 1) ссылаются заказы в orders
DELETE FROM customers WHERE id = 1;

-- Сработает спокойно: на Дину (id = 4) не ссылается ни один заказ
DELETE FROM customers WHERE id = 4 RETURNING id, full_name;

-- Вернём Дину обратно, чтобы её NULL-возраст пригодился в Уроке 1.3!
INSERT INTO customers (full_name, email, age)
VALUES ('Дина Касымова', 'dina@school.kz', NULL);
