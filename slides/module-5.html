01 · Зачем нужна репликация

Проблема одного сервера: SPOF, Primary и Hot Standby

✗ Один сервер (SPOF)
  • Единая точка отказа: авария диска или сбой сервера полностью останавливают работу.
  • Очередь на чтение: тяжёлые отчёты от аналитиков тормозят оплату заказов.
✓ Primary + Hot Standby
  • Primary (:5432): принимает все записи (INSERT/UPDATE/DELETE) и критичные чтения.
  • Hot Standby (:5433): держит точную копию и разгружает главный сервер от тяжёлых SELECT.
🖨️
Аналогия «живого ксерокса»: физическая репликация копирует не отдельные SQL-команды, а весь кластер целиком — все БД, роли и индексы байт-в-байт.

02 · Архитектура под капотом

Как две базы остаются одинаковыми: WAL и LSN

1

Базовый снимок · pg_basebackup

Копирует каталог $PGDATA целиком на старте реплики.

2

Дневник действий · WAL + LSN

Каждая правка 8-КБ страницы получает адрес LSN (0/3000148).

3

Прямой эфир · walsender → walreceiver

Свежие байты WAL мгновенно передаются по TCP на Standby.

4

Повтор движений · startup (WAL Replay)

Применяет принятые WAL-правки к локальным файлам таблиц.

03 · Распределение нагрузки

Read/Write Splitting: разделяем оплаты и отчёты

Операция / метрика Primary (порт 5432) Standby (порт 5433)
CREATE / INSERT / UPDATE Выполняется и пишется в WAL Ошибка! Только чтение
SELECT (тяжёлые отчёты) Выполняется (нагружает CPU/диск) Выполняется (hot_standby = on)
Позиция журнала WAL pg_current_wal_lsn() pg_last_wal_replay_lsn()
✗ Как НЕ надо
# Все сервисы идут на Primary
APP_DB_PORT=5432
BI_REPORTS_PORT=5432

Тяжёлый отчёт аналитиков съедает CPU и диск — клиенты не могут оплатить заказ.

✓ Как правильно
# Запись и транзакции -> Primary
APP_WRITE_PORT=5432
# Тяжёлые отчёты -> Standby
BI_READ_PORT=5433

Read/Write Splitting разгружает главный сервер без дублирования логики.

⚡
Важная оговорка (Read-your-writes): экран «Спасибо за заказ!» в миллисекунду после оплаты оставляй на Primary — из-за сетевой задержки Standby может отстать на доли секунды.

05 · Слоты репликации (Replication Slots)

Как спасти реплику от потери WAL при обрыве сети

Катастрофа без слота (если Standby отстал > 128MB)
FATAL: could not receive data from WAL stream:
ERROR: requested WAL segment
  000000010000000000000005 has already been removed
🔖 Слот — «закладка в архиве»
  • Без слота Primary удаляет старые 16-МБ сегменты WAL сверх wal_keep_size.
  • Replication Slot запрещает удалять WAL новее restart_lsn, пока реплика его не заберёт.
  • Аргумент true сразу резервирует текущую точку LSN.
SQL Практика 7 · Primary (:5432) · Создать, проверить, удалить 
-- 1. Создаём физический слот с резервированием WAL
SELECT * FROM pg_create_physical_replication_slot('standby_slot_1', true);

-- 2. Смотрим, сколько байт WAL удерживает слот
SELECT slot_name, slot_type, active, restart_lsn, wal_status,
  pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
    AS retained_wal
FROM pg_replication_slots;

-- 3. Обязательно удаляем неактивный учебный слот!
SELECT pg_drop_replication_slot('standby_slot_1');

05 · Инженерная ловушка

Забытый слот и предохранитель max_slot_wal_keep_size

Слот работает безотказно, но слепо: если реплика умерла навсегда (active = f), Primary будет копить WAL до 0 байт на диске и аварийно упадёт сам!

✗ Как НЕ надо
-- Создать слот и забыть мёртвую реплику
SELECT pg_create_physical_replication_slot(
  'old_replica_slot', true
);
-- max_slot_wal_keep_size = -1 (без лимита!)

Слот с active = f заблокирует очистку WAL. Через несколько часов активной записи Primary забьёт диск и остановится.

✓ Как правильно
-- 1. Включаем предохранитель (напр., 2 ГБ)
ALTER SYSTEM SET max_slot_wal_keep_size = '2GB';
SELECT pg_reload_conf();

-- 2. Мониторим заброшенные слоты
SELECT slot_name, active, wal_status
FROM pg_replication_slots;

max_slot_wal_keep_size ограничивает аппетит слота: лучше потерять одну сломанную реплику, чем уронить главный сервер.

🚨
Классика продакшена в 3 часа ночи: удалили контейнер Standby, но забыли pg_drop_replication_slot(...) → алерт No space left on device. Всегда ставь алерт на active = false!

Универсальный «паспорт» узла

Напиши один SQL-запрос, который без ошибок выполнится и на Primary (:5432), и на Standby (:5433). Верни 3 колонки: подпись роли ('PRIMARY (Read/Write)' или 'STANDBY (Read-Only)'), имя БД (current_database()) и актуальный LSN (на Standby pg_current_wal_lsn() выдаст ошибку — используй CASE WHEN pg_is_in_recovery()).
SQL Эталонное решение · Работает и на 5432, и на 5433 
-- CASE вычисляет только нужную ветку, поэтому ошибки на Standby не будет
SELECT
    CASE
        WHEN pg_is_in_recovery() THEN 'STANDBY (Read-Only)'
        ELSE 'PRIMARY (Read/Write)'
    END AS node_role,
    current_database() AS db_name,
    CASE
        WHEN pg_is_in_recovery() THEN pg_last_wal_replay_lsn()
        ELSE pg_current_wal_lsn()
    END AS current_lsn;

Сквозной тест репликации на изменении данных

На Primary (:5432) пересоздай таблицу ha_heartbeat (id INT PRIMARY KEY, status TEXT, updated_at TIMESTAMPTZ), вставь строки id = 1 и id = 2, затем обнови id = 1 на 'verified'. 06 · Мини-практикум · Задача 4 из 4 (Отладка)

Почему на Standby упал отчёт с TEMP TABLE?

Отчёт аналитика на Standby (:5433) упал с ERROR: cannot execute CREATE TABLE in a read-only transaction из-за CREATE TEMP TABLE. Объясни, почему даже временные таблицы запрещены на Standby, и перепиши запрос через CTE (WITH ...) для поиска категорий с выручкой > 10000.
🔍
Причина: даже TEMP TABLE требует записи новой строки в системный каталог pg_class и выдачи XID — а физический Standby запрещает любые записи. Решение: заменить на WITH (CTE)!
SQL 
DROP TABLE IF EXISTS sales_report_demo;
CREATE TABLE sales_report_demo (
    id SERIAL PRIMARY KEY, category TEXT NOT NULL, amount NUMERIC(10, 2) NOT NULL
);
INSERT INTO sales_report_demo (category, amount) VALUES
    ('Одежда', 14500.00), ('Одежда', 6900.00),
    ('Аксессуары', 1200.00), ('Книги', 8500.00), ('Книги', 4200.00);
-- Вместо CREATE TEMP TABLE используем CTE — чистый Read-Only SELECT
WITH category_totals AS (
    SELECT category, count(*) AS orders_cnt, sum(amount) AS total_revenue
    FROM sales_report_demo GROUP BY category
)
SELECT category, orders_cnt, total_revenue
FROM category_totals
WHERE total_revenue > 10000
ORDER BY total_revenue DESC;

off Карандаш на черновике Не ждёт даже сброса своего WAL на диск Primary Макс. скорость; риск потерять ~0.6 с при крахе
local Закрыл в своём сейфе Ждёт только диск Primary (игнорирует Standby) Быстро; ведёт себя как обычная async
remote_write Передал коробку в руки Standby записал WAL в буфер ОС (без fsync) Выживет при крахе Postgres, но не при обрыве света обоих узлов
on (дефолт) Друг запер в свой сейф Standby сбросил WAL на физический диск (flush_lsn) Золотой стандарт для банков (RPO = 0)
remote_apply Друг расставил на полки Standby сохранил и применил WAL (replay_lsn) Медленнее всех, но данные сразу видны в SELECT на Standby!

02 · Ловушка синхронного режима

Что будет, если единственный синхронный Standby упадёт?

При схеме 1 Primary + 1 sync Standby обрыв питания на реплике заморозит все COMMIT на Primary. При нажатии Ctrl+C клиент увидит честное предупреждение:

Предупреждение PostgreSQL при отмене зависшего синхронного COMMIT
WARNING:  canceling wait for synchronous replication due to user request
DETAIL:  The transaction has already committed locally, but might not have been replicated to the standby.
✗ Как НЕ надо (1 реплика)
-- Только 1 реплика в кластере!
ALTER SYSTEM SET
  synchronous_standby_names = '*';

Падение одной реплики полностью парализует запись на Primary. Доступность стала хуже, чем была вообще без реплики!

✓ Как правильно (минимум 2 реплики)
-- Кворумная репликация (ANY 1 из 2)
ALTER SYSTEM SET
  synchronous_standby_names =
  'ANY 1 (standby_a, standby_b)';

Ждём подтверждения от любой одной из двух реплик. Если одна упадёт — вторая сразу подхватит работу без простоя.

02 · Практика 3 · Гибридный режим

Разная надёжность для разных транзакций: SET LOCAL

Деньгам нужна максимальная защита (remote_apply), а логам кликов — скорость (off). PostgreSQL позволяет менять synchronous_commit внутри одной транзакции!

    account_id INT NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

    page_url   TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 1. Важный платёж: ждём применения на Standby (сразу видно в SELECT!)
BEGIN;

INSERT INTO bank_transfers (account_id, amount) VALUES (101, 25000.00);

Replication Lag: 4 причины и как его измерять

⚽ Почему реплика отстаёт? (4 причины)
  • Шквал записи на Primary: массовый UPDATE, COPY или CREATE INDEX генерируют гигабайты WAL.
  • Слабое железо Standby: медленный диск или узкое место — startup применяет WAL в один поток!
  • Проблемы с сетью: потери пакетов или узкий канал между узлами.
  • Долгие SELECT на Standby: тяжёлый отчёт мешает применению WAL.

flush_lag

now() - pg_last_xact_replay_timestamp() Standby: время с последней применённой транзакции (осторожно на тихих базах!).

Ловушка «тихой базы» и честный расчёт лага

🌙
Ночной ложный алерт: последний заказ был в 23:00. В 01:00 формула now() - pg_last_xact_replay_timestamp() кричит «Лаг 2 часа!» — хотя реплика на 100% актуальна, просто 2 часа не было записей!
SQL Standby (:5433) · Безопасная формула без ложных срабатываний 
-- Если received_lsn = replayed_lsn, реальный лаг строго равен 0!
SELECT
    pg_last_wal_receive_lsn() AS received_lsn,
    pg_last_wal_replay_lsn()  AS replayed_lsn,
    CASE
        WHEN pg_last_wal_receive_lsn() = pg_last_wal_replay_lsn() THEN 0
        ELSE EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()))::INT
    END AS real_lag_seconds;
Ответ Standby (:5433)
 received_lsn | replayed_lsn | real_lag_seconds
--------------+--------------+------------------
 0/425F1A0    | 0/425F1A0    |                0
💓
Прод-паттерн (Heartbeat Table): фоновый скрипт раз в секунду делает UPDATE replication_heartbeat SET ts = now() на Primary. Тогда now() - ts на Standby ловит даже полный обрыв сети на тихой базе!
04 · Конфликты на Hot Standby

Почему падают долгие SELECT на реплике?

На Primary сборщик мусора VACUUM не знает про 5-минутный отчёт на Standby, удаляет старые версии строк и шлёт об этом WAL. Через 30s Standby спасает репликацию и отменяет запрос!

Типичная ошибка при долгом отчёте на Hot Standby
ERROR:  canceling statement due to conflict with recovery
DETAIL:  User query might have needed to see row versions that must be removed.

Светофор здоровья реплики для алертинга

Напиши запрос для Primary (:5432) к pg_stat_replication: выведи application_name, sync_state, размер отставания (pg_size_pretty) и колонку health_status по разнице pg_current_wal_lsn() - replay_lsn:
'OK' (< 1 МБ = 1048576), 'WARNING' (1–16 МБ = 16777216), 'CRITICAL' (> 16 МБ или state <> 'streaming').
SQL Эталонное решение · Primary (:5432) 
WITH lag_metrics AS (
    SELECT application_name, state, sync_state,
           pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
    FROM pg_stat_replication
)
SELECT
    application_name, sync_state,
    pg_size_pretty(lag_bytes) AS lag_pretty,
    CASE
        WHEN state <> 'streaming' OR lag_bytes > 16777216 THEN 'CRITICAL'
        WHEN lag_bytes >= 1048576 THEN 'WARNING'
        ELSE 'OK'
    END AS health_status
FROM lag_metrics;

04 · Высокая доступность (HA)

Переключение ролей: Switchover vs Failover

✈️
Аналогия кабины самолёта: Switchover — капитан спокойно передаёт штурвал второму пилоту перед уходом за кофе (приборы равны, потерь 0). Failover — капитан внезапно потерял сознание, второй пилот мгновенно перехватывает управление!
Характеристика Switchover (плановое) Failover (аварийное)
Причина Обслуживание, обновление ОС/железа, переезд Внезапный отказ Primary, сбой питания/диска
Потеря данных (RPO) 0 байт (ждём полного совпадения LSN) 0 при sync; возможны потери при async
Время простоя (RTO) 1–5 секунд (полностью контролируемо) 10–60 сек (детекция сбоя + promote + трафик)
Старый Primary Корректно переводится в роль Standby Изолируется (Fencing), чинится через pg_rewind или pg_basebackup
⏱️
Две главные метрики HA: RPO (Recovery Point Objective — сколько данных допустимо потерять) и RTO (Recovery Time Objective — за сколько секунд сервис обязан снова заработать).

Мониторинг всех логических слотов на Publisher

Каждая логическая подписка создаёт логический слот на Publisher (и забытый слот тоже может забить диск!). Напиши запрос для Publisher (:5432) к pg_replication_slots только по слотам slot_type = 'logical': выведи slot_name, database, active, wal_status, confirmed_flush_lsn и объём удерживаемого WAL через pg_size_pretty.
SQL Эталонное решение · Publisher (:5432) 
SELECT
    slot_name,
    database,
    active,
    wal_status,
    confirmed_flush_lsn,
    pg_size_pretty(
        pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
    ) AS retained_wal_size
FROM pg_replication_slots
WHERE slot_type = 'logical'
ORDER BY slot_name;

01 · Защита от ошибок людей

Почему репликация — НЕ бэкап, и два вида копий

⚡
Репликация защищает только от поломки железа. Случайный DELETE FROM orders; без WHERE реплика скопирует за 2 мс и сотрёт всё!
🔐
Бэкап (Backup) защищает от ошибок людей, багов и шифровальщиков — копия в отдельном сейфе, куда DROP TABLE не дотянется.
Критерий Логический (pg_dump / pg_restore) Физический (pg_basebackup + WAL)
Аналогия Рецепт блюда текстом (CREATE + COPY) Полная копия файлов диска всего кластера
Что копирует Одну БД, схему или 1 конкретную таблицу Весь кластер целиком (все БД, роли, индексы)
Восстановление Медленнее на больших БД (пересборка индексов) Очень быстро (распаковка готовых файлов)
Откат до секунды (PITR) Нет (только момент старта pg_dump) Да! С архивом WAL — до миллисекунды
Где применять БД до ~50–100 ГБ, перенос таблиц, апгрейды Боевые продакшен-кластеры любого размера

02 · Point-in-Time Recovery (PITR)

Машина времени: базовый снимок + архив WAL

1️⃣ Базовый кадр

Ночью делаем физический снимок pg_basebackup (состояние на 00:00).

2️⃣ Несгораемый архив WAL

archive_mode=on складывает каждый 16-МБ сегмент WAL в отдельное хранилище.

3️⃣ Перемотка + СТОП

Кладём recovery.signal и задаём точное время или закладку restore_point.

03 · Пулинг соединений

Проблема «1000 официантов» и метрдотель PgBouncer

🍽️ Почему «голый» PostgreSQL не любит 1000 клиентов
  • Process-per-connection: на каждый коннект ОС запускает тяжёлый процесс (fork()) на 5–10 МБ RAM.
  • 98% времени — idle: 1000 процессов съедают 10 ГБ RAM впустую и толкаются на CPU (context switch).
  • PgBouncer (C): тратит ~2 КБ на клиента и мультиплексирует сотни подключений в 10–50 реальных процессов!
Ошибка перегрузки без пулера
FATAL:  sorry, too many clients already
⚙️
В нашем docker-compose.yaml: course_pgbouncer (:6432) → MAX_CLIENT_CONN=200, DEFAULT_POOL_SIZE=10, POOL_MODE=transaction.

Три режима pool_mode и формула размера пула

Режим Когда коннект возвращается в пул Плюсы, минусы и применение
session Только после полного отключения клиента 100% совместимость со всеми фичами Postgres, но слабая экономия (idle-клиенты всё равно держат процесс).
transaction
(стандарт!)		 Сразу после каждого COMMIT или ROLLBACK Экономия 10x–50x! Настроен у нас в docker-compose.yaml. Нельзя полагаться на «память сессии» между транзакциями.

04 · Практика 6 · Подвох Transaction Mode

Ловушки TEMP TABLE, SET и PREPARE в пуле

SQL Опасный паттерн в Transaction Mode (автокоммит!) 
-- Транзакция 1: попала на backend PID 142
CREATE TEMP TABLE my_cart (item TEXT);
INSERT INTO my_cart VALUES ('Кроссовки');

-- (После COMMIT другой клиент забрал PID 142, нам дали PID 149!)

-- Транзакция 2: читаем таблицу уже на ДРУГОМ backend!
SELECT * FROM my_cart;
Ошибка при смене бэкенда между транзакциями
ERROR:  relation "my_cart" does not exist
LINE 1: SELECT * FROM my_cart;
✗ Как НЕ надо (утечёт чужому!)
SET search_path TO analytics;
SELECT * FROM reports;
CREATE TEMP TABLE tmp (id INT);

Обычный SET остаётся висеть на процессе после возврата в пул и ломает следующего клиента!

✓ Как правильно (строго в транзакции)
BEGIN;
SET LOCAL search_path TO analytics;
CREATE TEMP TABLE tmp (id INT)
  ON COMMIT DROP;
SELECT * FROM reports;
COMMIT;

SET LOCAL и ON COMMIT DROP гарантированно очищаются при COMMIT и безопасны в пуле.

05 · Мини-практикум · Задача 2 из 4 (Практический)

Мониторинг здоровья WAL-архиватора

Напиши SQL-запрос для Primary (:5432) к pg_stat_archiver: выведи archive_mode, archived_count, failed_count, last_archived_wal и статус archiver_health: 'DISABLED' (archive_mode = 'off'), 'ERROR' (failed_count > 0 и последняя ошибка позже последнего успеха или успехов не было) или 'OK'.
SQL Эталонное решение · Primary (:5432) 
SELECT
    current_setting('archive_mode') AS archive_mode,
    archived_count,
    failed_count,
    last_archived_wal,
    CASE
        WHEN current_setting('archive_mode') = 'off' THEN 'DISABLED'
        WHEN failed_count > 0
             AND (last_archived_time IS NULL OR last_failed_time > last_archived_time)
            THEN 'ERROR'
        ELSE 'OK'
    END AS archiver_health
FROM pg_stat_archiver;
05 · Мини-практикум · Задача 3 из 4 (Инженерный)

Аудит соединений в pg_stat_activity

Напиши запрос для Primary (:5432) по всем клиентским подключениям из pg_stat_activity (backend_type = 'client backend'): сгруппируй по state (active, idle, idle in transaction), посчитай количество соединений, рядом выведи лимит max_connections и процент занятости лимита (до 1 знака).
SQL Эталонное решение · Primary (:5432) 
WITH limits AS (
    SELECT current_setting('max_connections')::INT AS max_conn
)
SELECT
    COALESCE(a.state, 'unknown') AS conn_state,
    count(*) AS connections_cnt,
    l.max_conn,
    round(100.0 * count(*) / l.max_conn, 1) AS pct_of_limit
FROM pg_stat_activity AS a
CROSS JOIN limits AS l
WHERE a.backend_type = 'client backend'
GROUP BY a.state, l.max_conn
ORDER BY connections_cnt DESC;
05 · Мини-практикум · Задача 4 из 4 (Отладка)

Чиним «протекающий» скрипт для PgBouncer

Скрипт SET work_mem = '32MB'; CREATE TEMP TABLE tmp_calc (x INT); INSERT INTO tmp_calc SELECT generate_series(1, 5); SELECT sum(x) FROM tmp_calc; портит настройки соседям в course_pgbouncer (transaction mode). Перепиши его в одну безопасную транзакцию (SET LOCAL + ON COMMIT DROP) и проверь через SHOW work_mem;!
BASH Эталонное решение · Безопасный запуск через course_pgbouncer 
docker exec -e PGPASSWORD=student_pass course_pg_primary \
  psql -h pgbouncer -p 5432 -U student -d learning_db -c "
  BEGIN;
    SET LOCAL work_mem = '32MB';
    CREATE TEMP TABLE tmp_calc (x INT) ON COMMIT DROP;
    INSERT INTO tmp_calc SELECT generate_series(1, 5);
    SELECT sum(x) AS total_sum, current_setting('work_mem') AS tx_work_mem
    FROM tmp_calc;
  COMMIT;
  SHOW work_mem;"
✓
Внутри транзакции total_sum = 15 и tx_work_mem = 32MB, а сразу после COMMIT SHOW work_mem снова показывает 4MB!
