01 · Правило «всё или ничего»

Зачем нужны транзакции?

✗ Без BEGIN (Autocommit)
UPDATE wallets SET balance = balance - 300 WHERE owner = 'Алиса';
-- Тут обрыв сети или пропал свет!
UPDATE wallets SET balance = balance + 300 WHERE owner = 'Боб';

Первый шаг уже сохранился навсегда — 300 монет испарились.

✓ Внутри транзакции (BEGIN ... COMMIT)
BEGIN;
UPDATE wallets SET balance = balance - 300 WHERE owner = 'Алиса';
UPDATE wallets SET balance = balance + 300 WHERE owner = 'Боб';
COMMIT;

При любом сбое до COMMIT база сама откатит списание у Алисы.

📝
Аналогия: транзакция — как редактирование реферата. Пока правишь (BEGIN), файл на диске цел. «Сохранить» = COMMIT, «Закрыть без сохранения» = ROLLBACK.

02 · Аварийный режим и гигиена

Режим aborted и антипаттерн «зависшей» транзакции

SQL 
BEGIN;

-- Пытаемся списать 5000 у Алисы (700 - 5000 = -4300)
UPDATE wallets
SET balance = balance - 5000.00
WHERE owner = 'Алиса';
-- Любой запрос в сломанной транзакции будет отклонён:
SELECT * FROM wallets;

-- Единственный честный выход из режима aborted:
ROLLBACK;
Ошибка PostgreSQL · Транзакция перешла в aborted
ERROR:  new row for relation "wallets" violates check constraint "wallets_balance_check"
DETAIL:  Failing row contains (1, Алиса, -4300.00).
Ошибка PostgreSQL · Блокировка команд до ROLLBACK
ERROR:  current transaction is aborted, commands ignored until end of transaction block

-- После ROLLBACK; -> ROLLBACK (сессия снова здорова)
👀
Подсказка psql: learning_db=# (обычный) → learning_db=*# (открыт BEGIN) → learning_db=!# (сломан, ждёт ROLLBACK).
✗ «Зависшая» транзакция
BEGIN;
UPDATE wallets SET balance = balance - 100
WHERE owner = 'Алиса';
-- Ждём API 15 сек или клик пользователя...

Статус idle in transaction держит блокировки строк и мешает уборщику памяти. 100 таких юзеров положат сайт!

✓ Короткая транзакция
-- Расчёты и запросы к API — ДО BEGIN!
BEGIN;
UPDATE wallets SET balance = balance - 100
  WHERE owner = 'Алиса';
UPDATE wallets SET balance = balance + 100
  WHERE owner = 'Боб';
COMMIT;

Золотое правило: транзакция должна длиться миллисекунды, а не секунды.

02 · Чекпоинты в SQL

SAVEPOINT: сохраняемся перед сложным шагом

SQL Пример 4 · Спасаем награду Чарли за квест (+100 монет) 
BEGIN;

-- Шаг 1: Чарли прошёл квест (+100 монет -> стало 300)
UPDATE wallets SET balance = balance + 100.00 WHERE owner = 'Чарли';

SAVEPOINT after_quest; -- Ставим игровой чекпоинт!

-- Шаг 2: попытка купить меч за 600 (упадёт по CHECK balance >= 0)
UPDATE wallets SET balance = balance - 600.00 WHERE owner = 'Чарли';

ROLLBACK TO SAVEPOINT after_quest; -- Откат к чекпоинту!
COMMIT;

SELECT owner, balance FROM wallets WHERE owner = 'Чарли';
Ответ PostgreSQL · Награда за квест спасена!
 owner | balance
-------+---------
 Чарли |  300.00
(1 row)
🎮 Как чекпоинт перед боссом
  • SAVEPOINT имя фиксирует промежуточное состояние внутри транзакции.
  • ROLLBACK TO SAVEPOINT имя отменяет только шаги после чекпоинта.
  • Снимает аварийный статус aborted и позволяет довести транзакцию до COMMIT.
✓
Не теряй 8 успешных шагов из-за одного рискованного 9-го — оберни опасный запрос точкой сохранения.

03 · Четыре гарантии надёжности

Что такое ACID в PostgreSQL?

Буква Принцип Аналогия из жизни Гарантия PostgreSQL
A Atomicity
Атомарность		 Автомат с едой: либо списались деньги и выпала шоколадка, либо деньги вернулись. Неделимость: всё или ничего. Частичный перевод невозможен.
C Consistency
Согласованность		 Закон сохранения: сколько ушло из одного кармана, столько появилось в другом. После COMMIT соблюдены все CHECK, UNIQUE, FK, NOT NULL.
I Isolation
Изолированность		 Кабинки в магазине: другие не видят твоих промежуточных примерок. Параллельные транзакции не видят чужих «сырых» правок.
D Durability
Долговечность		 Запись ручкой в прошитой книге учёта, а не мелом на доске. После ответа COMMIT данные переживут обрыв питания.
📓
Как работает Durability под капотом? Механизм WAL (Write-Ahead Logging): до ответа COMMIT сервер гарантированно дописывает изменения в журнал на диске. После сбоя питания Postgres перечитает WAL и восстановит всё подтверждённое.
03 · ACID в действии

Пример 5: покупка 2 щитов при остатке 1 на складе

У Боба 800.00 монет — на 2 «Щита новичка» по 300 денег хватает, но на складе остался всего 1 щит:

SQL 
BEGIN;

-- Шаг 1: списываем 600 монет у Боба (800 - 600 = 200, всё ок!)
UPDATE wallets SET balance = balance - 600.00 WHERE owner = 'Боб';

-- Шаг 2: пытаемся забрать 2 щита со склада (1 - 2 = -1 -> CHECK!)
UPDATE shop_items SET stock = stock - 2 WHERE title = 'Щит новичка';
ROLLBACK;

SELECT owner, balance FROM wallets WHERE owner = 'Боб';
SELECT title, stock FROM shop_items WHERE title = 'Щит новичка';
Ошибка PostgreSQL · Сработала Consistency (CHECK stock >= 0)
ERROR:  new row for relation "shop_items" violates check constraint "shop_items_stock_check"
DETAIL:  Failing row contains (3, Щит новичка, 300.00, -1).
Ответ PostgreSQL · Сработала Atomicity (деньги Боба возвращены)
ROLLBACK
 owner | balance       title    | stock
-------+---------    -----------+-------
 Боб   |  800.00     Щит новичка |     1
🛡️
Двойная защита: Consistency поймала попытку продать несуществующий щит, а Atomicity целиком отменила списание 600 монет у Боба.
04 · Многопользовательский доступ

Чёрная пятница в БД: 4 аномалии конкурентности

Когда сотни пользователей одновременно читают и меняют одни и те же строки, возникают 4 классических бага:

Аномалия Аналогия Что произошло По умолчанию в Postgres?
Dirty Read
Грязное чтение		 «Подглядел в черновик» (потом стёрли) Прочитали чужие неподтверждённые правки до ROLLBACK. Нет! Запрещена на всех уровнях.
Non-Repeatable Read
Неповторяемое чтение		 «Переклеили ценник за спиной» Два SELECT одной строки в транзакции дали разные числа. Да (READ COMMITTED).
Phantom Read
Фантомное чтение		 «Опоздавший зашёл в класс» Повторный SELECT ... WHERE вернул другое число строк. Да (READ COMMITTED).
Lost Update
Потерянное обновление		 «Перезаписали чужую работу» Два кассира записали значения поверх друг друга. Да (если считать в коде).
🔎
Разница Non-Repeatable vs Phantom: при Non-Repeatable изменилось значение в той же строке (UPDATE), а при Phantom — в выборке WHERE появились или исчезли строки (INSERT / DELETE).

04 · Эксперимент 2 в двух окнах psql

Два кассира: побеждаем Lost Update за 10 секунд

SQL Пример 7 · Два параллельных пополнения (+100 и +200 к 700) 
UPDATE wallets SET balance = 700.00 WHERE owner = 'Алиса';

-- [ШАГ 1 · Т1] Пополняем на +100 (НЕ коммитим сразу!)
BEGIN;
UPDATE wallets SET balance = balance + 100.00 WHERE owner = 'Алиса';

-- [ШАГ 2 · Т2] Пополняем на +200 -> Т2 вежливо ЗАМРЁТ и ждёт Т1!
BEGIN;
UPDATE wallets SET balance = balance + 200.00 WHERE owner = 'Алиса';

-- [ШАГ 3 · Т1] COMMIT;  -> Т2 «проснётся», возьмёт 800 и добавит +200!
-- [ШАГ 4 · Т2] COMMIT;
SELECT owner, balance FROM wallets WHERE owner = 'Алиса';
Ответ PostgreSQL · Ни одной монеты не потеряно!
 owner | balance
-------+---------
 Алиса | 1000.00
(1 row)
✗ Расчёт в коде (Lost Update)
  • Оба кассира прочитали 700 в Python/JS.
  • Т1 отправил SET balance = 800.
  • Т2 отправил SET balance = 900 — пополнение Т1 стёрлось!
✓ Атомарный UPDATE в SQL
  • Пишем SET balance = balance + 200.
  • Postgres блокирует строку: Т2 ждёт COMMIT Т1, перечитывает 800 и честно пишет 1000.
🔮
Спойлер (Урок 4.3): запретить Non-Repeatable и Phantom Read помогут уровни изоляции (REPEATABLE READ, SERIALIZABLE) и явные блокировки строк.

Безопасный перевод с записью в журнал

Убедись, что у Боба на счёте 500.00, а у Чарли 200.00 (подготовь данные автономно). Затем в одной транзакции переведи 150.00 монет от Боба к Чарли и добавь запись об этом в transfer_log. В конце выведи балансы обоих игроков.

BEGIN;
UPDATE wallets SET balance = balance - 150.00 WHERE owner = 'Боб';

SELECT owner, balance FROM wallets WHERE owner IN ('Боб', 'Чарли') ORDER BY owner;

Покупка двух предметов с чекпоинтом SAVEPOINT

У Алисы 400.00 монет. Внутри одной транзакции она покупает «Зелье маны» за 150.00 (списываем деньги и stock - 1), ставит точку сохранения after_potion, затем пытается купить «Алмазный меч» за 600.00 (сработает CHECK). Откати только неудачную покупку меча и сохрани покупку зелья.
SQL Эталонное решение · Задача 2 
INSERT INTO wallets (owner, balance) VALUES ('Алиса', 400.00)
ON CONFLICT (owner) DO UPDATE SET balance = 400.00;
INSERT INTO shop_items (title, price, stock) VALUES
    ('Зелье маны', 150.00, 5), ('Алмазный меч', 600.00, 2)
ON CONFLICT (title) DO UPDATE SET price = EXCLUDED.price, stock = EXCLUDED.stock;

BEGIN;
UPDATE wallets SET balance = balance - 150.00 WHERE owner = 'Алиса';
UPDATE shop_items SET stock = stock - 1 WHERE title = 'Зелье маны';
SAVEPOINT after_potion;
UPDATE wallets SET balance = balance - 600.00 WHERE owner = 'Алиса'; -- ERROR CHECK
ROLLBACK TO SAVEPOINT after_potion;
COMMIT;

-- Проверка: у Алисы 250.00, зелий осталось 4
SELECT owner, balance FROM wallets WHERE owner = 'Алиса';
SELECT title, stock FROM shop_items WHERE title = 'Зелье маны';

01 · Многоверсионность (MVCC)

Почему UPDATE не стирает строку на месте?

Золотое правило PostgreSQL: читатели никогда не блокируют писателей, а писатели не блокируют читателей. При UPDATE старая версия остаётся на диске, а рядом рождается новая:

ctid · Адрес на диске

Точные координаты строки: (номер_страницы, номер_строки).

xmin · Рождение

ID транзакции, которая создала эту версию строки.

xmax · Устаревание

ID удалившей/обновившей транзакции (0, если версия живая).

01 · Практика MVCC

Рентген PostgreSQL: доказываем «переезд» строки при UPDATE

SQL 
DROP TABLE IF EXISTS mvcc_heroes;

CREATE TABLE mvcc_heroes (
    id   SERIAL PRIMARY KEY,
    name TEXT NOT NULL,

Враги уборщика: зависшие транзакции и Wraparound

✗ Брошенная транзакция (парализует VACUUM!)
BEGIN;
SELECT count(*) FROM orders;
-- Ушли на обед на 3 часа (idle in transaction)...

Пока открыт старый снимок, VACUUM не имеет права удалять ни одну мёртвую строку новее утра — вся база пухнет!

✓ Защита таймаутом и точечный тюнинг
SET idle_in_transaction_session_timeout = '30s';

-- Для гигантских таблиц (100M строк): уборка при 1%
ALTER TABLE big_table
  SET (autovacuum_vacuum_scale_factor = 0.01);

Таймаут сам прервёт забытую сессию, а scale_factor = 0.01 не даст накопить 20 млн мёртвых строк.

🚨
Никогда не отключай Autovacuum в проде! Номер xmin — 32-битный (~4 млрд, как одометр старой машины). Без периодической «заморозки» древних строк (VACUUM FREEZE) случится Transaction ID Wraparound, и база остановит запись!
🛠️
Как сжать таблицу 50 ГБ без простоя? Не запускай VACUUM FULL orders; днём — используй регулярный VACUUM (ANALYZE) или утилиту pg_repack.

Главные выводы и следующий шаг

01

Многоверсионность MVCC

Читатели и писатели не блокируют друг друга: каждая строка хранит ctid, xmin и xmax, а сессии читают свой Snapshot.

Dead Tuples и Bloat

После UPDATE/DELETE остаются мёртвые копии, из-за которых таблицы раздуваются (мониторим в pg_stat_user_tables).

Обычный VACUUM безопасен и освобождает слоты внутри файла; VACUUM FULL отдаёт место ОС под жёстким замком.

04

Autovacuum — жизненно важен

Закрывай idle in transaction таймаутом и никогда не отключай автоуборку, чтобы избежать Transaction ID Wraparound.

🏥
Что такое Write Skew? Два врача на смене одновременно видят «нас двое, могу уйти» и правят разные строки — дежурство остаётся пустым. REPEATABLE READ пропустит, а SERIALIZABLE остановит второго.
🔁
Цена строгой изоляции: используя REPEATABLE READ или SERIALIZABLE, всегда пиши в коде повтор (retry) транзакции при ошибке сериализации (40001)!

02 · Строчные блокировки (Row-level locks)

Табличка «ЗАНЯТО» на строке: FOR UPDATE, NOWAIT, SKIP LOCKED

🎟️ Зачем нужен FOR UPDATE?

Обычный SELECT не блокирует строку — два болельщика одновременно увидят status = 'free' и купят одно и то же кресло.

🤝 А что делает FOR SHARE?

«Только не меняйте!»: пускает других с FOR SHARE, но не даёт сделать UPDATE или DELETE до конца транзакции.

02 · Практика строчных замков

Очередь билетов: NOWAIT, SKIP LOCKED и антипаттерн LOCK TABLE

SQL

BEGIN;

WHERE status = 'free' ORDER BY id LIMIT 1
FOR UPDATE; -- Заблокирован id = 1

-- [ШАГ 3 · Т2] Откатываем ошибку и берём свободное

UPDATE ticket_queue SET status = 'reserved',

03 · Взаимная блокировка (Deadlock)

Тупик на узком мостике: воспроизводим Deadlock

⏱️
Дежурный судья: через deadlock_timeout (~1 сек) Postgres находит цикл, прерывает одну сессию (Т2) и размораживает Т1!
SQL Пример 5 · Выполняй 4 шага строго по очереди 
UPDATE lock_accounts SET balance = 1000.00 WHERE id IN (1, 2);

BEGIN;
UPDATE lock_accounts SET balance = balance - 100 WHERE id = 1;

-- [ШАГ 2 · Т2] Захватываем счёт 2 (Боб)
BEGIN;
UPDATE lock_accounts SET balance = balance - 50 WHERE id = 2;

-- [ШАГ 3 · Т1] Ждём счёт 2 (ЗАМРЁТ!)
UPDATE lock_accounts SET balance = balance + 100 WHERE id = 2;

-- [ШАГ 4 · Т2] Замыкаем цикл на счёте 1!
UPDATE lock_accounts SET balance = balance + 50 WHERE id = 1;

03 · Профилактика Deadlock

Главное лекарство: единый порядок блокировок (ORDER BY id)

✗ Как НЕ надо (разный порядок)
-- Перевод 1 (Алиса -> Боб):
--   сначала id = 1, потом id = 2

-- Перевод 2 (Боб -> Алиса):
--   сначала id = 2, потом id = 1
  • Транзакции идут навстречу друг другу по одному мостику.
  • При параллельной нагрузке гарантированно сталкиваются лбами → DEADLOCK.
✓ Как правильно (единый порядок id)
BEGIN;
-- Сначала берём замки СТРОГО по возрастанию id:
SELECT id FROM lock_accounts
WHERE id IN (1, 2) ORDER BY id FOR UPDATE;

-- Теперь обе строки наши — обновляем в любом порядке!
UPDATE lock_accounts SET balance = balance - 50 WHERE id = 2;
UPDATE lock_accounts SET balance = balance + 50 WHERE id = 1;
COMMIT;

Кто первый схватил меньший id, тот спокойно проходит весь перевод; второй ждёт миллисекунду и идёт следом. Цикл математически невозможен!

🛡️
Deadlock — не поломка сервера! Ошибка 40P01 (deadlock detected) — это защита PostgreSQL. В продакшене комбинируют два правила: 1) единый порядок ORDER BY id; 2) автоматический повтор (retry) транзакции в коде при 40P01.

Ищем виновника в pg_stat_activity и ставим lock_timeout

SQL 
-- [ШАГ 1 · Т1] Удерживаем замок на Чарли (id = 3), не коммитим!
BEGIN;
UPDATE lock_accounts SET balance = balance + 10.00 WHERE id = 3;

-- [ШАГ 2 · Т2] Предохранитель на 2 сек — не висим вечно!
SET lock_timeout = '2s';
UPDATE lock_accounts SET balance = balance + 20.00 WHERE id = 3;
-- Выполни в 3-м окне, пока Т2 ждёт без lock_timeout (RESET lock_timeout):
SELECT
    pid AS waiting_pid, pg_blocking_pids(pid) AS blocked_by_pids,
    wait_event_type, wait_event, state, left(query, 50) AS waiting_query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

SQL 
DROP TABLE IF EXISTS task1_prices;

CREATE TABLE task1_prices (
    id    INT PRIMARY KEY,
    item  TEXT NOT NULL,
    price INT NOT NULL
);

INSERT INTO task1_prices VALUES
    (1, 'Меч', 500),
    (2, 'Щит', 300);
-- [ШАГ 1 · Т1] Замораживаем отчёт (вернёт 800, не коммитим!)
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT SUM(price) AS total_price FROM task1_prices;

SELECT SUM(price) AS total_price FROM task1_prices; COMMIT;

Два воркера разбирают очередь через SKIP LOCKED

Создай task2_jobs (id SERIAL PRIMARY KEY, task_name TEXT, status TEXT DEFAULT 'pending', worker TEXT) с 3 задачами: 'Отправить письмо', 'Сжать видео', 'Собрать отчёт'. В Т1 захвати одну pending-задачу через FOR UPDATE SKIP LOCKED (не коммить!). В Т2 тем же запросом забери 2-ю задачу. Обнови статусы на 'done' ('worker_1', 'worker_2') и закоммить оба окна.
SQL 
DROP TABLE IF EXISTS task2_jobs;

CREATE TABLE task2_jobs (
    id        SERIAL PRIMARY KEY,
    task_name TEXT NOT NULL,
    status    TEXT NOT NULL DEFAULT 'pending',
    worker    TEXT
);

INSERT INTO task2_jobs (task_name) VALUES
    ('Отправить письмо'), ('Сжать видео'), ('Собрать отчёт');
-- [ШАГ 1 · Т1] Воркер 1 берёт задачу id = 1 (не коммитим!)
BEGIN;
SELECT id, task_name FROM task2_jobs
WHERE status = 'pending' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
-- [ШАГ 2 · Т2] Воркер 2 сразу получает id = 2 и завершает её
BEGIN;
SELECT id, task_name FROM task2_jobs
WHERE status = 'pending' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;
UPDATE task2_jobs SET status = 'done', worker = 'worker_2' WHERE id = 2; COMMIT;
-- [ШАГ 3 · Т1] Завершаем id = 1 и проверяем итог
UPDATE task2_jobs SET status = 'done', worker = 'worker_1' WHERE id = 1; COMMIT;
SELECT id, task_name, status, worker FROM task2_jobs ORDER BY id;

Почини Deadlock единым порядком блокировок

Создай task3_wallets (id INT PRIMARY KEY, name TEXT, gold INT) с (10, 'Игрок А', 500) и (20, 'Игрок Б', 500). Выполни встречные переводы одновременно (Т1: 100 от 10 к 20; Т2: 50 от 20 к 10), предваряя оба переводом через SELECT id FROM task3_wallets WHERE id IN (10, 20) ORDER BY id FOR UPDATE. Убедись, что Deadlock нет, а итог — 450 и 550.
SQL 
DROP TABLE IF EXISTS task3_wallets;

CREATE TABLE task3_wallets (
    id   INT PRIMARY KEY,
    name TEXT NOT NULL,
    gold INT NOT NULL
);

INSERT INTO task3_wallets VALUES
    (10, 'Игрок А', 500),
    (20, 'Игрок Б', 500);
-- [ШАГ 1 · Т1] 100 от 10 к 20 (НЕ коммитим, идём в Т2!)
BEGIN;
SELECT id FROM task3_wallets WHERE id IN (10, 20) ORDER BY id FOR UPDATE;
UPDATE task3_wallets SET gold = gold - 100 WHERE id = 10;
UPDATE task3_wallets SET gold = gold + 100 WHERE id = 20;
-- [ШАГ 2 · Т2] 50 от 20 к 10 — ТАКОЙ ЖЕ ORDER BY id (ждёт на id=10!)
BEGIN;
SELECT id FROM task3_wallets WHERE id IN (10, 20) ORDER BY id FOR UPDATE;
-- [ШАГ 3 · Т1] COMMIT;  ->  [ШАГ 4 · Т2] «Проснулся» без Deadlock!
UPDATE task3_wallets SET gold = gold - 50 WHERE id = 20;
UPDATE task3_wallets SET gold = gold + 50 WHERE id = 10; COMMIT;

HOT-обновления (Heap-Only Tuples) и fillfactor

SQL

CREATE TABLE duel_products (
    id SERIAL PRIMARY KEY, sku TEXT NOT NULL, views INT NOT NULL DEFAULT 0

CREATE INDEX idx_duel_products_sku ON duel_products (sku);

03 · Раунд 3А · Блокировки диапазонов

Gap Locks в InnoDB vs свободные «дырки» в PostgreSQL

SQL Пример 4 · Проверяем отсутствие Gap Locks (2 окна psql) 
DROP TABLE IF EXISTS duel_parking;
CREATE TABLE duel_parking (id INT PRIMARY KEY, car TEXT NOT NULL);
INSERT INTO duel_parking VALUES (10, 'Седан'), (30, 'Джип');

-- [ШАГ 1 · Т1] Блокируем диапазон 10..30 (НЕ коммитим!)
BEGIN;
SELECT * FROM duel_parking WHERE id BETWEEN 10 AND 30 FOR UPDATE;

-- [ШАГ 2 · Т2] Вставляем новую машину в «дырку» (id = 20)!
BEGIN;
INSERT INTO duel_parking VALUES (20, 'Спорткар');
COMMIT; -- В PostgreSQL МГНОВЕННО! В InnoDB зависло бы!

-- [ШАГ 3 · Т1] COMMIT; SELECT * FROM duel_parking ORDER BY id;
Ответ PostgreSQL · Спорткар (id=20) припарковался без задержки!
 id |   car
----+----------
 10 | Седан
 20 | Спорткар
 30 | Джип
🅿️ Аналогия парковки
  • На парковке заняты места 10 и 30, между ними — 19 пустых мест.
  • В MySQL/InnoDB (по умолчанию REPEATABLE READ) запрос BETWEEN 10 AND 30 FOR UPDATE натягивает красную ленту на все пустые места (Gap Lock) — вставить id = 20 нельзя!
  • В PostgreSQL (по умолчанию READ COMMITTED) Gap Locks не существует — блокируются только реально существующие строки 10 и 30.
✓
Отсутствие Gap Locks избавляет PostgreSQL от целого класса неожиданных Deadlocks на параллельных вставках INSERT.
