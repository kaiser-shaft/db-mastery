01 · Два мира баз данных

Зачем делить базы на «кассу» и «кабинет директора»?

Критерий OLTP (Касса) OLAP / DWH (Аналитика)
Кто пользуется Покупатели сайта, приложения, игроки Аналитики, директора, BI-графики, ML-модели
Типичные запросы Тысячи коротких INSERT, UPDATE, SELECT по id Мало запросов, но тяжёлые SUM, AVG, GROUP BY

02 · Пример 2 · Боль OLTP

Отчёт директора напрямую по OLTP: 5 JOIN

Задача простая: «Выручка и штуки по городам и категориям за Q1 2026, только оплаченные заказы». В нормализованной 3НФ приходится сплетать 6 таблиц:

SQL Отчёт по oltp_shop (5 JOIN + ручные фильтры) 
SELECT
    ci.name AS city_name,
    cat.name AS category_name,
    SUM(oi.qty) AS items_sold,
    SUM(oi.qty * oi.price_at_purchase - oi.discount) AS revenue
FROM oltp_shop.order_items oi
JOIN oltp_shop.orders     o   ON o.id   = oi.order_id
JOIN oltp_shop.customers  cu  ON cu.id  = o.customer_id
JOIN oltp_shop.cities     ci  ON ci.id  = cu.city_id
JOIN oltp_shop.products   p   ON p.id   = oi.product_id
JOIN oltp_shop.categories cat ON cat.id = p.category_id
WHERE o.status = 'paid'
  AND o.order_date >= DATE '2026-01-01'
  AND o.order_date <  DATE '2026-04-01'
GROUP BY ci.name, cat.name
ORDER BY revenue DESC;

03 · Метод Ральфа Кимбалла

Факты, Измерения, Зерно и Суррогатные ключи

1

Таблица фактов (fact_*)

События бизнеса и числа-метрики (выручка, штуки, скидка). Миллионы узких строк: числа + ссылки на справочники.

2

Таблица измерений (dim_*)

Контекст «Кто? Что? Где? Когда?» (dim_customer, dim_product, dim_date). Мало строк, много понятных текстовых полей.

3

Зерно / Гранулярность (Grain)

Чёткий ответ: «Что описывает ОДНА строка факта?» Например: 1 позиция товара в 1 оплаченном чеке.

4

Суррогатный ключ (_sk)

Искусственный ID хранилища (product_sk), отделённый от бизнес-ключа OLTP (product_bk). Защита при смене кассовой системы.

✗ Ловушка #1 · Цена из каталога
SELECT SUM(f.qty * p.price)
FROM fact_sales f
JOIN dim_product p ON p.id = f.product_id;

Клавиатура подорожала с 32 000 до 35 000 — выручка за январь волшебным образом выросла. История испорчена!

✓ Правильно · Сумма в строке факта
SELECT SUM(f.total_amount)
FROM fact_sales f;

Цена покупки, скидка и итог заморожены в fact_sales на момент чека и никогда не «плывут».

🌾
Золотое правило зерна: не пиши CREATE TABLE fact_..., пока не сформулируешь вслух зерно в 1 предложении. Нельзя смешивать в одной таблице позиции чека и доставку на весь заказ!
Мини-квиз #1 · Главная ловушка аналитика

Что сломает историю выручки?

В январе Айгерим купила клавиатуру за 32 000 ₸ (со скидкой 2 000 ₸). В феврале в каталоге products цену подняли до 35 000 ₸. Как правильно хранить финансовые метрики в fact_sales, чтобы январский отчёт никогда не изменился?
04 · Золотой стандарт DWH

Схема «Звезда» (Star Schema): ровно 1 JOIN до атрибута

Было в oltp_shop (7) Стало в dwh_star (4)
products + categories Плоская dim_product (категория внутри!)
customers + cities + countries Плоская dim_customer (город и страна внутри!)
Колонка order_date Готовый календарь dim_date с кварталами и выходными
orders + order_items Чистая fact_sales (только paid + готовая total_amount)
📅
Трюк с date_sk: вместо случайных 1, 2, 3 в DWH используют целое YYYYMMDD (например, 20260110) — читается глазами и быстро фильтруется по диапазонам!
04 · Пример 3 · Практика DDL

Создаём схему «Звезда» (dwh_star) в PostgreSQL

SQL 
DROP SCHEMA IF EXISTS dwh_star CASCADE;
CREATE SCHEMA dwh_star;

CREATE TABLE dwh_star.dim_date (
    date_sk     INT PRIMARY KEY,      -- формат YYYYMMDD, например 20260110
    full_date   DATE NOT NULL UNIQUE,
    year_num    INT NOT NULL, quarter_num INT NOT NULL, month_num INT NOT NULL,
    day_of_week INT NOT NULL,         -- 1 = Пн ... 7 = Вс
    is_weekend  BOOLEAN NOT NULL
);
CREATE TABLE dwh_star.dim_product (
    product_sk    SERIAL PRIMARY KEY, -- суррогатный ключ DWH
    product_bk    INT NOT NULL UNIQUE,-- бизнес-ключ из OLTP
    product_title TEXT NOT NULL,
    category_name TEXT NOT NULL
);
-- Измерение 3: Покупатели (денормализовано вместе с городом и страной)
CREATE TABLE dwh_star.dim_customer (
    customer_sk   SERIAL PRIMARY KEY,
    customer_bk   INT NOT NULL UNIQUE,
    full_name     TEXT NOT NULL,
    segment       TEXT NOT NULL,
    city_name     TEXT NOT NULL,
    country_name  TEXT NOT NULL
);
-- Таблица фактов: Зерно = 1 позиция товара в оплаченном заказе
CREATE TABLE dwh_star.fact_sales (
    sale_sk         BIGSERIAL PRIMARY KEY,
    order_bk        INT NOT NULL,     -- вырожденное измерение (номер чека)
    date_sk         INT NOT NULL REFERENCES dwh_star.dim_date(date_sk),
    product_sk      INT NOT NULL REFERENCES dwh_star.dim_product(product_sk),
    customer_sk     INT NOT NULL REFERENCES dwh_star.dim_customer(customer_sk),
    qty             INT NOT NULL CHECK (qty > 0),
    unit_price      NUMERIC(10, 2) NOT NULL,
    discount_amount NUMERIC(10, 2) NOT NULL DEFAULT 0,
    total_amount    NUMERIC(10, 2) NOT NULL
);
🔑
product_bk INT UNIQUE хранит старый ID из oltp_shop для стыковки при загрузке, а product_sk работает внутри хранилища.
🗺️
Три таблицы (customers, cities, countries) схлопнулись в одну плоскую dim_customer — никаких цепочек JOIN в отчётах!
🧾
Вырожденное измерение (order_bk): номер чека лежит прямо в fact_sales — заводить под него отдельную dim_order не нужно, а посчитать COUNT(DISTINCT order_bk) можно мгновенно!

Ловушка FOREIGN KEY и наполнение «Звезды»

VALUES
    (1001, 20260110, 1, 1, 1, 32000.00, 2000.00, 30000.00);
-- Генерируем календарь на весь 2026 год одной командой через generate_series
INSERT INTO dwh_star.dim_date
    (date_sk, full_date, year_num, quarter_num, month_num, day_of_week, is_weekend)
SELECT
    TO_CHAR(d, 'YYYYMMDD')::INT,
    d::DATE,
    EXTRACT(YEAR FROM d)::INT,
    EXTRACT(QUARTER FROM d)::INT,
    EXTRACT(MONTH FROM d)::INT,
    EXTRACT(ISODOW FROM d)::INT,
    EXTRACT(ISODOW FROM d) IN (6, 7)
FROM generate_series(DATE '2026-01-01', DATE '2026-12-31', INTERVAL '1 day') AS d
ON CONFLICT (date_sk) DO NOTHING;
-- Шаг 2: плоский справочник товаров (products + categories)
INSERT INTO dwh_star.dim_product (product_bk, product_title, category_name)
SELECT p.id, p.title, c.name
FROM oltp_shop.products p
JOIN oltp_shop.categories c ON c.id = p.category_id
ON CONFLICT (product_bk) DO NOTHING;

-- Шаг 3: плоский справочник покупателей (customers + cities + countries)
INSERT INTO dwh_star.dim_customer (customer_bk, full_name, segment, city_name, country_name)
SELECT cu.id, cu.full_name, cu.segment, ci.name, co.name
FROM oltp_shop.customers cu
JOIN oltp_shop.cities    ci ON ci.id = cu.city_id
JOIN oltp_shop.countries co ON co.id = ci.country_id
ON CONFLICT (customer_bk) DO NOTHING;
-- Шаг 4: загружаем только оплаченные заказы и подставляем _sk ключи
INSERT INTO dwh_star.fact_sales
    (order_bk, date_sk, product_sk, customer_sk, qty, unit_price, discount_amount, total_amount)
SELECT o.id, TO_CHAR(o.order_date, 'YYYYMMDD')::INT, dp.product_sk, dc.customer_sk,
       oi.qty, oi.price_at_purchase, oi.discount,
       (oi.qty * oi.price_at_purchase - oi.discount)
FROM oltp_shop.order_items oi
JOIN oltp_shop.orders o ON o.id = oi.order_id
JOIN dwh_star.dim_product  dp ON dp.product_bk  = oi.product_id
JOIN dwh_star.dim_customer dc ON dc.customer_bk = o.customer_id
WHERE o.status = 'paid';

04 · Пример 5 · Чистый отчёт и Fan-out

Отчёт по «Звезде» и ловушка гранулярности (Fan-out)

SQL 
-- Никаких ручных формул, статуса 'paid' и границ дат — просто quarter_num = 1!
SELECT
    dc.city_name, dp.category_name,
    SUM(f.qty) AS items_sold, SUM(f.total_amount) AS revenue
FROM dwh_star.fact_sales f
JOIN dwh_star.dim_date     dd ON dd.date_sk     = f.date_sk
JOIN dwh_star.dim_product  dp ON dp.product_sk  = f.product_sk
JOIN dwh_star.dim_customer dc ON dc.customer_sk = f.customer_sk
WHERE dd.year_num = 2026 AND dd.quarter_num = 1
GROUP BY dc.city_name, dp.category_name
ORDER BY revenue DESC;
-- Заказ 1001 содержит 2 позиции, а доставка (1500) указана на ВЕСЬ заказ!
-- Наивный JOIN размножит доставку на каждую позицию в чеке:
SELECT
    o.id,
    SUM(o.delivery_fee) AS broken_delivery,
    SUM(oi.qty * oi.price_at_purchase) AS items_sum
FROM orders_with_delivery o
JOIN oltp_shop.order_items oi ON oi.order_id = o.id
GROUP BY o.id;
-- Для заказа 1001 выдаст 3000 вместо 1500!
-- Сначала свёртываем позиции до зерна «1 заказ», и только потом делаем JOIN:
WITH items_by_order AS (
    SELECT order_id, SUM(qty * price_at_purchase - discount) AS items_sum
    FROM oltp_shop.order_items
    GROUP BY order_id
)
SELECT o.id, o.delivery_fee, i.items_sum
FROM orders_with_delivery o
JOIN items_by_order i ON i.order_id = o.id;

Ловушка #2 (Fan-out): при соединении разных зёрен («1 заказ» + «1 товар в заказе») метрики верхнего уровня незаметно умножаются на число позиций. Самая дорогая ошибка в отчётности!
✓
Архитектурное решение в DWH: создавай две отдельные таблицы фактов (fact_sales по товарам и fact_orders по заказам), либо честно распределяй доставку по позициям.

05 · Пример 6 · Практика Snowflake

Собираем dwh_snow и сравниваем отчёт

SQL 
DROP SCHEMA IF EXISTS dwh_snow CASCADE;
CREATE SCHEMA dwh_snow;

CREATE TABLE dwh_snow.dim_country (
    country_sk SERIAL PRIMARY KEY, country_bk INT NOT NULL UNIQUE, country_name TEXT NOT NULL
);
CREATE TABLE dwh_snow.dim_city (
    city_sk SERIAL PRIMARY KEY, city_bk INT NOT NULL UNIQUE, city_name TEXT NOT NULL,
    country_sk INT NOT NULL REFERENCES dwh_snow.dim_country(country_sk)
);
CREATE TABLE dwh_snow.dim_customer (
    customer_sk SERIAL PRIMARY KEY, customer_bk INT NOT NULL UNIQUE,
    full_name TEXT NOT NULL, segment TEXT NOT NULL,
    city_sk INT NOT NULL REFERENCES dwh_snow.dim_city(city_sk)
);
CREATE TABLE dwh_snow.dim_category (
    category_sk SERIAL PRIMARY KEY, category_bk INT NOT NULL UNIQUE, category_name TEXT NOT NULL
);
CREATE TABLE dwh_snow.dim_product (
    product_sk SERIAL PRIMARY KEY, product_bk INT NOT NULL UNIQUE, product_title TEXT NOT NULL,
    category_sk INT NOT NULL REFERENCES dwh_snow.dim_category(category_sk)
);
CREATE TABLE dwh_snow.dim_date AS TABLE dwh_star.dim_date;
ALTER TABLE dwh_snow.dim_date ADD PRIMARY KEY (date_sk);

CREATE TABLE dwh_snow.fact_sales (
    sale_sk BIGSERIAL PRIMARY KEY, order_bk INT NOT NULL,
    date_sk INT NOT NULL REFERENCES dwh_snow.dim_date(date_sk),
    product_sk INT NOT NULL REFERENCES dwh_snow.dim_product(product_sk),
    customer_sk INT NOT NULL REFERENCES dwh_snow.dim_customer(customer_sk),
    qty INT NOT NULL, total_amount NUMERIC(10, 2) NOT NULL
);

«Звезда» — выбор по умолчанию (1 JOIN и быстрый BI). «Снежинка» — для экономии и единой точки правки иерархий.

04 · Кэширование витрин

VIEW (рецепт) vs MATERIALIZED VIEW (готовая кастрюля)

📜 Обычное VIEW
  • Только сохранённый SQL-запрос, 0 байт данных на диске.
  • Всегда показывает 100% актуальные данные, но каждый раз заново считает JOIN и GROUP BY.
🍲 MATERIALIZED VIEW
  • Физически сохраняет готовую агрегированную табличку на диск — на неё можно вешать обычные индексы!
  • Не обновляется сама — пересчитывается по расписанию командой REFRESH.
04 · Пример 5 · Замер ускорения

Создаём MATERIALIZED VIEW: ускорение в 275×!

SQL 
DROP MATERIALIZED VIEW IF EXISTS dwh_part.mv_monthly_city_revenue;

-- Создаём витрину и сразу наполняем её данными (WITH DATA)
CREATE MATERIALIZED VIEW dwh_part.mv_monthly_city_revenue AS
SELECT
    DATE_TRUNC('month', sale_date)::DATE AS month_start,
    city_name,
    category,
    SUM(qty)          AS total_qty,
    SUM(total_amount) AS total_revenue
FROM dwh_part.fact_sales_part
GROUP BY DATE_TRUNC('month', sale_date)::DATE, city_name, category
WITH DATA;

-- На материализованном представлении работают обычные индексы!
CREATE INDEX idx_mv_month ON dwh_part.mv_monthly_city_revenue (month_start);
-- Тот самый февральский отчёт, который раньше занимал 24.180 ms:
EXPLAIN (ANALYZE, COSTS OFF)

✗ Как НЕ надо (в рабочие часы)

03 · Упаковка колонок

Сжатие: LowCardinality, Delta и ZSTD

📖 Словарное кодирование

Зачем 100 000 раз писать слово «Алматы»? LowCardinality(String) заводит мини-словарь (1=Алматы, 2=Астана) и хранит крошечные номера вместо текста.

📏 Кодеки Delta + ZSTD

Для растущих ID и дат Delta / DoubleDelta хранят разницу соседей (+1, +1), а ZSTD(3) упаковывает плотнее быстрого LZ4 по умолчанию.

sale_idUInt64 (LZ4)UInt64 CODEC(Delta, ZSTD(3)) — хранит дельты ID
sale_dateDate (LZ4)Date CODEC(DoubleDelta, ZSTD(3)) — для отсортированных дат
city, categoryОбычный StringLowCardinality(String) — словарь вместо повторов

04 · Два секретных ускорителя

Разреженный индекс по гранулам и Векторизация (SIMD)

📑 Телефонный справочник (Гранулы)

В PostgreSQL (B-Tree) закладка стоит на каждую строку → индекс весит гигабайты. В ClickHouse — 1 метка на 8 192 строки (гранулу), поэтому индекс для 1 млрд строк легко живёт в RAM.

🍎 Лопата вместо «по одному яблоку» (SIMD)

Построчная БД крутит цикл по 1 строке. Векторный движок грузит пачку чисел одной колонки и инструкциями SIMD (Single Instruction, Multiple Data) складывает сразу по 4–16 чисел за такт!

04 · Примеры 4 и 5 · Отсечение гранул и SIMD

-- В sales_opt ключ ORDER BY (city, sale_date):
-- Запрос А: фильтр по ПЕРВОЙ колонке ключа (city)

SELECT sum(amount) FROM sales_opt WHERE city = 'Алматы';

-- Запрос Б: фильтр по колонке НЕ из ORDER BY (category)
EXPLAIN indexes = 1

    city,
    count()                AS orders_cnt,
    uniqExact(sale_date)   AS active_days,
    sum(amount)            AS total_revenue,
    quantile(0.95)(amount) AS p95_check
FROM sales_opt
WHERE city IN ('Алматы', 'Костанай')
  AND sale_date >= toDate('2026-02-01') AND sale_date < toDate('2026-03-01')
GROUP BY city ORDER BY total_revenue DESC;

04 · Золотые правила MergeTree

Опасность мелких INSERT и выбор ключа ORDER BY

✗ Как НЕ надо (убивает MergeTree!)
-- Вставка по 1 строке в цикле!
INSERT INTO sales_opt VALUES (...);
INSERT INTO sales_opt VALUES (...);
-- 10 000 раз подряд = Too many parts!

Каждый INSERT создаёт новую пачку файлов (part) на диске. Частые одиночные вставки задушат фоновые слияния ошибкой Too many parts.

✓ Как правильно (родной режим батчей)
-- Вставлять большими пачками!
INSERT INTO sales_opt
VALUES (...), (...), (...);
-- От 10 000 строк за 1 запрос

Копи события в буфер (или Kafka) и записывай крупными батчами: 1 раз в секунду по 10 000–100 000 строк.

🧭
Правило ключа ORDER BY: ставь в начало колонки из частых фильтров WHERE и иди от меньшего числа уникальных значений к большему — ORDER BY (city, category, sale_date), а не (sale_id, city)! Так максимальны и сжатие, и отсечение гранул.

05 · Горизонтальное масштабирование

Архитектура MPP, шардирование и где здесь DuckDB?

🔪 Шард (Shard)

Хранит свою долю данных (hash(user_id)) — горизонтальный рост на десятки ТБ.

🪞 Реплика (Replica)

Копия шарда на соседнем сервере — страховка при поломке диска.

👨‍🍳 Координатор

Шарды шлют по сети не гигабайты строк, а пару чисел промежуточного итога.

А где DuckDB? ClickHouse — серверный комбайн для кластеров и BI 24/7. DuckDB — те же колончатость + сжатие + SIMD, но как встраиваемая библиотека («SQLite для аналитики») для анализа Parquet / CSV прямо на ноутбуке!
05 · Пример 6 · Мини-MPP и перекос данных

Шарды + ENGINE = Merge и ловушка Data Skew

SQL 
DROP TABLE IF EXISTS sales_global;
DROP TABLE IF EXISTS sales_shard_kz;
DROP TABLE IF EXISTS sales_shard_ru;

CREATE TABLE sales_shard_kz (sale_date Date, city LowCardinality(String), amount UInt32)
ENGINE = MergeTree() ORDER BY (city, sale_date);

CREATE TABLE sales_shard_ru (sale_date Date, city LowCardinality(String), amount UInt32)
ENGINE = MergeTree() ORDER BY (city, sale_date);

INSERT INTO sales_shard_kz SELECT sale_date, city, amount FROM sales_opt WHERE city != 'Москва';
INSERT INTO sales_shard_ru SELECT sale_date, city, amount FROM sales_opt WHERE city = 'Москва';
-- «Координатор» поверх всех таблиц с префиксом sales_shard_
CREATE TABLE sales_global AS sales_shard_kz
ENGINE = Merge(currentDatabase(), '^sales_shard_');

-- Виртуальная колонка _table показывает, с какого шарда пришли данные!
SELECT _table AS shard_name, city, count() AS orders_cnt, sum(amount) AS total_revenue
FROM sales_global
GROUP BY _table, city
ORDER BY shard_name, total_revenue DESC;
-- ✗ ПЛОХО · Перекос данных (Data Skew):
-- SHARD KEY: country_code
-- 90% трафика идёт на один «горячий» Шард KZ, пока остальные 9 шардов простаивают!

-- ✓ ХОРОШО · Равномерный хэш-ключ:
-- SHARD KEY: cityHash64(user_id)
-- Все 10 шардов получают ровно по 10% данных и заканчивают работу одновременно!
🧩
В продакшене шарды живут на разных серверах (движок Distributed), а в одном контейнере тот же принцип отлично моделирует движок Merge.
Ответ ClickHouse · 2 млн строк с двух шардов параллельно за 0.015 сек!

02 · Пример 2 · Паттерн UPSERT

Идемпотентный ON CONFLICT DO UPDATE

В новой выгрузке заказ 102 исправлен (22 000 → 20 000) и добавлен заказ 104. Запустим UPSERT дважды подряд:

SQL 
TRUNCATE TABLE elt_lab.raw_orders;
INSERT INTO elt_lab.raw_orders VALUES
    (101, '2026-01-10', 1, 35000.00), -- без изменений
    (102, '2026-01-15', 2, 20000.00), -- сумма исправлена!
    (103, '2026-01-20', 3, 18000.00), -- без изменений
    (104, '2026-01-25', 1, 15000.00); -- новый заказ
-- Запусти этот запрос 2 или 50 раз — итог всегда один и без лишних записей на диск!
INSERT INTO elt_lab.dwh_orders (order_id, order_date, customer_bk, amount)
SELECT order_id, order_date, customer_bk, amount
FROM elt_lab.raw_orders
ON CONFLICT (order_id) DO UPDATE
SET
    order_date  = EXCLUDED.order_date,
    customer_bk = EXCLUDED.customer_bk,
    amount      = EXCLUDED.amount
WHERE elt_lab.dwh_orders.amount IS DISTINCT FROM EXCLUDED.amount;

SELECT COUNT(*) AS orders_cnt, SUM(amount) AS total_revenue FROM elt_lab.dwh_orders;
📥
Таблица EXCLUDED внутри ON CONFLICT содержит входящую строку из raw_orders, которая столкнулась с уже существующим order_id.
Ответ PostgreSQL · После 2-го запуска: 0 дублей, сумма точная!

------------+---------------

(1 row)

02 · Второй паттерн идемпотентности

Атомарный Delete-Insert для окна дат

Когда нужно полностью перезалить данные за конкретный день (или месяц), используют паттерн Delete-Insert — но строго внутри транзакции:

✗ Как НЕ надо (без транзакции!)
-- Два отдельных запроса без BEGIN!
DELETE FROM dwh_orders
WHERE order_date = '2026-01-25';

-- БАХ! Упала сеть или контейнер!
INSERT INTO dwh_orders ...;

Если скрипт оборвётся между DELETE и INSERT, день 25 января пропадёт с дашбордов директора!

✓ Как правильно (атомарно!)
-- Замена дня целиком или никак:
BEGIN;
    DELETE FROM dwh_orders
    WHERE order_date = '2026-01-25';

    INSERT INTO dwh_orders ...;
COMMIT;

Благодаря BEGIN ... COMMIT (и MVCC) читатели не увидят «дырку», а при сбое DELETE откатится автоматически.

🔁
Запусти этот блок 5 раз подряд — итог за 2026-01-25 всегда будет идентичен, а остальные даты останутся нетронутыми!

    item_bk INT PRIMARY KEY, order_bk INT NOT NULL, order_date DATE NOT NULL,
    product_sk INT NOT NULL REFERENCES proj_dwh.dim_product(product_sk),
    customer_sk INT NOT NULL REFERENCES proj_dwh.dim_customer_scd2(customer_sk),
    qty INT NOT NULL, total_amount NUMERIC(12, 2) NOT NULL
);
-- Плоская витрина-шлюз, которую ClickHouse читает по сети db_net
CREATE TABLE proj_dwh.export_sales_mart (
    item_bk INT PRIMARY KEY, order_bk INT NOT NULL, order_date DATE NOT NULL,
    customer_bk INT NOT NULL, city_name TEXT NOT NULL, segment TEXT NOT NULL,
    product_title TEXT NOT NULL, category_name TEXT NOT NULL,
    qty INT NOT NULL, total_amount NUMERIC(12, 2) NOT NULL
);
CREATE OR REPLACE PROCEDURE proj_dwh.run_elt(p_load_date DATE) LANGUAGE plpgsql AS $$
BEGIN
    -- 1. UPSERT dim_product (SCD Type 1)
    INSERT INTO proj_dwh.dim_product (product_bk, product_title, category_name)
    SELECT product_id, title, category_name FROM proj_oltp.products
    ON CONFLICT (product_bk) DO UPDATE SET product_title = EXCLUDED.product_title,
        category_name = EXCLUDED.category_name
    WHERE proj_dwh.dim_product.product_title IS DISTINCT FROM EXCLUDED.product_title
       OR proj_dwh.dim_product.category_name IS DISTINCT FROM EXCLUDED.category_name;
    -- 2А. SCD2: закрываем изменившихся клиентов
    UPDATE proj_dwh.dim_customer_scd2 d SET valid_to = p_load_date - INTERVAL '1 day', is_current = false
    FROM proj_oltp.customers s WHERE d.customer_bk = s.customer_id AND d.is_current = true
      AND (d.full_name IS DISTINCT FROM s.full_name OR d.city_name IS DISTINCT FROM s.city_name
        OR d.segment IS DISTINCT FROM s.segment);
    -- 2Б. SCD2: открываем новые версии (новые + изменившиеся)
    INSERT INTO proj_dwh.dim_customer_scd2 (customer_bk, full_name, city_name, segment, valid_from, valid_to, is_current)
    SELECT s.customer_id, s.full_name, s.city_name, s.segment, p_load_date, DATE '9999-12-31', true
    FROM proj_oltp.customers s LEFT JOIN proj_dwh.dim_customer_scd2 d
      ON d.customer_bk = s.customer_id AND d.is_current = true WHERE d.customer_bk IS NULL;
    -- 3. Point-in-Time JOIN + UPSERT оплаченных фактов
    INSERT INTO proj_dwh.fact_sales (item_bk, order_bk, order_date, product_sk, customer_sk, qty, total_amount)
    SELECT oi.item_id, o.order_id, o.order_date, dp.product_sk, dc.customer_sk, oi.qty, (oi.qty * oi.unit_price - oi.discount)
    FROM proj_oltp.order_items oi JOIN proj_oltp.orders o ON o.order_id = oi.order_id
    JOIN proj_dwh.dim_product dp ON dp.product_bk = oi.product_id
    JOIN proj_dwh.dim_customer_scd2 dc ON dc.customer_bk = o.customer_id
     AND o.order_date BETWEEN dc.valid_from AND dc.valid_to WHERE o.status = 'paid'
    ON CONFLICT (item_bk) DO UPDATE SET qty = EXCLUDED.qty, total_amount = EXCLUDED.total_amount;
    -- 4. Обновляем плоский шлюз export_sales_mart для ClickHouse
    TRUNCATE TABLE proj_dwh.export_sales_mart;
    INSERT INTO proj_dwh.export_sales_mart
    SELECT f.item_bk, f.order_bk, f.order_date, dc.customer_bk, dc.city_name, dc.segment,
           dp.product_title, dp.category_name, f.qty, f.total_amount
    FROM proj_dwh.fact_sales f JOIN proj_dwh.dim_customer_scd2 dc ON dc.customer_sk = f.customer_sk
    JOIN proj_dwh.dim_product dp ON dp.product_sk = f.product_sk;
END; $$;
CALL proj_dwh.run_elt(DATE '2026-01-01');

DQ-проверка входных заказов через FILTER

Создай в learning_db таблицу proj_lab.raw_orders (order_id, status, amount) и вставь 4 заказа: 2 оплаченных (12000, 8000), 1 отменённый (5000) и 1 битый оплаченный (-300). Одним SQL-запросом выведи valid_paid_cnt, valid_revenue, bad_rows_cnt (amount <= 0) и dq_status ('FAIL' или 'PASS').
SQL (PG) 
CREATE SCHEMA IF NOT EXISTS proj_lab;
DROP TABLE IF EXISTS proj_lab.raw_orders;

CREATE TABLE proj_lab.raw_orders (
    order_id INT PRIMARY KEY, status TEXT NOT NULL, amount NUMERIC(10, 2) NOT NULL
);
INSERT INTO proj_lab.raw_orders VALUES
    (1, 'paid', 12000), (2, 'paid', 8000),
    (3, 'cancelled', 5000), (4, 'paid', -300); -- битая строка!
SELECT
    COUNT(*) FILTER (WHERE status = 'paid' AND amount > 0)                AS valid_paid_cnt,
    COALESCE(SUM(amount) FILTER (WHERE status = 'paid' AND amount > 0), 0) AS valid_revenue,
    COUNT(*) FILTER (WHERE amount <= 0)                                   AS bad_rows_cnt,
    CASE WHEN COUNT(*) FILTER (WHERE amount <= 0) > 0
         THEN 'FAIL' ELSE 'PASS' END                                      AS dq_status
FROM proj_lab.raw_orders;

В ClickHouse MATERIALIZED VIEW работает как автоматический триггер на INSERT! Создай в analytics_db: 1) lab_raw_clicks (click_date, page, clicks); 2) накопитель lab_daily_clicks_agg на SummingMergeTree(); 3) mv_daily_clicks TO lab_daily_clicks_agg. DROP TABLE IF EXISTS lab_daily_clicks_agg; DROP TABLE IF EXISTS lab_raw_clicks;

CREATE TABLE lab_raw_clicks (click_date Date, page LowCardinality(String), clicks UInt32)
ENGINE = MergeTree() ORDER BY (click_date, page);

CREATE TABLE lab_daily_clicks_agg (click_date Date, page LowCardinality(String), clicks UInt64)
ENGINE = SummingMergeTree() ORDER BY (click_date, page);

CREATE MATERIALIZED VIEW mv_daily_clicks TO lab_daily_clicks_agg AS
SELECT click_date, page, sum(clicks) AS clicks
FROM lab_raw_clicks GROUP BY click_date, page;
