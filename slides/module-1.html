01 · Проблема

Зачем нужна база данных, если есть Excel?

5 заказов в день отлично живут в таблице. Но при 5 000 покупателей одновременно файл превращается в катастрофу:

✗ Файл Excel / CSV
  • Толкучка: Петя и Маша одновременно купили последний значок и перезаписали файл.
  • Тормоза: на 2 млн строк файл открывается минутами.
  • Мусор в типах: в «Цену» вписали «договоримся» — формулы сломались.
  • Хрупкость: отключение света легко повреждает открытый файл.
✓ СУБД (PostgreSQL)
  • Порядок в очереди: тысячи клиентов работают параллельно без потерь.
  • Поиск за ~0.001 сек: находит строку среди миллионов мгновенно.
  • Строгий контроль: не пропустит текст в числовую колонку.
  • Надёжность: сохраняет данные даже при отключении питания.
📚
БД vs СУБД: Сами книги и карточки — это база данных (БД). Супер-библиотекарь, который мгновенно ищет книги и держит полки в порядке, — это СУБД (PostgreSQL).

04 · Среда курса

Запускаем PostgreSQL 16 в Docker Compose

YAML 
services:
  pg_primary:
    image: postgres:16
    container_name: course_pg_primary
    restart: unless-stopped
    environment:
      POSTGRES_DB: learning_db
      POSTGRES_USER: student
      POSTGRES_PASSWORD: student_pass
    ports:
      - "5432:5432"
    volumes:
      - pg_primary_data:/var/lib/postgresql/data
      - ./backups:/backups
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U student -d learning_db"]
      interval: 5s
volumes:
  pg_primary_data:
# 1. Скачать образ (в первый раз) и запустить pg_primary в фоне (-d)
docker compose up -d

# 2. Проверить статус и здоровье контейнера
docker compose ps

# Пауза после занятия / возобновление на следующий день
docker compose stop
docker compose start

Команда SELECT работает даже без таблиц. Переключай вкладки, чтобы разобрать 3 примера подряд:

SQL 
-- Слово AS даёт колонке понятное имя в ответе
SELECT
    2 + 2 * 2 AS school_math,
    2 ^ 10    AS power_of_two,
    10 / 3    AS int_division,   -- оба числа целые -> остаток отбросится!

-- Оператор || склеивает кусочки текста в одну строку

    upper('база данных')        AS loud_text,
    length('PostgreSQL')        AS letters_count,
    current_date                AS today,
    current_date + 7            AS next_week;
SELECT
    current_user       AS who_am_i,
    current_database() AS where_am_i,
    current_schema()   AS active_folder;

01 · Типы данных

Каждому грузу — своя коробка

Тип PostgreSQL Что внутри Когда использовать
INT / BIGINT Целые числа: INT до 2 млрд, BIGINT до 9 квинтиллионов. Возраст, остаток (INT); главные id в крупных проектах (BIGINT).
NUMERIC(10, 2) Точные десятичные дроби: до 10 цифр, 2 после запятой. Всегда для денег, цен, скидок, процентов и точных весов.
TEXT / VARCHAR(n) Любой текст. В PostgreSQL TEXT столь же быстр, как VARCHAR. Имя, email, название товара, статус заказа.
BOOLEAN Логическое «Да» или «Нет» (true / false). Флаги: is_paid, is_active.
DATE Календарная дата без времени: '2026-11-25'. День рождения, дата начала акции, срок годности.
TIMESTAMPTZ Дата + время + часовой пояс (timestamp with time zone). Момент регистрации или покупки (created_at).
📦
Аналогия склада: суп наливают в термос, обувь кладут в коробку. Правильный тип запретит записать 'бесплатно' в цену, сэкономит место и ускорит сортировку.
01 · Ловушка типов

Эксперимент с «пропавшей копейкой»: почему не FLOAT?

Двоичные дроби FLOAT (DOUBLE PRECISION) хороши для 3D-игр и физики, но дают погрешность в десятичной арифметике:

SQL Складываем 0.1 + 0.2 двумя способами (:: — приведение типа) 
SELECT
    0.1::DOUBLE PRECISION + 0.2::DOUBLE PRECISION AS float_sum,
    0.1::NUMERIC          + 0.2::NUMERIC          AS numeric_sum;
Ответ PostgreSQL
      float_sum      | numeric_sum
---------------------+-------------
 0.30000000000000004 |         0.3
(1 row)
✗ Как НЕ надо (для денег)
price DOUBLE PRECISION

На миллионах чеков «хвостики» вроде 0.00000000000000004 накопятся, и выручка перестанет сходиться с банком.

✓ Как правильно (для денег)
price NUMERIC(10, 2)

Хранит и считает десятичные дроби с абсолютной точностью до последней копейки или тиына.

02 · Целостность данных

Ограничения (Constraints): «охранники» на входе

Число -5000 — валидный NUMERIC, но худи не может столько стоить. Ограничения проверяют каждую строку и отклоняют мусор с ошибкой:

Ограничение Что проверяет «охранник» Жизненный пример
PRIMARY KEY Уникальный номер строки, никогда не пустой. Один на таблицу. id клиента — как ИИН или паспорт.
NOT NULL Запрещает оставлять ячейку пустой (NULL). У товара обязательны название и цена.
UNIQUE Значение не повторяется во всей колонке (или паре колонок). email или никнейм игрока.
CHECK (...) Любое логическое условие (как if в коде). CHECK (price > 0), рейтинг 1–5.
FOREIGN KEY Гарантирует, что указанный id существует в другой таблице. Запрет заказа для клиента №999.
DEFAULT ... «Помощник»: подставит значение сам, если его не передали. created_at TIMESTAMPTZ DEFAULT now().
02 · Ключи и поведение при удалении

Автоинкремент IDENTITY и правила ON DELETE

🎟️ Автомат с талончиками

В реальных проектах id не пишут вручную — PostgreSQL выдаёт номера сам:

SQL Стандарт PostgreSQL 16 
id BIGINT GENERATED ALWAYS AS IDENTITY
   PRIMARY KEY
✓
А что с SERIAL? Старый вариант работает, но GENERATED ALWAYS AS IDENTITY соответствует стандарту SQL и защищает счётчик от ручных правок.
Что делать, если удаляют клиента с заказами?
1

ON DELETE RESTRICT · «Не дам удалить!»

По умолчанию. База заблокирует удаление клиента, пока у него есть заказы. Лучший выбор для магазинов и банков.

2

ON DELETE CASCADE · «Эффект домино»

Удалил клиента — база автоматически снесёт все его заказы. Удобно для комментариев поста, но опасно для финансов!

3

ON DELETE SET NULL · «Забыть автора»

Клиент удалится, а в его заказах в поле customer_id запишется пустота NULL (колонка должна допускать NULL).

03 · Практика DDL

Создаём 3 таблицы через CREATE TABLE

SQL 
CREATE TABLE customers (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name  TEXT NOT NULL,
    email      TEXT NOT NULL UNIQUE,
    age        INT CHECK (age >= 12 AND age <= 120),
    is_active  BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE products (
    id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title     TEXT NOT NULL UNIQUE,
    price     NUMERIC(10, 2) NOT NULL CHECK (price > 0),

SQL Эталонное решение · Задача 2

02 · Фильтрация строк

Пропускной пункт WHERE и приоритет AND / OR

Оператор Что делает и пример
=, <> (!=) Равно / не равно: category = 'Книги'
>, <, >=, <= Сравнение чисел и дат: stock > 0
BETWEEN a AND b Отрезок включая границы: price BETWEEN 2000 AND 10000
IN (...) Совпадение со списком: category IN ('Одежда', 'Книги')
LIKE / ILIKE Шаблон (% — любые, _ — 1 символ). ILIKE без регистра!
AND, OR, NOT Логические «И», «ИЛИ», «НЕ»: stock > 0 AND price < 5000
✗ Как НЕ надо (ловушка AND / OR)
SELECT title, category, stock FROM products
WHERE stock > 0
  AND category = 'Одежда'
   OR category = 'Аксессуары';

У AND приоритет выше, чем у OR (как × перед +)! Просочится «Коврик XL» с stock = 0.

✓ Как правильно (скобки или IN)
SELECT title, category, stock FROM products
WHERE stock > 0
  AND (category = 'Одежда'
    OR category = 'Аксессуары');

Всегда ставь скобки при смешивании AND и OR, либо заменяй на category IN (...).

04 · Главная ловушка SQL

Коварство NULL: 3 коробки и трёхзначная логика

✗ Как НЕ надо
-- 1) Всегда вернёт 0 строк!
SELECT * FROM products
WHERE discount_pct = NULL;

-- 2) Молча потеряет 4 товара с NULL!
SELECT * FROM products
WHERE discount_pct <> 10;

Обычные = и <> с NULL дают UNKNOWN — и WHERE выкидывает эти строки.

✓ Как правильно
-- 1) Проверка на пустоту
WHERE discount_pct IS NULL;

-- 2) «Безопасное не равно» (включая NULL!)
WHERE discount_pct IS DISTINCT FROM 10;

IS NULL, IS NOT NULL и IS DISTINCT FROM всегда дают строго TRUE или FALSE.

04 · Культура SQL

Декартово произведение и явный INNER JOIN

✗ Как НЕ надо (старый стиль через запятую)
-- Забыли условие связи в WHERE:
SELECT p.title, c.name
FROM products p, categories c;
  • Каждый из 8 товаров умножится на каждую из 5 категорий → 40 бессмысленных строк (декартово произведение).
  • «Худи» внезапно окажется в «Книгах» и «Гаджетах».
  • На таблицах по 100 000 строк такой запрос положит сервер (10 млрд строк!).
✓ Как правильно (явный INNER JOIN ... ON)
SELECT p.title, c.name
FROM products AS p
INNER JOIN categories AS c
  ON p.category_id = c.id;
  • Условие склейки чётко отделено в ON, а бизнес-фильтры живут в WHERE.
  • Синтаксис SQL физически не даст забыть ON.
  • Запрос читается сверху вниз как понятная схема связей.
📌
Не путай: короткое слово JOIN в PostgreSQL и стандарте SQL — это точный синоним INNER JOIN. Пока учишься, пиши INNER JOIN полностью, чтобы помнить: строки без пары отбрасываются.

UPDATE products
SET is_active = false
WHERE id = 4

История покупок Софии

Объедини таблицы orders и products, чтобы вывести все заказы покупателя 'София'.
Покажи номер заказа (o.id), название товара (p.title), количество (o.qty) и статус (o.status). Отсортируй по номеру заказа по возрастанию.
SQL Эталонное решение · Задача 3 
SELECT
  o.id AS order_id,
  p.title,
  o.qty,
  o.status
FROM orders AS o
INNER JOIN products AS p
  ON o.product_id = p.id
WHERE o.customer = 'София'
ORDER BY o.id ASC;

Отчёт для менеджера Тимура

Склей три таблицы (orders, products, categories) и выведи все заказы товаров из категорий, за которые отвечает менеджер 'Тимур'.
Покажи колонки: order_id (o.id), customer, title, category_name (c.name) и total_sum (p.price * o.qty). Отсортируй от самой большой суммы к меньшей.
SQL Эталонное решение · Задача 4 
SELECT
  o.id AS order_id,
  o.customer,
  p.title,
  c.name AS category_name,
  p.price * o.qty AS total_sum
FROM orders AS o
INNER JOIN products AS p   ON o.product_id = p.id
INNER JOIN categories AS c ON p.category_id = c.id
WHERE c.manager = 'Тимур'
ORDER BY total_sum DESC, o.id ASC;
