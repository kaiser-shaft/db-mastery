01 · Хранение на диске

Как таблица живёт на диске: файлы и страницы по 8 КБ

📓 Тетрадь с равными листами
  • Каждая таблица — отдельный файл (нарезается на сегменты по 1 ГБ).
  • Внутри файл поделён на страницы (Blocks) по 8 КБ (8192 байта).
  • Минимальная порция I/O: ради 50 байт PostgreSQL всегда читает лист 8 КБ целиком.
  • Указатели сверху и строки снизу растут навстречу друг другу, экономя перезапись.
🍞
А если строка > 8 КБ? Включается TOAST: база сжимает гигантский TEXT, нарезает его в скрытую таблицу, а на странице 8 КБ оставляет короткую ссылку.

02 · Куча (Heap) и MVCC

Адрес ctid и почему UPDATE не перезаписывает строку

Таблица в PostgreSQL — это Heap (куча) без порядка. У каждой версии строки (кортежа) есть физический адрес ctid = (страница, слот):

🔄
Зачем так сложно? Это MVCC: читатели видят старую карточку без блокировок, пока пишется новая. Мёртвые версии (dead tuples) позже очищает VACUUM.
⚠️
Частая ошибка: никогда не храни ctid в приложении как ID — любой UPDATE или VACUUM FULL мгновенно его меняет! Всегда используй PRIMARY KEY.

✗ Как НЕ надо (пустые UPDATE)

SET rarity = 'epic'

WHERE price >= 500

04 · Практика №4 · Рентген памяти

Холодное vs горячее чтение: EXPLAIN (ANALYZE, BUFFERS)

SQL 
DROP TABLE IF EXISTS orders_big;
CREATE TABLE orders_big (
    id INT NOT NULL, customer_name TEXT NOT NULL,
    amount NUMERIC(10, 2) NOT NULL, created_at TIMESTAMPTZ NOT NULL
);
INSERT INTO orders_big (id, customer_name, amount, created_at)
SELECT g, 'Покупатель #' || (g % 5000),
       (500 + (g * 13) % 9500)::NUMERIC(10, 2), now() - (g || ' minutes')::INTERVAL
FROM generate_series(1, 50000) AS g;
VACUUM ANALYZE orders_big;
# Очищаем Shared Buffers перезапуском сервиса pg_primary из docker-compose.yaml
docker compose restart pg_primary

# Возвращаемся в psql
docker compose exec -it pg_primary psql -U student -d learning_db
-- Запускаем один и тот же запрос ДВА раза подряд после перезапуска pg_primary:
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders_big WHERE amount > 5000;

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders_big WHERE amount > 5000;
Ситуация Строка Buffers: Что произошло физически
Было: 1-й запуск после рестарта («холодный» кэш) shared read=417 Стол пуст — все 417 страниц (3.3 МБ) загружены из ОС / с диска.
Стало: 2-й запуск следом («горячий» кэш) shared hit=417 Все 417 страниц уже в Shared Buffers — диск не трогали!
🔄
Зачем рестарт? После INSERT и VACUUM ANALYZE страницы таблицы уже прогреты в RAM. Перезапуск pg_primary честно очищает «письменный стол» Shared Buffers.

04 · Практика №5 · Рентген Shared Buffers

Смотрим содержимое кэша через pg_buffercache

SQL 
-- Расширение лежит в образе postgres:16, но по умолчанию оно выключено:
SELECT count(*) FROM pg_buffercache;
CREATE EXTENSION IF NOT EXISTS pg_buffercache;

SELECT
    c.relname AS table_name,
    count(*) AS buffers_count,
    pg_size_pretty(count(*) * 8192) AS cached_size,
    count(*) FILTER (WHERE b.isdirty) AS dirty_buffers
FROM pg_buffercache AS b
JOIN pg_class AS c ON b.relfilenode = pg_relation_filenode(c.oid)
WHERE b.reldatabase = (SELECT oid FROM pg_database WHERE datname = current_database())
  AND c.relnamespace = 'public'::regnamespace AND c.relkind = 'r'
GROUP BY c.relname
ORDER BY buffers_count DESC;
Ошибка PostgreSQL · Расширение ещё не включено
ERROR:  relation "pg_buffercache" does not exist
LINE 1: SELECT count(*) FROM pg_buffercache;
Ответ PostgreSQL · Точное совпадение: 417, 9 и 1 буфер!
 table_name | buffers_count | cached_size | dirty_buffers
------------+---------------+-------------+---------------
 orders_big |           417 | 3336 kB     |             0
 game_items |             9 | 72 kB       |             0
 backpack   |             1 | 8192 bytes  |             0
📈
Ориентир продакшена (Cache Hit Ratio): для OLTP-приложений (магазины, CRM) доля попаданий в кэш должна быть ≥ 99%. Ниже 95% — данные не помещаются в RAM.
04 · Практика №6 · Раздувание Heap

Мёртвые строки (dead tuples) и работа VACUUM

SQL 
-- Обновляем 10 000 заказов (создаём 10 000 новых версий строк в Heap)
UPDATE orders_big SET amount = amount + 100 WHERE id <= 10000;

SELECT relname AS table_name, n_live_tup, n_dead_tup,
       pg_size_pretty(pg_relation_size('orders_big')) AS heap_size,
       pg_relation_size('orders_big') / 8192 AS pages_count
FROM pg_stat_user_tables WHERE relname = 'orders_big';
-- Запускаем уборщика мёртвых строк
VACUUM orders_big;

SELECT relname AS table_name, n_live_tup, n_dead_tup,
       pg_size_pretty(pg_relation_size('orders_big')) AS heap_size,
       pg_relation_size('orders_big') / 8192 AS pages_count
FROM pg_stat_user_tables WHERE relname = 'orders_big';
После UPDATE · Таблица выросла с 417 до 501 страницы!
 table_name | n_live_tup | n_dead_tup | heap_size | pages_count
------------+------------+------------+-----------+-------------
 orders_big |      50000 |      10000 | 4008 kB   |         501
После VACUUM · n_dead_tup = 0, но файл всё равно 4008 kB!
 table_name | n_live_tup | n_dead_tup | heap_size | pages_count
------------+------------+------------+-----------+-------------
 orders_big |      50000 |          0 | 4008 kB   |         501
🧹
Почему файл не уменьшился обратно до 3336 kB? Обычный VACUUM не отдаёт пустое место ОС — он помечает свободные слоты внутри 8-килобайтных страниц для повторного использования будущими INSERT / UPDATE без лишней работы с диском.

01 · Устройство B-Tree

Сбалансированное дерево B-Tree и переход в Heap

🏛️ Каталог энциклопедии (8 КБ)
  • Root (Корень): верхний указатель на «шкафы» — старт любого поиска.
  • Branch (Ветки): направляют влево или вправо по диапазонам ключей.
  • Leaf (Листья): отсортированные ключи + ctid строки в Heap.

    id BIGSERIAL PRIMARY KEY, order_code TEXT NOT NULL, customer_id INT NOT NULL,

INSERT INTO shop_orders (order_code, customer_id, email, status, total_price, created_at)

       ROUND((500 + (RANDOM() * 45000))::NUMERIC, 2), TIMESTAMPTZ '2026-01-01 00:00:00+05' + (g * INTERVAL '2 minutes')

Правило левого префикса и покрывающий INCLUDE

Школьный справочник отсортирован строго по паре (Класс, Фамилия): 7А Иванов, 7А Смирнов, 7Б Алексеев, 7Б Иванов... — порядок колонок в скобках решает всё!

Условие в WHERE Индекс (customer_id, total_price) Почему так происходит
customer_id = 42 AND total_price > 30000 ✓ Отлично работает Точно заходим в «класс 42», затем берём диапазон цен.
customer_id = 42 ✓ Отлично работает Используется левая часть (префикс) индекса.
total_price > 30000 ✗ Seq Scan Нет левой колонки customer_id — дорогие заказы разбросаны по всем клиентам.
🃏
Суперспособность INCLUDE (Покрывающий индекс): если создать CREATE INDEX idx_cover ON shop_orders (customer_id) INCLUDE (total_price);, то SELECT total_price FROM shop_orders WHERE customer_id = 42; выполнится как Index Only Scan — вообще без похода в Heap!

03 · Когда индексы молчат

5 причин, почему PostgreSQL игнорирует индекс

1

Функция или формула вокруг колонки

LOWER(email), price * 1.2, EXTRACT(YEAR ...) — «читать каталог задом наперёд».

2

Шаблон LIKE '%777%' с % в начале

Неизвестно начало слова — обычный B-Tree не знает, с какой буквы искать.

3

Низкая селективность (например, 85% строк)

Для status = 'paid' проще один раз прочитать книгу подряд (Seq Scan), чем прыгать по указателю.

4

Несовпадение типов данных

Приведение самой колонки (order_code::INT) ломает индекс так же, как функция.

5

Крошечная таблица (1–2 страницы 8 КБ)

Дешевле прочитать один лист целиком, чем лезть в отдельный файл индекса.

✗ Как НЕ надо
WHERE LOWER(email) = 'user42@example.com';
WHERE total_price * 1.2 > 48000;
WHERE EXTRACT(YEAR FROM created_at) = 2026;

Колонка спрятана внутри выражения → база вычислит его для всех 100 000 строк.

✓ Как правильно
-- 1) Индексируем само выражение:
CREATE INDEX ... ON shop_orders (LOWER(email));
-- 2) Переносим математику вправо:
WHERE total_price > 40000;
-- 3) Диапазон дат вместо EXTRACT:
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01';

04 · Спецтехника · BRIN (Практика №6)

BRIN: индекс в 180 раз меньше B-Tree для логов

BRIN (Block Range Index) не хранит каждую строку — он клеит одну наклейку min..max на каждые 128 страниц Heap (1 МБ) и мгновенно отбрасывает 99% ненужных «коробок»!

SQL 
DROP TABLE IF EXISTS sensor_logs;
CREATE TABLE sensor_logs (
    id BIGSERIAL PRIMARY KEY, sensor_id INT NOT NULL,
    temp_c NUMERIC(5, 2) NOT NULL, logged_at TIMESTAMPTZ NOT NULL
);
-- Вставляем 200 000 записей строго в хронологическом порядке (append-only)
INSERT INTO sensor_logs (sensor_id, temp_c, logged_at)
SELECT (g % 50) + 1, ROUND((18 + (RANDOM() * 12))::NUMERIC, 2),
       TIMESTAMPTZ '2026-01-01 00:00:00+05' + (g * INTERVAL '10 seconds')
FROM generate_series(1, 200000) AS g;
ANALYZE sensor_logs;
CREATE INDEX idx_logs_time_btree ON sensor_logs USING btree (logged_at);
CREATE INDEX idx_logs_time_brin  ON sensor_logs USING brin  (logged_at);

SELECT pg_size_pretty(pg_relation_size('sensor_logs'))         AS table_size,
       pg_size_pretty(pg_relation_size('idx_logs_time_btree')) AS btree_size,
       pg_size_pretty(pg_relation_size('idx_logs_time_brin'))  AS brin_size;

DROP INDEX idx_logs_time_btree;
EXPLAIN ANALYZE SELECT COUNT(*), ROUND(AVG(temp_c), 2) FROM sensor_logs
WHERE logged_at >= '2026-01-15 12:00:00+05' AND logged_at < '2026-01-15 13:00:00+05';

Аналогия архива: 10 000 коробок квитанций стоят строго по датам. На коробке №1 наклейка «1–3 янв», на №2 — «4–6 янв». Зачем карточка на каждую бумажку?

------------+------------+-----------

  Heap Blocks: lossy=128  |  Rows Removed by Index Recheck: 17140

Главное ограничение BRIN: работает ТОЛЬКО при естественном физическом порядке строк (created_at в append-only логах). Если данные лежат вперемешку, на каждой коробке будет «2001–2026» и индекс станет бесполезен!

02 · Словарь цифр плана

Как читать каждую метрику EXPLAIN (ANALYZE, BUFFERS)

Метрика в плане Простыми словами На что смотрит инженер
cost=0.00..2185.00 Стоимость в условных «попугаях»: до 1-й строки .. до всех строк. Не миллисекунды! 1.0 ≈ чтение 1 страницы подряд с диска.
rows=100 (слева / справа) Слева — прогноз планировщика; справа — реальный факт. Расхождение в 10+ раз → слепой планировщик, нужен ANALYZE.
width=25 Средний вес одной строки в байтах. SELECT * раздувает width и выталкивает сортировки на диск.
actual time=... loops=1 Реальные мс за одну итерацию (1-я строка .. все). Общее время узла всегда = actual time × loops!
Rows Removed by Filter Сколько строк прочитали и выбросили в корзину. 99 900 выброшенных строк — крик базы: «Нужен индекс!»
Buffers: shared hit / read Страницы 8 КБ: hit из RAM, read с диска / ОС. Главная честная метрика объёма работы (не скачет как мс).
💡
Привычка профи: всегда пиши EXPLAIN (ANALYZE, BUFFERS) — время в миллисекундах скачет от фоновой нагрузки, а число страниц Buffers честно показывает реальную работу!
03 · Стратегии чтения

Четыре способа читать таблицу: Scan-узлы

Как найти в толстом учебнике истории все упоминания слова «Наполеон»? У PostgreSQL есть ровно 4 стратегии:

Узел в плане Аналогия с учебником истории Когда выбирает PostgreSQL
Seq Scan
Последовательное		 Листаешь книгу подряд от 1-й страницы до последней. Нет индекса, таблица крошечная, или нужно >15–20% строк.
Index Scan
По индексу		 Смотришь указатель в конце и прыгаешь на нужную страницу (Heap) за строкой. Нужно мало строк (единицы/десятки) по подходящему B-Tree.
Bitmap Index Scan +
Bitmap Heap Scan		 Выписываешь номера страниц на черновик, сортируешь их и один раз плавно проходишь книгу. Среднее число строк (сотни/тысячи): прыгать вразнобой дорого, а читать всё — ещё дороже.
Index Only Scan
Только из индекса		 Ответ уже написан прямо в оглавлении — саму книгу (Heap) даже не открываем! Все нужные колонки есть в индексе + свежая карта видимости (Visibility Map).

04 · Чтение дерева плана и JOIN

Читаем снизу вверх и различаем 3 вида JOIN

🍔
Кухня бургерной: читай план снизу вверх — от самых глубоких стрелок -> (чтение таблиц) к кассиру наверху (Limit).
1

Nested Loop · Вложенный цикл

Для каждой из 5 строк ищем пару по индексу в телефонной книге. Идеален при малом числе строк + индексе.

2

Hash Join · Хеш-соединение

Меньшую таблицу складывает в «ящики» в RAM (Hash), а большую проходит 1 раз. Топ для больших выборок без индексов.

3

Merge Join · Слияние

Два уже отсортированных списка проходятся «двумя пальцами» сверху вниз за один проход.

06 · Чек-лист детектива

5 «красных флагов» в выводе EXPLAIN (ANALYZE, BUFFERS)

1

Seq Scan + огромный Rows Removed by Filter

База прочитала полтаблицы и выкинула 99% строк. Нужен индекс (или ты спрятал колонку внутри функции).

2

Прогноз rows отличается от actual rows в 10+ раз

Статистика устарела (запусти ANALYZE имя_таблицы;) или условие слишком сложное для планировщика.

3

Огромные Buffers (shared hit + read)

Запрос перелопачивает десятки мегабайт 8-килобайтных страниц ради маленького ответа.

4

Sort Method: external merge Disk

Сортировка не влезла в оперативную память (work_mem) и свалилась на медленный диск!

5

Большой loops внутри Nested Loop

Если внутренний узел выполняется loops=50000, даже 0.1 мс на шаг превратятся в 5 секунд ожидания.

02 · Практика №1 · Трогаем WAL руками

LSN, сегменты по 16 МБ и замер WAL на 10 000 строках

Файлы в папке pg_wal/ нарезаны на сегменты по 16 МБ. «Километровый столбик» в ленте — LSN (0/4B210A8, смещение в байтах от создания БД).

SQL 
DROP TABLE IF EXISTS wal_orders;
CREATE TABLE wal_orders (
    id         SERIAL PRIMARY KEY,
    order_code TEXT NOT NULL,
    amount     NUMERIC(10, 2) NOT NULL,
    status     TEXT NOT NULL DEFAULT 'paid'
);

-- Текущая позиция в журнале (LSN) и имя активного 16-мегабайтного файла в pg_wal/
SELECT
    pg_current_wal_lsn() AS current_lsn,
    pg_walfile_name(pg_current_wal_lsn()) AS wal_file;
WITH lsn_before AS (SELECT pg_current_wal_lsn() AS pos),
inserted AS (
    INSERT INTO wal_orders (order_code, amount)
    SELECT 'ORD-' || g, round((500 + (g * 13 % 9000))::numeric, 2)
    FROM generate_series(1, 10000) AS g
    RETURNING id
)
SELECT count(*) AS rows_inserted,
       (SELECT pos FROM lsn_before) AS lsn_start,
       pg_current_wal_lsn() AS lsn_end,

Поймай Full Page Image (FPI) после CHECKPOINT

Докажи на практике работу full_page_writes: создай task4_fpi(id INT PRIMARY KEY, val TEXT) и вставь (1, 'v1').
Выполни CHECKPOINT;, затем сделай 1-й UPDATE и замерь WAL (~8 КБ из-за полного снимка страницы!), а сразу следом 2-й UPDATE без чекпоинта — убедись, что WAL упал до пары сотен байт!
SQL Эталонное решение · Задача 4

WITH s AS (SELECT pg_current_wal_lsn() AS pos),
u AS (UPDATE task4_fpi SET val = 'v2' WHERE id = 1)

u AS (UPDATE task4_fpi SET val = 'v3' WHERE id = 1)
